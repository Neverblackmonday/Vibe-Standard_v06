# 02. 부서 구조 및 작업구역

> 이 문서가 정하는 것: 저장소 구조, 구역과 관리 책임, 부서별 책임과 산출물, 비서실·PM의 책무, 작업 구역(누가 언제 어디를 수정할 수 있는가).
> 다른 문서가 정하는 것: 조직·구역의 권한 한계 → `AGENTS.md` 「조직·구역과 권한 한계」, 산출물 이름·번호 → `Workflow/07_문서_서식_및_번호`.

## 1. 저장소 구조

```text

├── .githooks/pre-commit # 커밋 전 check_standard.py 실행

│       └── update/      # 업데이트 패키지를 푸는 자리. .gitkeep만 추적 (같은 절)
```

### 1.1 구역과 관리 책임

조직(비서실과 부서)과 그 기능은 정규 규칙(REQ·scope·판정)을 따르므로 `Departments/` 안에 둔다. 정규 규칙 밖이거나 독립해야 하는 구역은 저장소 루트에 둔다. 구역마다 관리 책임 조직을 하나씩 정한다.

| 구역 | 경로 | 쓰임 | 관리 책임 조직 |
| :--- | :--- | :--- | :--- |
| 표준 | `Workflow/` | 매뉴얼과 서식 | 대표실 |
| 대표님 자료 | `CEO/` | 대표님 전용 자료 | 대표실 |
| 보관 | `_archive/` | 지난 버전 기록 | 대표실 |
| 외부감사실 | `Audits/` | 외부 보고서 | 비서실 |
| 실험실 | `Lab/` | 버리는 코드와 시안 | 비서실 |
| 자료실 | `Storage/` | 서버실(`server/`)과 패키지 자리(`package/sample/`, `package/update/`) | 운영 |

- 관리 책임은 그 구역의 쓰임과 정리를 책임지는 것이며, 수정 권한(4절)을 바꾸지 않는다.

- 서브에이전트 정의는 `.claude/agents/<서브에이전트>.md`에 둔다. 정의 파일은 역할과 참조할 절만 적고, 이 문서의 책임·산출물을 다시 적지 않는다.
- 설계 파라미터(`Design/assets/live/`)는 명세가 정하는 기준값이고, 런타임 파라미터(`Operations/assets/live/`)는 운영 중 바뀌는 값이다.
- 기능은 조직이 하는 일이며 그 조직의 폴더에서 한다. 시험실·부적합 관리는 품질의 기능이고, 보안은 운영의 기능이며, 시각 디자인은 마케팅의 기능이다. 시험실·부적합 관리의 내용은 `Workflow/03_라이프사이클` 「시험실」·「부적합 관리」를 따른다. 시각 디자인 문서의 작성·판정과 입력은 `Workflow/03_라이프사이클` 「시각 디자인 단계」를 따른다.
- 설계 서브에이전트 이름 `engineering`과, 시각 디자인을 마케팅의 기능으로 둔 조직 구성은 `REQ-027` 커밋 뒤에 기동하는 PM 세션(실행 명령으로 기동하는 파이프라인 실행)부터 적용한다. 이미 실행 중인 PM 세션은 기동 때의 규정으로 진행한다. 이미 작성된 기록(머리말 `author.agent`, 판정서·결과서 본문의 서브에이전트 이름과 부서 폴더 경로 등)은 바꾸지 않는다.

### 2.1 비서실과 PM의 책무 (REQ-029_v05)

| 주체 | 책무 |
| :--- | :--- |
| 비서실 (코워크, Antigravity, 채팅 서비스) | ① 대표님과 대화해 요구를 모으고 `Departments/Secretariat/assets/inbox/`에 ORDER를 작성한다. ORDER 머리말 `classification_proposal`에 분류를 제안한다(정의 기준은 `Workflow/03_라이프사이클` 「분류별 단계」). 모델 등급은 분류로 정해지므로 ORDER에 적지 않는다 ② PM 실행 명령을 서비스별 방식으로 전달한다(`Workflow/05_인수인계_및_실행명령` 「비서실 서비스별 명령 전달 방식」) ③ 최종 판정서의 체크리스트 번호별 근거를 대조해 대표님께 보고한다. 보고에 대조할 승인 기록 경로와 결과서의 반영 대상 목록(반영 명령 표의 원본 경로와 삭제 대상)과 최종 판정서의 「삭제 대상」을 함께 적는다 ④ 핫픽스를 수행한다. 사전 승인 요청, 수정, 검증, HOTFIX 작성의 절차는 `Workflow/03_라이프사이클` 「핫픽스 트랙」을 따른다 ⑤ 대표님에게서 직접 받은 승인 문구로 승인 기록을 남기고 승인 필드와 「결정」 열을 기재한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」) ⑥ 외부 보고서(AUDIT)를 작성한다 ⑦ 셸을 실행할 수 있는 비서실 서비스는 최종 판정서 승인 뒤 적용본 반영·정리·스테이징·커밋 전 검사·커밋을 한다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」) ⑧ 조사 자료를 `assets/research/`에, 브리핑을 `assets/briefings/`에 작성한다. 조사 자료의 이름과 머리말은 `Workflow/07_문서_서식_및_번호` 「문서 체계」·「머리말」을 따른다. 브리핑의 요건·종류·작성 시점은 `Workflow/05_인수인계_및_실행명령` 「브리핑」을 따른다 ⑨ 대표님이 아이디어 덤프·기획 단계·기획을 요청하면 기획 트랙을 수행한다(`Workflow/03_라이프사이클` 「기획 트랙」) ⑩ 대표님이 따로 명시적으로 요청한 푸시를 한다(`Workflow/05_인수인계_및_실행명령` 1절 「푸시」 항) ⑪ 실험실(`Lab/`)을 관리한다(사용 승인과 정리. 절차는 `Workflow/03_라이프사이클` 「실험실」) ⑫ 운영의 보안 점검 결과를 대표님께 보고한다(`Workflow/05_인수인계_및_실행명령` 「완료 보고」 8항) ⑬ REQ·HOTFIX를 끝내는 커밋(최종 승인 커밋, 핫픽스 커밋)을 하거나, 커밋 없는 종결(흡수, 중단 뒤 종료)의 대표님 결정을 대표님에게서 직접 받으면 종결 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「종결 기록」) ⑭ 원스톱 실행 명령을 안내하거나 실행하기 전에 착수 순서와 실행 중인 안건(클라우드 세션 포함)을 확인하고, 다른 안건과의 겹침으로 멈춘 REQ 작성 명령·REQ 새 버전 명령을 진행 중이던 안건이 끝난 뒤 다시 안내하거나 실행한다(`Workflow/03_라이프사이클` 「원스톱 착수 조건」·「다른 안건이 진행 중일 때의 REQ 작성」) |
| PM (Claude Code 메인 세션) | ① ORDER로 REQ와 체크리스트를 작성하고 분류를 REQ 머리말 `classification:`에 확정하고, 그 근거와(ORDER 제안과 다르면) 다른 사유를 REQ에 적는다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항 「분류 근거」). REQ를 처음 작성할 때 ORDER 머리말 `related_req`에 그 REQ 이름을 더한다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」) ② REQ 작성 파이프라인과 원스톱 파이프라인을 지휘한다. 서브에이전트를 단계마다 정해진 모델로(`Workflow/04_모델_운용` 「단계별 모델」) 순서대로 기동·인계하고 진행 상태를 보고한다 ③ REQ 판정 `fail` 때와, 최종 판정 반려 누적 뒤 대표님이 격상이나 모델·effort 승인을 정했을 때(`Workflow/03_라이프사이클` 「반려와 격상」) REQ 새 버전을 작성한다 ④ 안건마다 실행 기록을 작성한다(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」) ⑤ 대표님 요청으로 REQ·HOTFIX를 끝내는 커밋을 하면 그 안건의 종결 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「종결 기록」) ⑥ REQ 작성 명령·REQ 새 버전 명령으로 기동되면 REQ 파일을 저장하기 전에 다른 안건과의 겹침을, 원스톱 실행 명령으로 기동되면 첫 단계 전에 착수 조건을 판단한다(`Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」·「원스톱 착수 조건」) |

- 비서실은 ORDER, 승인 기록, 요청 기록(4절), 종결 기록(4절), 승인 필드와 「결정」 열(4절), 외부 보고서, 핫픽스의 대상 파일과 HOTFIX(4절), 조사 자료, 아이디어 백로그, 기획안, 브리핑(4절), 최종 판정서 승인 뒤 반영 명령 대상(거버넌스 파일 포함)과 정리 대상(4절), 실험실(`Lab/`)(4절) 외에는 저장소 파일을 수정하지 않는다. 비서실의 외부 보고서는 외부감사실(`Audits/`)에 둔다. PM이 수정할 수 있는 경로는 4절을 따른다.
- 비서실이 저장소나 셸에서 하는 작업의 공통 규칙과 고정 절차, 비서실의 여러 세션을 함께 쓸 때의 담당과 기록은 `Workflow/05_인수인계_및_실행명령` 「비서실 실행 절차」를 따른다.
- 승인 필드(`approved:`, `confirmed:`)와 REQ 「결정」 열의 기재 주체와 방법은 `Workflow/07_문서_서식_및_번호` 「승인 기록」을 따른다.

## 3. 공통 1차 하위폴더

```text
Departments/<부서>/
├── docs/       # 정제된 문서(기획서, 명세, 안건)
├── assets/     # 실제 자산(코드, 테스트, 스크립트, 파라미터, 조사 자료)
├── results/    # 공식 결과서와 판정서
└── workspace/  # 중간 산출물, 메모, 거버넌스 적용본
```

빈 폴더는 `.gitkeep`으로 유지한다. 비서실 `assets/`에는 바로 아래에 파일을 두지 않고 하위 폴더(`inbox/`, `research/`, `planning/`, `briefings/`)에만 둔다. 최종 산출물은 `docs/`, `assets/`, `results/`에만 둔다.
