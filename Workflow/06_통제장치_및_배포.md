# 06. 통제장치 및 배포

> 이 문서가 정하는 것: 규칙을 집행하는 통제 계층과 한계, 운영의 보안 점검, 권한 설정·커밋 전 검사의 동작, 거버넌스 파일 개정 절차, 배포본과 업데이트 패키지.

## 1. 통제 계층

| 계층 | 파일 | 시점 | 위반 시 결과 | 한계 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | `.claude/settings.json` | 기능 실행 시도 시 | 거부(`deny`) 또는 사용자 확인(`ask`) | Claude Code에만 적용된다. 저장소 밖 서비스인 비서실의 수정(핫픽스, 최종 판정서 승인 뒤 적용본 반영 포함)에는 적용되지 않는다. 핫픽스는 계층 3(scope 대조, HOTFIX의 파일 수와 거버넌스 파일·`CEO/`·`_archive/` 제외 검사)과 대표님 사후 확인(`Workflow/03_라이프사이클` 「핫픽스 트랙」 3항)으로 통제하고, 적용본 반영은 최종 판정을 받은 결과서의 반영 명령 표와 계층 3(scope 대조)으로 통제한다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」). `Edit`·`Write`만 막으므로 셸 명령으로 쓰는 파일은 막지 않는다 |

### 1.1 보안 점검

운영의 정기 보안 점검의 시점, 진행, 항목, 결과 기록은 이 절이 원천이다. 운영의 보안 책임은 `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」을 따른다.

1. **시점**: 달력 주기 없이 두 시점에 한다. ① 배포본·업데이트 패키지를 만들기 전(6절) ② 대표님이 요청할 때.
2. **진행**: 운영은 REQ `workflow:`로만 기동하므로 ORDER → REQ로 진행하고, REQ `workflow:`에 `Operations: 보안 점검`을 적는다. 분류와 단계는 `Workflow/03_라이프사이클`을 따른다.
3. **항목**
   - ① 추적 파일과 커밋 이력에 비밀정보(키, 비밀번호, 접속 토큰)가 없는지. 커밋 전 검사의 비밀정보 검출(4절)은 커밋 대상 변경분만 보므로, 이 항목은 그 검출이 보지 않는 범위(이미 추적 중인 파일, 커밋 이력, `--no-verify`로 들어간 커밋)를 본다. 확인 방법은 `python Departments/Development/assets/scripts/check_standard.py --scan-all`이다. 형식이 없는 비밀정보는 검출 규칙이 잡지 못하므로 검출 결과와 함께 사람이 확인한 범위를 적는다.
   - ② `.gitignore`의 비밀정보 파일 규칙.
   - ③ `.claude/settings.json`의 `deny`·`ask` 목록과 `AGENTS.md` 「불변 원칙」 3항의 일치, 2.1절 권한 완화 항목의 유지 필요.

   | :--- | :--- | :--- | :--- | :--- |

5. **보고**: `Workflow/05_인수인계_및_실행명령` 「완료 보고」 8항을 따른다. 운영은 표준·설정을 고치지 않고, 고칠 곳은 「발견된 위험과 권고 조치」에 적는다.

## 2. 권한 설정 (`.claude/settings.json`)

- **`deny`**: 거버넌스 파일 목록, `CEO/**`, `_archive/**`를 `Edit(<경로>)`·`Write(<경로>)` 짝으로 등록한다. 목록이 `AGENTS.md` 「불변 원칙」 3항과 일치하는지는 개정 때마다 대조한다. 보안 점검(1.1절 항목 ③) 때도 대조한다.
- `Lab/`과 `Storage/`는 `deny`에 넣지 않는다. 실험 단계의 서브에이전트가 `Lab/`에 쓰기 때문이다(`Workflow/03_라이프사이클` 「실험 단계」).
- `Write` 도구 기준으로 경로 구분자가 없는 규칙(`AGENTS.md`)과 폴더 규칙(`Workflow/**`)은 하위 폴더의 같은 이름 파일·폴더에도 적용된다(실측. 근거 `Departments/Development/results/DEV-008_v01.md` 4.3절). `Edit` 도구, 그 밖의 `deny` 규칙(`.claude/**`, `.githooks/**`, `Departments/Development/assets/scripts/**` 등)의 하위 폴더 적용과 거부 규칙이 어느 설정 계층에서 왔는지는 실측하지 않았다(7절 4행). 그래서 적용본은 파일·폴더 이름 끝에 `.적용본`을 붙여 작성한다(5절).
- **`ask`**: 삭제·이동(`rm`, `del`, `mv`, `move`)과 `git commit`, `git push`는 실행 전에 확인을 받는다.
- `.claude/settings.local.json`은 PC별 개인 설정이므로 `.gitignore`로 저장소에서 뺀다.

### 2.1 무인 실행 권한 (REQ-025_v02)

- 파이프라인은 `--permission-mode acceptEdits`로 파일 편집 확인을 생략한다. 이 모드에서도 2절의 `deny`(거버넌스 파일·`CEO/`·`_archive/` 쓰기 차단)와 `ask`(삭제·이동·커밋·푸시 확인)는 그대로 적용된다.
- 표준 절차의 조회·검사·시험 명령은 `allow`에 등록되어 있어 확인 없이 실행된다. 목록의 원천은 `settings.json`이다.
- 임시 Git 저장소가 필요한 시험은 부서 `workspace/`의 Python 스크립트로 작성해 `allow` 규칙(`Bash(python Departments/*/workspace/*)`)으로 실행한다. 이 규칙은 에이전트가 작성한 스크립트를 확인 없이 실행하게 하므로 사실상 임의 명령 실행을 허용한다. 대표님이 이 완화를 승인했으며(v02 REQ-002), `deny`·`ask`와 커밋 전 검사가 위험을 줄인다.
- **명령 도구**: 조회·검사·시험 명령은 Bash 도구로 실행한다. Bash 도구가 거부되면 PowerShell 도구로 대신한다. PowerShell 도구에는 `Bash(...)` 규칙이 적용되지 않으므로, `settings.json`은 표준 절차의 Git 조회, 커밋 전 검사, 인수 시험 실행을 `PowerShell(...)` 규칙으로 따로 등록한다. PowerShell의 시각 조회(`Get-Date`)는 Claude Code가 기본으로 허용하는 읽기 전용 명령이므로 등록하지 않는다.
- **명령 형태**: 권한 규칙은 명령 앞부분의 문자열로 맞추고, 묶은 명령은 하위 명령마다 따로 검사한다(근거 `Departments/Development/results/DEV-019_v01.md` 6절). 그래서 명령 형태는 아래 원리 하나로 정한다.
  - **원리**: 명령은 저장소 루트(작업 폴더)에서 실행하고, 그 앞부분(묶었으면 하위 명령마다)이 `allow` 규칙이나 Claude Code가 기본으로 허용하는 읽기 전용 명령과 글자 그대로 맞아야 한다. 이 원리를 벗어나면 `allow`에 있는 명령도 권한 확인 요청이 된다.
  - **원리를 벗어나는 형태의 예**: 아래는 예일 뿐이며, 예에 없는 형태도 원리를 벗어나면 같다.
    - ① 작업 폴더를 바꾸거나 다른 폴더를 가리키는 앞부분: `cd <폴더>`, `git -C <경로>`
    - ② 프로그램 이름과 하위 명령 사이의 전역 옵션: `git -c <설정>`, `git --no-pager`. Git 명령은 `git` 바로 뒤에 하위 명령(`status`, `diff`, `log`, `show`, `ls-files`)을 쓴다. 경로의 한글 표시 설정(`core.quotepath`)은 `setup.cmd`가 저장소 설정으로 넣으므로 명령행에 붙이지 않는다.
    - ③ 명령 앞의 환경 변수 대입: `NAME=값 명령`
    - ④ `allow` 규칙에도 기본 읽기 전용 명령에도 들지 않는 하위 명령을 `;`·`&&`·`|`로 묶음(예: `echo "exit=$?"`를 덧붙임)과 셸 구문(변수 대입, 중괄호 묶음, `while`·`for` 반복문, `xargs`)
    - ⑤ PowerShell 도구의 하위 식(`$(...)`)과 괄호 식
  - **경로와 세션 기본 안내**: 명령의 경로는 저장소 루트 기준 상대 경로로 적는다. 절대 경로를 쓰라는 세션 기본 안내는 파일 도구(Read·Write·Edit 등)의 경로에만 적용하며, 이 원리보다 앞서지 않는다.
  - **PowerShell 도구**: 같은 원리를 따른다. 명령은 `PowerShell(...)` 규칙의 앞부분(예: `git status `, `python -m pytest `)이나 기본으로 허용하는 읽기 전용 명령(예: `Get-Date`)으로 시작한다.
  - **원리 안에서 할 수 없는 묶음·반복**: 여러 파일의 반복 처리, 결과 가공처럼 묶음·반복이 필요하면 `allow` 규칙을 더하지 않고 이미 있는 규칙 안의 경로로 실행한다. 검색은 Grep·Glob 도구나 인자를 나열한 단독 `grep` 명령(`Bash(grep *)`)으로 하고, 그 밖은 부서 `workspace/`의 일회성 Python 스크립트를 `Bash(python Departments/*/workspace/*)` 규칙으로 실행한다. 스크립트 이름은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「부서 `workspace/` 파일」 항을 따른다.
  - **커밋 해시 조회**: `git rev-parse`는 `allow`에 없어 권한 확인 요청이 된다. HEAD의 커밋 해시는 `git log -1 --format=%H`로 조회한다(`Bash(git log*)`, `PowerShell(git log *)`). 5절 2항의 기준 커밋 조회도 이 명령으로 한다.
  - **문서가 지정하는 명령**: EC, 결과서, 적용본, 인수 시험 절차서(ACC) 등 문서가 뒤 단계의 Claude Code 세션(PM·서브에이전트)에 실행을 지정하는 명령도 이 원리를 따른다. EC 판정·명세 판정이 이를 확인한다(`Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」). 비서실이 실행하는 반영 명령은 Claude Code 권한 규칙이 적용되지 않으므로(1절 표 계층 1) 대상이 아니다.
- 판정 세션이 명령을 실행하지 못했을 때의 처리는 `Workflow/03_라이프사이클` 「판정 세션의 명령 실행」을, 판정 세션 밖 서브에이전트가 명령을 실행하지 못했을 때의 처리는 같은 문서 「판정 세션 밖의 명령 실행」을 따른다.

## 3. 서브에이전트 정의 (`.claude/agents/`)

- 부서마다 정의 파일 하나를 둔다. 비서실은 저장소 밖 서비스이므로 정의 파일을 두지 않는다. 모든 정의 파일은 `disallowedTools: Agent`를 지정해 서브에이전트가 다른 서브에이전트를 기동하지 못하게 한다.
- 정의 파일 본문의 작성 기준은 `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」을 따른다. 모델 필드는 `Workflow/04_모델_운용` 「모델」을 따른다.

## 4. 커밋 전 검사 (`check_standard.py`)

`setup.cmd`가 `git config core.hooksPath .githooks`를 설정하고 훅 파일의 실행 권한을 기록한다. 저장소를 복제한 PC마다 `setup.cmd`를 한 번 실행한다. 훅은 `--staged` 옵션으로 변경 목록을 커밋 대상(index)에서 읽고(승인 기록, 비밀정보 검출 예외 목록, 테스트는 작업 트리 기준이고, 비밀정보 검출은 커밋 대상의 내용 기준), 옵션 없이 직접 실행하면 작업 트리 전체(`git status --porcelain -uall`)를 검사한다. `CEO/`와 `Lab/` 아래 변경의 처리는 두 검사가 다르다(순서 3).

| 순서 | 검사 | 통과 조건 | 실패 시 |

- **승인 요건(구현)**: REQ는 `approved:`, HOTFIX는 `confirmed:`가 `YYYY-MM-DDTHH:MM:SS+09:00` 형식이고 실재하는 일시여야 한다. HOTFIX는 추가로 `HOTFIX_MAX_SCOPE`와 `GOVERNANCE_PATHS`로 `Workflow/03_라이프사이클` 「핫픽스 트랙」의 대상 조건 가운데 파일 수와 거버넌스 파일·`CEO/`·`_archive/` 제외를 검사한다. 파일 수는 두 가지로 검사한다. ① scope 항목 수가 1~`HOTFIX_MAX_SCOPE`개다. ② 그 HOTFIX 하나로 덮이는 변경 파일 수가 `HOTFIX_MAX_SCOPE` 이하다. 폴더 항목 하나가 여러 파일을 덮을 수 있어 ①만으로는 파일 수를 확인할 수 없기 때문이다. ②의 변경 파일은 순서 5(대조 제외)를 거친 뒤 남은 파일이며, 대조 제외 구역의 변경 파일(`Departments/Secretariat/results/`의 HOTFIX 기록 포함)은 세지 않는다. ②를 넘으면 그 HOTFIX로는 통과하지 않는다. 같은 변경 파일 전체를 덮는 승인된 REQ가 있으면 REQ로 통과하고, 없으면 순서 6의 실패로 처리하며 사유에 덮는 변경 파일 수와 허용 수를 적는다. 제외 검사는 scope 항목이 `GOVERNANCE_PATHS`의 경로이거나 그 안의 경로인 경우뿐 아니라, 아래 「scope 일치 규칙」으로 보아 그 경로를 포함하는 항목(상위 폴더, 확장자를 뺀 파일명. 예: `Departments/Development/assets`, `AGENTS`)도 제외 대상으로 보고, 그런 항목이 있는 HOTFIX는 승인 요건을 갖추지 못한 것으로 처리한다.
- **scope 일치 규칙**: 변경 파일 `f`와 scope 항목 `s`(끝의 `/`와 줄 끝 주석 제거)가 `f == s`이거나 `f`가 `s + "/"`로 시작하면 포함으로 본다. `s`의 마지막 이름에 확장자가 없을 때만, 확장자를 뺀 `f` 또는 확장자와 버전 접미사(`_vNN`)를 뺀 `f`가 `s`와 같아도 포함으로 본다. 그래서 scope에 `Departments/Design/docs/tad/EC-007`처럼 버전 없이 적은 항목은 EC의 모든 버전을 포함한다.

## 5. 거버넌스 파일 개정 절차 (REQ-025_v02)

1. PM이 개정 REQ의 `scope:`에 대상 거버넌스 파일을 기재하고, REQ 판정을 거쳐 대표님 승인을 받는다.
2. 담당 부서가 자기 `workspace/<REQ 번호>_적용본_v01/`에 원본과 같은 상대 경로로 적용본을 작성한다. 설계는 `AGENTS.md`·`CLAUDE.md`·`Workflow/`를, 개발은 `setup.cmd`·`.gitattributes`·`.gitignore`·`.claude/`·`.githooks/`·`Departments/Development/assets/scripts/`를 맡는다. `deny` 규칙과 이름이 같은 파일·폴더는 이름 끝에 `.적용본`을 붙인다(예: `Workflow.적용본/03_라이프사이클.md`, `AGENTS.md.적용본`). 파일별 반영 명령 목록을 자기 결과서에 적는다. 결과서에는 적용본의 기준 커밋(적용본을 복사해 시작한 원본의 커밋 해시)을 적는다. 기준 커밋의 조회 명령은 2.1절 「명령 형태」의 「커밋 해시 조회」를 따른다.
3. 구현 단계에서 개발 서브에이전트가 개정된 규칙과 `check_standard.py`·`settings.json`(적용본 포함)이 어긋나지 않는지 대조해 `DEV-xxx`에 적는다. 서브에이전트 정의 파일(`.claude/agents/`)을 고치는 개정은 대상 정의 파일 목록을 `.claude/agents/`의 파일 전체와 대조하고, 대상에서 빼는 파일마다 사유를 `DEV-xxx`에 적는다.
4. 품질 서브에이전트가 최종 판정(명세 판정이 있으면 명세 판정도)에서 적용본을 판정한다. 판정 지적을 반영하면 폴더 버전을 올린다(`_v02`).
5. 최종 판정서 승인 뒤 `Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」대로 적용본을 원본 위치에 복사해 반영한다. `.적용본`은 반영할 때 뗀다.

## 6. 배포본과 업데이트 패키지

두 묶음은 같은 원천(이 저장소의 커밋)에서 `git archive`로 만들지만 용도와 내용이 다르다. 묶음마다 자료실(`Storage/package/`) 아래에 푸는 폴더를 하나씩 둔다.

| 구분 | 폴더 | 용도 | 내용 | 상태 |
| :--- | :--- | :--- | :--- | :--- |
| 배포본 | `Storage/package/sample/` | 신규 프로젝트를 시작할 때 이 폴더를 폴더째 복사해 가져간다 | 저장소 전체에서 `.gitattributes`의 `export-ignore` 대상을 뺀 것 | 운용(6.1절) |
| 업데이트 패키지 | `Storage/package/update/` | 기존 프로젝트의 표준을 최신으로 바꿀 때 덮어쓰기용으로 쓴다 | 표준 구역 파일(거버넌스 파일 목록과 `Workflow/templates/`)만. 필요하면 이관 안내 문서를 함께 둔다(6.3절) | 운용(6.2절). 빌더 스크립트 없이 `git archive`로 만든다. v02 빌더(`_archive/v02/`)는 보관 기록이며 쓰지 않는다 |

- 두 폴더(`Storage/package/sample/`, `Storage/package/update/`)의 내용은 커밋하지 않는다. `.gitignore`가 두 폴더 아래를 모두 무시하고, 두 폴더 바로 아래의 `.gitkeep`만 추적한다. 그래서 폴더를 채워도 내용이 `git status`, 커밋 전 검사의 변경 목록, `git archive`에 나타나지 않는다.
- 두 묶음은 대표님이 만든다(셸을 실행할 수 있는 비서실에 지시해 실행할 수 있다). 대표님 최종 승인과 커밋 뒤, Git Bash에서 저장소 루트로 이동해 실행한다. `<임시경로>`는 Git Bash 형식(예: `/d/tmp`)으로 적는다.
- 두 묶음을 만들기 전에 1.1절의 보안 점검을 거친다(점검 시점 ①). 점검 결과서에 발견된 위험이 있으면 대표님의 조치 결정 뒤에 만든다.
- 커밋하지 않은 파일은 `git archive`에 포함되지 않는다.
- GNU tar는 `D:`처럼 드라이브 문자가 붙은 경로를 원격 호스트로 해석하므로 `--force-local`을 붙인다.
- **비우기 명령**: 두 폴더는 아래 명령으로 `.gitkeep`만 남기고 비운다. `-X`는 `.gitignore`가 무시하는 파일만 지우므로 추적 중인 `.gitkeep`은 남는다. `-n`으로 바꿔 실행하면(`git clean -ndX -- <폴더>/`) 지우지 않고 삭제 예정 목록만 보여 준다. 이 명령은 풀기 전 비우기(6.1절 3항, 6.2절 3항)와 사용 직후 비우기(6.4절)에 함께 쓴다.
  ```bash
  git clean -fdX -- Storage/package/sample/
  git clean -fdX -- Storage/package/update/
  ```

### 6.1 배포본 만드는 법

1. 저장소 전체를 묶고 목록을 출력한다.
   ```bash
   git archive --format=tar -o "<임시경로>/vibe_sample.tar" HEAD
   tar --force-local -tf "<임시경로>/vibe_sample.tar"
   ```
2. 목록에서 확인한다(제외 규칙은 `Workflow/02_부서_구조_및_작업구역` 「공통 1차 하위폴더」의 비서실 `assets/` 규칙을 전제한다. 바로 아래의 확장자 없는 파일은 빠지지 않는다): ① `_archive/` 아래 파일 0건, `Storage/server/`·`Storage/package/sample/`·`Storage/package/update/`·`Audits/`·`Lab/` 아래는 `.gitkeep`만 ② `Departments/` 아래 REQ·EC 0건 ③ 부서 `results/`·`workspace/`, 품질 `assets/acceptance/`·`docs/nonconformance/`, 비서실 `assets/` 아래는 `.gitkeep`만.
3. 풀기 전에 `Storage/package/sample/`을 `.gitkeep`만 남기고 비운다(6절 비우기 명령). 이전 배포본에만 있던 파일이 남아 신규 프로젝트로 복사되는 것을 막기 위해서다. 비운 뒤 `Storage/package/sample/`에 푼다.
   ```bash
   git clean -fdX -- Storage/package/sample/
   tar --force-local -xf "<임시경로>/vibe_sample.tar" -C Storage/package/sample
   ```
4. `Storage/package/sample/`을 폴더째 신규 프로젝트를 둘 위치에 복사하고, 복사한 폴더의 이름을 신규 프로젝트 이름으로 바꾼다. 복사한 폴더 루트의 `.gitkeep`(3항의 비우기 뒤 남긴 파일)은 신규 프로젝트에 필요 없으므로 지운다. 그다음 신규 프로젝트 폴더에서 `setup.cmd`를 한 번 실행한다(4절).
5. 복사를 마치면 바로 `Storage/package/sample/`을 비운다(6.4절).

### 6.2 업데이트 패키지 만드는 법

1. 표준 구역 경로만 묶고 목록을 출력한다. 경로 목록의 원천은 `AGENTS.md` 「불변 원칙」 3항이다. 아래 명령은 그 목록을 옮긴 예시이며, 목록이 바뀌면 3항을 따른다. `Workflow/templates/`는 `Workflow` 안에 들어 있다.
   ```bash
   git archive --format=tar -o "<임시경로>/vibe_update.tar" HEAD AGENTS.md CLAUDE.md setup.cmd .gitattributes .gitignore .claude .githooks Departments/Development/assets/scripts Workflow
   tar --force-local -tf "<임시경로>/vibe_update.tar"
   ```
2. 목록에 3항의 경로 밖 파일이 0건인지 확인한다.
3. 풀기 전에 `Storage/package/update/`를 `.gitkeep`만 남기고 비운다(6절 비우기 명령). 비운 뒤 `Storage/package/update/`에 푼다.
   ```bash
   git clean -fdX -- Storage/package/update/
   tar --force-local -xf "<임시경로>/vibe_update.tar" -C Storage/package/update
   ```
4. 그 업데이트에 덮어쓰기만으로 끝나지 않는 변경이 있으면 6.3절대로 이관 안내 문서를 `Storage/package/update/` 바로 아래에 둔다.
5. `Storage/package/update/`의 파일을 대상 프로젝트 루트에 같은 상대 경로로 복사해 덮어쓴다. `Storage/package/update/` 루트의 `.gitkeep`과 이관 안내 문서는 대상 프로젝트에 복사하지 않는다. 이관 안내 문서가 있으면 대상 프로젝트는 6.3절 4항대로 처리한다. 대상 프로젝트에 `Departments/Development/assets/scripts/secret_allowlist.txt`가 이미 있으면 그 파일은 덮어쓰지 않는다.
6. 덮어쓰기를 마치면 바로 `Storage/package/update/`를 비운다(6.4절).

### 6.3 복잡한 업데이트

업데이트마다 6.2절대로 표준 구역 파일을 `Storage/package/update/`에 만든다. 덮어쓰기만으로 끝나지 않는 변경이 있을 때만 그 업데이트의 수작업 절차를 적은 이관 안내 문서를 함께 둔다.

1. **필요한 조건**: 그 업데이트에 다음 변경이 하나라도 있을 때만 이관 안내 문서를 둔다.
   - 폴더 이름·구조 변경(표준 구역 파일의 삭제·이동 포함. 덮어쓰기로는 옛 파일이 지워지지 않는다)
   - 기록 파일명·머리말 형식 변경
   - 고객 작업 구역 파일 수정
2. **문서**: 파일명은 `이관안내.md`이고 `Storage/package/update/` 바로 아래에 하나만 둔다. 그 업데이트의 수작업 절차(대상 경로, 순서, 명령)를 적는다. 별도 서식은 두지 않는다.
3. **작성 주체와 근거**: 패키지를 만드는 사람(대표님, 또는 대표님 지시를 받은 비서실)이 그 업데이트에 포함된 표준 개정 REQ와 결과서(DEV·RPT의 적용본 반영 명령)를 근거로 작성한다. `Storage/package/update/`는 커밋하지 않으므로 이 문서도 커밋되지 않고, 다음 비우기 때 함께 지워진다.
4. **대상 프로젝트의 처리**: 대상 프로젝트는 이관 안내 문서를 자기 REQ로 처리한다.

### 6.4 작업 트리 안 표준 사본의 위험과 대응

두 폴더를 채우면 폴더마다 `AGENTS.md`, `CLAUDE.md`, `.claude/`, `Workflow/` 사본이 이 저장소의 작업 트리 안에 생긴다. Claude Code의 하위 폴더 `CLAUDE.md` 자동 로드는 실측하지 못했다(7절 6행). `deny`는 `Write` 도구 기준으로 사본의 `AGENTS.md`와 `Workflow/` 아래 파일에 적용된다(2절, 7절 4행). `Edit` 도구, 그리고 `CLAUDE.md`·`.claude/` 사본 등 그 밖의 사본에 `deny`가 적용되는지는 실측하지 않았다(7절 4행). 사본이 현행 규정과 다른 버전이면 에이전트가 사본의 규정을 읽을 수 있고, 실측하지 않은 범위에서는 `deny`가 사본에 적용되지 않을 수 있다.

| 폴더 | 위험 | 대응 |
| :--- | :--- | :--- |
| `Storage/package/sample/` | 6.1절 3항으로 푼 배포본의 `AGENTS.md`·`CLAUDE.md`·`.claude/`·`Workflow/` 사본이 남아 위의 위험이 생긴다 | 6.1절 4항의 복사를 마친 직후 6절 비우기 명령으로 비운다. 이 폴더를 채운 상태로 Claude Code 파이프라인을 실행하지 않는다 |
| `Storage/package/update/` | 6.2절 3항으로 푼 업데이트 패키지의 `AGENTS.md`·`CLAUDE.md`·`.claude/`·`Workflow/` 사본이 남아 위의 위험이 생긴다 | 6.2절 5항의 덮어쓰기를 마친 직후 6절 비우기 명령으로 비운다. 이 폴더를 채운 상태로 Claude Code 파이프라인을 실행하지 않는다 |

- 이 「사용 직후 비우기」는 6.1절 3항·6.2절 3항의 「풀기 전 비우기」와 별개다. 풀기 전 비우기는 이전 묶음에만 있던 파일이 남는 것을 막고, 사용 직후 비우기는 사본이 작업 트리에 남는 것을 막는다. 어느 한쪽이 다른 쪽을 대신하지 않는다.

| 3 | 업데이트 패키지 빌더 | 해결: 빌더 없이 `git archive`로 만든다(6.2절) |
