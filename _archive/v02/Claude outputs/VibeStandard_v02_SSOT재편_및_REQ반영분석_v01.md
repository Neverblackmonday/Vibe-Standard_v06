## 4. SSOT 재편안 (REQ-006 범위 안, 7대 매뉴얼 유지)

### 4.1 원칙

1. **주제마다 원천 문서 하나:** 다른 문서는 「무엇을, 어디서」 한 줄로만 참조합니다(예: 「등급별 흐름은 `03` 「등급별 흐름」」). 값·목록·절차를 다시 적지 않습니다.
2. **기계가 집행하는 목록은 코드·설정 파일이 원천:** 허용 구역은 `check_standard.py` `WHITELIST_PREFIXES`, 거버넌스 차단은 `settings.json` deny가 원천입니다. 문서는 목록의 뜻과 위치만 적고 목록을 복사하지 않습니다. 이렇게 하면 문서와 코드가 어긋날 수 없습니다.
3. **서식의 본문 구조는 템플릿이 원천:** `07`은 필드의 뜻과 검사 규칙만 둡니다(REQ-006 과제 1-7과 같은 방향).
4. **각 문서 첫머리에 범위를 둡니다:** 「이 문서가 정하는 것 / 다른 문서가 정하는 것(→ 위치)」을 3~5줄로 적습니다. 사람과 AI 모두 처음 몇 줄만 읽고 맞는 문서를 고를 수 있고, `04` 「타깃 컨텍스트 규칙」(필요한 절만 읽기)과도 맞습니다.

### 4.3 사람과 AI가 이해하기 쉽게 하는 보완

1. **문서 지도를 질문형으로:** `AGENTS.md` 0절을 「질문 → 문서·절」 형태로 바꿉니다. AI가 필요한 절만 찾아 읽기 쉽고, 사람도 바로 찾아갈 수 있습니다.
   - 예: 승인 전에 어디를 고칠 수 있나 → `02` 「작업 구역 권한」
   - 예: 파이프라인은 언제 멈추나 → `03` 「중단 조건」
2. **용어집을 `01`에 신설:** EC 판정, 최종 판정, 체크리스트, 부서, 외부감사실, 적용본, 오케스트레이터를 각각 한 줄로 정의하고, 쓰지 않을 동의어를 명시합니다(예: 「1차 게이트」, 「삼중 검수」, 「점검표」 사용 금지). 쓰지 않을 동의어는 검사 스크립트나 품질 판정의 `grep` 대상으로 삼을 수 있습니다.
3. **리비전 태그를 REQ 번호로:**
   - 현재 `(v03)` 태그는 무엇의 버전인지 정의되어 있지 않습니다. 매뉴얼은 파일명에 버전이 없고, 개정 이력 표는 REQ 번호로 관리합니다.
   - 태그를 `(REQ-005)`처럼 REQ 번호로 바꾸면 태그와 하단 개정 이력 표가 같은 키를 쓰게 되어, 대조할 수 있고 의미도 분명해집니다.
   - 이 변경은 대표님이 정할 사항입니다(5절 결정 2).
4. **경과 서술은 근거 쪽으로:**
   - 규정 문장 안의 「2026-10-06 명세 단계에서 확인」(`06` 18행), 「대표님이 이 권한 완화를 승인했으며」(`06` 28행) 같은 경과는 개정 이력이나 REQ에 두고, 규정에는 결론만 남깁니다.
   - 복제해 간 고객 프로젝트에서는 의미가 없는 문장이기 때문입니다.
5. **파일명·제목 정합:** `02_5대_도메인_구조_및_역할`은 실제로 7개 부서와 외부감사실을 다룹니다. REQ-006 요청 원문 5번(「4대가 아니고 7대 아님?」)도 같은 문제를 지적했습니다. REQ-006이 파일명 유지를 전제로 하므로, 최소한 제목과 본문의 「5대」 표기를 실제 구성과 맞추기를 권고합니다(5절 결정 3).
