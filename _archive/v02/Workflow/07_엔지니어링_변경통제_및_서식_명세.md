# 07. 엔지니어링 변경 통제 및 서식 명세 (Change Control & Document Specs)

> 본 문서는 공식 문서의 위치, 번호, 머리말, 본문 구성, 유효성 규칙을 정의한다. 각 서식의 원천은 템플릿 파일이며, 본 문서는 필드의 의미와 검사 방법을 설명한다.

## 1. 문서 체계

| 문서 | 이름 | 작성 부서 | 파일 위치 | 서식 원천 |
| :--- | :--- | :--- | :--- | :--- |
| REQ | 공식 안건 | 비서실 | `Departments/Secretariat/docs/requests/REQ-xxx.md` | `Workflow/templates/REQ_TEMPLATE.md` |
| RP | 재작업 절차서 | 비서실 | `Departments/Secretariat/docs/requests/RP-xxx.md` | `Workflow/templates/RP_TEMPLATE.md` |
| EC | 엔지니어링 변경 계획서 | 설계 | `Departments/Design/docs/tad/EC-xxx.md` | `Workflow/templates/EC_TEMPLATE.md` |
| PRD | 제품 요구사항 정의서 | 설계 | `Departments/Design/docs/prd/<번호>_<주제>.md` | `Workflow/templates/PRD_TEMPLATE.md` |
| TAD | 기술 아키텍처 명세서 | 설계 | `Departments/Design/docs/tad/<번호>_<주제>.md` | `Workflow/templates/TAD_TEMPLATE.md` |
| DEV | 개발 결과서 | 개발 | `Departments/Development/results/DEV-xxx.md` | 자체 보고 서식 (실행 명령·시각·결과 원문 포함) |
| RES | 품질 판정서 | 품질 | `Departments/Quality/results/RES-xxx-EC.md`, `RES-xxx.md` | `Workflow/templates/RES_TEMPLATE.md` |
| HOTFIX | 핫픽스 기록 | 비서실 | `Departments/Secretariat/results/HOTFIX-xxx.md` | `Workflow/templates/HOTFIX_TEMPLATE.md` |
| AUDIT | 외부 감사 보고서 | 외부감사/독립감사 | `Audits/AUDIT_YYYYMMDD_<주제>_v01.md` | `Workflow/templates/AUDIT_TEMPLATE.md` |

추적 관계: REQ `task_id` → RP(`task_id`) → EC(`gate:` → `RES-xxx-EC`) → PRD·TAD(`related_req`) → DEV → `RES-xxx`(`task_id`). HOTFIX는 REQ 없이 대표님 사전 승인과 `confirmed:`로 추적한다. AUDIT은 비정기 날짜 기반으로 감사 이력을 영구 보존한다.

## 2. 공통 규칙

### 2.1 번호
- `xxx`는 세 자리 순번(`001`부터)이다. REQ 번호가 원천이며 EC, DEV, RES는 같은 번호를 쓴다. 한 REQ에는 EC 하나만 두고, 다시 작성해야 하면 같은 파일을 개정한다.
- `HOTFIX-xxx`는 REQ와 별도의 세 자리 순번을 쓴다.
- `AUDIT_YYYYMMDD_<주제>_v01.md`는 비정기 감사의 특성을 반영하여 일련번호 대신 날짜 기반 명명을 사용한다.
- **작업 중 재심사 (In-flight)**: 판정서는 단일 파일(`RES-xxx.md`, `RES-xxx-EC.md`)을 유지하고 머리말과 본문에 차수(1차, 2차)를 누적한다. 파일명에 차수를 붙이지 않는다.
- **종결 후 재의뢰 (Post-close)**: 종결된 안건에 사후 결함이나 추가 요청이 생기면 하위 번호(`REQ-xxx-1.md` → `RES-xxx-1.md`)를 부여해 원천 안건과의 관계를 남긴다.
- 템플릿(`*_TEMPLATE.md`)에는 번호를 붙이지 않는다. `check_standard.py`는 REQ 목록에서 `REQ_TEMPLATE.md`를 뺀다. 템플릿 8종의 원천은 `Workflow/templates/`에 집약 보관한다.

### 2.2 파일명과 참조
- PRD·TAD는 버전 번호 없는 파일명 하나로 유지하고, 개정 이력은 Git 커밋 로그와 문서 하단 「📝 개정 이력」 표로 관리한다.
- 문서 간 참조는 확장자 없는 상대 경로로 적는다(예: `Departments/Design/docs/tad/01_아키텍처`). 절 참조는 절 번호 대신 절 제목(「상태 전이」)으로 적는다.

### 2.3 머리말
- 공식 문서는 `---`로 감싼 YAML 머리말로 시작한다. 날짜는 `"YYYY-MM-DD"`, 시각은 `"YYYY-MM-DDThh:mm:ss+09:00"` 형식의 문자열이다.
- 목록 필드(`scope:`, `workflow:`)는 두 칸 들여쓰기 뒤 `- `로 시작한다. `check_standard.py`는 `scope:` 아래 두 칸 또는 네 칸 들여쓰기 뒤 `- `로 시작하는 줄만 읽는다.
- `scope:` 항목 줄에는 주석(`#`)을 붙이지 않는다. `check_standard.py`가 주석을 경로의 일부로 읽기 때문이다.
- `scope:`의 폴더 항목은 표기를 통일하기 위해 끝에 `/`를 붙이지 않는다(예: `Workflow`).
- 작성·판정 모델은 `Workflow/04_모델_운용_기준` 「모델 메타데이터 기록」대로 실제 실행 모델을 기재한다.

### 2.4 문서 섹션별 개정 번호 마킹 규칙 및 SOP (v03)
- 문서 버전이 리비전될 때(예: `_v03`), **이번 리비전에서 실제로 변경되거나 추가된 섹션(제목) 끝에만 현행 버전 태그 `(v03)`**를 붙여 표기한다.
- **예시**:
  - `1. 표준의 정의` (변경 없음)
  - `2. 상품 구성과 폴더 격리 원칙 (v03)` (변경 있음)
  - `3. 해결하는 핵심 과제` (변경 없음)
- **엔지니어링 표준 절차 (SOP)**:
  1. `[1단계: 실변경 식별]`: 개발 완료 후 `git diff HEAD`로 실변경 H2/H3 섹션을 추출한다.
  2. `[2단계: 구 태그 청소]`: 문서 전체에서 정규식 `\s*\([vV]\d+\)`를 적용하여 이전 버전 마크를 일괄 제거한다.
  3. `[3단계: 현행 태그 부착]`: 실변경 H2/H3 섹션 제목 끝에만 1칸 공백 후 현행 버전 태그(예: ` (v03)`)를 부착한다.
  4. `[4단계: 품질 검증 강제]`: 품질팀(RES)은 `git diff` 실변경 섹션과 헤더 태그를 대조하여 누락/오부착 시 즉시 `fail` 판정한다.
- 목차나 제목만 훑어보아도 이번 개정 위치를 대표님이 즉시 파악할 수 있도록 한다.

## 3. REQ (공식 안건) (v03)

- **머리말**: `task_id`(세 자리 순번), `classification`(`Critical`·`Major`·`Minor`), `created`, `approved`(대표님만 기재, 미승인 시 `""`), `author`(`agent`·`model`·`thinking`), `workflow`(실행 부서를 단계 순서대로), `scope`(수정 허용 경로. Critical·Major는 `Departments/Design/docs/tad/EC-xxx.md`를 포함한다). `approved` 밖의 필드는 비서실이 기재한다.
- **본문**: 1. 요청 원문(대표님 지시 원형 인용) 2. 배경 및 목적 3. 결정 사항 및 선택지(`| 정할 일 | 권고안 | 대안 | 결정 |`) 4. 워크플로우 및 부서별 실행 계획 5. 검증 및 완료 기준(체크리스트: 요청 원문 항목과 1:1로 대응하는 번호 목록) 6. 작업자 인수인계 및 Claude Code CLI 실행 명령(`Workflow/05_비서실_클로드cli_인수인계_정책` 「원스톱 실행 명령」)

## 4. EC (엔지니어링 변경 계획서)

### 4.1 머리말
`ec_id`·`task_id`(대상 REQ 번호), `created`, `author`(작성 부서 `Design`, 실제 모델, effort), `status`(`draft` 또는 `approved`), `gate`(`approved`일 때 근거 판정서 경로, 예: `Departments/Quality/results/RES-xxx-EC`), `scope`(REQ `scope:`의 부분집합).

### 4.2 상태 전이
```text
draft ──(RES-xxx-EC result: pass)──▶ approved
draft ──(RES-xxx-EC result: fail)──▶ draft (수정 후 재판정)
```
- `status:`는 설계팀이 바꾼다. `approved`로 바꿀 때 `gate:`에 판정서 경로를 함께 기재한다.
- `approved` 이후 범위를 바꿔야 하면 `draft`로 되돌리고 EC 판정을 다시 받는다.

### 4.3 본문
1. 개요 및 변경 배경 2. 작업 범위(신규 생성 파일, 기존 수정 파일, 범위 제외 항목. 「담당 단계」는 단계명 `명세`·`구현`으로 적는다) 3. 세부 설계(구조 변경, 단계별 작업) 4. 위험 분석 및 대응 5. 완료 기준(검증 방법 포함) 6. 📝 개정 이력(`| REQ | 판정 차수 | 변경 요지 |`, 다시 판정받을 때마다 행 추가)

## 5. PRD (제품 요구사항 정의서)
- **머리말**: `doc_type`(`PRD`), `title`, `updated`(최종 개정일), `related_req`(작성·개정한 REQ 번호 목록)
- **본문**: 1. 제품 개요 2. 범위(포함, 제외) 3. 사용자 시나리오 4. 기능 요구사항(`FR-번호`, 우선순위, 수용 기준) 5. 비기능 요구사항(`NFR-번호`, 측정 기준) 6. 제약 조건 및 가정 7. 미결 사항 8. 📝 개정 이력

## 6. TAD (기술 아키텍처 명세서)
- **머리말**: `doc_type`(`TAD`), `title`, `updated`, `related_req`, `related_prd`(근거 PRD 경로 목록, 확장자 없음)
- **본문**: 1. 아키텍처 개요 2. 구성 요소 3. 데이터 모델 4. 인터페이스 5. 오류 처리 및 로깅 6. 보안 고려 사항 7. 설계 결정 기록 8. 요구사항 추적표(`FR`·`NFR` → 구성 요소 → 테스트) 9. 📝 개정 이력

## 7. RES (품질 판정서)
- **종류**: EC 판정서(`RES-xxx-EC.md`, EC 판정 단계), 최종 판정서(`RES-xxx.md`, 최종 판정 단계). 판정 기준은 `Workflow/03_라이프사이클_및_워크플로우` 「단계별 기준」을 따른다.
- **머리말**: `task_id`, `result`, `completed_at`(시간대 포함), `auditor`(`Quality`, 실제 모델, effort)
- **`result` 값**: `pass`는 판정 기준의 결함이 없다는 뜻이며 완성도를 보증하지 않는다. `fail`은 결함이 있어 해당 부서가 고친 뒤 변경분을 다시 판정한다는 뜻이다. `rejected`는 안건 자체가 성립하지 않는다는 뜻이다(예: REQ 미승인, 요구 모순).
- **본문**: `RES_TEMPLATE.md` 구성(1. 판정 요약 2. 판정 기준별 검증 결과 3. 검증 결과 로그)을 따른다. 최종 판정서는 2절에 체크리스트 번호별 근거를 기재한다. `fail`이면 「4. 결함 목록과 반려 부서」를 추가한다. EC 판정서는 2절 판정 항목을 EC 판정 기준 네 가지로 바꾸어 작성한다.

## 8. HOTFIX (핫픽스 기록)
- **대상과 절차**: `Workflow/03_라이프사이클_및_워크플로우` 「핫픽스 트랙」을 따른다.
- **머리말**: `hotfix_id`(세 자리 순번), `created`, `author`(`Secretariat`, 실제 모델, effort), `confirmed`(대표님만 기재, 미확인 시 `""`), `scope`(수정 파일 3개 이하, 거버넌스 경로 제외)
- **본문**: 1. 지시 원문, 승인된 대상 파일 목록, 현상과 위험도 2. 수정 내역(파일별 변경 전후) 3. 검증 결과(`| 항목 | 명령 | 시각 | 결과 원문 |`) 4. 대표님 사후 확인란
- **커밋 연동**: `check_standard.py`는 `confirmed:`가 기재된 `HOTFIX-xxx.md`의 `scope:`를 승인 범위로 인정한다(`Workflow/06_거버넌스_엔지니어링_아키텍처` 「커밋 전 검사」). 커밋 메시지는 `fix: [HOTFIX-001] 요약`이다.

## 9. 유효성 규칙 (v03)
- **기계 검사** (`check_standard.py`): REQ `approved:`가 비어 있지 않다. 변경 파일이 승인된 REQ 하나 또는 `confirmed:`가 있는 HOTFIX의 `scope:`에 포함된다. `CEO/` 아래 변경이 없다.
- **사람 확인** (품질 판정서에 기재): EC `scope:`가 REQ `scope:`의 부분집합인가. EC `status: approved`에 대응하는 `RES-xxx-EC.md`가 `result: pass`인가. 머리말의 모델명이 실제 실행 모델인가. PRD·TAD 「📝 개정 이력」에 이번 REQ가 있는가. 요구사항 추적표의 `FR`·`NFR`이 구성 요소와 테스트에 모두 연결되었는가. 체크리스트의 모든 번호에 근거가 있는가.
