## 3. 걸리는 점

### F1. 7개 부서 고정: 범용성

- **현상:** 모든 프로젝트가 7개 부서와 부서마다 4개 폴더를 받습니다. 직전 검토 때 폴더 조회로 `.gitkeep` 40건을 셌습니다.
- **문제:** 예를 들어 CMM 데이터 브리지나 매매 프로그램에는 마케팅·비주얼 부서가 필요 없습니다. 표준은 모든 프로젝트에 공통인 최소 집합만 두고 나머지는 선택으로 두는 편이 맞습니다. v01 8차 점검(쓰이지 않는 폴더 5건)의 교훈과도 같습니다.
- **권고:** 비서실·설계·개발·품질 4개 부서를 기본으로 두고, 운영·마케팅·비주얼은 「선택 부서」로 둡니다(결정 1).
  - 개발 부서를 기본에 넣는 이유는 검사 스크립트가 `Departments/Development/assets/scripts/`에 있기 때문입니다.
  - 코드를 거의 쓰지 않는 프로젝트(예: 상품 등록 업무)도 이 경로는 필요합니다.

### F2. 템플릿과 표준 저장소의 혼재

1. **초기화 커밋 뒤에는 `PROJECT.md`를 고칠 수 없습니다.**
   - [실측] 초기화 커밋 뒤 `PROJECT.md` 한 줄을 고쳐 커밋하면 「[FAIL] 거버넌스 규정 … 무단 수정이 감지되었습니다 … PROJECT.md」가 나오고 커밋이 막힙니다(종료 코드 1).
   - 초기화 커밋 전에 고치면 통과합니다(코드 60~66행 `is_initial_commit`). 이것이 지금 쓸 수 있는 임시 우회 방법입니다.
   - [판정 재현] 거버넌스 목록에서 `PROJECT.md`만 빼도 해결되지 않습니다. 「[FAIL] 활성화된 REQ 안건 문서가 없습니다」가 나옵니다(종료 코드 1). `PROJECT.md`는 허용 목록에 없기 때문입니다.
2. **대표님도 거버넌스 파일을 고쳐 커밋할 수 없습니다.**
   - AGENTS 38행은 거버넌스 파일을 「대표님 단독 수정 구역」으로 정합니다.
   - 그러나 검사는 수정한 사람을 구분하지 못합니다. 대표님이 커밋할 수 있는 길은 `git commit --no-verify`(검사 건너뛰기)뿐입니다.
   - [판정 재현] 거버넌스 검사만 끄면 이번에는 「활성화된 REQ 안건 문서가 없습니다」로 막힙니다. 거버넌스 파일은 scope에 적을 수도 없습니다.
3. **표준 저장소 자체의 정보가 그대로 복사됩니다.**
   - `PROJECT.md` 내용이 「프로젝트명: Vibe Standard v02」입니다.
   - 폴더 전체를 복사하면 `_archive/`(이 저장소의 검토 기록)도 새 프로젝트로 넘어갑니다.

- **권고:** 결정 2를 따릅니다. 아울러 `PROJECT.md`는 빈칸 서식으로 바꾸고, 표준 저장소의 작업 기록은 템플릿 밖에 둡니다.

### F3. 규정의 강제 수준과 실제가 다름

- **규정:** AGENTS 2절은 「Fail-Closed」, 「모든 후속 작업 및 커밋이 차단된다」(34행), 「에이전트의 수정을 전면 금지한다」(38행)고 적습니다.
- **실제:** 실제 장치는 커밋할 때 실행되는 검사뿐이며, 아래 빈틈이 있습니다.
  - **작업 중 차단 없음:** 수정을 미리 막는 장치가 없습니다. `settings.json` deny에는 `CEO/`만 있습니다.
  - **REQ 위조 가능:** `approved:` 줄과 REQ의 `scope:`는 에이전트도 고칠 수 있습니다. REQ 폴더는 검사의 허용 목록이라, 승인 뒤에 scope를 넓혀도 검사가 잡지 못합니다.
  - **조회 실패 시 통과:** `git status` 조회가 실패하면 「[WARN]」만 출력하고 통과합니다(코드 114~117행).
- **판단:** 표준이 실제보다 강한 보장을 약속하면, 사용자는 지켜지지 않는 보호를 믿게 됩니다. 규정 문구를 장치별 실제 대상에 맞추고(결정 3), 작업 중 차단은 `settings.json` deny로 보강합니다.
  - deny는 Claude Code의 파일 편집 기능에만 적용됩니다. Bash 명령으로 쓰는 것(`echo >`, `git checkout` 등)은 막지 못합니다.

- **경로 표기:** AGENTS 2절 1번·3절과 `design.md`·`secretariat.md` 19행은 경로에서 `Departments/`를 빼고 적었습니다(직전 검토 S7).

- **거버넌스 목록 불일치:** 코드의 거버넌스 목록에는 `.gitignore`와 `.gitattributes`가 있지만(32~33행), AGENTS 38행 목록에는 없습니다.

- **줄 끝 규칙:** `.gitattributes`는 `*.bat`·`*.cmd` 두 줄뿐입니다. 직전 검토 D3이 권고한 `.githooks/* text eol=lf`가 없어서, `core.autocrlf=true` 환경에서는 `pre-commit`이 다시 CRLF로 바뀔 수 있습니다.
- **`setup.cmd` 파일 형식:**
  - [실측] `setup.cmd`는 UTF-8 BOM으로 시작합니다(`od` 결과 첫 바이트 `357 273 277`). 줄 끝은 LF입니다.
  - 새 프로젝트는 폴더를 복사한 뒤 `git init` 전에 `setup.cmd`를 실행합니다. 따라서 `.gitattributes`의 CRLF 변환이 적용되기 전의 파일(LF와 BOM)이 그대로 실행됩니다.
  - v01은 실제 사고(W-1)를 근거로 배치 파일의 CRLF와 BOM 없음을 검사했습니다.
  - **권고:** 원본을 CRLF로, BOM 없이 저장합니다. Windows `cmd`의 실제 동작은 확인 불가입니다.
- **명세 파일명:** 명세 파일명에 버전을 붙이지 않는 방식(AGENTS 3절)은 전역 지침 v28 2부 7항과 맞지 않습니다.

  - 대표님은 편집기로 고친 뒤 일반 커밋을 합니다.
- **채택 시 남는 약점**
  - 에이전트가 Bash로 거버넌스 파일을 고치면 커밋 때 잡히지 않습니다. `git commit`은 `ask`(확인 창) 대상이므로, 이 경우는 대표님이 커밋 확인 창에서 변경 파일을 보고 막아야 합니다.
  - deny 경로를 어떤 기준(프로젝트 루트 또는 작업 폴더)으로 해석하는지는 확인 불가입니다. 적용한 뒤 Claude Code의 `/permissions`로 규칙이 표시되는지 확인합니다.

## 5. 권고 작업 순서

1. **F4-3을 고칩니다.** 승인 없이 커밋할 수 있는 경로입니다. 코드 한 곳만 고치면 됩니다.
2. **결정 2를 정하고 F2를 고칩니다.** 새 프로젝트가 처음 막히는 지점입니다.
3. **F4-1·F4-2·F4-4와 결정 3**을 정하고 고칩니다.
4. **결정 1**(부서 구성)을 정하고 F5를 고칩니다.
5. **실제 적용으로 확인합니다.** 빈 폴더에 복사해 `setup.cmd`를 실행하고, 작은 안건 하나를 처음부터 커밋까지 진행합니다.
