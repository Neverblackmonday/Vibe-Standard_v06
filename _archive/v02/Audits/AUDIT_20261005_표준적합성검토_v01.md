## 3. 걸리는 점

### F1. 7개 부서 고정: 범용성

- 모든 프로젝트가 7개 부서(마케팅·비주얼 포함)와 부서마다 4개 폴더를 받습니다. `.gitkeep`이 40건(폴더 조회로 셈)입니다.
- 대표님의 기존 프로젝트를 예로 들면, CMM 데이터 브리지나 매매 프로그램에는 마케팅·비주얼 부서가 필요 없습니다. 반대로 Shopee 상품 등록 같은 일에는 개발 부서가 거의 필요 없습니다.
- 표준은 모든 프로젝트에 공통인 최소 집합만 두고 나머지는 선택으로 두는 편이 맞습니다. v01 8차 점검(쓰이지 않는 폴더 5건)의 교훈과도 같습니다.
- **권고:** 핵심 부서(비서실·설계·개발·품질)만 기본으로 둡니다. 운영·마케팅·비주얼은 「선택 부서」로 정의해, 필요할 때 에이전트 파일 하나와 폴더를 추가합니다(결정 1).

### F2. 템플릿과 표준 저장소의 혼재

1. **`PROJECT.md`를 고칠 수 없습니다.**
   - `PROJECT.md`는 프로젝트마다 반드시 고쳐야 하는 파일입니다. 그런데 거버넌스 파일 목록에 들어 있습니다.
   - [실측] 초기화 커밋 뒤 `PROJECT.md` 한 줄을 고쳐 커밋했더니, 「[FAIL] 거버넌스 규정 … 무단 수정이 감지되었습니다 … PROJECT.md」가 출력되고 커밋이 차단되었습니다(종료 코드 1).
   - 이 차단은 에이전트뿐 아니라 대표님에게도 같게 적용됩니다. `AGENTS.md`는 거버넌스 파일을 「대표님 단독 수정 구역」이라고 적었지만, 대표님이 커밋할 방법이 정해져 있지 않습니다. 남은 방법은 `git commit --no-verify`(검사 건너뛰기)뿐입니다.
   - 같은 이유로 표준 자체의 개정(`AGENTS.md` 수정)도 커밋할 수 없습니다.
2. **`PROJECT.md` 내용이 템플릿이 아닙니다.** 내용이 「프로젝트명: Vibe Standard v02」로 되어 있어, 복사해 간 프로젝트가 그대로 물려받습니다.
3. **표준 저장소 자체의 기록이 함께 복사됩니다.** 폴더 전체를 복사하면 `_archive/`(이 저장소의 검토 기록)도 새 프로젝트로 넘어갑니다.

**권고:** 거버넌스 파일 목록에서 `PROJECT.md`를 뺍니다. 대표님이 거버넌스 파일을 고칠 때 쓸 절차를 하나 정합니다(결정 2). `PROJECT.md`는 빈칸 서식으로 바꿉니다. 표준 저장소의 작업 기록은 템플릿 밖에 둡니다.

### F3. 규정의 강제 수준과 실제가 다름

- **규정:** `AGENTS.md` 2절은 「Fail-Closed」, 「모든 후속 작업 및 커밋이 차단된다」, 「에이전트의 수정을 전면 금지한다」고 적습니다.
- **실제:** 실제 장치는 커밋할 때 실행되는 검사뿐입니다. 아래와 같은 빈틈이 있습니다.
  - 수정 전에 막는 훅이 없습니다. `settings.json`의 deny에는 `CEO/`만 있습니다.
  - `approved:` 줄과 REQ의 `scope:`는 에이전트도 고칠 수 있습니다. REQ 폴더는 검사 허용 목록에 들어 있어서, 승인 뒤 scope를 넓혀도 검사가 잡지 못합니다.
  - `git status` 조회가 실패하면 「[WARN]」만 출력하고 통과합니다(`check_standard.py` 112~114행).
- **판단:** 표준이 실제보다 강한 보장을 약속하면, 사용자는 지켜지지 않는 보호를 믿게 됩니다. 문구를 실제 수준에 맞추거나, 장치를 보강해야 합니다(결정 3).
  - 문구를 맞추는 예: 「커밋 시점 검사로 차단한다. 작업 중 차단은 하지 않는다.」
  - 장치를 보강하는 예: 거버넌스 파일에 대한 Edit·Write를 `settings.json` deny에 추가합니다. `settings.json` deny는 기본 기능이라 코드를 추가하지 않아도 됩니다.

### F4. 검사의 오판

| 번호 | 현상 | [실측] 결과 | 권고 |
|---|---|---|---|
| F4-1 | 새 하위 폴더 안의 새 파일을 Git이 폴더 한 줄로만 출력합니다. 그래서 scope에 적힌 파일 경로와 맞지 않습니다 | 승인된 REQ의 scope에 `…/assets/src/pkg/mod.py`를 적고 이 파일을 만들었더니 `[FAIL] 승인된 scope 외 …`가 출력되었습니다(종료 코드 1) | `git status --porcelain -uall`을 사용합니다 |
| F4-2 | 「마지막 번호의 REQ」 하나만 기준으로 대조합니다 | 승인된 `REQ-001`로 작업하는 중에 승인 전 초안 `REQ-002`를 만들었더니 `[FAIL] REQ-002.md 안건이 아직 … 승인을 받지 않았습니다`가 출력되었습니다(종료 코드 1) | 승인된 REQ 가운데 커밋되지 않은 안건 하나를 기준으로 삼습니다. 또는 커밋 메시지의 REQ 번호를 기준으로 삼습니다 |
| F4-3 | 경로 중간에 `results`나 `workspace`라는 이름이 있으면 어디에 있든 허용합니다(`is_whitelisted`) | 미실행. 해당 상황을 실측하지 못했습니다 | 경로 앞부분으로만 판정합니다. 예: `Departments/*/results/` |

### F5. 일관성

- **경로 표기:** `AGENTS.md` 2절 1번·3절과 `design.md`·`secretariat.md` 19행은 경로에서 `Departments/`를 빼고 적었습니다(직전 검토 S7, 이번 사본에서도 그대로입니다).
- **결과서 이름:** 품질 결과서는 `RES-001`, 설계 결과서는 「RES-설계」이고, 나머지 부서는 정해져 있지 않습니다(직전 검토 S5).
- **REQ 판정:** 라이프사이클 ①에 「REQ 판정」이 있지만, 누가 판정하고 어디에 기록하는지 없습니다. REQ 서식에도 판정 절이 없습니다(직전 검토 S8).
- **`setup.cmd` 파일 형식:**
  - `setup.cmd`가 UTF-8 BOM으로 시작하고 줄 끝이 LF입니다([실측] `od` 결과 첫 바이트가 `357 273 277`).
  - v01은 배치 파일의 CRLF·BOM을 실제 사고(W-1)를 근거로 검사했습니다.
  - `.gitattributes`가 다음 체크아웃 때 CRLF로 바꿉니다. 그러나 BOM은 그대로 남습니다.
  - Windows `cmd`가 BOM이 붙은 첫 줄을 어떻게 처리하는지는 확인 불가입니다.
- **명세 파일명:** 명세 파일명에 버전을 붙이지 않는 규정(`AGENTS.md` 3절)은 전역 지침 v28 2부 7항과 맞지 않습니다. 직전 검토와 같은 쟁점입니다.
