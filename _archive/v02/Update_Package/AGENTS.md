## 2. 핵심 원칙

1. **승인 전 착수 금지 (Fail-Closed)**: 대표님 승인은 REQ 머리말 `approved: "YYYY-MM-DD"` 기재로 확정한다. `approved:`가 비어 있는 REQ는 미승인 안건이며, 명세(`Departments/Design/docs/`)·코드(`Departments/Development/assets/src/`) 수정과 커밋을 하지 않는다. 승인 전에는 `Departments/Secretariat/assets/inbox/`, `Departments/Secretariat/docs/requests/`, 각 부서 `workspace/`에서만 작업한다.
2. **범위 통제 (Scope Quarantine)**: 승인된 REQ `scope:` 밖의 파일은 수정하지 않는다. 각 단계 서브에이전트는 scope 가운데 자기 단계 경로와 자기 부서 `results/`·`workspace/`만 수정한다. 품질팀은 `git status --porcelain -uall` 결과를 scope와 대조해 범위 밖 수정·생성이 있으면 `fail`로 판정한다.
3. **승인 목록 간주**: 승인된 REQ의 `scope:`를 사용자 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」의 승인 목록으로 본다. scope 밖 파일이 필요하면 파이프라인을 멈추고 보고한다.
4. **거버넌스 구역**: 거버넌스 파일(`AGENTS.md`, `CLAUDE.md`, `setup.cmd`, `.claude/`, `.githooks/`, `Departments/Development/assets/scripts/`, `Workflow/`)과 `CEO/References/`는 에이전트가 직접 수정하지 않는다. 거버넌스 파일 개정이 필요하면 REQ `scope:`에 해당 파일을 기재하고, 담당 부서가 자기 `workspace/`에 적용본을 작성해 품질 판정과 대표님 최종 승인을 거친 뒤 대표님이 원본에 반영한다(`Workflow/06_거버넌스_엔지니어링_아키텍처` 「거버넌스 파일 개정 절차」). `CEO/References/`는 REQ `scope:`에 기재할 수 없다.
5. **대표님 거버넌스 직접 수정·커밋 권한**: 대표님은 거버넌스 파일을 직접 수정할 수 있다. 승인된 REQ의 scope 안 변경은 일반 커밋으로 `check_standard.py`를 통과한다. REQ 없는 거버넌스 수정은 대표님만 `git commit --no-verify`로 커밋할 수 있으며, 에이전트는 대표님의 명시적 지시 없이 `--no-verify`를 사용하지 않는다.
6. **생성과 판정의 분리**: 본문을 작성한 세션(설계·개발·운영·비서실)은 스스로 판정하지 않고, 독립된 품질 서브에이전트가 검증과 판정을 수행한다. 품질팀은 판정서만 작성하며, EC의 `status:` 변경은 EC 판정서의 `result: pass`를 근거로 설계팀이 수행한다.
7. **단순성 우선 (KISS·YAGNI)**: 요청하지 않은 기능, 미사용 추상화, 실측 없는 조기 최적화를 추가하지 않는다.
8. **추측 금지**: 요구사항이나 명세가 모호하면 임의로 구현하지 않고 역질문하거나 반려 사유를 밝혀 반려한다.
9. **규칙 비대화 방지**: 새 규칙은 사고의 근본 원인이 입증되고 플랫폼 기본 기능으로 막을 수 없을 때만 추가한다. 사고 이력이 없거나 기본 기능으로 대체할 수 있는 규칙은 폐지하거나 권고로 완화한다. 하나의 REQ에는 하나의 목적만 담는다.
10. **문서와 버전**: `docs/`의 명세는 버전 번호 없는 파일명 하나로 유지하고, 개정 이력은 Git 커밋 로그와 문서 하단 「📝 개정 이력」 표로 관리한다. 소스코드 파일마다 버전을 적지 않고 패키지 설정 파일과 Git 태그로 관리한다. 문서 간 참조는 확장자 없는 상대 경로로 적는다.

## 3. 원스톱 단일 승인제

1. **승인 시점**: 대표님 승인은 REQ 승인(착수)과 최종 승인(완료) 두 시점뿐이다. 모든 등급에서 중간 승인을 두지 않는다.
2. **무인 자동 인계**: 대표님이 원스톱 실행 명령을 한 번 실행하면 메인 세션이 오케스트레이터가 되어 REQ `workflow:`에 기재된 부서만 순서대로 서브에이전트로 기동하고 인계한다. 절차는 `Workflow/03_라이프사이클_및_워크플로우` 「원스톱 파이프라인」, 명령은 `Workflow/05_비서실_클로드cli_인수인계_정책` 「원스톱 실행 명령」을 따른다.
3. **중단 조건**: 아래 경우에만 파이프라인을 멈추고 대표님께 보고한다. 이 밖의 판단은 묻지 않고 끝까지 진행한다.
   - ① scope 밖 변경이 필요한 경우
   - ② REQ가 여러 뜻으로 읽혀 `rejected`로 판정된 경우
   - ③ 최종 판정 누적 3회 반려(Critical은 격상할 등급이 없으므로 중단)
   - ④ 거버넌스 적용본의 원본 반영이 필요한 경우
   - ⑤ `ask` 목록 명령(삭제·이동·커밋·푸시) 또는 `allow` 목록 밖 명령의 권한 확인 요청이 발생한 경우. 표준 절차의 검증 명령은 `allow` 목록 안에서 실행한다(`Workflow/06_거버넌스_엔지니어링_아키텍처` 「무인 실행 권한」)
4. **등급**: 비서실은 REQ 작성 시 등급(Critical, Major, Minor)을 지정한다. Critical·Major는 EC 작성과 EC 판정을 거친다. Minor는 정규 절차(REQ → 약식 명세 → 구현 → 품질 RES → 대표님 승인)를 유지하며 EC를 생략한다. 모든 등급은 품질팀의 최종 판정서 발행과 대표님 최종 승인으로 완료한다. 등급별 흐름은 `Workflow/03_라이프사이클_및_워크플로우` 「등급별 흐름」을 따른다.
5. **반려와 격상**: 최종 판정이 누적 3회 `fail`이면 작업을 중단하고 차상위 등급(`Minor → Major → Critical`)의 절차로 처음부터 다시 진행한다. EC 판정 `fail`은 이 횟수에 넣지 않는다.
6. **모델**: 설계·개발·품질은 모든 등급에서 `Claude Opus 5.5`를 사용한다. 세부 기준은 `Workflow/04_모델_운용_기준`을 따른다.
7. **품질 판정 기준**: 품질팀은 REQ 요구사항·구현 파일·테스트의 양방향 추적성을 확인하고, REQ·EC에 없는 기능을 발견하면 `fail`로 판정한다. 승인된 REQ와 EC는 승인 시점에 동결하며 작업 중 수정하지 않는다.

## 4. 비서실 책무와 핫픽스

1. **전수 점검표 책무**: 비서실은 모든 REQ의 「검증 및 완료 기준」 절에 전수 점검표를 작성한다. 점검표 번호는 「요청 원문」 절의 지시 항목과 1:1로 대응시킨다. 품질팀은 최종 판정서에 점검표 번호별 근거를 기재하고, 비서실은 대표님께 최종 보고하기 전에 모든 번호에 근거가 있는지 대조한다.
2. **직접 구현 금지와 예외**: 비서실은 코드와 명세를 직접 구현하지 않는다. 예외는 아래 핫픽스 전결뿐이다.
3. **핫픽스 전결**: 기존 기능의 결함 또는 오탈자로서 수정 파일 3개 이하이고 거버넌스 파일·`CEO/`·`.claude/`·새 기능·새 파일을 포함하지 않는 경우, 대표님이 대상 파일 목록을 사전 승인하면 비서실이 정규 라이프사이클 없이 수정하고 `HOTFIX-xxx.md`로 사후 보고한다. 대표님의 `confirmed:` 기재로 종결한다. 조건에 하나라도 어긋나면 정규 REQ로 전환한다. 절차는 `Workflow/03_라이프사이클_및_워크플로우` 「핫픽스 트랙」, 서식은 `Workflow/07_엔지니어링_변경통제_및_서식_명세` 「HOTFIX」를 따른다.

## 5. 네이밍과 커밋

- 공식 문서의 파일명과 번호 규칙은 `Workflow/07_엔지니어링_변경통제_및_서식_명세` 「번호」를 따른다.
- 커밋 메시지는 `feat: [REQ-001] 요약`, 핫픽스는 `fix: [HOTFIX-001] 요약` 형식으로 적는다. `setup.cmd`가 초기화 때 만드는 첫 커밋(`chore: 바이브 코딩 표준 v02 초기화`)은 REQ 번호 기재와 REQ 검사에서 면제한다.
- 커밋은 최종 판정 `result: pass`와 대표님 최종 승인 뒤, 대표님의 명시적 요청이 있을 때만 수행한다. 푸시도 같다.
