## 3. 세부 설계

### 3.1 `AGENTS.md` 개정 요지
1. **원스톱 단일 승인제**: 대표님 승인은 REQ 승인(착수)과 최종 승인(완료) 두 시점뿐이다. 그 사이 단계는 오케스트레이터 세션이 `workflow:` 순서대로 서브에이전트를 자동 인계한다. Critical의 중간 승인을 폐지한다.
2. **승인 목록 간주 규정**: 승인된 REQ의 `scope:`를 사용자 전역 지침의 「파일 삭제·덮어쓰기 전 사용자 승인」 승인 목록으로 본다. scope 밖 파일이 필요하면 파이프라인을 멈추고 보고한다.
3. **중단 조건 (대표님 호출 사유)**: ① scope 밖 변경 필요 ② REQ가 여러 뜻으로 읽히는 모호성(`rejected`) ③ 품질 누적 3회 반려(Critical은 격상할 등급이 없으므로 중단) ④ 거버넌스 적용본 반영 ⑤ `ask` 목록 명령(삭제·이동·커밋·푸시) 또는 `allow` 목록 밖 명령의 권한 확인 요청. 이 밖에는 묻지 않고 끝까지 진행한다. 표준 절차의 검증 명령은 ⑤에 걸리지 않도록 3.2절 무인 실행 권한 목록 안에서 실행한다.
4. **비서실 공식 책무**: REQ 5절 전수 점검표를 REQ 1절 요청 원문 항목과 1:1로 작성한다. 품질팀은 RES에 점검표 번호별 근거를 기재하고, 비서실은 최종 보고 전에 모든 번호에 근거가 있는지 대조한다.
5. **핫픽스 전결**: 3.3절 조건을 충족하는 결함은 대표님이 대상 파일 목록을 사전 승인한 뒤(3.3절 절차 1) 비서실이 정규 라이프사이클 없이 수정하고 `HOTFIX-xxx.md`로 사후 보고한다. 「비서실은 코드를 직접 구현하지 않는다」에 이 예외를 명시한다. Minor는 정규 절차(REQ → 약식 명세 → 구현 → 품질 RES → 대표님 승인)를 유지한다.
6. **대표님 거버넌스 직접 수정·커밋 권한**: 대표님은 거버넌스 파일을 직접 수정할 수 있다. 승인 REQ의 scope 안이면 일반 커밋으로 `check_standard.py`를 통과한다. REQ 없는 수정은 대표님만 `git commit --no-verify`로 커밋할 수 있고, 에이전트는 대표님의 명시적 지시 없이 `--no-verify`를 사용하지 않는다(4절 결정 사항 6).
7. **모델**: 설계·개발·품질은 모든 등급에서 `Claude Opus 5.5`를 사용한다.
8. **축소 방식**: 등급 표, 네이밍 표, 재심사 번호 규칙 같은 세부 규정은 해당 `Workflow/` 매뉴얼로 옮기고 `AGENTS.md`에는 원칙과 참조만 남긴다. 규정의 원천은 `AGENTS.md`로 유지한다. 「Critical 대표승인 2회」를 삭제한다.

  - 조회: `Bash(git status*)`, `Bash(git diff*)`, `Bash(git log*)`, `Bash(git show*)`, `Bash(git ls-files*)`, `Bash(wc *)`, `Bash(od *)`, `Bash(head *)`, `Bash(grep *)`, `Bash(date*)`, `Bash(tar -t*)`
  - 검사·시험: `Bash(python Departments/Development/assets/scripts/check_standard.py*)`, `Bash(python -m pytest*)`, `Bash(python Departments/*/workspace/*)`
  - 임시 Git 저장소가 필요한 시험(`check_standard.py` Red/Green, `git archive` 목록 확인, `setup.cmd` BOM 실측)은 개발·품질 `workspace/`의 Python 시험 스크립트로 작성하고 위 규칙으로 실행한다. 임시 저장소의 `git init`·`git add`·`git commit`·`git archive`와 `cmd /c`는 스크립트 안에서 실행되므로 `ask`의 `git commit*`에 걸리지 않으며, 저장소 원본에는 커밋하지 않는다.
  - 검증 명령은 Bash 도구로 실행한다. PowerShell 도구는 `Bash(...)` 규칙의 적용을 받지 않기 때문이다.
  - `deny`(거버넌스 파일 쓰기 차단)와 `ask`(삭제·이동·커밋·푸시)는 그대로 유지한다.
  - `Bash(python Departments/*/workspace/*)`는 에이전트가 작성한 스크립트를 확인 없이 실행하게 하므로 사실상 임의 명령 실행을 허용한다. 권한 완화이므로 대표님 결정 사항이다(4절 결정 사항 4).
  - `allow` 목록은 적용본 반영 뒤에 효력이 생긴다. REQ-002의 남은 단계는 현행 권한 설정으로 진행하므로 권한 확인 요청이 뜰 수 있다(결정 사항 3).
- **타깃 컨텍스트 규칙** (`04`): ① 서브에이전트 지시문에는 REQ 경로, EC 경로, 대상 파일 경로, 단계명만 넣고 매뉴얼 본문을 붙여 넣지 않는다 ② 매뉴얼은 필요한 절만 `Grep` 후 범위 지정으로 읽는다 ③ 재판정 지시문에는 직전 RES의 결함 표와 `git diff` 변경분만 전달한다 ④ 작성 과정의 대화 내용은 판정 세션에 전달하지 않는다(전역 지침 8절).
- **배포본 복제 규칙** (`01`): `robocopy /MIR`은 받는 쪽에 이미 있는 제외 대상 파일을 지우지 않고, 커밋하지 않은 파일과 `.gitignore` 대상까지 복사하므로 사용하지 않는다(품질 실측, `RES-002-EC.md` 2차 차수). 대신 Git 기본 기능을 쓴다.
  - `.gitattributes`에 아래 `export-ignore` 규칙을 추가해 표준 개발 이력을 배포 대상에서 뺀다. 이미 커밋된 `Claude outputs/` 3건과 구 명칭 `RES_DEV-001.md`도 규칙으로 제외한다(`git ls-files` 실측). 커밋하지 않은 파일은 `git archive`에 원래 포함되지 않는다.
    ```text
    _archive/** export-ignore
    Claude?outputs/** export-ignore
    Departments/**/REQ-0*.md export-ignore
    Departments/**/EC-0*.md export-ignore
    Departments/**/DEV-0*.md export-ignore
    Departments/**/RES-0*.md export-ignore
    Departments/**/RES_DEV-0*.md export-ignore
    Departments/**/HOTFIX-0*.md export-ignore
    Departments/*/workspace/** export-ignore
    Departments/*/workspace/.gitkeep -export-ignore
    Departments/Secretariat/assets/inbox/** export-ignore
    Departments/Secretariat/assets/inbox/.gitkeep -export-ignore
    ```
    폴더 형태(`workspace/`)로 쓰면 `.gitkeep`을 되살리는 규칙이 적용되지 않아 폴더가 배포본에서 사라지므로 `/**` 형태로 쓴다(품질 실측, `RES-002-EC.md` 3차 차수). `Claude?outputs`의 `?`는 공백 한 글자에 일치시키기 위한 표기다(품질 실측, `RES-002-EC.md` 4차 차수에서 일치 확인).
  - 저장소 루트(`D:\Vibe Coding\Vibe Standard_v02`)에서 `git archive --format=tar -o "<임시경로>/vibe_v02_sample.tar" HEAD`로 배포본을 만든다. 압축 해제 전에 `tar --force-local -tf "<임시경로>/vibe_v02_sample.tar"`로 목록이 읽히는지 먼저 확인한다. 대표님 승인 뒤 `Vibe Standard_v02_sample` 내용을 비우고(비우기는 삭제이므로 실행 시점에 대상 목록 승인을 받는다), `D:\Vibe Coding`에서 `tar --force-local -xf "<임시경로>/vibe_v02_sample.tar" -C "Vibe Standard_v02_sample"`로 푼다. 명령은 Git Bash에서 실행하며, `<임시경로>`는 Git Bash 형식(예: `/d/tmp`)으로 적는다. GNU tar는 `D:`처럼 드라이브 문자가 붙은 경로를 원격 호스트로 해석하므로 `--force-local`을 붙인다(품질 실측, `RES-002-EC.md` 5차 차수: 미지정 시 종료 코드 128). zip 형식은 Git Bash의 GNU tar가 풀지 못하므로 쓰지 않는다(품질 실측, `RES-002-EC.md` 4차 차수: zip은 종료 코드 2·추출 0건, tar 형식은 Git Bash에서 68건·한글 파일명 정상).
  - 구현 단계는 임시 Git 저장소에 규칙을 반영해 커밋한 뒤 `git archive HEAD | tar -t` 목록으로 결과를 확인한다(위 무인 실행 권한의 Python 시험 스크립트 안에서 실행).

### 3.3 핫픽스 트랙과 `HOTFIX_TEMPLATE.md`
- **대상 조건 (모두 충족)**: 기존 기능의 결함 또는 오탈자, 수정 파일 3개 이하, 거버넌스 파일·`CEO/`·`.claude/` 제외, 새 기능·새 파일 없음. 하나라도 어긋나면 정규 REQ로 전환한다.
- **절차**:
  1. **사전 승인**: 핫픽스는 비서실이 임의로 작업할 수 없으며, 수정할 구체적 내용(원인, 변경 요지)과 대상 파일 목록을 대표님께 사전에 제시하여 승인을 받은 뒤에만 작업을 착수한다. 이 승인된 목록이 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」의 승인 목록이 되며, 비서실은 수정 전에 지시 원문과 승인 내역을 `HOTFIX-xxx.md` 1절에 기록한다.
  2. 비서실 수정 → `check_standard.py`와 관련 테스트 실행 → `HOTFIX-xxx.md` 2·3절 작성
  3. **사후 확인**: 대표님이 머리말 `confirmed:`를 기재한다. 대표님 확인이 독립 판정을 대신하므로 작성 세션 자기 판정 금지 원칙과 충돌하지 않는다.
- **서식 구성**: 머리말(`hotfix_id`, `created`, `author`, `confirmed`, `scope` 3개 이하) / 1. 지시 원문, 승인된 대상 파일 목록, 현상과 위험도 / 2. 수정 내역(파일별 변경 전후) / 3. 검증 결과(`| 항목 | 명령 | 시각 | 결과 원문 |`) / 4. 대표님 사후 확인란
- **커밋 연동**: `check_standard.py`는 `confirmed:`가 기재된 `HOTFIX-xxx.md`의 `scope:`를 승인 범위로 인정한다(3.4절 2번 ⑥). 커밋 메시지는 `fix: [HOTFIX-001] 요약`이다.
