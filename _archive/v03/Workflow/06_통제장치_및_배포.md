# 06. 통제장치 및 배포

> 이 문서가 정하는 것: 규칙을 집행하는 통제 계층과 한계, 권한 설정·커밋 전 검사의 동작, 거버넌스 파일 개정 절차, 배포본과 업데이트 패키지.
> 다른 문서가 정하는 것: 거버넌스 파일 목록 → `AGENTS.md` 「불변 원칙」 3항, 작업 구역 규정 → `Workflow/02_부서_구조_및_작업구역` 「작업 구역」.

## 1. 통제 계층

| 계층 | 파일 | 시점 | 위반 시 결과 | 한계 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | `.claude/settings.json` | 기능 실행 시도 시 | 거부(`deny`) 또는 사용자 확인(`ask`) | Claude Code에만 적용된다. `Edit`·`Write`만 막으므로 셸 명령으로 쓰는 파일은 막지 않는다 |
| 2 | `.claude/agents/*.md` | 서브에이전트 기동 시 | `disallowedTools: Agent`는 기계적 차단 | 작업 경로 제한은 모델이 따르는 지시다 |
| 3 | `.githooks/pre-commit` → `check_standard.py --staged` | 커밋 시 | 커밋 중단(종료 코드 1) | `--no-verify`로 건너뛸 수 있고, `core.hooksPath`를 설정하지 않은 PC에서는 실행되지 않는다. REQ·HOTFIX 기록은 대조에서 빠지므로 에이전트가 `approved:`·`confirmed:`를 대리 기재하는 것과, 종결된 안건의 승인으로 같은 경로를 다시 커밋하는 것을 막지 못한다. 검사 대상(커밋 대상·작업 트리)의 구분은 4절을 따른다 |
| 4 | 품질 판정 | REQ·EC·최종 판정 | `result: fail` | 판정 기준 밖의 결함은 놓칠 수 있다 |

어느 계층도 혼자서는 완전하지 않으므로 네 계층을 함께 운영한다. 셸 명령으로 쓴 파일은 계층 3과 4에서 확인한다. 승인 필드는 대표님이 커밋 전에 직접 확인한다.

## 2. 권한 설정 (`.claude/settings.json`)

- **`deny`**: 거버넌스 파일 목록, `CEO/**`, `_archive/**`를 `Edit(<경로>)`·`Write(<경로>)` 짝으로 등록한다. 목록이 `AGENTS.md` 「불변 원칙」 3항과 일치하는지는 개정 때마다 대조한다.
- 경로 구분자가 없는 규칙(`AGENTS.md`)과 폴더 규칙(`Workflow/**`)이 하위 폴더의 같은 이름 파일·폴더에도 적용될 수 있다(확인 불가, 7절). 그래서 적용본은 파일·폴더 이름 끝에 `.적용본`을 붙여 작성한다(5절).
- **`ask`**: 삭제·이동(`rm`, `del`, `mv`, `move`)과 `git commit`, `git push`는 실행 전에 확인을 받는다.
- `.claude/settings.local.json`은 PC별 개인 설정이므로 `.gitignore`로 저장소에서 뺀다.

### 2.1 무인 실행 권한

- 파이프라인은 `--permission-mode acceptEdits`로 파일 편집 확인을 생략한다.
- 표준 절차의 조회·검사·시험 명령은 `allow`에 등록되어 있어 확인 없이 실행된다. 목록의 원천은 `settings.json`이다.
- 임시 Git 저장소가 필요한 시험은 부서 `workspace/`의 Python 스크립트로 작성해 `allow` 규칙(`Bash(python Departments/*/workspace/*)`)으로 실행한다. 이 규칙은 에이전트가 작성한 스크립트를 확인 없이 실행하게 하므로 사실상 임의 명령 실행을 허용한다. 대표님이 이 완화를 승인했으며(v02 REQ-002), `deny`·`ask`와 커밋 전 검사가 위험을 줄인다.
- 검증 명령은 Bash 도구로 실행한다. PowerShell 도구에는 `Bash(...)` 규칙이 적용되지 않는다.

## 3. 서브에이전트 정의 (`.claude/agents/`)

- 부서마다 정의 파일 하나를 둔다. 모든 정의 파일은 `disallowedTools: Agent`를 지정해 서브에이전트가 다른 서브에이전트를 기동하지 못하게 한다.
- 정의 파일 본문의 작성 기준은 `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」을 따른다. 모델 필드는 `Workflow/04_모델_운용` 「모델」을 따른다.

## 4. 커밋 전 검사 (`check_standard.py`)

`setup.cmd`가 `git config core.hooksPath .githooks`를 설정하고 훅 파일의 실행 권한을 기록한다. 저장소를 복제한 PC마다 `setup.cmd`를 한 번 실행한다. 훅은 `--staged` 옵션으로 변경 목록을 커밋 대상(index)에서 읽고(승인 기록과 테스트는 작업 트리 기준), 옵션 없이 직접 실행하면 작업 트리 전체(`git status --porcelain -uall`)를 검사한다.

| 순서 | 검사 | 통과 조건 | 실패 시 |
| :---: | :--- | :--- | :--- |
| 1 | 초기 커밋 예외 | `.git`이나 `HEAD`가 없으면 검사를 생략한다 | — |
| 2 | 변경 파일 조회 | `git rev-parse --show-toplevel`과 변경 목록 조회(`--staged`: `git diff --cached --name-status -M -z`, 그 밖: `git status --porcelain -uall -z`)가 성공한다. 이름 변경은 원래 경로와 새 경로를 모두 대조한다 | `[FAIL]`과 원인·조치 |
| 3 | 대표님 구역 | `CEO/` 아래 변경이 없다 | `[FAIL]`과 경로 |
| 4 | 대조 제외 | `WHITELIST_PREFIXES`의 경로와 부서 직속 `results/`·`workspace/`는 대조에서 뺀다 | — |
| 5 | scope 대조와 승인 | 남은 변경 파일 전체가 승인된 REQ 하나 또는 확인된 HOTFIX 하나의 `scope:` 안에 있다. 번호별 최신 버전만 쓴다 | `[FAIL]`, 대상 파일, 승인 요건을 갖추지 못한 기록과 사유 |
| 6 | 조건부 테스트 | `assets/src/`·`assets/tests/` 변경이 있으면 `pytest`를 실행해 종료 코드 0. 테스트 폴더 아래(하위 폴더 포함)에 `test_*.py`가 없거나 종료 코드 5면 `[WARN]` | `[FAIL]`과 종료 코드 |

- **승인 요건(구현)**: REQ는 `approved:`, HOTFIX는 `confirmed:`가 `YYYY-MM-DDTHH:MM:SS+09:00` 형식이고 실재하는 일시여야 한다. HOTFIX는 추가로 `HOTFIX_MAX_SCOPE`와 `GOVERNANCE_PATHS`로 `Workflow/03_라이프사이클` 「핫픽스 트랙」의 대상 조건 가운데 파일 수와 거버넌스 파일·`CEO/`·`_archive/` 제외를 검사한다.
- **scope 일치 규칙**: 변경 파일 `f`와 scope 항목 `s`(끝의 `/`와 줄 끝 주석 제거)가 `f == s`이거나 `f`가 `s + "/"`로 시작하면 포함으로 본다. `s`의 마지막 이름에 확장자가 없을 때만, 확장자를 뺀 `f` 또는 확장자와 버전 접미사(`_vNN`)를 뺀 `f`가 `s`와 같아도 포함으로 본다. 그래서 scope에 `Departments/Design/docs/tad/EC-007`처럼 버전 없이 적은 항목은 EC의 모든 버전을 포함한다.
- **기록 파일명**: `Workflow/07_문서_서식_및_번호` 「번호와 버전」 형식이 아닌 REQ·HOTFIX 파일은 `[INFO]`를 출력하고 검사에서 뺀다.
- **대표님 전용 구역의 커밋**: 거버넌스 파일과 `_archive/`도 scope 대조 대상이므로 승인된 REQ의 scope 안이면 일반 커밋으로 통과한다. REQ 없는 수정과 `CEO/` 변경(scope와 관계없이 차단된다)은 `git commit --no-verify`로 커밋하며, 사용 주체는 `AGENTS.md` 「불변 원칙」 5항을 따른다.

## 5. 거버넌스 파일 개정 절차

1. 비서실 세션이 개정 REQ의 `scope:`에 대상 거버넌스 파일을 기재하고, REQ 판정을 거쳐 대표님 승인을 받는다.
2. 담당 부서가 자기 `workspace/<REQ 번호>_적용본_v01/`에 원본과 같은 상대 경로로 적용본을 작성한다. 설계는 `AGENTS.md`·`CLAUDE.md`·`Workflow/`를, 개발은 `setup.cmd`·`.gitattributes`·`.gitignore`·`.claude/`·`.githooks/`·`Departments/Development/assets/scripts/`를 맡는다. `deny` 규칙과 이름이 같은 파일·폴더는 이름 끝에 `.적용본`을 붙인다(예: `Workflow.적용본/03_라이프사이클.md`, `AGENTS.md.적용본`). 파일별 반영 명령 목록을 자기 결과서에 적는다.
3. 구현 단계에서 개발 서브에이전트가 개정된 규칙과 `check_standard.py`·`settings.json`(적용본 포함)이 어긋나지 않는지 대조해 `DEV-xxx`에 적는다.
4. 품질 서브에이전트가 최종 판정에서 적용본을 판정한다. 판정 지적을 반영하면 폴더 버전을 올린다(`_v02`).
5. 대표님이 최종 승인 때 적용본을 원본 위치에 복사해 반영한다. `.적용본`은 반영할 때 뗀다.

## 6. 배포본과 업데이트 패키지

두 묶음은 같은 원천(이 저장소의 커밋)에서 만들지만 용도와 내용이 다르다.

| 구분 | 용도 | 내용 | 상태 |
| :--- | :--- | :--- | :--- |
| 배포본 | 신규 프로젝트를 시작할 때 복제 | 저장소 전체에서 `.gitattributes`의 `export-ignore` 대상을 뺀 것 | 보류(첫 배포 전) |
| 업데이트 패키지 | 기존 프로젝트의 표준을 최신으로 바꿀 때 덮어쓰기 | 표준 구역 파일(거버넌스 파일 목록과 `Workflow/templates/`)만 | 보류. 빌더는 v02 기록으로 `_archive/v02/`에 보관했다. 다시 도입할 때 별도 REQ로 진행한다 |

### 6.1 배포본 만드는 법

배포본은 대표님이 만든다(셸을 실행할 수 있는 창구에 지시해 실행할 수 있다).

1. 대표님 최종 승인과 커밋 뒤, Git Bash에서 저장소 루트로 이동해 실행한다. `<임시경로>`는 Git Bash 형식(예: `/d/tmp`)으로 적는다.
   ```bash
   git archive --format=tar -o "<임시경로>/vibe_sample.tar" HEAD
   tar --force-local -tf "<임시경로>/vibe_sample.tar"
   ```
2. 목록에서 확인한다(제외 규칙은 `Workflow/02_부서_구조_및_작업구역` 「공통 1차 하위폴더」의 비서실 `assets/` 규칙을 전제한다. 바로 아래의 확장자 없는 파일은 빠지지 않는다): ① `_archive/` 아래 파일 0건, `Update_Package/`·`Audits/` 아래는 `.gitkeep`만 ② `Departments/` 아래 REQ·EC 0건 ③ 부서 `results/`·`workspace/`와 비서실 `assets/` 아래는 `.gitkeep`만.
3. 새로 만든 빈 폴더(`<배포본 폴더>`)에 푼다. 기존 폴더에 풀면 같은 이름의 파일을 덮어쓰므로 쓰지 않는다.
   ```bash
   tar --force-local -xf "<임시경로>/vibe_sample.tar" -C "<배포본 폴더>"
   ```

- 커밋하지 않은 파일은 `git archive`에 포함되지 않는다.
- GNU tar는 `D:`처럼 드라이브 문자가 붙은 경로를 원격 호스트로 해석하므로 `--force-local`을 붙인다.
