아래는 사용자 전역 지침이 하위 지침으로 바꿀 수 없다고 정한 항목(불변 예외)의 원문이다.

### 4. 보안 및 불변 데이터 보호

* API 키, 비밀번호, 접속 토큰, 개인정보는 대화창·화면에 노출하거나 파일로 내보내지 않는다. 인증 정보는 대리 입력하지 않고 사용자가 직접 입력하게 한다.

* 기밀, 식별 정보, 비공개 데이터는 공개 저장소나 외부 산출물에 넣기 전에 승인을 받는다.

* 사람이 확정했거나 마감 날짜가 지정된 기록은 수정하지 않고 새 기록을 추가(Append)한다.

* 외부 원자료는 본 지침의 문체 기준으로 교정하지 않고 원형을 보존한다.

* 파일 삭제·덮어쓰기 전 사용자 승인: 기존 파일의 삭제와 덮어쓰기는 대상 경로 목록을 제시하고 승인을 받는다. 승인 시점에 목록을 확정할 수 없으면 실측한 뒤 목록을 제시하고 승인을 받는다. 승인 목록 밖 대상, 승인 뒤 사용자가 수정한 파일은 별도로 승인을 받는다. 새 파일 생성은 승인 없이 하되 기록 직전에 경로를 알린다.

* Git 커밋 및 푸시는 명시적 요청 시에만 수행: 커밋과 푸시(Push)는 각각 사용자의 명시적 요청이 있을 때만 수행한다.

* 지침 문서 수정 전 사용자 승인: 위 계층의 지침 문서와 저장소의 서비스별 지침 파일(`CLAUDE.md`, `GEMINI.md`, `.agents/rules/` 등)은 수정안을 제시하고 승인을 받은 뒤 수정한다. 절의 신설·삭제·이동, 문구, 버전 번호, 오탈자 수정을 포함한다. 사용자가 제시한 수정안을 임의로 재구성하지 않는다.

1. **승인 전 착수 금지**: REQ 머리말 `approved:`가 비어 있으면 명세·코드를 수정하지 않고 커밋하지 않는다. 승인 전에는 `Workflow/02_부서_구조_및_작업구역` 「작업 구역」의 승인 전 구역과 비서실 승인을 받은 `Lab/` 경로에서만 작업한다. 핫픽스는 REQ 대신 대표님 사전 승인과 HOTFIX `confirmed:`를 따른다(`Workflow/03_라이프사이클` 「핫픽스 트랙」). 승인 필드의 기재 방법은 `Workflow/07_문서_서식_및_번호` 「승인 기록」을 따른다.
2. **범위 통제**: 승인된 REQ `scope:` 밖의 파일은 수정하지 않는다. scope는 사용자 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」의 승인 목록으로 본다. scope 밖 파일이 필요하면 멈추고 보고한다. `Lab/`의 파이프라인 밖 사용은 REQ가 없으므로 이 항 대신 비서실이 승인한 범위(`Workflow/03_라이프사이클` 「실험실」) 안에서만 쓴다. 파이프라인 안의 실험 단계는 이 항을 그대로 따른다.
3. **거버넌스 구역**: 거버넌스 파일은 `AGENTS.md`, `CLAUDE.md`, `setup.cmd`, `.gitattributes`, `.gitignore`, `.claude/`, `.githooks/`, `Departments/Development/Implementation/assets/scripts/`, `Workflow/`이다. 에이전트는 거버넌스 파일과 `CEO/`를 직접 수정하지 않는다. 예외는 최종 판정서 승인 뒤 형상통제팀(C02)이 결과서의 반영 명령대로 적용본을 반영하는 것(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」)과, 전역 지침 원본이 바뀌어 형상통제팀(C01)이 다시 생성한 생성물을 대표님 승인 뒤 원천과 일치하는 것에 한해 반영하는 것(`Workflow/05_인수인계_및_실행명령` 「형상통제 절차」)뿐이다. 개정 절차는 `Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」를 따른다. 이 목록의 원천은 이 항이다.
4. **생성과 판정의 분리**: 작성한 세션은 스스로 판정하지 않는다. 판정은 Claude Code의 독립된 품질보증부 서브에이전트가 `Workflow/04_모델_운용`이 정한 모델로 수행한다. 그 밖의 세션이 작성한 판정서는 무효다.

6. **단순성 우선**: 요청하지 않은 기능, 쓰지 않는 추상화, 실측 없는 최적화를 더하지 않는다.
7. **추측 금지**: 요구나 명세가 여러 뜻으로 읽히면 임의로 진행하지 않고 반려 사유를 밝혀 반려하거나 보고한다.

9. **단일 원천**: 같은 규칙을 두 문서에 다시 적지 않는다. 다른 문서는 원천의 문서명과 절 제목을 참조한다. 매뉴얼과 이 문서가 어긋나면 이 문서를 따르고 대표님께 보고한다.
10. **추적성**: 대표님 지시부터 ORDER, REQ, 판정, 승인, 커밋까지와 ORDER를 거치지 않는 작업(핫픽스, 요청 커밋)에서, 각 기록이 어느 기록의 어느 버전에서 나왔는지 기록만으로 찾을 수 있게 남긴다. 세부(추적 식별자, 추적 관계, 다른 안건 기록의 참조, 적용 시점)는 `Workflow/07_문서_서식_및_번호` 「문서 체계」를 원천으로 따른다.

## 3. 팀 폴더와 공통 하위폴더

부서 폴더(`Departments/<부>/`) 아래에 팀 폴더(2.2절 「팀 폴더」 열)를 두어 「부 → 팀」 두 단계로 나눈다. 팀 폴더 안에는 공통 하위 폴더 `docs/`(정제된 문서: 기획서, 명세, 안건), `assets/`(실제 자산: 코드, 테스트, 스크립트, 파라미터, 조사 자료), `results/`(공식 결과서와 판정서), `workspace/`(중간 산출물, 메모, 거버넌스 적용본) 가운데 그 팀이 쓰는 것만 둔다. 파트 폴더는 두지 않는다. 한 파트만 계속 쓰는 자산은 팀 폴더 아래 용도 이름의 하위 폴더에 둔다(예: `Departments/Quality/Test/assets/acceptance/`). 대기 팀 폴더는 만들지 않고 그 팀의 파트를 활성으로 바꾸는 안건에서 만든다. 활성 파트가 있는 팀이 없는 운영부·마케팅부는 부서 폴더 바로 아래 `.gitkeep` 하나만 둔다. 지금 활성 팀 폴더와 하위 폴더는 아래와 같다.

```text

│   ├── Secretary/        # 비서팀(S01~S03)
│   │   ├── assets/inbox/      # ORDER, 승인 기록, 요청 기록, 종결 기록, 요구 메모
│   │   ├── assets/research/   # 조사 자료
│   │   ├── assets/planning/   # 아이디어 백로그, 기획안
│   │   ├── assets/briefings/  # 브리핑

│   │   ├── workspace/연락/    # 연락 파일(기록)
│   │   └── workspace/셸작업/  # 셸 작업 지시·결과 파일
│   ├── PM/               # PM팀(P01·P02)

│       ├── assets/live/           # 설계 파라미터
│       └── workspace/             # 설계부 거버넌스 적용본

│   ├── Implementation/   # 구현팀(V01·V02)

│   │   ├── results/           # 개발부 결과서(DEV)
│   │   └── workspace/         # 개발부 거버넌스 적용본, 일회성 파일
```

- 결과서는 번호 묶음(버전)이 한 폴더에 있어야 「가장 높은 번호가 현행본」이 성립하므로 기록 종류마다 한 폴더를 둔다. 설계부 결과서는 모든 안건의 첫 버전을 EC 판단(E01)이 만들므로 `Departments/Design/EC/results/`에 두고 명세(E03)가 다음 버전을 같은 폴더에 쓴다. 개발부 결과서는 실험(X01)과 구현(V01)이 함께 `Departments/Development/Implementation/results/`에 쓴다. 대기 팀의 결과서 위치는 그 단계를 맡은 파트의 팀 `results/`다(`Departments/<부>/<팀>/results/`. 예: 보안 점검 결과서는 `Departments/Operations/Security/results/`, 시각 디자인 단계의 마케팅부 결과서는 `Departments/Marketing/VisualDesign/results/`). 시각 디자인 문서는 `Departments/Marketing/VisualDesign/docs/DESIGN.md`, 런타임 파라미터는 `Departments/Operations/Release/assets/live/`에 둔다.
- 요청 기록·종결 기록은 형상통제팀(C02)·PM이 쓰지만 비서팀 `assets/inbox/`에 둔다. 종결 기록을 읽는 위치(커밋 전 검사와 `Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」 4항)와 판정 전제 제외 범위를 한 폴더로 두기 위해서다. 쓰기 권한은 4절 표가 정한다.

빈 폴더는 `.gitkeep`으로 유지한다. 비서팀 `assets/`에는 바로 아래에 파일을 두지 않고 하위 폴더(`inbox/`, `research/`, `planning/`, `briefings/`, `queue/`)에만 둔다. 최종 산출물은 팀 폴더의 `docs/`, `assets/`, `results/`에만 둔다.

## 4. 모델 메타데이터 기록

공식 문서(REQ, EC, DEV, RES, HOTFIX)의 머리말에 작성하거나 판정한 모델과 effort를 아래 기준으로 적는다.

- **모델**: 확인할 수 없으면 `"확인 불가"`로 적는다. 단, RES의 `auditor.model`에는 `"확인 불가"`를 적지 않는다. 판정서를 작성하는 세션이 자기 실행 모델을 확인할 수 없으면 판정서를 발행하지 않고 오케스트레이터에 보고한다.
- **effort(REQ, EC, DEV, RES, HOTFIX)**: 실행 명령 지시문의 effort 값을 출처와 함께 `"<값> (실행 명령 기준)"`으로 적는다(예: `"medium (실행 명령 기준)"`). PM은 자기 지시문의 표기(`Workflow/05_인수인계_및_실행명령` 「실행 명령」), 서브에이전트는 PM 지시문의 표기(3절 1항), 핫픽스팀(V03)은 핫픽스 실행 명령 지시문의 표기를 출처로 쓴다. 출처에서 값을 얻을 수 없을 때만 `"확인 불가"`로 적는다.
- **기준 모델·effort**: 판정서는 9절 「기준 모델·effort」에 판정 지시문의 유효 값 표(3절 1항)와 판정 세션 자신의 실행 모델·effort를 적고, 하향 확인을 거친 칸(1.4절 4항)이 있으면 그 칸과 확인 시각을 따로 적는다. HOTFIX는 1절 「기준 모델·effort」 항에 V03 칸 「분류 없음」의 유효 값과 출처, CEO 설정 `saved_at`을 적는다. 판정이 없는 커밋(최종 승인 커밋, 요청 커밋, PM 커밋)은 커밋 메시지 근거 줄 `Model-Effort`에 커밋한 세션의 모델과 effort를 남긴다(`Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「커밋 메시지」).
- **`REQ-031` 커밋 전의 HOTFIX**: 비서실이 실행 명령 없이 작성했으므로 실제 적용한 effort를 적었다. 고치지 않는다.

```yaml
author:            # RES는 auditor:
  agent: "Design"
  model: "Claude Opus 5.5"
  effort: "medium (실행 명령 기준)"
```

### 2.1 무인 실행 권한

- 파이프라인은 `--permission-mode acceptEdits`로 파일 편집 확인을 생략한다. 이 모드에서도 2절의 `deny`(거버넌스 파일·`CEO/`·`_archive/` 쓰기 차단)와 `ask`(삭제·이동·커밋·푸시 확인)는 그대로 적용된다.
- 표준 절차의 조회·검사·시험 명령은 `allow`에 등록되어 있어 확인 없이 실행된다. 목록의 원천은 `settings.json`이다.
- 임시 Git 저장소가 필요한 시험은 팀 `workspace/`의 Python 스크립트로 작성해 `allow` 규칙(`Bash(python Departments/*/*/workspace/*)`)으로 실행한다. 이 규칙은 에이전트가 작성한 스크립트를 확인 없이 실행하게 하므로 사실상 임의 명령 실행을 허용한다. 대표님이 이 완화를 승인했으며(v02 REQ-002), `deny`·`ask`와, 승인되었고 끝나지 않은 REQ와 확인되었고 끝나지 않은 HOTFIX의 `scope:`로 변경을 대조하는 커밋 전 검사(4절 순서 7)가 위험을 줄인다. 이 규칙으로 실행하는 스크립트 안의 명령(`git commit`·`git push`, 삭제·이동 포함)은 `ask`를 거치지 않으므로, 스크립트가 이 저장소에 커밋하거나 파일을 지울 수 있는 경로가 남는다. 이 경로는 막지 않으며, 위의 대표님 승인과 커밋 전 검사로 위험을 줄인다.
- 이 규칙으로 실행하는 스크립트 안에서 `allow` 밖이거나 `ask` 대상인 명령(이 저장소의 커밋·푸시·삭제·이동, `claude` 실행 등)을 실행하지 않는다. 예외는 운영체제 임시 폴더나 pytest `tmp_path` 아래에 만든 시험 저장소 안의 명령이다(인수 시험·단위 시험의 임시 Git 저장소). 위반은 판정에서 결함으로 본다.
- **명령 도구**: 조회·검사·시험 명령은 Bash 도구로 실행한다. Bash 도구가 거부되면 PowerShell 도구로 대신한다. PowerShell 도구에는 `Bash(...)` 규칙이 적용되지 않으므로, `settings.json`은 표준 절차의 Git 조회, 커밋 전 검사, 인수 시험 실행을 `PowerShell(...)` 규칙으로 따로 등록한다. PowerShell의 시각 조회(`Get-Date`)는 Claude Code가 기본으로 허용하는 읽기 전용 명령이므로 등록하지 않는다. PowerShell 도구로 내리는 `git commit`·`git push`와 삭제·이동은 `PowerShell(...)` 규칙으로 `ask`에 따로 등록한다(2절 「`ask`」).
- **명령 형태**: 권한 규칙은 명령 앞부분의 문자열로 맞추고, 묶은 명령은 하위 명령마다 따로 검사한다(근거 `Departments/Development/Implementation/results/DEV-019_v01.md` 6절). 그래서 명령 형태는 아래 원리 하나로 정한다.
  - **원리**: 명령은 저장소 루트(작업 폴더)에서 실행하고, 그 앞부분(묶었으면 하위 명령마다)이 `allow` 규칙이나 Claude Code가 기본으로 허용하는 읽기 전용 명령과 글자 그대로 맞아야 한다. 이 원리를 벗어나면 `allow`에 있는 명령도 권한 확인 요청이 된다.
  - **원리를 벗어나는 형태의 예**: 아래는 예일 뿐이며, 예에 없는 형태도 원리를 벗어나면 같다.
    - ① 작업 폴더를 바꾸거나 다른 폴더를 가리키는 앞부분: `cd <폴더>`, `git -C <경로>`
    - ② 프로그램 이름과 하위 명령 사이의 전역 옵션: `git -c <설정>`, `git --no-pager`. Git 명령은 `git` 바로 뒤에 하위 명령(`status`, `diff`, `log`, `show`, `ls-files`)을 쓴다. 경로의 한글 표시 설정(`core.quotepath`)은 `setup.cmd`가 저장소 설정으로 넣으므로 명령행에 붙이지 않는다.
    - ③ 명령 앞의 환경 변수 대입: `NAME=값 명령`
    - ④ `allow` 규칙에도 기본 읽기 전용 명령에도 들지 않는 하위 명령을 `;`·`&&`·`|`로 묶음(예: `echo "exit=$?"`를 덧붙임)과 셸 구문(변수 대입, 중괄호 묶음, `while`·`for` 반복문, `xargs`)
    - ⑤ PowerShell 도구의 하위 식(`$(...)`)과 괄호 식
  - **경로와 세션 기본 안내**: 명령의 경로는 저장소 루트 기준 상대 경로로 적는다. 절대 경로를 쓰라는 세션 기본 안내는 파일 도구(Read·Write·Edit 등)의 경로에만 적용하며, 이 원리보다 앞서지 않는다.
  - **PowerShell 도구**: 같은 원리를 따른다. 명령은 `PowerShell(...)` 규칙의 앞부분(예: `git status `, `python -m pytest `)이나 기본으로 허용하는 읽기 전용 명령(예: `Get-Date`)으로 시작한다.
  - **원리 안에서 할 수 없는 묶음·반복**: 여러 파일의 반복 처리, 결과 가공처럼 묶음·반복이 필요하면 `allow` 규칙을 더하지 않고 이미 있는 규칙 안의 경로로 실행한다. 검색은 Grep·Glob 도구나 인자를 나열한 단독 `grep` 명령(`Bash(grep *)`)으로 하고, 그 밖은 팀 `workspace/`의 일회성 Python 스크립트를 `Bash(python Departments/*/*/workspace/*)` 규칙으로 실행한다. 스크립트 이름은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「팀 `workspace/` 파일」 항을 따른다.
  - **커밋 해시 조회**: `git rev-parse`는 `allow`에 없어 권한 확인 요청이 된다. HEAD의 커밋 해시는 `git log -1 --format=%H`로 조회한다(`Bash(git log*)`, `PowerShell(git log *)`). 5절 2항의 기준 커밋 조회도 이 명령으로 한다.
  - **문서가 지정하는 명령**: EC, 결과서, 적용본, 인수 시험 절차서(ACC) 등 문서가 뒤 단계의 Claude Code 세션(PM·서브에이전트)에 실행을 지정하는 명령도 이 원리를 따른다. EC 판정·명세 판정이 이를 확인한다(`Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」). 형상통제팀(C02)이 실행하는 반영 명령은 결과서가 정하는 명령이지만 Claude Code 세션에 무인 실행을 지정하는 명령이 아니므로 대상이 아니다. Claude Code로 연 세션에서 반영 명령을 실행하면 확인 화면이 뜬다(2.2절).
- 판정 세션이 명령을 실행하지 못했을 때의 처리는 `Workflow/03_라이프사이클` 「판정 세션의 명령 실행」을, 판정 세션 밖 서브에이전트가 명령을 실행하지 못했을 때의 처리는 같은 문서 「판정 세션 밖의 명령 실행」을 따른다.

REQ 체크리스트 번호(REQ 서식 5절)와 최종 판정서의 체크리스트 대조 번호(판정서 서식 3절)는 그 요구 항목 번호를 그대로 이어받으며, REQ 머리말 `source_order`의 ORDER 번호와 합쳐 추적 식별자가 된다. 그래서 두 문서 안에서는 번호만 적는다. ORDER에는 파생 번호가 없으므로 추적 식별자의 끝 번호는 파생 번호가 아니다. - **다른 안건 기록의 참조**: 다른 안건이 정한 규정을 근거로 들 때는 그 규정이 있는 현행 원천 문서와 절(예: `Workflow/03_라이프사이클` 「재작업 구분」)을 적고, 그 안건의 기록(REQ, EC, 결과서, 판정서 등)을 버전으로 가리키지 않는다. 다른 안건 기록의 버전은 그 버전에 대한 사실(승인, 판정, 결정, 커밋)을 적을 때만 쓴다(예: 「`REQ-019_v03` D1(권고안)이 정한 처리 순서」). 같은 안건 안의 기록과 `scope:`의 기록 문서(3절)는 이 항목의 대상이 아니다.

- **번호**: REQ 번호가 원천이다. EC·DEV·RPT·RES는 같은 번호를 쓴다. 새 REQ 번호는 `Departments/Secretariat/PM/docs/requests/`의 가장 큰 번호에 1을 더한다.

- **인수 시험**: 폴더 이름은 `<REQ 번호>_vNN`이다(파생 안건은 `REQ-xxx-n_vNN`). 폴더 버전은 시험을 바꿀 때만 올리며 ACC 버전과 다를 수 있다. 현행 ACC는 가장 높은 버전의 ACC이고, 현행 인수 시험은 현행 ACC 머리말 `test_dir`이 가리키는 폴더다. 시험을 바꾸면 새 버전 폴더와 새 ACC를 만들고, 시험을 바꾸지 않고 판단만 적으면 새 ACC만 만든다. 이전 버전은 지우지 않는다. 「대상 없음」이면 폴더를 만들지 않는다.
- **부적합 기록**: 번호 자리에 그 안건 번호를 쓰고, 뒤에 그 안건의 부적합 기록 가운데 가장 큰 일련번호에 1을 더한 두 자리 번호를 붙인다(없으면 `01`. 예: `NCR-019_01.md`, 파생 안건 `NCR-019-1_01.md`). 버전을 붙이지 않고 작성 뒤 고치지 않는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **팀 `workspace/` 파일**: 안건을 위해 팀 직속 `workspace/`에 만드는 파일과 폴더는 이름을 그 안건의 REQ 번호와 `_`로 시작한다(예: `REQ-014_복사_20261009a.py`, `REQ-008_실측_v01/`. 파생 안건은 `REQ-xxx-n_`). PM 실행 기록은 「실행 기록」 항을 따른다. 일회성 파일의 판단과 정리는 `Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」의 최종 판정 기준 7을 따른다.
- **파생 번호**: 원 안건에서 미결로 남거나 새로 생긴 작업에 `1`부터 붙인다(`Workflow/03_라이프사이클` 「진행 중 변경과 파생 안건」).
- **버전**: 내용이 바뀌면 새 파일로 저장하고 버전을 올린다. 가장 높은 버전이 현행본이다. 판정에서 지적을 받아 고친 문서와 재판정 판정서도 새 버전으로 저장한다. 이전 버전은 지우지 않는다.

- **서식**: `*_TEMPLATE.*`(`.md`, `.html`)에는 번호와 버전을 붙이지 않는다.

- **머리말 형식**: 공식 문서는 `---`로 감싼 YAML 머리말로 시작한다. 브리핑은 예외이며 작성 정보를 본문 맨 끝에 적는다(`Workflow/05_인수인계_및_실행명령` 「브리핑」). 시각 디자인 문서도 예외이며 업계 통용 형식을 따르고, 안건과의 연결은 문서 하단 개정 이력 표(4절)로 남긴다.
- **날짜·시각 형식**: 날짜는 `"YYYY-MM-DD"`, 시각은 `"YYYY-MM-DDTHH:MM:SS+09:00"` 문자열이다. **`approved:`와 `confirmed:`는 시각 형식만 허용한다.** 형식은 커밋 전 검사에서 확인한다.
- **목록 필드**: 목록 필드(`scope:`, `workflow:`, `related_req:`, `causes:`, `proposals:`)는 두 칸 들여쓰기 뒤 `- `로 시작한다. 폴더 항목은 끝에 `/`를 붙이지 않는다(예: `Workflow`).
- **scope의 기록 문서**: `scope:`에 적는 기록 문서(EC 등)는 버전과 확장자 없이 적는다(예: `Departments/Design/EC/docs/EC-007`). 새 버전이 생겨도 scope를 고치지 않기 위해서다.
- **작성·판정 모델**: 작성·판정 모델은 `Workflow/04_모델_운용` 「모델 메타데이터 기록」대로 적는다.

- **NCR의 시각 필드**: NCR은 개정 제안의 건수를 기록 순서로 세므로(`Workflow/03_라이프사이클` 「부적합 관리」) `created` 대신 시각 필드 `recorded_at`을 쓴다. 원인과 제안을 머리말에 두어 기존 기록을 머리말만 읽고 대조할 수 있게 한다.

2. **매뉴얼 읽기**: 매뉴얼은 필요한 절만 찾아 읽는다. 각 매뉴얼 첫머리의 「이 문서가 정하는 것」으로 읽을 문서를 고른다. 파트 카드로 기동한 서브에이전트는 카드에 실린 지침을 따르고, 카드 끝 「필요할 때 읽는 문서」의 문서와 절은 필요할 때 찾아 읽는다(5절 5항).

## 2. 구성 수단

1. **문서 체계**: 모든 작업은 승인된 안건(REQ)에서 시작해 최종 판정서(RES)로 끝난다. 긴급 결함은 핫픽스 기록(HOTFIX)으로 처리한다.
2. **폴더 체계**: 부서 폴더 아래에 팀 폴더를 두어 작업 공간을 나누고, 팀 폴더는 같은 공통 하위폴더 가운데 쓰는 것만 둔다(`Workflow/02_부서_구조_및_작업구역` 「팀 폴더와 공통 하위폴더」).
3. **기계적 통제**: Claude Code 권한 설정과 커밋 전 검사로 규칙 위반을 막는다.
4. **독립 판정**: 품질 판정은 작성 세션과 분리된 Claude Code 품질보증부 서브에이전트가 수행한다.

### 5.1 판정 지적의 구분과 문체 지적 처리

판정 지적의 구분 기준과 문체 지적의 처리는 이 절이 원천이다.

1. **구분 기준**: 판정자는 지적을 「결함」과 「문체」로 나눈다. 결함은 판정 기준에 어긋나거나 실행 실패·반려·오독을 일으킬 수 있는 지적(사실 오류, 모순, 누락, 지칭 불명확, 중의성 포함)이고, 문체는 그 밖의 표현 지적이다. 분류는 판정자가 정한다. `result`는 결함으로만 정하며, 문체 지적만 있으면 `pass`다.
2. **기재**: 판정서는 문체 지적마다 위치, 원문, 수정 문안, 대상 부서를 서식 `RES_TEMPLATE.md`의 「문체 지적」 절에 적는다.
3. **`pass` 판정서의 문체 지적**: 반영하지 않고 이월한다. 같은 문서의 다음 버전이 다른 사유로 생기면 그 버전에 함께 반영한다. 대표님이 승인 문구에 「문체 반영」을 덧붙이면 그 승인 때 반영한다(5항).
   - 「같은 문서의 다음 버전」은 파일명에 버전(`_vNN`)이 있는 기록 문서(REQ·EC·결과서)와 적용본 폴더의 다음 버전만 가리킨다. 버전 없이 고쳐 쓰는 원본(`AGENTS.md`, `Workflow/` 등)을 다른 안건이 개정하는 것은 다음 버전이 아니다. 그 안건이 커밋으로 끝나면 이월한 문체 지적은 반영하지 않고 종결한다.
   - 적용본 폴더의 다음 버전을 만들면 그 적용본의 반영 명령을 적은 결과서(RPT·DEV)도 다음 버전을 만들고 기계적 갱신을 함께 한다. 기계적 갱신은 적용본 폴더 경로가 들어간 적용본 경로와 반영 명령의 경로를 새 폴더로 바꾸고, 「원본과의 차이」 명령을 새 폴더로 다시 실행해 그 결과로 바꾸는 것이다.
4. **EC 판정·명세 판정·시각 디자인 판정 `pass`의 문체 지적**: 이월하고, 판정 대상 문서(EC, 명세 판정은 적용본 폴더와 결과서, 시각 디자인 판정은 시각 디자인 문서와 마케팅부 결과서. 시각 디자인 문서는 파일명에 버전이 없으므로 마케팅부 결과서의 다음 버전으로 판단한다)의 다음 버전이 다른 사유로 생기지 않으면 반영하지 않고 종결한다. 세 판정에는 대표님 승인이 없으므로 「문체 반영」이 적용되지 않는다.
5. **「문체 반영」 승인의 처리**
   1. **확인**: 대리 기재한 REQ 승인은 승인 기록의 「승인 문구 원문」으로, 대표님 본인이 기재한 REQ 승인은 승인 필드 줄 끝 주석 `# 문체 반영`으로, 최종 판정서 승인은 그 승인 기록으로 확인한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」). 어디에도 「문체 반영」이 없으면 「문체 반영」이 없는 승인으로 본다.
   2. **반영 대상**: 그 승인의 근거 판정서(REQ 승인은 최신 `RES-xxx-REQ`, 최종 판정서 승인은 그 `RES-xxx`)의 문체 지적이다.
   3. **반영 주체와 시점**: REQ 승인이면 원스톱 파이프라인 첫 단계 전에 PM이 REQ 새 버전(문체 반영본)을 작성한다. 최종 판정서 승인이면 비서실이 원스톱 실행 명령을 다시 실행하고, PM이 판정서에 적힌 대상 부서의 서브에이전트를 기동해 반영하게 한다. 대상이 적용본이면 그 부서가 적용본 폴더의 다음 버전과 결과서의 다음 버전(기계적 갱신 포함)을 만든다.
   4. **반영 범위**: 수정 문안 그대로만 고친다. 결과서에는 기계적 갱신만 더한다.
   5. **대조**: 품질보증부 서브에이전트가 변경이 수정 문안과 같은지만 대조하고, 대표님 재승인은 받지 않는다. 대조는 판정서 새 버전으로 발행한다. `gate:`는 대상 판정과 같고, 1절 「판정 차수」에 「문체 반영 대조」와 직전 판정서 경로를 적는다. 변경 전체가 직전 판정서의 수정 문안과 같으면 `pass`, 다르거나 수정 문안 밖 변경이 있으면 `fail`이다. 기계적 갱신은 수정 문안 밖 변경으로 보지 않는다. 대신 품질보증부 서브에이전트는 ① 직전 적용본 폴더와 새 폴더의 `git diff --no-index` 결과가 수정 문안과 같고 ② 새 결과서의 적용본 경로·반영 명령이 새 폴더를 가리키며 ③ 「원본과의 차이」 결과가 새 폴더로 다시 실행한 결과와 같은지 확인한다.
   6. **대조 `fail`**: 수정 문안과 다른 곳을 고친 새 버전으로 다시 대조한다. 수정 문안 밖 변경을 남기려면 현행대로 판정과 대표님 재승인을 받는다.
   7. **문체 반영본 REQ의 승인 필드**: `Workflow/07_문서_서식_및_번호` 「승인 기록」 7항대로 기재한다.
6. **`fail` 판정서의 문체 지적**: 결함을 고치는 같은 새 버전에 함께 반영한다. 수정 문안 그대로 반영한 곳은 결함 재판정 대상에서 빼고 수정 문안과 같은지만 대조한다. 수정 문안과 다르게 고친 곳은 변경분으로 재판정한다.

### 5.2 판정 세션의 명령 실행

판정 세션이 판정에 필요한 명령을 실행하지 못했을 때의 처리와 판정서 머리말 `completed_at`의 조회·기재는 이 절이 원천이다. 명령 도구와 형태, 권한은 `Workflow/06_통제장치_및_배포` 「무인 실행 권한」을 따른다.

1. **대상**: 품질보증부 서브에이전트가 REQ 판정, EC 판정, 명세 판정, 시각 디자인 판정, 최종 판정, 5.1절 5항의 문체 반영 대조에서 판정 기준이 요구하는 확인을 위해 실행하는 명령이다. 시각 조회, Git 조회(`git diff --no-index` 포함), 커밋 전 검사 실행, 인수 시험 재실행(`python -m pytest`)이 여기에 든다.
2. **실행하지 못함**: 명령이 권한 거부되었거나, 권한 확인 요청이 승인되지 않아 실행되지 않은 경우다. 명령이 실행되어 실패한 경우(종료 코드가 0이 아님)는 판정 근거이며 여기에 들지 않는다. 권한 확인 요청이 승인되어 실행된 명령은 실행한 명령으로 보고 판정을 계속하며, 판정서 「검증 기록」의 그 명령 행에 확인 요청이 있었다는 사실과 메시지 원문을 적는다.
3. **대신할 수 있을 때**: 판정 기준이 요구하는 값(시각, 변경 목록, 종료 코드와 출력, 해시)을 같게 얻는 다른 허용 명령·도구로 다시 실행한다. 판정서 「검증 기록」 절에 실행하지 못한 명령, 메시지 원문, 대신한 명령과 그 결과 원문을 적은 뒤 판정을 계속한다(예: Bash `date -Iseconds` 대신 PowerShell `Get-Date -Format "yyyy-MM-ddTHH:mm:sszzz"`). 시각 조회를 다른 허용 명령·도구로 대신한 경우도 여기에 든다. 파일 열람이나 추정으로 값을 채우는 것은 대신이 아니다.
4. **대신할 수 없을 때**: 판정서를 발행하지 않고, 오케스트레이터에 실행하지 못한 명령, 메시지 원문, 시도한 대신 수단과 그 결과를 보고한다. 어떤 허용 명령·도구로도 시각을 조회하지 못해 머리말 `completed_at`을 적을 수 없는 경우도 여기에 든다. `completed_at`에 「확인 불가」를 적지 않는다. 오케스트레이터는 7절 8항으로 멈춘다.
5. **이유**: 판정 근거가 빠진 판정서로 다음 단계에 넘어가지 않게 하기 위해서다. 판정서를 작성하는 세션이 자기 실행 모델을 확인할 수 없을 때의 처리는 `Workflow/04_모델_운용` 「모델 메타데이터 기록」을 따른다.
6. **완료 시각**: 판정서 머리말 `completed_at`에는 판정 기준별 확인을 모두 마치고 판정서를 저장하기 직전에 시각 조회 명령으로 조회한 시각을 조회 결과 그대로 적는다. 조회 명령은 출력이 머리말 형식(`YYYY-MM-DDTHH:MM:SS+09:00`)과 같은 Bash `date -Iseconds` 또는 PowerShell `Get-Date -Format "yyyy-MM-ddTHH:mm:sszzz"`로 한다. 반올림하거나 추정한 값, 다른 시점에 조회한 값, 파일 저장 시각을 적지 않는다. 조회 명령과 결과 원문은 판정서 「검증 기록」에 적는다. 두 명령을 모두 실행하지 못했을 때는 3·4항을 따른다.

### 5.3 재작업 구분

판정 결함의 재작업 구분(Rework·Repair)은 이 절이 원천이다. 별도 RP 문서를 두지 않고 판정서 결함 목록의 태그로만 기록한다.

1. **대상**: EC 판정, 명세 판정, 시각 디자인 판정, 최종 판정의 결함마다 Rework 또는 Repair 하나를 붙인다. REQ 판정의 결함은 대상이 아니며, 판정서 결함 목록의 「구분」 칸에 「해당 없음」을 적는다. REQ 판정은 승인 전 판정이어서 아직 승인된 기준이 없기 때문이다. 문체 지적(5.1절)은 결함이 아니므로 대상이 아니다.
2. **판단 주체와 기준**: 구분은 판정자가 결함을 적을 때 정하며, 반려 부서(그 결함을 고치는 부서)는 구분을 바꾸지 않는다. 기준은 승인된 기준, 곧 승인된 REQ의 요구·`scope:`·「결정」 열과 판정 `pass`를 받은 EC(있으면)다. 그 결함을 승인된 기준을 바꾸거나 벗어나지 않고 고쳐 그 기준에 맞출 수 있으면 Rework, 승인된 기준을 바꾸거나 벗어나야 고칠 수 있으면 Repair다(예: `scope:` 밖 파일을 고쳐야 함, 「결정」 열과 다른 방법으로만 고칠 수 있음). REQ가 여러 뜻으로 읽히거나 요구가 서로 모순되면 현행대로 `rejected`다(7절 2항). 「반려 부서」 칸은 구분과 관계없이 그 결함이 있는 산출물의 부서를 적는다.
3. **Rework의 처리**: 8절의 `fail` 처리(반려 부서 수정, 변경분 재판정)를 따르며 대표님 승인을 거치지 않는다.
4. **Repair의 처리**: 판정서 결함 목록에 Repair 결함이 하나라도 있으면 오케스트레이터는 7절 10항으로 멈추고 보고한다. 같은 판정서의 Rework 결함도 이때 고치지 않는다. 대표님 결정 뒤 6절 「진행 중인 안건의 요구가 바뀜」대로 PM이 REQ 새 버전을 작성해(기동은 3절 1항 「REQ 새 버전 명령」) REQ 판정과 대표님 재승인을 받는다. 재승인 뒤 원스톱 파이프라인은 새 REQ로 `workflow:` 첫 단계부터 다시 실행한다. 이때 EC 판단 단계의 「EC 판단」 절은 2.1절 5항대로 옮기고, 옮긴 판단이 새 REQ에 맞지 않으면 2.1절 7·8항대로 바로잡는다.
5. **기록**: 구분은 판정서 결함 목록(서식 `Workflow/templates/RES_TEMPLATE.md` 5절 「구분」 열)에만 적는다. 결과서와 부적합 기록에는 다시 적지 않고, 필요하면 판정서 결함 번호로 가리킨다.
6. **다른 승인과의 관계**: Rework에 대표님 승인이 필요 없다는 것은 REQ 새 버전과 대표님 재승인이 필요 없다는 뜻이며, 사용자 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」·「지침 문서 수정 전 사용자 승인」을 면제하지 않는다. Rework의 수정은 승인된 REQ `scope:`(전역 지침의 승인 목록. `AGENTS.md` 「불변 원칙」 2항) 안에서만 하고, 거버넌스 파일은 적용본으로 고쳐 최종 판정서 승인 뒤 반영하므로(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」), 두 승인은 REQ 승인과 최종 판정서 승인으로 거친다.
7. **적용 시점**: `REQ-024` 커밋 뒤에 첫 버전을 작성하는 REQ와 그 새 버전의 판정부터 적용한다. 그 전에 첫 버전을 작성한 REQ는 새 버전도 적용하지 않으며, 판정서 「구분」 칸에 「해당 없음」을 적고 8절의 `fail` 처리대로 진행한다. 이미 작성된 판정서는 바꾸지 않는다.

## 8. 반려와 격상

- **재판정 한도**: REQ 판정, EC 판정, 명세 판정, 시각 디자인 판정은 최초 판정 뒤 재판정을 3회까지 한다. 세 번째 재판정도 `fail`이면 중단하고 보고한다. 재판정은 변경분만 판정한다. 5.1절의 문체 반영 대조는 재판정 횟수에 넣지 않는다.
  - **목적**: 재판정 한도는 무인으로 진행되는 동안 대표님께 빨리 보고하기 위한 장치다.
  - **초기화**: 오케스트레이터가 중단 조건(7절)으로 멈춰 보고하거나 대표님께 의결을 요청하고 대표님이 답하면, 그 뒤의 REQ 판정·EC 판정·명세 판정·시각 디자인 판정은 재판정 횟수를 새로 센다. 답을 받아 같은 세션에서 계속하는 경우와 `Workflow/05_인수인계_및_실행명령` 1절대로 같은 명령을 다시 실행하는 경우 모두 같다. 대표님 답 뒤 처음 하는 재판정이 1회다.
  - **기록**: 오케스트레이터는 그 재판정의 지시문에 횟수를 새로 센다는 사실과 직전 판정서 경로를 적는다(`Workflow/04_모델_운용` 「타깃 컨텍스트 규칙」 3항). 품질보증부 서브에이전트는 판정서 1절 「판정 차수」에 「재판정 1차(대표님 답 뒤 다시 셈, 직전 판정서 <경로>)」 형태로 적는다. 횟수는 판정서의 「판정 차수」로 판단한다.
  - **적용 제외**: 최종 판정 반려 누적 3회는 격상을 판단하는 장치이므로 초기화하지 않는다. ORDER 변경으로 생긴 REQ 새 버전은 최초 판정부터 다시 센다.
- EC 판정 `fail`: 설계부가 EC 새 버전을 작성하고 다시 판정한다. 격상 횟수에 넣지 않는다.
- 명세 판정 `fail`: 설계부가 명세 산출물의 다음 버전(적용본 폴더와 결과서)을 만들고 변경분을 다시 판정한다. 격상 횟수에 넣지 않는다.
- 시각 디자인 판정 `fail`: 마케팅부가 시각 디자인 문서를 고치고 마케팅부 결과서의 다음 버전을 작성한 뒤 변경분을 다시 판정한다. 격상 횟수에 넣지 않는다.
- 최종 판정 `fail`: 판정서에 적힌 반려 부서가 고친 뒤 판정서 새 버전으로 변경분을 다시 판정한다.
- 판정서 결함 목록에 `Repair` 결함이 있으면 위의 EC 판정·명세 판정·시각 디자인 판정·최종 판정 `fail` 항목 대신 5.3절 4항을 따른다. 그 최종 판정 `fail`도 반려 누적에 든다.
- 최종 판정 `fail` 누적 3회: 중단하고 보고한다. 대표님은 아래 가운데 하나를 정한다. ① Minor를 Major로 격상(기본 모델 등급이 중급에서 고급으로 바뀌고, 명세 판정(EC가 없을 때)과 인수 시험이 붙는다. 격상한 안건은 모델 매트릭스의 「중급(시범)」 칸과 CEO 설정의 하향과 관계없이 모든 파트를 고급 이상으로 실행한다. PM은 REQ 2절 「분류 근거」에 이 격상이 적혀 있으면 유효 값 명령에 `--escalated`를 준다. `Workflow/04_모델_운용` 「단계별 모델」 6항 ③) ② 분류는 그대로 두고 최고급 모델이나 `high` 이상의 effort를 승인(`Workflow/04_모델_운용` 「기본값 밖 사용」) ③ 그 밖의 처리(범위 분할, 중단 등). ①·②는 PM이 REQ 새 버전을 작성하고(작성 모델과, PM 세션의 모델·effort가 그와 다를 때의 처리는 `Workflow/04_모델_운용` 「단계별 모델」), REQ 판정과 대표님 재승인을 거쳐 원스톱 파이프라인을 처음부터 다시 실행한다. Major에서 Critical로의 격상은 두지 않는다. 두 분류는 단계와 기본 모델 등급이 같아 격상해도 강화되는 것이 없기 때문이다.

## 13. 부적합 관리

부적합 기록의 대상, 기록 주체와 시점, 원인 분류, 표준 개정 제안은 이 절이 원천이다. 문서 이름·머리말은 `Workflow/07_문서_서식_및_번호`를 따른다.

1. **대상**: ① 모든 판정(REQ 판정, EC 판정, 명세 판정, 시각 디자인 판정, 최종 판정. 5.1절 5항의 문체 반영 대조 포함)의 `fail` ② `rejected` ③ 7절 「중단 조건」 1·3·5·6·7·8·10. 7절 4·9·11·12항과 「문체」 지적만 있는 `pass`는 대상이 아니다. 문체 반영 대조를 넣는 이유는 대조도 판정서로 발행되며 그 `gate:`가 대상 판정과 같기 때문이다. 9항을 넣지 않는 이유는 REQ 새 버전을 정해진 모델의 PM 세션으로 넘기는 절차이며 결함이 아니기 때문이다. 11·12항을 넣지 않는 이유는 다른 안건을 기다리거나 REQ를 맞추는 절차이며 결함이 아니기 때문이다.
2. **적용 시점**: `REQ-017` 커밋 뒤에 나온 판정·중단부터 기록하고 소급하지 않는다. 표준 개정을 제안할 때 기존 판정서를 참고 자료로 읽을 수 있다.
3. **기록 주체와 시점**
   - 판정 결과의 부적합(`fail`, `rejected`, 그 판정으로 생긴 중단 3·7·10)은 그 판정을 한 품질보증부 서브에이전트가 판정서와 함께 기록한다. 판정서 1절 「부적합 기록」에 그 경로를 적는다.
   - 중단 3·7·10은 그 `fail` 기록 하나에 중단 조건 번호를 함께 적고 기록을 따로 만들지 않는다. 같은 사건을 두 번 세지 않기 위해서다. 품질보증부는 판정서 「판정 차수」(REQ 판정·EC 판정·명세 판정·시각 디자인 판정의 재판정 3차 `fail`이면 7)와 그 안건의 최종 판정 `fail` 판정서 수(이번을 포함해 3건이면 3)로 중단 여부를 판단한다. 10은 그 판정서 결함 목록에 `Repair` 결함이 있는지로 판단한다.
   - 판정 없이 멈춘 중단(1·5·6·8)은 PM이 멈춰 보고하기 직전에 기록하게 한다. PM은 먼저 실행 기록에 중단 행을 적고(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」 6항 ④), 품질보증부 서브에이전트를 새로 기동한다. 지시문의 단계명은 `부적합 기록(중단 조건 <번호>)`, 대상 파일 경로는 PM 실행 기록과 멈춘 단계의 최신 산출물이다. 품질보증부 서브에이전트는 부적합 기록만 작성하고 판정서를 쓰지 않는다.
4. **기록 내용**: 부적합 하나에 기록 하나이며, 결함·사유마다 원인과 원인 분류, 재발 방지책을 적는다. 작성 뒤 고치지 않는다. 서식은 `NCR_TEMPLATE.md`다.
5. **원인 분류**: 결함·사유마다 아래 코드 하나를 붙인다. 「같은 원인」은 같은 코드다.

   | 코드 | 원인 분류 | 해당하는 결함·사유 |
   | :---: | :--- | :--- |
   | `C1` | 요구 반영 | 요청 원문·결정의 누락·왜곡, 체크리스트 대응 오류 |
   | `C2` | 범위 | scope 누락·초과, 범위 밖 변경 |
   | `C3` | 단일 원천 | 규칙·값의 중복 기재, 참조 불일치 |
   | `C4` | 기록 규칙 | 머리말, 파일명·버전, 리비전 태그, 개정 이력 |
   | `C5` | 표현 | 중의성, 지칭 불명확, 쓰지 않는 말 |
   | `C6` | 통제 장치 불일치 | 규칙과 검사·설정·서브에이전트 정의의 어긋남 |
   | `C7` | 검증 | 검사·시험의 미실행, 결과의 오류·누락, 인수 시험 실패 |

   - 건수는 그 코드가 머리말 `causes:`에 있는 부적합 기록의 수다. 그 코드를 `proposals:`에 적은 가장 최근 기록 뒤(`recorded_at` 기준)의 기록만 센다. 한 번 제안한 원인으로 기록마다 같은 제안이 반복되지 않게 하기 위해서다.
   - `C9`는 원인이 서로 다르므로 세지 않는다.
6. **표준 개정 제안**: 기록하는 품질보증부 서브에이전트가 기존 기록과 대조해, 이번 기록을 포함한 건수가 2건 이상인 코드가 있으면 그 기록 「표준 개정 제안」 절에 제안을 적고 `proposals:`에 그 코드를 적는다. PM은 `Workflow/05_인수인계_및_실행명령` 「완료 보고」 7항대로 보고한다. 비서실이 대표님께 보고하고, 대표님이 ORDER 발행 여부를 정한다. 품질보증부는 ORDER·REQ를 작성하지 않는다.

### 2.1 EC 적용 기준

EC의 정의, EC를 붙이는 기준, 설계부의 EC 판단과 그 기록·확인은 이 절이 원천이다. 이 표준에서 「EC가 있다」·「EC가 없다」(「EC가 있으면」, 「EC(있으면)」, 「EC가 있을 때」, 「EC가 없는 Critical·Major」 등)는 EC 파일의 존재가 아니라 최신 설계부 결과서 「EC 판단」 절의 판단(「EC 있음」·「EC 없음」)을 말한다. 8항에 따라 `draft`로 남은 EC는 뒤 단계의 입력과 판정의 대조 기준이 아니다.

1. **정의**: EC(Engineering Change)는 기존 설계나 코드를 변경할 때 변경점을 평가하는 항목이다. 무엇이 어떻게 바뀔지 설계부가 계획하고(EC 작성), 개발부가 수정하고(구현), 품질보증부가 결과를 평가한다(최종 판정). 품질보증부는 수정 전에 계획도 판정한다(EC 판정). 문서의 위치·서식은 `Workflow/07_문서_서식_및_번호` 「문서 체계」를 따른다.
2. **붙이는 경우**: 이미 승인되어 쓰이는 산출물(커밋된 표준·거버넌스 파일, 명세, 코드, 승인된 콘텐츠 포맷)의 동작·규칙·규격을 바꾸는 경우에만 붙인다. 기존 코드의 동작을 고치는 결함 수정도 여기에 든다.
3. **늘 붙이는 경우**: 거버넌스 파일(`AGENTS.md` 「불변 원칙」 3항의 목록)과 보안·권한 설정(예: 접근 권한 규칙, 인증·키의 보관과 사용 설정, 비밀정보 검출 규칙과 예외 목록)의 동작·규칙·설정을 바꾸는 변경에는 설계부 판단과 관계없이 늘 붙인다. 오탈자·표현 보완은 4항 ①대로 붙이지 않는다.
4. **붙이지 않는 경우**: ① 오탈자·표현 보완처럼 동작·규칙·규격을 바꾸지 않는 수정 ② 승인된 명세·포맷을 그대로 따르는 반복 작업(예: 승인된 콘텐츠 포맷에 따른 회차 제작) ③ 기존 산출물을 바꾸지 않는 신설(새 기능 파일, 포맷 신설). 한 안건에 2·3항의 변경과 이 항의 변경이 섞이면 EC를 붙인다.
5. **판단과 기록**: 설계부가 EC 판단 단계에서 REQ마다 판단한다. 시점은 REQ 승인 뒤이며, 실험 단계가 있으면 그 뒤다. 설계부는 판단(「EC 있음」·「EC 없음」), 해당하는 2~4항, 사유를 설계부 결과서(RPT)의 「EC 판단」 절(서식 `Workflow/templates/DEV_TEMPLATE.md` 8절)에 적는다. Minor이고 「EC 없음」이면 명세 산출물(PRD·TAD, 적용본)이 필요한지와 사유를 함께 적는다. 실험 단계가 있으면 실험 결과는 EC가 있으면 EC가, 없으면 설계부 결과서 「EC 판단」 절이 인용한다(11.2절 5항). 같은 안건에서 설계부 결과서의 다음 버전을 쓰면 설계부 결과서 「EC 판단」 절을 그대로 옮긴다(판단을 바꾸는 경우는 8항). 판단 결과로 REQ 새 버전을 작성하거나 재승인을 받지 않는다(REQ 작성 기준은 3절 1항 「EC 판단과 REQ」).
6. **판단에 따른 실행**: 오케스트레이터는 EC 판단 단계 뒤 최신 설계부 결과서의 「EC 판단」 절로 아래 단계의 실행 여부를 정한다(4절 2항).

   | 판단 | EC 작성·EC 판정 | 명세 | 명세 판정 |
   | :--- | :---: | :---: | :---: |
   | EC 있음 | 실행 | 실행 | 건너뜀 |
   | EC 없음(Critical·Major) | 건너뜀 | 실행 | 실행 |
   | EC 없음(Minor, 명세 산출물 필요) | 건너뜀 | 실행 | 해당 없음 |
   | EC 없음(Minor, 명세 산출물 불필요) | 건너뜀 | 건너뜀 | 해당 없음 |

7. **판단의 확인**: EC 판단 단계는 따로 판정하지 않는다. 「EC 있음」 판단은 EC 판정이 EC와 함께 확인한다(5절 표 「EC 판정」 행 ⑥). 「EC 없음」 판단은 그 뒤 첫 판정이 2~4항과 대조한다. Critical·Major는 명세 판정(5절 표 「명세 판정」 행 ⑦), Minor는 최종 판정(5절 최종 판정 기준 9)이다. 판단이 2~4항에 맞지 않으면 결함이며 반려 부서는 설계부다.
8. **판단이 바뀐 경우**: 7항의 결함을 고치려고 설계부가 판단을 바꾸면 설계부 결과서의 다음 버전 「EC 판단」 절에 바꾼 판단과 근거 판정서 경로를 적는다. 「EC 있음」으로 바뀌면 오케스트레이터는 `workflow:`의 EC 작성부터 순서대로 다시 실행한다. 「EC 없음」으로 바뀌면 EC는 `draft`로 두고 EC 판정 다음 단계부터 6항 표대로 실행한다. 그 EC는 이 절 첫 문단대로 뒤 단계의 입력이 아니다. 최종 판정에서 바뀐 경우 그 `fail`은 8절의 반려 누적에 든다.
9. **적용 시점**: `REQ-021` 커밋 뒤에 작성하는 REQ부터 적용한다. 그 전에 승인된 REQ는 승인 때의 규정으로 진행한다.
