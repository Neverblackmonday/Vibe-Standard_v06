### 2.1 비서실과 PM의 책무

| 주체 | 책무 |
| :--- | :--- |
| 비서실(비서팀 S01~S03, 형상통제팀 C01~C03) | ① (S01) 대표님과 대화해 요구를 모으고 `Departments/Secretariat/Secretary/assets/inbox/`에 ORDER를 작성한다. ORDER 머리말 `classification_proposal`에 분류를 제안한다(정의 기준은 `Workflow/03_라이프사이클` 「분류별 단계」). 모델 등급은 분류로 정해지므로 ORDER에 적지 않는다. ORDER를 발행하기 전에 작업 큐로 겹침과 충돌을 확인한다(⑯) ② (S01) PM 실행 명령을 전달한다. 셸을 실행할 수 있는 비서실 세션은 직접 실행하고, 실행할 수 없는 세션은 명령문 전문을 대표님께 제시하거나 셸 작업 지시 파일로 넘긴다(`Workflow/05_인수인계_및_실행명령` 「비서실 세션의 명령 전달 방식」) ③ (S03) 최종 판정서의 체크리스트 번호별 근거를 대조해 대표님께 보고한다. 보고에 대조할 승인 기록 경로와 결과서의 반영 대상 목록(반영 명령 표의 원본 경로와 삭제 대상)과 최종 판정서의 「삭제 대상」을 함께 적는다 ④ (S01) 핫픽스의 사전 승인을 대표님께 요청하고, 승인을 받으면 핫픽스팀(V03) 세션을 기동한다. 수정·검증·HOTFIX 작성은 V03이 한다(`Workflow/03_라이프사이클` 「핫픽스 트랙」) ⑤ (S01) 대표님에게서 직접 받은 승인 문구로 승인 기록을 남기고 승인 필드와 「결정」 열을 기재한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」) ⑥ (S02) 외부 보고서(AUDIT)를 작성한다 ⑦ (C02) 형상통제팀은 최종 판정서 승인 뒤 적용본 반영·기준선 기록·정리·스테이징·커밋 전 검사·커밋을 한다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」) ⑧ (S02) 조사 자료를 `Departments/Secretariat/Secretary/assets/research/`에, 브리핑을 `Departments/Secretariat/Secretary/assets/briefings/`에 작성한다. 조사 자료의 이름과 머리말은 `Workflow/07_문서_서식_및_번호` 「문서 체계」·「머리말」을 따른다. 브리핑의 요건·종류·작성 시점은 `Workflow/05_인수인계_및_실행명령` 「브리핑」을 따른다 ⑨ (S01) 대표님이 아이디어 덤프·기획 단계·기획을 요청하면 기획 트랙을 수행한다(`Workflow/03_라이프사이클` 「기획 트랙」) ⑩ (C02) 형상통제팀은 대표님이 요청한 그 밖의 커밋(「요청 커밋」)과, 대표님이 따로 명시적으로 요청한 푸시를 한다(`Workflow/05_인수인계_및_실행명령` 1절 「커밋」·「푸시」 항) ⑪ (S01) 실험실(`Lab/`)을 관리한다(사용 승인과 정리. 절차는 `Workflow/03_라이프사이클` 「실험실」) ⑫ (S01) 운영부의 보안 점검 결과를 대표님께 보고한다(`Workflow/05_인수인계_및_실행명령` 「완료 보고」 8항) ⑬ REQ·HOTFIX를 끝내는 커밋을 하는 형상통제팀(C02)과, 커밋 없는 종결(흡수, 중단 뒤 종료)의 대표님 결정을 대표님에게서 직접 받은 비서실 세션(S01)은 종결 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「종결 기록」) ⑭ (S01) 원스톱 실행 명령을 안내하거나 실행하기 전에 착수 순서와 실행 중인 안건(클라우드 세션 포함)을 확인하고, 다른 안건과의 겹침으로 멈춘 REQ 작성 명령·REQ 새 버전 명령을 진행 중이던 안건이 끝난 뒤 다시 안내하거나 실행한다(`Workflow/03_라이프사이클` 「원스톱 착수 조건」·「다른 안건이 진행 중일 때의 REQ 작성」) ⑮ (C01·C03) 형상통제팀은 지침 통합과 프로세스 맵 관리(C01. `Workflow/03_라이프사이클` 「프로세스 맵」)와 형상 현황판(C03)을 맡는다. C01의 절차는 `Workflow/05_인수인계_및_실행명령` 「형상통제 절차」를 따르고, C03의 절차는 그 일을 정하는 뒤 안건이 정한다 ⑯ (S01) 작업 큐를 관리한다. ORDER·REQ의 처리 순서를 작업 큐에 적고, 새 ORDER 발행이나 순서 변경 전에 작업 큐로 겹침과 충돌을 확인한다(`Workflow/05_인수인계_및_실행명령` 「작업 큐」) |
| PM(비서실 PM팀 P01·P02. 실행 명령으로 기동한 Claude Code 메인 세션) | ① ORDER로 REQ와 체크리스트를 작성하고 분류를 REQ 머리말 `classification:`에 확정하고, 그 근거와(ORDER 제안과 다르면) 다른 사유를 REQ에 적는다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항 「분류 근거」). REQ를 처음 작성할 때 ORDER 머리말 `related_req`에 그 REQ 이름을 더한다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」) ② REQ 작성 파이프라인과 원스톱 파이프라인을 지휘한다. 서브에이전트를 단계마다 정해진 모델로(`Workflow/04_모델_운용` 「단계별 모델」) 순서대로 기동·인계하고 진행 상태를 보고한다 ③ REQ 판정 `fail` 때와, 최종 판정 반려 누적 뒤 대표님이 격상이나 모델·effort 승인을 정했을 때(`Workflow/03_라이프사이클` 「반려와 격상」) REQ 새 버전을 작성한다 ④ 안건마다 실행 기록을 작성한다(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」) ⑤ 대표님 요청으로 REQ·HOTFIX를 끝내는 커밋을 하면 그 안건의 종결 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「종결 기록」) ⑥ REQ 작성 명령·REQ 새 버전 명령으로 기동되면 REQ 파일을 저장하기 전에 다른 안건과의 겹침을, 원스톱 실행 명령으로 기동되면 첫 단계 전에 착수 조건을 판단한다(`Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」·「원스톱 착수 조건」) |

- 비서실은 ORDER, 작업 큐(4절), 승인 기록, 요청 기록(4절), 종결 기록(4절), 승인 필드와 「결정」 열(4절), 외부 보고서, 조사 자료, 아이디어 백로그, 기획안, 브리핑(4절), 최종 판정서 승인 뒤 형상통제팀(C02)의 반영 명령 대상(거버넌스 파일 포함)과 정리 대상(4절), 실험실(`Lab/`)(4절), 셸 작업 지시·결과 파일(4절), 형상통제팀의 형상통제 기록·기준선 기록과 지침 재생성 반영 대상(4절) 외에는 저장소 파일을 수정하지 않는다. 비서실의 외부 보고서는 외부감사실(`Audits/`)에 둔다. PM이 수정할 수 있는 경로는 4절을 따른다.
- 비서실 세션의 능력과 경계: 셸이 필요한 절차는 셸을 실행할 수 있는 비서실 세션이, 저장소 파일 수정이 필요한 절차는 저장소 파일을 수정할 수 있는 비서실 세션이 맡고, 형상통제팀(C01~C03)은 두 가지를 모두 할 수 있는 비서실 세션이 맡는다. 능력의 확인과 능력이 없을 때의 처리는 `Workflow/05_인수인계_및_실행명령` 「공통 규칙」 11항을 따른다. 비서실 세션은 셸을 실행할 수 있어도 PM·부서의 일(REQ·EC·명세·코드·판정서 작성, 부서 서브에이전트 기동)과 핫픽스팀(V03)의 일(핫픽스 대상 파일 수정, HOTFIX 작성)을 직접 하지 않고, PM 지시문이나 핫픽스 실행 명령을 실행해 별도 세션에 맡긴다.
- 비서실이 저장소나 셸에서 하는 작업의 공통 규칙과 고정 절차, 비서실의 여러 세션을 함께 쓸 때의 담당과 기록은 `Workflow/05_인수인계_및_실행명령` 「비서실 실행 절차」를 따른다.
- 승인 필드(`approved:`, `confirmed:`)와 REQ 「결정」 열의 기재 주체와 방법은 `Workflow/07_문서_서식_및_번호` 「승인 기록」을 따른다.

### 2.2 조직 표

부·팀·파트의 이름, 코드, 팀 폴더 이름, 주요 업무, 상태는 이 절이 원천이다.

- **명명 규칙**: 「실」은 대표실과 비서실에만 쓰고, 그 밖의 부는 「○○부」로 쓴다. 모든 파트는 팀에 속한다(예외 X01). 팀 이름은 맡는 일로 짓고 부 이름과 같은 이름을 쓰지 않는다(예외: 비서실 비서팀). 파트 이름은 업무를 나타내는 명사구 하나다. 코드는 부 머리글자(설계부 E, 개발부 V, 품질보증부 Q, 운영부 O, 마케팅부 M. 비서실은 팀 머리글자 S·P·C, 실험은 X)와 두 자리 번호이며, 폐지한 코드는 다시 쓰지 않는다.

- **팀 폴더 이름**: 팀의 영문 이름이며, 부서 폴더처럼 영문 대문자로 시작하는 단어를 이어 쓴다. 디자인팀은 부서 폴더 `Design`과 헷갈리지 않게 `VisualDesign`으로 한다. 폴더 구조는 3절을 따른다.

## 3. 팀 폴더와 공통 하위폴더

부서 폴더(`Departments/<부>/`) 아래에 팀 폴더(2.2절 「팀 폴더」 열)를 두어 「부 → 팀」 두 단계로 나눈다. 팀 폴더 안에는 공통 하위 폴더 `docs/`(정제된 문서: 기획서, 명세, 안건), `assets/`(실제 자산: 코드, 테스트, 스크립트, 파라미터, 조사 자료), `results/`(공식 결과서와 판정서), `workspace/`(중간 산출물, 메모, 거버넌스 적용본) 가운데 그 팀이 쓰는 것만 둔다. 파트 폴더는 두지 않는다. 한 파트만 계속 쓰는 자산은 팀 폴더 아래 용도 이름의 하위 폴더에 둔다(예: `Departments/Quality/Test/assets/acceptance/`). 대기 팀 폴더는 만들지 않고 그 팀의 파트를 활성으로 바꾸는 안건에서 만든다. 활성 파트가 있는 팀이 없는 운영부·마케팅부는 부서 폴더 바로 아래 `.gitkeep` 하나만 둔다. 지금 활성 팀 폴더와 하위 폴더는 아래와 같다.

```text
Departments/
├── Secretariat/
│   ├── Secretary/        # 비서팀(S01~S03)
│   │   ├── assets/inbox/      # ORDER, 승인 기록, 요청 기록, 종결 기록, 요구 메모
│   │   ├── assets/research/   # 조사 자료
│   │   ├── assets/planning/   # 아이디어 백로그, 기획안
│   │   ├── assets/briefings/  # 브리핑
│   │   ├── assets/queue/      # 작업 큐
│   │   ├── workspace/연락/    # 연락 파일(기록)
│   │   └── workspace/셸작업/  # 셸 작업 지시·결과 파일
│   ├── PM/               # PM팀(P01·P02)
│   │   ├── docs/requests/     # REQ
│   │   └── workspace/         # PM 실행 기록
│   └── ConfigControl/    # 형상통제팀(C01~C03). 두 하위 폴더는 첫 기록 때 생기며 그 전에는 .gitkeep만
│       ├── results/           # 기준선 기록, 형상통제 기록
│       └── workspace/         # 지침 재생성 작업
├── Design/
│   ├── EC/               # EC팀(E01·E02)
│   │   ├── docs/              # EC
│   │   ├── results/           # 설계부 결과서(RPT)
│   │   └── workspace/
│   └── Spec/             # 명세팀(E03·E04)
│       ├── docs/prd/, docs/tad/   # PRD·TAD
│       ├── assets/live/           # 설계 파라미터
│       └── workspace/             # 설계부 거버넌스 적용본
├── Development/
│   ├── Implementation/   # 구현팀(V01·V02)
│   │   ├── assets/scripts/    # 커밋 전 검사 등 검사·준비 명령, 검사 장치 대장(거버넌스 구역)
│   │   ├── assets/src/, assets/tests/
│   │   ├── results/           # 개발부 결과서(DEV)
│   │   └── workspace/         # 개발부 거버넌스 적용본, 일회성 파일

│       └── results/           # HOTFIX

│       └── results/           # 인수 시험 절차서(ACC)
├── Operations/.gitkeep   # 대기 팀만 있음(배포팀 Release, 보안팀 Security)
```

- 결과서는 번호 묶음(버전)이 한 폴더에 있어야 「가장 높은 번호가 현행본」이 성립하므로 기록 종류마다 한 폴더를 둔다. 설계부 결과서는 모든 안건의 첫 버전을 EC 판단(E01)이 만들므로 `Departments/Design/EC/results/`에 두고 명세(E03)가 다음 버전을 같은 폴더에 쓴다. 개발부 결과서는 실험(X01)과 구현(V01)이 함께 `Departments/Development/Implementation/results/`에 쓴다. 대기 팀의 결과서 위치는 그 단계를 맡은 파트의 팀 `results/`다(`Departments/<부>/<팀>/results/`. 예: 보안 점검 결과서는 `Departments/Operations/Security/results/`, 시각 디자인 단계의 마케팅부 결과서는 `Departments/Marketing/VisualDesign/results/`). 시각 디자인 문서는 `Departments/Marketing/VisualDesign/docs/DESIGN.md`, 런타임 파라미터는 `Departments/Operations/Release/assets/live/`에 둔다.
- 요청 기록·종결 기록은 형상통제팀(C02)·PM이 쓰지만 비서팀 `assets/inbox/`에 둔다. 종결 기록을 읽는 위치(커밋 전 검사와 `Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」 4항)와 판정 전제 제외 범위를 한 폴더로 두기 위해서다. 쓰기 권한은 4절 표가 정한다.

빈 폴더는 `.gitkeep`으로 유지한다. 비서팀 `assets/`에는 바로 아래에 파일을 두지 않고 하위 폴더(`inbox/`, `research/`, `planning/`, `briefings/`, `queue/`)에만 둔다. 최종 산출물은 팀 폴더의 `docs/`, `assets/`, `results/`에만 둔다.

## 4. 모델 메타데이터 기록

공식 문서(REQ, EC, DEV, RES, HOTFIX)의 머리말에 작성하거나 판정한 모델과 effort를 아래 기준으로 적는다.

- **모델**: 확인할 수 없으면 `"확인 불가"`로 적는다. 단, RES의 `auditor.model`에는 `"확인 불가"`를 적지 않는다. 판정서를 작성하는 세션이 자기 실행 모델을 확인할 수 없으면 판정서를 발행하지 않고 오케스트레이터에 보고한다.
- **effort(REQ, EC, DEV, RES, HOTFIX)**: 실행 명령 지시문의 effort 값을 출처와 함께 `"<값> (실행 명령 기준)"`으로 적는다(예: `"medium (실행 명령 기준)"`). PM은 자기 지시문의 표기(`Workflow/05_인수인계_및_실행명령` 「실행 명령」), 서브에이전트는 PM 지시문의 표기(3절 1항), 핫픽스팀(V03)은 핫픽스 실행 명령 지시문의 표기를 출처로 쓴다. 출처에서 값을 얻을 수 없을 때만 `"확인 불가"`로 적는다.
- **기준 모델·effort**: 판정서는 9절 「기준 모델·effort」에 판정 지시문의 유효 값 표(3절 1항)와 판정 세션 자신의 실행 모델·effort를 적고, 하향 확인을 거친 칸(1.4절 4항)이 있으면 그 칸과 확인 시각을 따로 적는다. HOTFIX는 1절 「기준 모델·effort」 항에 V03 칸 「분류 없음」의 유효 값과 출처, CEO 설정 `saved_at`을 적는다. 판정이 없는 커밋(최종 승인 커밋, 요청 커밋, PM 커밋)은 커밋 메시지 근거 줄 `Model-Effort`에 커밋한 세션의 모델과 effort를 남긴다(`Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「커밋 메시지」).
- **`REQ-031` 커밋 전의 HOTFIX**: 비서실이 실행 명령 없이 작성했으므로 실제 적용한 effort를 적었다. 고치지 않는다.

```yaml
author:            # RES는 auditor:
  agent: "Design"
  model: "Claude Opus 5.5"
  effort: "medium (실행 명령 기준)"
```

### 1.1 최종 판정서 승인과 커밋

형상통제팀(C02)의 실행 순서·예외·보고는 8절 「최종 승인 커밋」 절차를 따른다.

1. **원칙**: 대표님이 최종 판정서(`RES-xxx_vNN`)를 승인하면 형상통제팀(C02)이 커밋까지 진행한다. 승인 문구를 커밋의 명시적 요청으로 보고, 결과서 반영 명령 표의 덮어쓰기·삭제 승인과 그 최종 판정서 「삭제 대상」 목록의 삭제 승인으로도 본다. 푸시는 이 절차에 넣지 않고 대표님이 따로 정한다. PM은 이 절차에서 커밋하지 않는다.
2. **문구를 받은 세션과 승인 기록**: 문구를 대표님에게서 직접 받은 비서실 세션이 승인 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」). 커밋은 형상통제팀(C02)이 한다. 문구를 직접 받은 세션이 셸을 실행하고 저장소 파일을 수정할 수 있으면 그 세션이 C02로서 이어서 한다. 그런 세션이 아니면 승인 기록만 남기고 커밋하지 않으며, 「최종 승인 커밋」 호출 문구를 셸 작업 지시 파일(8.6절)로 남기거나 대표님께 드리거나 1절 「커밋」 항의 다른 경로를 쓴다. 지시 파일에는 승인 문구를 넣지 않으므로, 대표님은 그 지시를 처리하는 C02 세션에 승인 문구를 직접 입력한다(8.6절).
3. **「문체 반영」**: 승인 문구에 「문체 반영」이 있으면 원스톱 실행 명령을 다시 실행해 `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」 5항을 마치고, 대조 `pass`를 확인한 뒤 4번으로 간다. 대표님 재승인은 받지 않는다.
4. **적용본 반영**: 최종 판정을 받은 결과서(RPT·DEV)의 반영 명령대로 반영한다. 반영 명령에는 파일 전체 적용본의 복사와 변경 파일 적용본의 반영(`apply_delta.py --write`. `Workflow/06_통제장치_및_배포` 「생성·반영 명령」)이 있다. 3번의 대조를 거쳤으면 대조 `pass`를 받은 최신 버전 결과서의 반영 명령(새 적용본 폴더)대로 반영한다. 반영 전에 원본마다 `git diff --stat <기준 커밋> HEAD -- <원본 경로>`가 비어 있는지 확인한다. 기준 커밋은 결과서에 적힌 값이다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」 2항). 비어 있지 않으면 반영하지 않고 5절의 상세 보고를 한다. 반영 전에 `prepare_final_commit.py`를 실행해 반영 목록과 삭제 목록을 얻는다(`Workflow/06_통제장치_및_배포` 「준비·판단 명령」). 형상통제팀(C02)은 그 반영 목록과 삭제 목록을 그대로 쓰고, 명령이 실패하거나 실행되지 않으면 손으로 대신하지 않고 멈춰 5절의 상세 보고를 한다. 반영을 마친 뒤 6번 스테이징 앞에, 반영한 변경에 원천(계층 구성표, 구성표가 고른 원천 문서, `Workflow/02_부서_구조_및_작업구역` 「조직 표」, 프로세스 맵)이나 생성물이 있으면 8.8절 2항대로 기준선 기록을 남긴다. 기준선 기록 명령이 실패하면 멈춰 5절의 상세 보고를 한다.
5. **정리**: 결과서에 적힌 삭제 대상과, 승인받은 최종 판정서의 「삭제 대상」을 처리한다. 추적 중인 파일은 `git rm -- <경로>`로, 추적하지 않는 파일은 `rm -- <경로>`로 지운다.
6. **스테이징**: 스테이징 앞에 `Workflow/07_문서_서식_및_번호` 「종결 기록」대로 그 안건의 종결 기록을 작성한다. 날짜와 관계없이 같은 기록 이름의 종결 기록이 이미 있으면 새로 쓰지 않는다. 그 안건의 변경만 스테이징한다. 「그 안건의 변경」은 작업 트리의 변경 가운데 아래 ①~⑫에 해당하는 것이다. 형상통제팀(C02)은 종결 기록 작성 뒤 `prepare_final_commit.py`를 다시 실행해 그 스테이징 목록을 그대로 쓰고, 분류하지 못한 변경은 스테이징하지 않고 보고에 적는다. 분류 기준은 아래 ①~⑫이다. 명령이 실패하거나 실행되지 않으면 손으로 분류하지 않고 멈춰 5절의 상세 보고를 한다. ①~⑫에 들지 않는 변경(다른 안건의 파일, 안건 번호가 없는 파일)은 스테이징하지 않고 보고에 적는다. 그 가운데 비서실 산출물(어느 안건의 승인 브리핑도 ORDER 근거 자료도 아닌 조사 자료·브리핑, REQ가 아직 없는 ORDER 등)은 대표님이 요청하면 8.3절 「요청 커밋」으로 커밋한다.
   - ① `Workflow/07_문서_서식_및_번호` 「문서 체계」의 파일명에서 안건 번호 자리(`xxx`. 파생 안건은 파생 번호까지 포함)가 그 안건 번호와 같은 REQ, EC, DEV, RPT, RES(REQ 판정, EC 판정, 명세 판정, 시각 디자인 판정, 최종 판정), ACC, NCR. 승인을 받은 최종 판정서 자신과, 있으면 「문체 반영」으로 생긴 새 버전(REQ, 결과서)과 대조 판정서도 여기에 들어간다
   - ② 그 안건의 승인 기록(REQ 승인 기록과 최종 판정서 승인 기록. 파일명은 `Workflow/07_문서_서식_및_번호` 「승인 기록」 4항)
   - ③ 머리말 `related_req`에 그 안건의 REQ가 있는 ORDER의 모든 버전(같은 `ORD-xxx` 번호의 `_v01`부터 최신 버전까지. 버전마다 `related_req` 기재 여부와 관계없다)
   - ④ 팀 `workspace/`의 그 안건 적용본 폴더(`<REQ 번호>_적용본_vNN/`. 「문체 반영」으로 생긴 다음 버전 포함) 아래 파일
   - ⑤ ①의 결과서(RPT·DEV) 「변경 파일」 절에 적힌 경로
   - ⑥ REQ·EC `scope:` 안의 변경(REQ `scope:`의 `Lab/` 경로 안 실험 파일 포함. `Workflow/03_라이프사이클` 「실험 단계」), 4번의 반영 명령으로 바뀐 원본 경로, 5번의 정리로 지운 경로
   - ⑦ 그 안건의 PM 실행 기록(`Departments/Secretariat/PM/workspace/실행기록_REQ-xxx.md`. 7절)
   - ⑧ 그 안건의 인수 시험 폴더(`Departments/Quality/Test/assets/acceptance/<REQ 번호>_vNN/`, 모든 버전) 아래 파일. 폴더 안 파일 이름에는 안건 번호가 없으므로 폴더 이름으로 고른다
   - ⑨ 그 안건의 승인 브리핑: `Departments/Secretariat/Secretary/assets/briefings/`에서 파일명의 주제가 그 안건의 REQ 번호와 `_`로 시작하는 브리핑(모든 버전. 이름 규칙은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」). 접두어는 `_`까지 비교한다(`REQ-014_`는 `REQ-014-1_`과 일치하지 않는다)
   - ⑩ ③의 ORDER 「근거 자료」 줄에 경로가 적힌 조사 자료(`Departments/Secretariat/Secretary/assets/research/` 아래 파일)
   - ⑪ 그 안건의 종결 기록(`Departments/Secretariat/Secretary/assets/inbox/종결기록_<YYYYMMDD>_<기록 이름>.md`. 이름은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「종결 기록」 항)
   - ⑫ 그 안건의 기준선 기록(`Departments/Secretariat/ConfigControl/results/기준선_<14자리 시각>_<그 안건의 기록 이름>.json`. 4번 끝과 8.8절 2항)
7. **커밋 전 검사**: 따로 실행하지 않는다. 8번 커밋 때 훅(pre-commit의 `check_standard.py --staged`, commit-msg의 `check_commit_msg.py`)이 실행하며, 훅이 출력한 결과로 판단한다. 커밋 전 검사는 스테이징한 변경만 검사하므로 다른 안건이 진행 중이어도 이 안건의 검사 결과에 영향이 없다.
8. **커밋**: `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「커밋 메시지」대로 제목 줄과 근거 줄을 적어 커밋한다(예: `git commit -m "<제목 줄>" -m "<근거 줄(줄마다 줄바꿈)>"`). 메시지는 6번에서 다시 실행한 `prepare_final_commit.py`가 만든 것을 그대로 쓴다. 예외로, 근거 줄 `Model-Effort`의 자리 줄(`<`·`>`로 감싼 자리)만 이 세션의 모델과 effort로 채운다(`Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「커밋 메시지」). 채우지 않으면 커밋 메시지 검사가 실패한다. 커밋 때 훅이 실패하면 `--no-verify`를 쓰지 않고 멈춰 5절의 상세 보고를 한다.
9. **완료 보고**: 5절대로 요약 보고하고, 커밋 해시, 종결 기록 경로(6번), 스테이징하지 않은 변경(6번), 「대표님이 할 일: 푸시 여부 결정」을 적는다.

### 2.1 무인 실행 권한

- 파이프라인은 `--permission-mode acceptEdits`로 파일 편집 확인을 생략한다. 이 모드에서도 2절의 `deny`(거버넌스 파일·`CEO/`·`_archive/` 쓰기 차단)와 `ask`(삭제·이동·커밋·푸시 확인)는 그대로 적용된다.
- 표준 절차의 조회·검사·시험 명령은 `allow`에 등록되어 있어 확인 없이 실행된다. 목록의 원천은 `settings.json`이다.
- 임시 Git 저장소가 필요한 시험은 팀 `workspace/`의 Python 스크립트로 작성해 `allow` 규칙(`Bash(python Departments/*/*/workspace/*)`)으로 실행한다. 이 규칙은 에이전트가 작성한 스크립트를 확인 없이 실행하게 하므로 사실상 임의 명령 실행을 허용한다. 대표님이 이 완화를 승인했으며(v02 REQ-002), `deny`·`ask`와, 승인되었고 끝나지 않은 REQ와 확인되었고 끝나지 않은 HOTFIX의 `scope:`로 변경을 대조하는 커밋 전 검사(4절 순서 7)가 위험을 줄인다. 이 규칙으로 실행하는 스크립트 안의 명령(`git commit`·`git push`, 삭제·이동 포함)은 `ask`를 거치지 않으므로, 스크립트가 이 저장소에 커밋하거나 파일을 지울 수 있는 경로가 남는다. 이 경로는 막지 않으며, 위의 대표님 승인과 커밋 전 검사로 위험을 줄인다.
- 이 규칙으로 실행하는 스크립트 안에서 `allow` 밖이거나 `ask` 대상인 명령(이 저장소의 커밋·푸시·삭제·이동, `claude` 실행 등)을 실행하지 않는다. 예외는 운영체제 임시 폴더나 pytest `tmp_path` 아래에 만든 시험 저장소 안의 명령이다(인수 시험·단위 시험의 임시 Git 저장소). 위반은 판정에서 결함으로 본다.
- **명령 도구**: 조회·검사·시험 명령은 Bash 도구로 실행한다. Bash 도구가 거부되면 PowerShell 도구로 대신한다. PowerShell 도구에는 `Bash(...)` 규칙이 적용되지 않으므로, `settings.json`은 표준 절차의 Git 조회, 커밋 전 검사, 인수 시험 실행을 `PowerShell(...)` 규칙으로 따로 등록한다. PowerShell의 시각 조회(`Get-Date`)는 Claude Code가 기본으로 허용하는 읽기 전용 명령이므로 등록하지 않는다. PowerShell 도구로 내리는 `git commit`·`git push`와 삭제·이동은 `PowerShell(...)` 규칙으로 `ask`에 따로 등록한다(2절 「`ask`」).
- **명령 형태**: 권한 규칙은 명령 앞부분의 문자열로 맞추고, 묶은 명령은 하위 명령마다 따로 검사한다(근거 `Departments/Development/Implementation/results/DEV-019_v01.md` 6절). 그래서 명령 형태는 아래 원리 하나로 정한다.
  - **원리**: 명령은 저장소 루트(작업 폴더)에서 실행하고, 그 앞부분(묶었으면 하위 명령마다)이 `allow` 규칙이나 Claude Code가 기본으로 허용하는 읽기 전용 명령과 글자 그대로 맞아야 한다. 이 원리를 벗어나면 `allow`에 있는 명령도 권한 확인 요청이 된다.
  - **원리를 벗어나는 형태의 예**: 아래는 예일 뿐이며, 예에 없는 형태도 원리를 벗어나면 같다.
    - ① 작업 폴더를 바꾸거나 다른 폴더를 가리키는 앞부분: `cd <폴더>`, `git -C <경로>`
    - ② 프로그램 이름과 하위 명령 사이의 전역 옵션: `git -c <설정>`, `git --no-pager`. Git 명령은 `git` 바로 뒤에 하위 명령(`status`, `diff`, `log`, `show`, `ls-files`)을 쓴다. 경로의 한글 표시 설정(`core.quotepath`)은 `setup.cmd`가 저장소 설정으로 넣으므로 명령행에 붙이지 않는다.
    - ③ 명령 앞의 환경 변수 대입: `NAME=값 명령`
    - ④ `allow` 규칙에도 기본 읽기 전용 명령에도 들지 않는 하위 명령을 `;`·`&&`·`|`로 묶음(예: `echo "exit=$?"`를 덧붙임)과 셸 구문(변수 대입, 중괄호 묶음, `while`·`for` 반복문, `xargs`)
    - ⑤ PowerShell 도구의 하위 식(`$(...)`)과 괄호 식
  - **경로와 세션 기본 안내**: 명령의 경로는 저장소 루트 기준 상대 경로로 적는다. 절대 경로를 쓰라는 세션 기본 안내는 파일 도구(Read·Write·Edit 등)의 경로에만 적용하며, 이 원리보다 앞서지 않는다.
  - **PowerShell 도구**: 같은 원리를 따른다. 명령은 `PowerShell(...)` 규칙의 앞부분(예: `git status `, `python -m pytest `)이나 기본으로 허용하는 읽기 전용 명령(예: `Get-Date`)으로 시작한다.
  - **원리 안에서 할 수 없는 묶음·반복**: 여러 파일의 반복 처리, 결과 가공처럼 묶음·반복이 필요하면 `allow` 규칙을 더하지 않고 이미 있는 규칙 안의 경로로 실행한다. 검색은 Grep·Glob 도구나 인자를 나열한 단독 `grep` 명령(`Bash(grep *)`)으로 하고, 그 밖은 팀 `workspace/`의 일회성 Python 스크립트를 `Bash(python Departments/*/*/workspace/*)` 규칙으로 실행한다. 스크립트 이름은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「팀 `workspace/` 파일」 항을 따른다.
  - **커밋 해시 조회**: `git rev-parse`는 `allow`에 없어 권한 확인 요청이 된다. HEAD의 커밋 해시는 `git log -1 --format=%H`로 조회한다(`Bash(git log*)`, `PowerShell(git log *)`). 5절 2항의 기준 커밋 조회도 이 명령으로 한다.
  - **문서가 지정하는 명령**: EC, 결과서, 적용본, 인수 시험 절차서(ACC) 등 문서가 뒤 단계의 Claude Code 세션(PM·서브에이전트)에 실행을 지정하는 명령도 이 원리를 따른다. EC 판정·명세 판정이 이를 확인한다(`Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」). 형상통제팀(C02)이 실행하는 반영 명령은 결과서가 정하는 명령이지만 Claude Code 세션에 무인 실행을 지정하는 명령이 아니므로 대상이 아니다. Claude Code로 연 세션에서 반영 명령을 실행하면 확인 화면이 뜬다(2.2절).
- 판정 세션이 명령을 실행하지 못했을 때의 처리는 `Workflow/03_라이프사이클` 「판정 세션의 명령 실행」을, 판정 세션 밖 서브에이전트가 명령을 실행하지 못했을 때의 처리는 같은 문서 「판정 세션 밖의 명령 실행」을 따른다.

  | 종결 기록 | 끝난 REQ·HOTFIX, 끝낸 커밋 | 파일명의 기록 이름과 「대상 기록」 항목, 「끝낸 커밋」 항목(「이 기록을 더한 커밋」이면 `git log --diff-filter=A --format=%H -- <종결 기록 경로>`)(1.1절 4항) |
  | NCR | 판정서나 PM 실행 기록 | 머리말 `source` |
  | CEO 설정 파일 | 그 설정으로 실행한 판정서·HOTFIX | 판정서 9절·HOTFIX 1절 「기준 모델·effort」의 CEO 설정 `saved_at`(`Workflow/04_모델_운용` 「모델 메타데이터 기록」) |
  | 기준선 기록 | 그 기록을 넣은 커밋(최종 승인 커밋이나 지침 재생성 반영 커밋) | 파일 이름의 기록 이름(`REQ-xxx`나 `C01반영`)과 내용의 `head`, `git log --diff-filter=A --format=%H -- <기준선 기록 경로>` |
  | 형상통제 기록(지침 재생성) | 그 반영의 요청 커밋 | 요청 커밋의 근거 줄 `Request-Record`와 그 요청 기록의 커밋할 경로 목록 |
  | 「기록」 승인 기록 | 그 기록으로 고친 모델 매트릭스의 커밋 | 요청 커밋의 근거 줄 `Request-Record`와 그 요청 기록의 커밋할 경로 목록(승인 기록 경로와 모델 매트릭스 경로. 4절 「모델 ID 갱신의 예외」) |

- **추적 식별자**: 대표님 요구 하나는 ORDER 번호와 그 ORDER의 요구 항목 번호를 `-`로 이은 추적 식별자 `ORD-<ORDER 번호>-<요구 항목 번호>`(예: `ORD-006-12`)로 가리킨다. REQ 체크리스트 번호(REQ 서식 5절)와 최종 판정서의 체크리스트 대조 번호(판정서 서식 3절)는 그 요구 항목 번호를 그대로 이어받으며, REQ 머리말 `source_order`의 ORDER 번호와 합쳐 추적 식별자가 된다. 그래서 두 문서 안에서는 번호만 적는다. ORDER에는 파생 번호가 없으므로 추적 식별자의 끝 번호는 파생 번호가 아니다. ORDER를 거치지 않는 작업은 그 기록의 이름(HOTFIX 번호, 요청 기록 파일명)으로 가리킨다.
- **다른 안건 기록의 참조**: 다른 안건이 정한 규정을 근거로 들 때는 그 규정이 있는 현행 원천 문서와 절(예: `Workflow/03_라이프사이클` 「재작업 구분」)을 적고, 그 안건의 기록(REQ, EC, 결과서, 판정서 등)을 버전으로 가리키지 않는다. 다른 안건 기록의 버전은 그 버전에 대한 사실(승인, 판정, 결정, 커밋)을 적을 때만 쓴다(예: 「`REQ-019_v03` D1(권고안)이 정한 처리 순서」). 같은 안건 안의 기록과 `scope:`의 기록 문서(3절)는 이 항목의 대상이 아니다.
- **추적 규정의 적용 시점**: 이 절의 추적 관계 표·추적 식별자·다른 안건 기록의 참조, 2절의 승인 브리핑 이름·「요청 기록」·「커밋 메시지」의 근거 줄, 3절의 REQ `source_order`·HOTFIX `origin`, ORDER 서식의 「근거 자료」 줄, `Workflow/03_라이프사이클` 「판정 세션의 명령 실행」 6항, `Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 6번 ⑨⑩과 「비서실 실행 절차」의 요청 기록은 `REQ-026` 커밋 뒤에 첫 버전을 작성하는 기록(ORDER, REQ, HOTFIX, 판정서, 브리핑 등)과 `REQ-026` 커밋 뒤에 하는 커밋부터 적용한다. 이미 작성된 기록과 이미 한 커밋, `REQ-026` 자신의 기록과 커밋은 바꾸지 않으며 적용하지 않는다. `REQ-026` 커밋 때 커밋되지 않은 비서실 산출물은 `Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 6번 ⑨⑩으로 안건 커밋에 넣지 않고 대표님 요청에 따른 「요청 커밋」으로 남긴다.

### 1.1 종결 기록

REQ·HOTFIX가 끝났는지와 언제 어떤 경로로 끝났는지는 이 절이 원천이다.

1. **끝난 안건**: 아래 (가)·(나) 가운데 하나에 해당하고 그 종결 기록이 커밋된 REQ·HOTFIX다. 판단은 기록 이름(번호) 단위이며 버전과 관계없다. 파생 안건은 원 안건과 따로 판단한다.
   - (가) 그 안건을 끝내는 커밋을 마친 것: REQ는 최종 판정서 승인 뒤의 커밋(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 또는 같은 문서 1절 「커밋」 항의 다른 경로), HOTFIX는 `confirmed:` 기재 뒤의 커밋(핫픽스 커밋)이다. 한 안건의 커밋이 둘 이상이면 마지막 커밋이 끝내는 커밋이다.
   - (나) 커밋 없이 끝난 것: 다른 안건에 흡수된 것, 중단 조건(`Workflow/03_라이프사이클` 「중단 조건」. 판정 `rejected` 포함)으로 멈춘 뒤 더 진행하지 않기로 한 것이다.
   - 판정 `fail` 뒤 고쳐서 계속하는 안건과, 멈춘 뒤 대표님 결정으로 계속하는 안건(REQ 새 버전 포함)은 끝난 것이 아니다.
2. **효력**: 커밋된 종결 기록이 있는 안건만 끝난 것으로 본다. 커밋 전 검사(`Workflow/06_통제장치_및_배포` 「커밋 전 검사」)와 공식 진행 상태(`Workflow/05_인수인계_및_실행명령` 1절)는 같은 기록으로 판단한다. 커밋하지 않은 종결 기록은 효력이 없으므로, 그 안건을 끝내는 커밋에 종결 기록을 함께 넣어도 그 커밋의 커밋 전 검사에서는 그 안건이 통과 근거로 남는다.
3. **위치·이름**: 1절 표의 「종결 기록」 행과 2절 「종결 기록」 항을 따른다.
4. **항목**: 머리말 없이 아래 항목을 목록으로 적고, 작성 뒤 고치지 않는다. 아래의 「8항의 기록」은 8항대로 `REQ-028` 구현 단계에서 개발부가 작성하는 종결 기록이다.
   - 대상 기록: 끝난 REQ·HOTFIX의 최신 버전 경로
   - 종결 경로: `커밋`, `흡수`, `중단 뒤 종료` 가운데 하나
   - 커밋 종류: 종결 경로가 `커밋`이면 `최종 승인 커밋`, `핫픽스 커밋`, `대표님 직접 커밋`, `PM 커밋` 가운데 하나. 8항의 기록에서 확인할 수 없으면 「확인 불가」. 종결 경로가 `커밋`이 아니면 「해당 없음」
   - 끝낸 커밋: 그 커밋에 함께 넣으면 「이 기록을 더한 커밋」으로 적는다. 커밋 해시는 `git log --diff-filter=A --format=%H -- <종결 기록 경로>`로 찾고, 끝난 시각은 그 커밋의 커밋 시각으로 본다. 8항의 기록은 끝낸 커밋의 40자리 해시를 적는다. 커밋 없이 끝났으면 「해당 없음」
   - 근거: 커밋으로 끝난 REQ는 최종 판정서 경로와(있으면) 그 승인 기록 경로, HOTFIX는 `confirmed:`가 기재된 HOTFIX 경로. 커밋 없이 끝났으면 대표님 결정 문구 원문과 문구를 받은 시각(`YYYY-MM-DDTHH:MM:SS+09:00`. 끝난 시각으로 본다), 흡수면 흡수한 안건(기록 이름이나 커밋). 8항의 기록이 이미 기록된 결정을 근거로 삼으면 그 기록의 경로와 줄(예: 커밋 메시지, 개정 이력 행)
   - 작성 주체: 비서실은 세션 식별자(`Workflow/05_인수인계_및_실행명령` 「비서실 동시 운용」)와 모델, PM은 「PM」과 모델, 대표님은 「대표님」, 8항의 기록은 작성 부서와 모델
   - 작성 시각: `YYYY-MM-DDTHH:MM:SS+09:00`
5. **커밋 없는 종결의 결정**: 흡수와 중단 뒤 종료는 대표님이 정한다. 비서실은 흡수로 보이는 안건과 중단 뒤 멈춘 안건을 대표님께 보고해 결정을 받는다. 결정 문구에는 대상 기록 이름과 끝낸다는 뜻(흡수면 흡수한 안건)이 들어 있어야 하고, 빠지면 결정으로 보지 않고 대표님께 되묻는다. 다른 세션·에이전트가 전한 문구는 근거로 쓰지 않는다(3.1절 「승인 기록」 2·3항과 같은 처리).
6. **기록 주체와 시점**

   | 끝나는 경로 | 기록 주체 | 시점 |
   | :--- | :--- | :--- |
   | 최종 승인 커밋 | 그 커밋을 하는 형상통제팀(C02) | `Workflow/05_인수인계_및_실행명령` 1.1절 6번 스테이징 앞. 그 커밋에 넣는다 |
   | 핫픽스 커밋(형상통제팀) | 그 커밋을 하는 형상통제팀(C02) | `Workflow/05_인수인계_및_실행명령` 「요청 커밋」 3)의 요청 기록 뒤. 그 커밋에 넣는다 |
   | 대표님 직접 커밋 | 대표님 | 그 커밋에 넣는다 |
   | PM 커밋(대표님 요청) | PM | 그 커밋에 넣는다 |
   | 흡수, 중단 뒤 종료 | 5항의 결정 문구를 대표님에게서 직접 받은 비서실 세션(저장소 파일을 수정할 수 있는 세션) | 결정을 받은 뒤. 커밋은 대표님 요청으로 `Workflow/05_인수인계_및_실행명령` 「요청 커밋」 1)의 (가)로 한다 |

   - 날짜와 관계없이 같은 기록 이름의 종결 기록이 있으면 새로 쓰지 않는다.
7. **다시 열지 않음**: 끝난 안건은 다시 열지 않으며, 종결 기록을 고치거나 취소하는 경로를 두지 않는다. 다시 할 일은 `Workflow/03_라이프사이클` 「진행 중 변경과 파생 안건」을 따른다.
8. **적용 시점**: 이 절과 이 절을 가리키는 규정은 `REQ-028` 커밋부터 적용한다. `REQ-028` 자신의 종결 기록은 그 최종 승인 커밋에서 비서실이 반영된 `Workflow/05_인수인계_및_실행명령` 1.1절 6번대로 작성해 그 커밋에 넣는다. `REQ-028` 커밋 전에 끝난 기록(지금 `Departments/Secretariat/PM/docs/requests/`·`Departments/Development/Hotfix/results/`에 있는 REQ·HOTFIX)의 종결 기록은 `REQ-028` 구현 단계에서 개발부가 작성해 `REQ-028` 커밋에 넣는다. 이미 있는 REQ·HOTFIX 파일은 바꾸지 않는다.

## 2. 번호와 버전

| 구분 | 형식 | 예 |
| :--- | :--- | :--- |
| 기본 | `<종류>-<세 자리 번호>_v<두 자리 버전>.md` | `REQ-007_v01.md`, `RES-007_v01.md` |
| 파생 안건 | `<종류>-<세 자리 번호>-<파생 번호>_v<두 자리 버전>.md` | `REQ-007-1_v01.md`, `RES-007-1_v01.md` |
| 판정 구분 | 번호 뒤에 `-REQ`·`-EC`·`-SPEC`·`-DESIGN`을 붙인다 | `RES-007-REQ_v01.md`, `RES-007-1-EC_v02.md`, `RES-007-SPEC_v01.md`, `RES-007-DESIGN_v01.md` |

- **번호**: REQ 번호가 원천이다. EC·DEV·RPT·RES는 같은 번호를 쓴다. 새 REQ 번호는 `Departments/Secretariat/PM/docs/requests/`의 가장 큰 번호에 1을 더한다.
- **HOTFIX**: REQ와 별도의 세 자리 번호를 쓴다. 새 번호는 `Departments/Development/Hotfix/results/`의 가장 큰 HOTFIX 번호에 1을 더한다(없으면 「시작 번호」 항의 번호). 파일을 저장하기 직전에 그 폴더를 다시 조회해 같은 번호가 생겼으면 다음 번호를 쓴다.
- **ORDER**: REQ와 별도의 세 자리 번호를 쓴다. 문서 종류 부분은 `ORD`다(예: `ORD-001_v01.md`). 새 번호는 `Departments/Secretariat/Secretary/assets/inbox/`의 가장 큰 ORDER 번호에 1을 더한다(없으면 「시작 번호」 항의 번호). 파일을 저장하기 직전에 그 폴더를 다시 조회해 같은 번호가 생겼으면 다음 번호를 쓴다.
- **시작 번호**: 표준 저장소(이 저장소)는 v02 기록(`_archive/v02/`)과 겹치지 않게 REQ `007`, HOTFIX `003`부터 썼다. v04 하드포크 때 v03의 REQ-007~010을 이관해 같은 번호로 계속 쓰고, REQ-011은 v04 개정에 흡수되어 종결되었으므로 다음 새 REQ 번호는 `012`다. 배포본으로 시작한 신규 프로젝트는 REQ와 HOTFIX 둘 다 `001`부터 쓴다. ORDER는 이 저장소와 신규 프로젝트 모두 `001`부터 쓴다. 서식의 `007`·`003`은 예시다. v05 저장소의 예외: 이 저장소(v05)는 v04 저장소와 번호가 겹치지 않도록 `REQ-031` 커밋 뒤에 받는 새 REQ·HOTFIX 번호를 `101`부터 쓴다. 「번호」·「HOTFIX」 항대로 구한 번호가 `101`보다 작으면 `101`을 쓴다. `REQ-031` 커밋 전에 받은 번호(`REQ-031`~`REQ-035`)는 그대로 쓴다. ORDER 번호는 이 예외 없이 「ORDER」 항을 따른다. v04와 함께 운영하는 동안 새 ORDER는 이 저장소에만 두므로 v04와 겹치지 않기 때문이다.
- **AUDIT**: 비정기 작업이므로 번호 대신 날짜를 쓴다.
- **조사 자료·아이디어 백로그·기획안·브리핑**: 번호 대신 날짜(`YYYYMMDD`)를 쓴다. 조사 자료는 조사 날짜, 그 밖은 v01을 작성한 날짜이며 새 버전에서도 바꾸지 않는다. 승인 브리핑(`Workflow/05_인수인계_및_실행명령` 「브리핑」)의 `<주제>`는 REQ 승인이면 `<REQ 번호>_REQ승인`, 최종 판정서 승인이면 `<REQ 번호>_최종승인`으로 시작한다(예: `브리핑_20261011_REQ-026_REQ승인_v01.html`).
- **작업 큐**: 번호와 날짜를 쓰지 않고 `작업큐_vNN.md`로 쓴다. 작업 큐는 하나이며 가장 높은 버전이 현행본이다. 버전을 올리는 시점은 「비서실 산출물의 버전」 항을 따른다.
- **실행 기록**: 번호 자리에 그 안건의 REQ 번호(`REQ-xxx`, 파생 안건은 `REQ-xxx-n`)를 쓰고 버전을 붙이지 않는다(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」).
- **요청 기록**: 번호 대신 요청을 받은 날짜(`YYYYMMDD`)와 주제를 쓰고 버전을 붙이지 않는다. 작성 뒤 고치지 않는다. 같은 이름의 파일이 있으면 주제를 바꾼다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **종결 기록**: 번호 대신 작성 날짜(`YYYYMMDD`, KST)와 끝난 REQ·HOTFIX의 기록 이름을 쓰고 버전을 붙이지 않는다. 기록 이름은 그 기록 파일명에서 `_v<버전>.md`를 뗀 것이다(`REQ-xxx`, `REQ-xxx-n`, `HOTFIX-xxx`. 예: `종결기록_20261013_REQ-011.md`). 파일명 형식은 정규식 `^종결기록_\d{8}_((?:REQ|HOTFIX)-\d{3}(?:-\d+)?)\.md$`이며, `Departments/Secretariat/Secretary/assets/inbox/` 바로 아래에 둔다. 안건 하나에 파일 하나이며 작성 뒤 고치지 않는다. 커밋 전 검사가 이 형식을 확인한다(`Workflow/06_통제장치_및_배포` 「커밋 전 검사」 순서 6). 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **기준선 기록**: 번호 대신 기록한 시각(`YYYYMMDDTHHMMSS`, 한국 시간)과 기록 이름(최종 승인 커밋이면 그 안건의 기록 이름 `REQ-xxx`, 지침 재생성 반영이면 `C01반영`)을 쓰고 버전을 붙이지 않는다(예: `기준선_20261020T101500_REQ-101.json`). 작성 뒤 고치지 않는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **형상통제 기록**: 번호 대신 작성 날짜(`YYYYMMDD`, 한국 시간)와 주제를 쓰고 버전을 붙이지 않는다. 같은 날 같은 주제가 둘이면 주제 끝에 `-2`부터 붙인다. 작성 뒤 고치지 않는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **인수 시험**: 폴더 이름은 `<REQ 번호>_vNN`이다(파생 안건은 `REQ-xxx-n_vNN`). 폴더 버전은 시험을 바꿀 때만 올리며 ACC 버전과 다를 수 있다. 현행 ACC는 가장 높은 버전의 ACC이고, 현행 인수 시험은 현행 ACC 머리말 `test_dir`이 가리키는 폴더다. 시험을 바꾸면 새 버전 폴더와 새 ACC를 만들고, 시험을 바꾸지 않고 판단만 적으면 새 ACC만 만든다. 이전 버전은 지우지 않는다. 「대상 없음」이면 폴더를 만들지 않는다.
- **부적합 기록**: 번호 자리에 그 안건 번호를 쓰고, 뒤에 그 안건의 부적합 기록 가운데 가장 큰 일련번호에 1을 더한 두 자리 번호를 붙인다(없으면 `01`. 예: `NCR-019_01.md`, 파생 안건 `NCR-019-1_01.md`). 버전을 붙이지 않고 작성 뒤 고치지 않는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다.
- **팀 `workspace/` 파일**: 안건을 위해 팀 직속 `workspace/`에 만드는 파일과 폴더는 이름을 그 안건의 REQ 번호와 `_`로 시작한다(예: `REQ-014_복사_20261009a.py`, `REQ-008_실측_v01/`. 파생 안건은 `REQ-xxx-n_`). PM 실행 기록은 「실행 기록」 항을 따른다. 일회성 파일의 판단과 정리는 `Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」의 최종 판정 기준 7을 따른다.
- **파생 번호**: 원 안건에서 미결로 남거나 새로 생긴 작업에 `1`부터 붙인다(`Workflow/03_라이프사이클` 「진행 중 변경과 파생 안건」).
- **버전**: 내용이 바뀌면 새 파일로 저장하고 버전을 올린다. 가장 높은 버전이 현행본이다. 판정에서 지적을 받아 고친 문서와 재판정 판정서도 새 버전으로 저장한다. 이전 버전은 지우지 않는다.
- **비서실 산출물의 버전**: 대상은 ORDER, 작업 큐, 조사 자료, 브리핑, 아이디어 백로그, 기획안이다. 수정하는 때에 그 파일이 「보인 뒤」가 아니면 버전을 올리지 않고 같은 파일을 고친다(판정 결과 반영 포함). 「보인 뒤」이거나 승인 뒤이면 새 버전으로 저장한다. 「보인 뒤」는 비서실이 대표님께 그 파일(경로나 내용)을 보고한 뒤다. ORDER에 `ceo_checked_at`이 기재되어 있으면 보인 시점은 그 시각이다(보고한 때보다 우선한다). 판단은 수정하는 때의 상태(보고 여부, `ceo_checked_at` 기재 여부)로 한다. ORDER `related_req`·`ceo_checked_at` 기재, ORDER 「담당 세션」 줄의 변경 기재(`Workflow/05_인수인계_및_실행명령` 「비서실 동시 운용」)와, 기획안 「대표님 결정」 표와 아이디어 백로그 「상태」 열의 결정 기재(「발행한 ORDER」 기재 포함. `Workflow/03_라이프사이클` 「기획 트랙」)는 「보인 뒤」에도 버전을 올리지 않는다. HOTFIX와 승인 기록은 대상이 아니다. 이 항은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이며, 그 밖의 문서(REQ, EC, 명세, DEV, 판정서 등)는 「버전」 항을 따른다.
- **승인과 버전**: `approved:`는 그 버전에만 효력이 있다. REQ 새 버전은 `approved: ""`로 시작하고, REQ 판정과 대표님 재승인을 다시 받는다. 예외로, 「문체 반영」 승인으로 만든 REQ 새 버전(문체 반영본)은 REQ 판정과 대표님 재승인 대신 `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」의 대조를 받고, 승인 필드는 3.1절 7항대로 기재한다. 재승인 방법은 3.1절 「승인 기록」을 따른다.
- **PRD·TAD·시각 디자인 문서**: 제품 명세와 시각 디자인 문서는 버전 번호 없는 파일명 하나로 유지하고 개정 이력은 Git과 문서 하단 개정 이력 표로 관리한다.
- **서식**: `*_TEMPLATE.*`(`.md`, `.html`)에는 번호와 버전을 붙이지 않는다.
- **커밋 메시지**: 제목 줄과 근거 줄로 쓴다.
  - **제목 줄**: `feat: [REQ-007] 요약`, `fix: [HOTFIX-003] 요약`. 제목 줄에는 버전을 적지 않는다. REQ·HOTFIX 없는 커밋은 `<유형>: [CEO] <요약>`으로 쓴다(예: `docs: [CEO] 비서실 research에 조사 자료 추가`). `[CEO]`는 대표님 직접 지시 커밋을 뜻하며 커밋 종류와 관계없이 같다. `<유형>`은 REQ 커밋과 같이 변경 성격에 맞게 적는다.
  - **근거 줄**: 커밋 하나에서 그 커밋이 반영한 승인본을 찾기 위해, 제목 줄 뒤 빈 줄 하나를 두고 근거 기록을 `<키>: <저장소 루트 기준 경로>`로 한 줄에 하나씩 적는다(`Follows`와 `Model-Effort`는 경로가 아니다. 아래 두 항목). REQ·HOTFIX 커밋은 커밋하는 주체와 관계없이 적는다. `[CEO]` 커밋은 형상통제팀(C02)이 하는 요청 커밋(`Workflow/05_인수인계_및_실행명령` 「요청 커밋」)만 적고, 대표님이 직접 하는 커밋에는 요구하지 않는다. `Request-Record`는 형상통제팀(C02)이 「요청 커밋」으로 하는 커밋에만 적는다(요청 기록은 그 절차에서만 작성한다).

    | 커밋 | 근거 줄 |
    | :--- | :--- |
    | REQ 커밋 | `Approved-REQ: <그 안건 REQ의 최신 버전(승인 필드가 기재된 버전)>`, `Approved-RES: <대표님이 승인한 최종 판정서>`, `Approval-Record: <그 최종 판정서의 승인 기록>`. 「문체 반영」 대조를 거쳤으면 `Style-Check-RES: <대조 판정서>`를 더한다 |
    | HOTFIX 커밋 | `Confirmed-HOTFIX: <confirmed:가 기재된 HOTFIX 버전>`. 형상통제팀(C02)이 「요청 커밋」으로 하면 `Request-Record: <요청 기록>`을 더한다 |
    | 형상통제팀(C02)의 그 밖의 요청 커밋 | `Request-Record: <요청 기록>` |

  - **같은 안건의 여러 커밋**: 같은 REQ·HOTFIX·요청 기록의 커밋이 둘 이상이면, 둘째 커밋부터 요약에 그 커밋이 담은 것을 적고(예: `docs: [REQ-022] 최종 판정서 추가`) 근거 줄 끝에 `Follows: <같은 안건 직전 커밋의 짧은 해시>`를 더한다. 커밋마다 담은 파일은 `git show --name-status --format= <커밋>`으로 확인한다.
  - **실행 모델·effort 줄**: 형상통제팀(C02)과 PM이 하는 커밋(최종 승인 커밋, 요청 커밋, PM 커밋)은 근거 줄 끝(`Follows`가 있으면 그 앞)에 `Model-Effort: <커밋한 세션의 모델 ID 또는 모델 이름> / <effort 또는 「확인 불가」>`를 적는다. 판정이 없는 일의 실제 사용 모델·effort를 남기기 위해서다(`Workflow/04_모델_운용` 「모델 메타데이터 기록」). 값은 경로가 아니다. 대표님이 직접 하는 커밋에는 요구하지 않는다. 최종 승인 커밋은 준비 명령이 이 줄의 자리(`<`·`>`로 감싼 자리)를 만들고 C02가 채운다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 8번).
  - **근거 줄의 키와 트레일러**: 근거 줄의 키는 위 표와 「같은 안건의 여러 커밋」·「실행 모델·effort 줄」이 정한 `Approved-REQ`, `Approved-RES`, `Approval-Record`, `Style-Check-RES`, `Confirmed-HOTFIX`, `Request-Record`, `Follows`, `Model-Effort`뿐이다. `Co-Authored-By:`로 시작하는 줄(대소문자 무시)은 Git 트레일러이며 근거 줄이 아니다.
  - **최종 승인 커밋의 제목 줄**: 최종 승인 커밋의 제목 줄 유형은 `feat`로 하고 요약은 REQ 제목(REQ 최신 버전 H1 제목에서 `REQ-xxx: ` 뒤 문구)으로 한다(준비 명령이 만든다. `Workflow/06_통제장치_및_배포` 「준비·판단 명령」).
  - **검사**: 커밋 메시지 검사(`Workflow/06_통제장치_및_배포` 「커밋 메시지 검사」)가 커밋 때 이 항을 확인한다.
  - `setup.cmd`가 만드는 첫 커밋(`chore: 바이브 코딩 표준 v05 초기화`)은 예외다.

## 3. 머리말

- **머리말 형식**: 공식 문서는 `---`로 감싼 YAML 머리말로 시작한다. 브리핑은 예외이며 작성 정보를 본문 맨 끝에 적는다(`Workflow/05_인수인계_및_실행명령` 「브리핑」). 시각 디자인 문서도 예외이며 업계 통용 형식을 따르고, 안건과의 연결은 문서 하단 개정 이력 표(4절)로 남긴다.
- **날짜·시각 형식**: 날짜는 `"YYYY-MM-DD"`, 시각은 `"YYYY-MM-DDTHH:MM:SS+09:00"` 문자열이다. **`approved:`와 `confirmed:`는 시각 형식만 허용한다.** 형식은 커밋 전 검사에서 확인한다.
- **목록 필드**: 목록 필드(`scope:`, `workflow:`, `related_req:`, `causes:`, `proposals:`)는 두 칸 들여쓰기 뒤 `- `로 시작한다. 폴더 항목은 끝에 `/`를 붙이지 않는다(예: `Workflow`).
- **scope의 기록 문서**: `scope:`에 적는 기록 문서(EC 등)는 버전과 확장자 없이 적는다(예: `Departments/Design/EC/docs/EC-007`). 새 버전이 생겨도 scope를 고치지 않기 위해서다.
- **작성·판정 모델**: 작성·판정 모델은 `Workflow/04_모델_운용` 「모델 메타데이터 기록」대로 적는다.

| 문서 | 필수 머리말 필드 |
| :--- | :--- |
| ORDER | `order_id`, `created`, `ceo_checked_at`(대표님이 ORDER 내용을 확인한 시각. 비어 있을 수 있다), `classification_proposal`(`Critical`·`Major`·`Minor`. 비서실의 제안이며 확정은 REQ `classification`. 정의 기준은 `Workflow/03_라이프사이클` 「분류별 단계」. ORDER에는 모델 등급 필드를 두지 않는다), `related_req`(이 ORDER로 작성한 REQ의 버전 없는 이름 목록) |
| REQ | `task_id`, `classification`(`Critical`·`Major`·`Minor`. 정의 기준과 분류별 단계·기본 모델 등급은 `Workflow/03_라이프사이클` 「분류별 단계」, 근거는 REQ 서식 2절 「분류 근거」), `created`, `created_at`(그 버전 파일을 PM이 처음 저장할 때 조회한 시각. 형식 `YYYY-MM-DDTHH:MM:SS+09:00`. 기재 방법은 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항, 쓰임과 적용 시점은 같은 문서 「원스톱 착수 조건」 5·8항), `source_order`(이 REQ 버전을 작성할 때 근거로 삼은 ORDER 파일의 저장소 루트 기준 경로와 버전. 1절 「요청 원문」의 출처와 같다. 추적 식별자는 1절), `approved`(3.1절 「승인 기록」), `author`, `workflow`(단계는 `Workflow/03_라이프사이클` 「분류별 단계」. - **NCR의 시각 필드**: NCR은 개정 제안의 건수를 기록 순서로 세므로(`Workflow/03_라이프사이클` 「부적합 관리」) `created` 대신 시각 필드 `recorded_at`을 쓴다. 원인과 제안을 머리말에 두어 기존 기록을 머리말만 읽고 대조할 수 있게 한다.
- ORDER의 `ceo_checked_at`은 승인 필드가 아니며 REQ 작성의 착수 조건이 아니다. 3.1절 「승인 기록」의 대상이 아니다.
- ORDER의 `related_req`는 PM이 REQ를 처음 작성할 때 더한다. 이 갱신은 같은 파일에서 하며 버전을 올리지 않는다(아래 EC `status:`·`gate:` 갱신과 같다).
- 조사 자료의 이름(1절, 2절)과 머리말(이 표) 규칙은 REQ-012 반영 뒤 새로 작성하는 파일부터 적용한다. 그 전에 작성한 파일에는 소급하지 않는다.

**EC 상태 전이**

```text
draft ──(최신 RES-xxx-EC result: pass)──▶ approved
draft ──(최신 RES-xxx-EC result: fail)──▶ EC 새 버전(draft) 작성 후 재판정
```

- `status:`는 설계부가 명세 단계를 시작할 때 바꾼다. `approved`로 바꿀 때 `gate:`에 판정서 경로를 함께 적는다. 최신 판정이 `pass`가 아니면 `approved`로 바꾸지 않는다.
- `status:`·`gate:` 갱신은 같은 파일에서 하며 버전을 올리지 않는다. 본문을 바꾸면 새 버전으로 저장하고 다시 판정한다.

**`result` 값**

| 값 | 뜻 |
| :--- | :--- |
| `pass` | 판정 기준의 결함이 없다. 완성도를 보증하지 않는다 |
| `fail` | 결함이 있다. 해당 부서가 고친 뒤 다시 판정한다 |
| `rejected` | 안건 자체가 성립하지 않는다(요구 모순, 여러 뜻으로 읽힘 등) |

### 3.1 승인 기록

승인 필드(REQ `approved:`, HOTFIX `confirmed:`)와 REQ 「결정 사항 및 선택지」 표의 「결정」 열의 기재 규칙, 최종 판정서 승인의 기록 규칙, CEO 설정과 「기록」의 승인 기록(10항)은 이 절이 원천이다.

1. **승인의 정의**: 승인은 대표님의 의사 표시다. 승인 필드와 「결정」 열은 그 의사를 기록한 것이다.
2. **승인 문구**: 대표님의 승인 문구에는 대상 파일명과 버전이 들어 있어야 한다. REQ는 결정(D번호별 결정 또는 「전부 권고안」)도 들어 있어야 한다. 예: 「REQ-007_v06 승인, D1~D5 권고안」, 「HOTFIX-003_v01 확인」. 최종 판정서 승인 문구에도 대상 파일명과 버전이 들어 있어야 한다(예: 「RES-007_v02 승인」). 승인 문구에 「문체 반영」을 덧붙일 수 있다(`Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」). 대표님 본인이 REQ 승인 필드를 기재하면서 「문체 반영」을 지시할 때는 승인 필드 줄 끝 주석에 `# 문체 반영`을 적는다. 필요한 항목이 빠진 문구는 승인으로 보지 않고 대표님께 되묻는다.
3. **기재 주체**: 대표님 본인, 또는 승인 문구를 대표님에게서 직접 받은 비서실이다. 다른 에이전트나 세션이 전달한 문구는 근거가 되지 않는다. PM과 서브에이전트는 승인 필드와 「결정」 열을 기재하지 않는다. 7항의 문체 반영본은 예외다.
   - 셸을 실행할 수 있는 비서실 세션이 PM을 실행하는 동안 대표님이 그 세션에 준 답은 그 세션이 대표님에게서 직접 받은 문구로 보고 그 세션이 기재한다. 그 세션은 PM 출력을 고치지 않고 원문 그대로 대표님께 전달한다.
   - 대표님이 실행 명령을 직접 실행한 경로에서 PM 세션에 직접 답한 승인 문구는 PM이 기재하지 않는다. 대표님이 그 문구를 비서실 세션에 다시 주거나 본인이 기재한다.
4. **기재 순서**: 대표님 본인이 기재할 때는 이 순서를 생략한다. 최종 판정서 승인은 승인 필드가 없으므로 1만 한다. 이때 파일명은 `승인기록_<YYYYMMDD>_RES-xxx_vNN.md`이고, 문구를 대표님에게서 직접 받은 비서실이 작성하며, 그 안건의 커밋에 넣는다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」). 7항의 문체 반영본은 예외다.
   1. `Departments/Secretariat/Secretary/assets/inbox/승인기록_<YYYYMMDD>_<대상 파일명>.md`를 작성한다. 승인 문구 원문, 문구를 받은 시각, 대상 파일 경로와 버전, 기재한 세션(세션 식별자, `Workflow/05_인수인계_및_실행명령` 「비서실 동시 운용」)과 모델을 적는다.
   2. 대상 파일의 승인 필드와, REQ이면 「결정」 열을 기재한다. 승인 필드 값은 문구를 받은 시각이다. 승인 필드 줄 끝의 서식 주석은 `# 대리 기재: <세션>, 근거 <승인 기록 경로>` 주석으로 바꾼다.
5. **대조**: 대표님은 최종 판정서를 승인하기 전에(HOTFIX는 커밋 전에) 대리 기재된 승인 필드와 「결정」 열을 승인 기록과 대조한다. 7항의 문체 반영본은 승인 필드가 직전 버전 값과 같은지와 대조 판정서가 `pass`인지를 대조한다.
6. **「결정」 열의 확정 시점**: 기재 주체(대표님 본인 또는 대리 기재)와 관계없이, REQ의 「결정」 열은 승인 필드와 같은 기재 작업에서 확정한다. 「결정」 열을 비워 두거나 승인 필드보다 나중에 채우는 방식으로 승인 필드를 기재하지 않는다. 승인 필드를 기재한 뒤 결정을 바꾸려면 REQ 새 버전을 작성한다(2절 「승인과 버전」). 7항의 문체 반영본은 예외다.
7. **문체 반영본의 승인 필드**: 「문체 반영」 승인으로 만든 REQ 새 버전(문체 반영본)은 `approved: ""`로 작성하고, 「결정」 열은 직전 버전 값을 그대로 옮긴다. `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」의 대조가 `pass`이면 PM이 같은 파일에서 버전을 올리지 않고 직전 버전의 `approved:` 값을 그대로 기재하고, 줄 끝 주석을 `# 문체 반영본: 승인 근거 <직전 버전 경로>, 대조 <대조 판정서 경로>`로 적는다. 이 기재는 새 승인 문구를 받아 하는 기재가 아니라 직전 버전에 이미 기록된 승인(직전 버전의 승인 필드와, 대리 기재였으면 그 승인 기록)을 옮겨 적는 것이다. 그래서 아래 예외를 둔다.
   1. 3항(기재 주체): 문체 반영본의 승인 필드는 PM이 직전 버전의 승인 필드(대리 기재였으면 그 승인 기록도)를 근거로 기재한다. 승인 문구를 대표님에게서 직접 받았는지와 관계없다.
   2. 4항(기재 순서): 새 승인 기록을 만들지 않고(4항 1 생략), 승인 필드 줄 끝 주석은 4항 2의 대리 기재 주석 대신 위 문체 반영본 주석을 쓴다.
   3. 5항(대조): 대표님의 대조 대상에 문체 반영본의 승인 필드를 더한다. 대조 내용은 5항 둘째 문장이다.
   4. 6항(「결정」 열의 확정 시점): 「결정」 열은 문체 반영본을 작성할 때 직전 버전 값으로 옮기고, 승인 필드는 대조 `pass` 뒤에 기재한다.
8. **대안 선택의 기록**: 대표님이 REQ 승인 문구(2항)에서 결정 표의 권고안이 아닌 선택지나 수정안을 고르면, 그 결정을 「결정」 열에 기록하고 REQ 새 버전을 작성하지 않는다. 이 기록은 6항대로 승인 필드와 같은 기재 작업에서 한다. 승인 필드를 기재한 뒤 대표님이 결정을 바꾸면(중단 조건으로 멈춘 뒤의 답에서 결정 표의 선택을 바꾸는 경우 포함) 이 항이 아니라 6항을 따라 REQ 새 버전을 작성한다. 기재 주체는 3항을 따른다. 「결정」 열과 체크리스트·실행 계획의 관계는 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항 「결정과 체크리스트」를 따른다.
9. **실험 단계의 승인**: REQ `workflow:`에 실험 단계가 있으면 그 REQ의 승인(4항의 승인 기록과 승인 필드 기재, 또는 대표님 본인의 승인 필드 기재)이 실험 단계의 `Lab/` 사용 승인(`Workflow/03_라이프사이클` 「실험실」)을 겸한다. 실험 단계에는 따로 실험실 승인을 받거나 기록하지 않으며, 파이프라인은 실험실 승인 때문에 멈추지 않는다.
10. **CEO 설정과 「기록」의 승인 기록**: 모델·effort의 「기본값 밖 사용」은 REQ 「결정」 열 밖에 CEO 설정으로도 승인된다(`Workflow/04_모델_운용` 「기본값 밖 사용」). 아래 두 기록은 대표님 조작으로 대시보드가 쓰는 승인 기록이며, 3항(기재 주체)과 4항(비서실이 `Departments/Secretariat/Secretary/assets/inbox/`에 쓰는 기재 순서)의 예외다. 비서실과 그 밖의 AI 세션은 두 기록을 쓰거나 고치지 않고 읽기만 한다.
    1. **저장된 CEO 설정 파일**: 「저장」된 `CEO/settings/model_settings.json`은 그 파일에 적힌 칸의 승인 기록의 한 형식이다. 별도 승인 기록을 남기지 않는다. 승인 시각은 `saved_at`이며, 효력과 범위는 `Workflow/04_모델_운용` 「CEO 설정」을 따른다. 「새로고침(기본값으로)」으로 비우면 그 승인은 다음 실행부터 효력을 잃는다.
    2. **「기록」의 승인 기록**: 작성 주체는 대표님(대표님 조작으로 대시보드가 쓴다)이고, 위치와 이름은 `CEO/settings/records/승인기록_<YYYYMMDDTHHMMSS>_모델매트릭스.json`(시각은 한국 시간)이다. UTF-8 JSON이며 `recorded_at`(`YYYY-MM-DDTHH:MM:SS+09:00`), `recorded_by`(「대표님(대시보드 「기록」)」), `matrix`(모델 매트릭스 경로 `Workflow/data/model_matrix.json`), `changes`(바꾼 칸마다 `part`, `role`, `class`, `before`, `after`. `before`·`after`는 `{ "model", "effort" }`)를 둔다. 작성 뒤 고치지 않는다. 이 기록이 그 모델 매트릭스 수정의 승인이자 개정 기록이다(4절 「모델 ID 갱신의 예외」).

## 2. 분류별 단계

분류의 정의 기준, 분류별 원스톱 파이프라인 단계, 분류별 기본 모델 등급은 이 절이 원천이다. 분류는 REQ의 중요도와 난이도로 정한다. 먼저 중요도로 정하고, 난이도가 높으면(변경이 여러 모듈·문서에 걸치거나 판단할 곳이 많으면) 한 단계 올린다(Minor → Major, Major → Critical). 난이도를 이유로 낮추지 않는다. 중요도는 항공 품질의 Critical·Major·Minor 결함 수준을 차용해, 그 변경에 결함이 생겼을 때의 영향으로 정한다(아래 표 「중요도」 열). 「예」 열은 흔한 예이며, 예와 중요도가 다르면 중요도를 따른다.

| 분류 | 중요도(결함이 생겼을 때의 영향) | 예 | 원스톱 파이프라인 단계 | 기본 모델 등급 |
| :---: | :--- | :--- | :--- | :---: |
| Critical | 모든 안건의 통제가 무너지거나 보안·데이터에 피해가 생기는 변경. 기능상 중대 결함이 우려되는 변경도 여기에 든다 | 거버넌스 파일, 보안·권한, 코어 구조 | (실험) → EC 판단 → [EC 작성 → EC 판정] → 명세 → [명세 판정] → (시각 디자인 → 시각 디자인 판정) → 인수 시험 → 구현 → 최종 판정 | 고급 |
| Major | 기능·성능·호환·규격에 영향이 있는 변경 | 신규 기능, 여러 모듈 수정, API 규격 | Critical과 같다 | 고급 |
| Minor | 결함이 생겨도 기능·품질에 영향이 없는 변경 | 단순 오탈자, 단일 파일 수정, 문서 보완 | (실험) → EC 판단 → [EC 작성 → EC 판정] → [명세] → (시각 디자인 → 시각 디자인 판정) → 구현 → 최종 판정 | 중급 |

- 괄호 안의 단계는 선택 단계다. 실험 단계는 실험이 필요한 REQ에만 넣고(11.2절), 시각 디자인·시각 디자인 판정 단계는 시각 디자인 문서를 처음 만들거나 바꾸는 REQ에만 함께 넣는다(5.5절).
- 대괄호 안의 단계는 `workflow:`에 늘 적고, EC 판단 결과에 따라 실행하거나 건너뛴다(2.1절 6항). 분류는 EC의 유무를 정하지 않는다.
- 설계 단계는 설계부가 맡는 EC 판단, EC 작성, 명세 단계를 묶어 부르는 말이다. 모든 분류의 원스톱 파이프라인은 설계 단계를 거치며, EC 판단 단계는 건너뛰지 않는다. 콘텐츠 안건도 같다.
- 핫픽스는 설계 단계를 포함한 정규 흐름의 예외다. REQ와 원스톱 파이프라인 없이 9절 「핫픽스 트랙」으로 처리한다.
- 인수 시험 단계는 Critical·Major에 늘 두고 Minor에는 두지 않는다(12절).
- 기본 모델 등급은 그 안건의 원스톱 파이프라인 모델 등급이다. 등급별 모델, 단계별 모델(REQ 작성 파이프라인과 최종 판정 포함), 기본값 밖 사용은 `Workflow/04_모델_운용` 「모델」을 따른다. 파트·역할별 값은 모델 매트릭스가 정하며, 이 표의 기본 모델 등급은 그 안건의 등급 기준이자 모델 매트릭스 「활성 때 정함」 칸의 값이다(`Workflow/04_모델_운용` 「단계별 모델」). Critical·Major를 중급으로 낮추는 경우와 그 조건은 `Workflow/04_모델_운용` 「기본값 밖 사용」 5항을 따른다.
- 분류에 따른 강화는 위 표의 단계 차이(명세 판정·인수 시험)와 기본 모델 등급으로 한다. Critical과 Major는 단계와 기본 모델 등급이 같으며, 더 필요한 강화(최고급 모델, `medium`보다 높은 effort)는 안건마다 REQ에 명시해 승인받는다(`Workflow/04_모델_운용` 「기본값 밖 사용」).
- 분류의 제안과 확정은 `Workflow/02_부서_구조_및_작업구역` 「비서실과 PM의 책무」, 근거 기재는 3절 1항 「분류 근거」, 확인은 3절 2항 ④를 따르며, 대표님이 REQ 승인 때 최종 결정한다.
- 이 절의 정의 기준·기본 모델 등급과 `Workflow/04_모델_운용` 1·2절은 `REQ-022` 커밋 뒤에 작성하는 REQ(새 버전 포함)부터 적용한다. 그 전에 작성한 REQ는 작성 때의 규정으로 진행한다.
- 모든 분류는 REQ 작성 파이프라인(REQ 판정 포함)을 거친다.
- 운영부·마케팅부의 지원 작업은 REQ `workflow:`가 정한 위치에 넣는다. 마케팅부의 시각 디자인 단계는 5.5절이 정한 위치에 넣는다.
- 단계는 번호가 아니라 단계명으로 부른다.

### 2.1 EC 적용 기준

EC의 정의, EC를 붙이는 기준, 설계부의 EC 판단과 그 기록·확인은 이 절이 원천이다. 이 표준에서 「EC가 있다」·「EC가 없다」(「EC가 있으면」, 「EC(있으면)」, 「EC가 있을 때」, 「EC가 없는 Critical·Major」 등)는 EC 파일의 존재가 아니라 최신 설계부 결과서 「EC 판단」 절의 판단(「EC 있음」·「EC 없음」)을 말한다. 8항에 따라 `draft`로 남은 EC는 뒤 단계의 입력과 판정의 대조 기준이 아니다.

1. **정의**: EC(Engineering Change)는 기존 설계나 코드를 변경할 때 변경점을 평가하는 항목이다. 무엇이 어떻게 바뀔지 설계부가 계획하고(EC 작성), 개발부가 수정하고(구현), 품질보증부가 결과를 평가한다(최종 판정). 품질보증부는 수정 전에 계획도 판정한다(EC 판정). 문서의 위치·서식은 `Workflow/07_문서_서식_및_번호` 「문서 체계」를 따른다.
2. **붙이는 경우**: 이미 승인되어 쓰이는 산출물(커밋된 표준·거버넌스 파일, 명세, 코드, 승인된 콘텐츠 포맷)의 동작·규칙·규격을 바꾸는 경우에만 붙인다. 기존 코드의 동작을 고치는 결함 수정도 여기에 든다.
3. **늘 붙이는 경우**: 거버넌스 파일(`AGENTS.md` 「불변 원칙」 3항의 목록)과 보안·권한 설정(예: 접근 권한 규칙, 인증·키의 보관과 사용 설정, 비밀정보 검출 규칙과 예외 목록)의 동작·규칙·설정을 바꾸는 변경에는 설계부 판단과 관계없이 늘 붙인다. 오탈자·표현 보완은 4항 ①대로 붙이지 않는다.
4. **붙이지 않는 경우**: ① 오탈자·표현 보완처럼 동작·규칙·규격을 바꾸지 않는 수정 ② 승인된 명세·포맷을 그대로 따르는 반복 작업(예: 승인된 콘텐츠 포맷에 따른 회차 제작) ③ 기존 산출물을 바꾸지 않는 신설(새 기능 파일, 포맷 신설). 한 안건에 2·3항의 변경과 이 항의 변경이 섞이면 EC를 붙인다.
5. **판단과 기록**: 설계부가 EC 판단 단계에서 REQ마다 판단한다. 시점은 REQ 승인 뒤이며, 실험 단계가 있으면 그 뒤다. 설계부는 판단(「EC 있음」·「EC 없음」), 해당하는 2~4항, 사유를 설계부 결과서(RPT)의 「EC 판단」 절(서식 `Workflow/templates/DEV_TEMPLATE.md` 8절)에 적는다. Minor이고 「EC 없음」이면 명세 산출물(PRD·TAD, 적용본)이 필요한지와 사유를 함께 적는다. 실험 단계가 있으면 실험 결과는 EC가 있으면 EC가, 없으면 설계부 결과서 「EC 판단」 절이 인용한다(11.2절 5항). 같은 안건에서 설계부 결과서의 다음 버전을 쓰면 설계부 결과서 「EC 판단」 절을 그대로 옮긴다(판단을 바꾸는 경우는 8항). 판단 결과로 REQ 새 버전을 작성하거나 재승인을 받지 않는다(REQ 작성 기준은 3절 1항 「EC 판단과 REQ」).
6. **판단에 따른 실행**: 오케스트레이터는 EC 판단 단계 뒤 최신 설계부 결과서의 「EC 판단」 절로 아래 단계의 실행 여부를 정한다(4절 2항).

   | 판단 | EC 작성·EC 판정 | 명세 | 명세 판정 |
   | :--- | :---: | :---: | :---: |
   | EC 있음 | 실행 | 실행 | 건너뜀 |
   | EC 없음(Critical·Major) | 건너뜀 | 실행 | 실행 |
   | EC 없음(Minor, 명세 산출물 필요) | 건너뜀 | 실행 | 해당 없음 |
   | EC 없음(Minor, 명세 산출물 불필요) | 건너뜀 | 건너뜀 | 해당 없음 |

7. **판단의 확인**: EC 판단 단계는 따로 판정하지 않는다. 「EC 있음」 판단은 EC 판정이 EC와 함께 확인한다(5절 표 「EC 판정」 행 ⑥). 「EC 없음」 판단은 그 뒤 첫 판정이 2~4항과 대조한다. Critical·Major는 명세 판정(5절 표 「명세 판정」 행 ⑦), Minor는 최종 판정(5절 최종 판정 기준 9)이다. 판단이 2~4항에 맞지 않으면 결함이며 반려 부서는 설계부다.
8. **판단이 바뀐 경우**: 7항의 결함을 고치려고 설계부가 판단을 바꾸면 설계부 결과서의 다음 버전 「EC 판단」 절에 바꾼 판단과 근거 판정서 경로를 적는다. 「EC 있음」으로 바뀌면 오케스트레이터는 `workflow:`의 EC 작성부터 순서대로 다시 실행한다. 「EC 없음」으로 바뀌면 EC는 `draft`로 두고 EC 판정 다음 단계부터 6항 표대로 실행한다. 그 EC는 이 절 첫 문단대로 뒤 단계의 입력이 아니다. 최종 판정에서 바뀐 경우 그 `fail`은 8절의 반려 누적에 든다.
9. **적용 시점**: `REQ-021` 커밋 뒤에 작성하는 REQ부터 적용한다. 그 전에 승인된 REQ는 승인 때의 규정으로 진행한다.

### 5.1 판정 지적의 구분과 문체 지적 처리

판정 지적의 구분 기준과 문체 지적의 처리는 이 절이 원천이다.

1. **구분 기준**: 판정자는 지적을 「결함」과 「문체」로 나눈다. 결함은 판정 기준에 어긋나거나 실행 실패·반려·오독을 일으킬 수 있는 지적(사실 오류, 모순, 누락, 지칭 불명확, 중의성 포함)이고, 문체는 그 밖의 표현 지적이다. 분류는 판정자가 정한다. `result`는 결함으로만 정하며, 문체 지적만 있으면 `pass`다.
2. **기재**: 판정서는 문체 지적마다 위치, 원문, 수정 문안, 대상 부서를 서식 `RES_TEMPLATE.md`의 「문체 지적」 절에 적는다.
3. **`pass` 판정서의 문체 지적**: 반영하지 않고 이월한다. 같은 문서의 다음 버전이 다른 사유로 생기면 그 버전에 함께 반영한다. 대표님이 승인 문구에 「문체 반영」을 덧붙이면 그 승인 때 반영한다(5항).
   - 「같은 문서의 다음 버전」은 파일명에 버전(`_vNN`)이 있는 기록 문서(REQ·EC·결과서)와 적용본 폴더의 다음 버전만 가리킨다. 버전 없이 고쳐 쓰는 원본(`AGENTS.md`, `Workflow/` 등)을 다른 안건이 개정하는 것은 다음 버전이 아니다. 그 안건이 커밋으로 끝나면 이월한 문체 지적은 반영하지 않고 종결한다.
   - 적용본 폴더의 다음 버전을 만들면 그 적용본의 반영 명령을 적은 결과서(RPT·DEV)도 다음 버전을 만들고 기계적 갱신을 함께 한다. 기계적 갱신은 적용본 폴더 경로가 들어간 적용본 경로와 반영 명령의 경로를 새 폴더로 바꾸고, 「원본과의 차이」 명령을 새 폴더로 다시 실행해 그 결과로 바꾸는 것이다.
4. **EC 판정·명세 판정·시각 디자인 판정 `pass`의 문체 지적**: 이월하고, 판정 대상 문서(EC, 명세 판정은 적용본 폴더와 결과서, 시각 디자인 판정은 시각 디자인 문서와 마케팅부 결과서. 시각 디자인 문서는 파일명에 버전이 없으므로 마케팅부 결과서의 다음 버전으로 판단한다)의 다음 버전이 다른 사유로 생기지 않으면 반영하지 않고 종결한다. 세 판정에는 대표님 승인이 없으므로 「문체 반영」이 적용되지 않는다.
5. **「문체 반영」 승인의 처리**
   1. **확인**: 대리 기재한 REQ 승인은 승인 기록의 「승인 문구 원문」으로, 대표님 본인이 기재한 REQ 승인은 승인 필드 줄 끝 주석 `# 문체 반영`으로, 최종 판정서 승인은 그 승인 기록으로 확인한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」). 어디에도 「문체 반영」이 없으면 「문체 반영」이 없는 승인으로 본다.
   2. **반영 대상**: 그 승인의 근거 판정서(REQ 승인은 최신 `RES-xxx-REQ`, 최종 판정서 승인은 그 `RES-xxx`)의 문체 지적이다.
   3. **반영 주체와 시점**: REQ 승인이면 원스톱 파이프라인 첫 단계 전에 PM이 REQ 새 버전(문체 반영본)을 작성한다. 최종 판정서 승인이면 비서실이 원스톱 실행 명령을 다시 실행하고, PM이 판정서에 적힌 대상 부서의 서브에이전트를 기동해 반영하게 한다. 대상이 적용본이면 그 부서가 적용본 폴더의 다음 버전과 결과서의 다음 버전(기계적 갱신 포함)을 만든다.
   4. **반영 범위**: 수정 문안 그대로만 고친다. 결과서에는 기계적 갱신만 더한다.
   5. **대조**: 품질보증부 서브에이전트가 변경이 수정 문안과 같은지만 대조하고, 대표님 재승인은 받지 않는다. 대조는 판정서 새 버전으로 발행한다. `gate:`는 대상 판정과 같고, 1절 「판정 차수」에 「문체 반영 대조」와 직전 판정서 경로를 적는다. 변경 전체가 직전 판정서의 수정 문안과 같으면 `pass`, 다르거나 수정 문안 밖 변경이 있으면 `fail`이다. 기계적 갱신은 수정 문안 밖 변경으로 보지 않는다. 대신 품질보증부 서브에이전트는 ① 직전 적용본 폴더와 새 폴더의 `git diff --no-index` 결과가 수정 문안과 같고 ② 새 결과서의 적용본 경로·반영 명령이 새 폴더를 가리키며 ③ 「원본과의 차이」 결과가 새 폴더로 다시 실행한 결과와 같은지 확인한다.
   6. **대조 `fail`**: 수정 문안과 다른 곳을 고친 새 버전으로 다시 대조한다. 수정 문안 밖 변경을 남기려면 현행대로 판정과 대표님 재승인을 받는다.
   7. **문체 반영본 REQ의 승인 필드**: `Workflow/07_문서_서식_및_번호` 「승인 기록」 7항대로 기재한다.
6. **`fail` 판정서의 문체 지적**: 결함을 고치는 같은 새 버전에 함께 반영한다. 수정 문안 그대로 반영한 곳은 결함 재판정 대상에서 빼고 수정 문안과 같은지만 대조한다. 수정 문안과 다르게 고친 곳은 변경분으로 재판정한다.

## 7. 중단 조건

오케스트레이터는 아래 경우에만 멈추고 상태·사유·필요한 결정을 보고한다.

1. scope 밖 변경이 필요한 경우
2. 판정이 `rejected`인 경우(REQ가 여러 뜻으로 읽히거나 요구가 서로 모순됨)
3. 최종 판정 반려 누적 3회(8절)
4. 거버넌스 적용본의 원본 반영이 필요한 경우. 파이프라인은 적용본 판정까지 마치고, 반영은 최종 판정서 승인 뒤 `Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」대로 한다
5. `ask` 목록 명령 또는 `allow` 목록 밖 명령의 권한 확인 요청이 생긴 경우(`Workflow/06_통제장치_및_배포` 「무인 실행 권한」). 다만 판정 세션 안에서 생긴 권한 확인 요청은 이 항의 멈춤 사유에 들지 않으며 5.2절을 따른다(멈추는 경우는 8항). 판정 세션 밖 서브에이전트에서 생긴 `allow` 목록 밖 명령의 권한 확인 요청도 5.4절 2항 끝 문장(확인 요청이 승인되어 실행함)이나 3항(대신함)에 해당하고 5.4절 5항의 자리에 적혔으면 이 항의 멈춤 사유에 들지 않는다. 5.4절 4항(대신하지 못함)에 해당하거나 5.4절 6항의 확인에서 멈춤에 해당하면 그 단계의 산출물을 받은 뒤 멈춘다
6. 판정서의 모델이 그 단계에 정해진 모델과 맞지 않는 판정서가 두 번 연속 나온 경우, 또는 PM이 세션을 그 단계에 정해진 모델·effort로 기동할 수 없는 경우(`Workflow/04_모델_운용` 「단계별 모델」)
7. REQ 판정·EC 판정·명세 판정·시각 디자인 판정의 재판정 한도(8절)를 넘긴 경우
8. 판정 세션이 판정에 필요한 명령을 실행하지 못하고 대신할 수단도 없어 판정서를 발행하지 않은 경우(5.2절 4항)
9. PM 세션의 모델·effort가 REQ 새 버전의 작성에 정해진 모델·effort(`Workflow/04_모델_운용` 「단계별 모델」)와 달라 REQ 새 버전을 작성하지 않은 경우
10. EC 판정·명세 판정·시각 디자인 판정·최종 판정의 판정서 결함 목록에 「구분」이 `Repair`인 결함이 있는 경우(5.3절 4항)
11. REQ 작성 때 저장할 REQ의 `scope:`가 진행 중인 안건과 겹치는 경우(3.1절 5·6항)
12. 원스톱 착수 때 실행 중인 다른 안건이 있거나, 끝난 안건과의 대조에서 겹침이나 변경이 나온 경우(4.1절 1·5항)
13. REQ 작성 때나 원스톱 착수 때 겹침·착수 판단 명령을 실행하지 못했거나 명령이 실패한 경우(3.1절 10항, 4.1절 9항)

멈출 때의 부적합 기록은 13절을 따른다. 멈춘 안건을 더 진행하지 않거나 다른 안건에 흡수할지는 대표님이 정하며, 정한 뒤의 기록은 `Workflow/07_문서_서식_및_번호` 「종결 기록」을 따른다.

## 8. 반려와 격상

- **재판정 한도**: REQ 판정, EC 판정, 명세 판정, 시각 디자인 판정은 최초 판정 뒤 재판정을 3회까지 한다. 세 번째 재판정도 `fail`이면 중단하고 보고한다. 재판정은 변경분만 판정한다. 5.1절의 문체 반영 대조는 재판정 횟수에 넣지 않는다.
  - **목적**: 재판정 한도는 무인으로 진행되는 동안 대표님께 빨리 보고하기 위한 장치다.
  - **초기화**: 오케스트레이터가 중단 조건(7절)으로 멈춰 보고하거나 대표님께 의결을 요청하고 대표님이 답하면, 그 뒤의 REQ 판정·EC 판정·명세 판정·시각 디자인 판정은 재판정 횟수를 새로 센다. 답을 받아 같은 세션에서 계속하는 경우와 `Workflow/05_인수인계_및_실행명령` 1절대로 같은 명령을 다시 실행하는 경우 모두 같다. 대표님 답 뒤 처음 하는 재판정이 1회다.
  - **기록**: 오케스트레이터는 그 재판정의 지시문에 횟수를 새로 센다는 사실과 직전 판정서 경로를 적는다(`Workflow/04_모델_운용` 「타깃 컨텍스트 규칙」 3항). 품질보증부 서브에이전트는 판정서 1절 「판정 차수」에 「재판정 1차(대표님 답 뒤 다시 셈, 직전 판정서 <경로>)」 형태로 적는다. 횟수는 판정서의 「판정 차수」로 판단한다.
  - **적용 제외**: 최종 판정 반려 누적 3회는 격상을 판단하는 장치이므로 초기화하지 않는다. ORDER 변경으로 생긴 REQ 새 버전은 최초 판정부터 다시 센다.
- EC 판정 `fail`: 설계부가 EC 새 버전을 작성하고 다시 판정한다. 격상 횟수에 넣지 않는다.
- 명세 판정 `fail`: 설계부가 명세 산출물의 다음 버전(적용본 폴더와 결과서)을 만들고 변경분을 다시 판정한다. 격상 횟수에 넣지 않는다.
- 시각 디자인 판정 `fail`: 마케팅부가 시각 디자인 문서를 고치고 마케팅부 결과서의 다음 버전을 작성한 뒤 변경분을 다시 판정한다. 격상 횟수에 넣지 않는다.
- 최종 판정 `fail`: 판정서에 적힌 반려 부서가 고친 뒤 판정서 새 버전으로 변경분을 다시 판정한다.
- 판정서 결함 목록에 `Repair` 결함이 있으면 위의 EC 판정·명세 판정·시각 디자인 판정·최종 판정 `fail` 항목 대신 5.3절 4항을 따른다. 그 최종 판정 `fail`도 반려 누적에 든다.
- 최종 판정 `fail` 누적 3회: 중단하고 보고한다. 대표님은 아래 가운데 하나를 정한다. ① Minor를 Major로 격상(기본 모델 등급이 중급에서 고급으로 바뀌고, 명세 판정(EC가 없을 때)과 인수 시험이 붙는다. 격상한 안건은 모델 매트릭스의 「중급(시범)」 칸과 CEO 설정의 하향과 관계없이 모든 파트를 고급 이상으로 실행한다. PM은 REQ 2절 「분류 근거」에 이 격상이 적혀 있으면 유효 값 명령에 `--escalated`를 준다. `Workflow/04_모델_운용` 「단계별 모델」 6항 ③) ② 분류는 그대로 두고 최고급 모델이나 `high` 이상의 effort를 승인(`Workflow/04_모델_운용` 「기본값 밖 사용」) ③ 그 밖의 처리(범위 분할, 중단 등). ①·②는 PM이 REQ 새 버전을 작성하고(작성 모델과, PM 세션의 모델·effort가 그와 다를 때의 처리는 `Workflow/04_모델_운용` 「단계별 모델」), REQ 판정과 대표님 재승인을 거쳐 원스톱 파이프라인을 처음부터 다시 실행한다. Major에서 Critical로의 격상은 두지 않는다. 두 분류는 단계와 기본 모델 등급이 같아 격상해도 강화되는 것이 없기 때문이다.

### 1.2 단계별 모델

세션마다 쓰는 모델 등급과 effort는 모델 매트릭스(`Workflow/data/model_matrix.json`)의 칸에서 구한 유효 값이다. 칸의 값은 그 데이터 파일이 원천이며 이 문서에 다시 적지 않는다. 칸의 형식, 값의 뜻, 유효 값을 구하는 규칙은 이 절이 원천이다.

1. **칸**: 칸은 (파트, 역할) 하나이며, 분류 키(`Critical`·`Major`·`Minor`와 필요하면 `분류 없음`)마다 모델 등급과 effort를 둔다. 칸의 목록은 프로세스 맵(`Workflow/03_라이프사이클` 「프로세스 맵」)에서 파트마다 맡는 (파트, 역할) 묶음과 같다. 파트는 `Workflow/02_부서_구조_및_작업구역` 「조직 표」의 코드다.
2. **역할**: 역할은 파트가 공정에서 맡는 일의 종류이며 세 가지다.
   - 작성: 산출물(ORDER, REQ, EC, 결과서, 명세, 적용본, 코드, 인수 시험, HOTFIX, 보고·조사 자료)을 만드는 일.
   - 판정: 판정서를 내는 일(`AGENTS.md` 「불변 원칙」 4항). 판정 파트가 판정과 함께 쓰는 부적합 기록은 같은 세션의 일이므로 판정 칸을 따른다.
   - 기록: 진행과 사건을 남기거나 반영하는 일(파이프라인 지휘와 실행 기록, 판정 없이 멈춘 중단의 부적합 기록, 반영·커밋, 형상 현황 집계).
3. **형식**: 최상위 키는 `cells` 하나다. 칸 하나는 `{ "part", "role", "effort_means", "Critical", "Major", "Minor" }`이며, 그 (파트, 역할)이 든 모든 단계(파트가 여럿인 단계는 그 파트마다)의 `classes` 합집합(이하 「분류 집합」)에 `분류 없음`이 있으면 `"분류 없음"` 키를 더하고, 없으면 두지 않는다. 분류 키의 값은 `{ "model", "effort" }`다. 분류 집합에 든 분류의 값은 「해당 없음」이 아니고, 분류 집합에 들지 않은 `Critical`·`Major`·`Minor`의 값은 `model`·`effort` 모두 「해당 없음」이다.
   - `model`: 「고급」, 「중급」, 「중급(시범)」, 「제한 없음」, 「활성 때 정함」, 「해당 없음」 가운데 하나. 등급의 모델 ID는 1.1절 표에서 읽으며 매트릭스에 적지 않는다.
   - `effort`: 2절의 허용 값, 「정하지 않음」, 「해당 없음」 가운데 하나.
   - `effort_means`: 「호출 인자」(서브에이전트가 맡는 파트. `Agent` 호출 인자 `effort`로 준다), 「실행 단위」(PM팀 P01·P02와 핫픽스팀 V03처럼 실행 명령의 `--effort`로만 정해지는 메인 세션 파트), 「정하지 않음」(비서실 세션 파트) 가운데 하나(2절).
4. **값의 읽는 법**
   - 「제한 없음」·「정하지 않음」: 비서실 세션 파트(비서팀 S01~S03, 형상통제팀 C01~C03)의 값이다. 모델과 effort를 정하지 않으며, 실제 실행 모델은 비서실 세션이 쓰는 기록의 머리말이나 작성 정보에 적는다(4절). 비서실 세션은 고급을 권고한다.
   - 「중급(시범)」: 시범(1.4절 5항)을 시작하기 전에는 고급으로 읽는다.
   - 「활성 때 정함」: 대기 파트의 값이며, 그 파트를 활성으로 바꾸는 안건이 값을 정한다. 그 전에 실행되면 그 분류의 기본 모델 등급(`Workflow/03_라이프사이클` 「분류별 단계」)으로 읽는다.
   - 「해당 없음」: 그 파트가 그 분류로 실행되지 않는 칸이다. 값을 쓰지 않는다.
   - 핫픽스팀(V03): 핫픽스에는 분류가 없으므로 「분류 없음」 키 하나에 값을 둔다. 핫픽스는 독립 판정 대신 대표님 사후 확인을 받는다(`Workflow/03_라이프사이클` 「핫픽스 트랙」 3항).
5. **분류**: 유효 값을 구할 때 쓰는 분류는 원스톱 실행 명령은 REQ `classification:`, REQ 새 버전 명령은 대상 REQ의 `classification:`, REQ 작성 명령은 ORDER `classification_proposal`, 핫픽스 실행 명령은 「분류 없음」이다.
6. **유효 값**: 칸과 분류마다 아래 순서로 정한다.
   - ① 모델 매트릭스의 값에 4항의 읽는 법을 적용한다.
   - ② CEO 설정 파일(1.4절)에 그 칸과 분류가 있으면 그 값으로 바꾼다. 파일이 없거나 `cells`가 빈 목록이면 ①을 쓴다.
   - ③ Minor에서 격상한 안건(`Workflow/03_라이프사이클` 「반려와 격상」 ①)이면 ①②의 결과가 고급 아래인 칸을 고급으로 올린다.
   - ④ REQ 「결정」 열이 그 안건에 모델·effort를 승인했으면(1.3절) 그 안건의 원스톱 파이프라인 세션에 그 값을 쓴다. 최종 판정(Q05)은 승인 모델이 최고급일 때만 그 모델, 승인 effort가 `high`·`xhigh`·`max`일 때만 그 effort를 쓰고, 그 밖에는 ①~③의 값을 쓴다. REQ 작성 파이프라인(P01·Q01)에는 쓰지 않는다.
   - 유효 값은 `resolve_model.py`(`Workflow/06_통제장치_및_배포` 「준비·판단 명령」)로 구한다. 명령이 실패하면 세션을 기동하지 않고 보고한다.
7. **적용 시점**: PM 세션은 시작할 때 유효 값을 구하고 그 실행이 끝날 때까지 그 값을 쓴다. 이미 실행 중인 세션과 그 세션이 띄우는 서브에이전트는 기동 때의 값으로 실행한다(1.1절 「갱신」 ②와 같은 방식). 핫픽스 실행 명령과 형상통제 절차도 같다.

- **`workflow:` 밖 세션**: `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」 5항의 문체 반영 대조는 대상 판정과 같은 모델·effort로 실행한다. `workflow:` 밖에서 실행하는 그 밖의 세션(최종 판정서 승인의 문체 반영, 인수 시험 수정, 중단 때 부적합 기록)은 그 일을 맡는 파트의 유효 값으로 실행한다.
- **REQ 새 버전**: PM이 작성하는 REQ의 모든 새 버전은 작성 사유와 관계없이 P01 칸의 유효 값(분류는 5항)으로 작성한다. 사유에는 REQ 판정 `fail`(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 3항), 진행 중인 안건의 요구 변경(같은 문서 「진행 중 변경과 파생 안건」), 실험 단계 추가(같은 문서 「실험 단계」 7항), 「문체 반영」 승인의 문체 반영본(같은 문서 「판정 지적의 구분과 문체 지적 처리」 5항), 최종 판정 반려 누적 뒤의 격상과 모델·effort 승인(같은 문서 「반려와 격상」), 승인 필드 기재 뒤의 결정 변경(`Workflow/07_문서_서식_및_번호` 「승인 기록」 6항)이 모두 든다. 그 REQ 판정은 Q01 칸, 문체 반영본의 대조는 대상 판정과 같은 칸의 유효 값을 따른다. PM은 REQ 새 버전을 작성하기 전에 자기 실행 모델(세션 시스템 정보)과 effort(실행 명령 지시문의 effort 표기)가 P01 칸의 유효 값과 같은지 확인한다. 같으면 그 세션에서 작성한다. 다르면 작성하지 않고 `Workflow/03_라이프사이클` 「중단 조건」 9항으로 멈추며, 보고의 「대표님이 할 일」에 REQ 새 버전 명령(`Workflow/05_인수인계_및_실행명령` 「실행 명령」)으로 PM을 다시 기동해야 한다는 사실, 대상 REQ 경로, 근거 파일(그 종류는 `Workflow/05_인수인계_및_실행명령` 「실행 명령」의 REQ 새 버전 명령 항목을 따른다)을 적는다.
- **PM의 책임**: PM은 유효 값으로 세션을 기동한다.
  - ① 실행 명령(`Workflow/05_인수인계_및_실행명령` 「실행 명령」)의 `--model`과 `--effort`로 PM 세션의 모델과 effort를 정한다. PM은 시작할 때 `resolve_model.py`로 자기 파트(원스톱 실행 명령은 P02, REQ 작성 명령과 REQ 새 버전 명령은 P01)의 유효 값을 구하고, 자기 실행 모델(세션 시스템 정보)과 지시문의 effort 표기가 그 값과 같은지 확인한다. 다르거나 명령이 실패하면 시작하지 않고 보고한다.
  - ② 서브에이전트가 맡는 파트의 유효 모델이 PM 모델과 같으면 `Agent` 호출 인자 `model`을 주지 않고 정의 파일의 `model: inherit`로 이어받게 한다.
  - ③ 다르면 `Agent` 호출 인자 `model`에 1.1절 표의 모델 ID(PM이 시작할 때 읽은 값. 1.1절 「갱신」. 최고급은 REQ나 CEO 설정에 적은 모델 ID)를 준다. 호출이 모델 ID를 받지 않으면 같은 계열의 별칭(예: `opus`)을 주고 PM 실행 기록 「사건」 칸에 적는다.
  - ④ 서브에이전트가 맡는 파트의 유효 effort가 PM 세션 effort와 같으면 호출 인자 `effort`를 주지 않고, 다르면 호출 인자 `effort`에 그 값을 준다(2절). 지시문의 effort 표기(3절 1항)는 그 서브에이전트의 유효 effort로 적는다.
  - ⑤ 유효 값으로 세션을 기동할 수 없으면 그 세션을 기동하지 않고 `Workflow/03_라이프사이클` 「중단 조건」 6항으로 멈춘다.
  - ⑥ `--model`과 호출 인자에는 별칭이 아닌 모델 ID를 쓴다(③의 별칭 대신 예외는 제외).
- **핫픽스 실행 명령**: 핫픽스 실행 명령을 실행하는 비서실 세션은 `--model`과 `--effort`를 V03 칸 「분류 없음」의 유효 값으로 적는다(`resolve_model.py --hotfix`). 모델 ID는 1.1절 표의 값이다.
- **서브에이전트 정의**: 서브에이전트 정의 파일(`.claude/agents/*.md`. 부서 정의와 파트 카드)은 머리말에 `model: inherit`를 적고 모델 이름과 `effort`를 적지 않는다. 파트 카드는 머리말에 `omitClaudeMd: true`를 더한다(5절 5항).
- **판정서 모델 대조**: PM은 두 파이프라인에서 판정서를 받으면 머리말 `auditor.model`을 그 판정 파트의 유효 모델(판정 지시문에 넣은 유효 값 표. 3절 1항)과 대조하고, 다르면 무효로 보고 판정을 다시 실행한다. 대조는 모델 이름이나 모델 ID로 하며, 1.1절 「갱신」의 대조 기준(이전 ID 허용)을 따른다. 판정서를 작성할 수 있는 주체는 `AGENTS.md` 「불변 원칙」 4항을 따른다.

### 1.3 기본값 밖 사용

1. **대상**: ① 최고급 모델 ② 유효 값의 기본값(모델 매트릭스)보다 높은 등급(예: Minor 안건 전체를 고급으로) ③ `medium` 밖의 effort(`low` 포함).
2. **명시와 승인**: 아래 두 가지 가운데 하나로만 쓴다. 명시하지 않거나 승인하지 않으면 기본값을 쓴다.
   - REQ 「결정」 열: PM이 REQ 「결정 사항 및 선택지」 표에 정할 일로 적고 대표님 승인을 받는다.
   - CEO 설정의 「저장」: 저장된 CEO 설정 파일이 그 칸의 승인이다(1.4절, `Workflow/07_문서_서식_및_번호` 「승인 기록」 10항).
3. **최고급**: 모든 분류에서 쓸 수 있다. 최고급에는 기본 모델이 없으므로 명시할 때 모델 이름과 모델 ID를 늘 적는다. 1.1절 「실행 도구의 모델 제한」 안의 모델만 적을 수 있다.
4. **적용 범위**: REQ 「결정」 열이 승인한 모델·effort는 그 안건의 원스톱 파이프라인 전체에 쓰고, 최종 판정은 1.2절 6항 ④를 따른다. CEO 설정이 승인한 값은 저장된 칸에, 다음 실행부터 「새로고침(기본값으로)」 전까지 쓴다(1.4절).
5. **낮추지 않음**: Critical·Major를 중급으로 낮추는 것은 모델 매트릭스 「중급(시범)」 칸의 시범과 CEO 설정으로만 하며, REQ 「결정」 열로는 낮추지 않는다. 판정 파트나 Critical 안건의 칸을 고급 아래로 두는 CEO 설정은 확인 창을 거친 것만 유효하다(1.4절 4항).

### 1.4 CEO 설정

CEO 설정 파일의 형식과 효력, 세 버튼(「저장」, 「새로고침(기본값으로)」, 「기록」)이 따르는 규정, 하향 확인, 시범은 이 절이 원천이다. 대시보드의 화면과 세 버튼의 동작은 대시보드를 만드는 안건이 만들고 이 절과 대조한다. 저장된 CEO 설정 파일과 「기록」 승인 기록을 승인 기록으로 보는 규정은 `Workflow/07_문서_서식_및_번호` 「승인 기록」 10항, 「기록」의 수정·커밋 절차는 같은 문서 「개정 이력과 리비전 태그」의 「모델 ID 갱신의 예외」가 원천이다.

1. **파일**: `CEO/settings/model_settings.json`(UTF-8). 대표님 구역이므로 대표님 조작으로 대시보드가 쓰고, AI는 읽기만 한다. 형식은 `{ "saved_at": "YYYY-MM-DDTHH:MM:SS+09:00", "cells": [ { "part", "role", "class", "model", "model_id", "effort", "downgrade_confirmed_at" } ] }`다.
   - `class`: `Critical`·`Major`·`Minor`·`분류 없음` 가운데 하나.
   - `model`: 「최고급」·「고급」·「중급」 가운데 하나. 「최고급」이면 `model_id`(1.1절 「실행 도구의 모델 제한」 안의 모델 ID)가 있어야 한다. 최고급에는 기본 모델이 없기 때문이다.
   - `model`과 `effort`는 둘 가운데 하나만 있어도 되며, 없는 쪽은 모델 매트릭스의 값을 쓴다.
   - `downgrade_confirmed_at`: 판정 역할의 칸이나 `Critical` 칸을 고급 아래(중급)로 두는 설정에만 필요하며, 대시보드가 확인 창에서 대표님이 확인한 시각을 적는다(4항).
   - 쓸 수 없는 칸: 비서실 세션 파트(「제한 없음」)와 「해당 없음」 칸. 설정이 있어도 쓰지 않는다.
2. **효력**: CEO 설정 파일이 있으면 다음 실행부터 모델 매트릭스의 값 위에 덮어 적용한다(1.2절 6항 ②). 파일이 없거나 `cells`가 빈 목록이면 모델 매트릭스의 기본값을 쓴다. 이미 실행 중인 세션에는 적용하지 않는다(1.2절 7항). 대시보드가 생기기 전에는 CEO 설정 파일이 없으므로 기본값만 쓴다.
3. **세 버튼**
   - 「저장」: 대시보드가 CEO 설정 파일에 바뀐 칸만 쓰고 `saved_at`을 적는다. 저장된 파일은 그 칸의 「기본값 밖 사용」 승인(1.3절 2항)이며, 별도 승인 기록을 남기지 않는다. 「새로고침(기본값으로)」을 누를 때까지 유효하다.
   - 「새로고침(기본값으로)」: CEO 설정 파일의 `cells`를 빈 목록으로 하고 `saved_at`을 적는다. 다음 실행부터 기본값으로 돌아간다.
   - 「기록」: CEO 설정 값을 모델 매트릭스의 기본값으로 올린다. 대시보드가 「기록」 승인 기록을 쓰고, 모델 매트릭스의 그 칸을 CEO 설정 값으로 고치며, CEO 설정 파일에서 그 칸을 뺀다. 이 수정은 대표님이 직접 고친 것으로 보며 판정 파이프라인을 거치지 않는다. 승인 기록의 형식은 `Workflow/07_문서_서식_및_번호` 「승인 기록」 10항, 수정과 커밋의 절차는 같은 문서 「모델 ID 갱신의 예외」를 따른다.
   - REQ로 모델 매트릭스의 기본값을 바꿀 때는 지금처럼 적용본으로 고친다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」).
4. **하향 확인**: 판정 역할의 칸이나 `Critical` 칸을 고급 아래로 두는 설정은 대시보드의 확인 창을 거쳐 `downgrade_confirmed_at`을 적은 것만 유효하다. 확인 없이 저장된 하향 칸이 있으면 `resolve_model.py`가 실패하고 세션을 기동하지 않는다(1.2절 6항). 하향 확인을 거친 칸으로 실행한 판정은 판정서 9절에 그 칸과 확인 시각을 적는다(4절). 그 밖의 칸(판정 역할이 아닌 Major·Minor 칸 등)을 낮추는 설정은 「저장」이 승인이며 확인 창을 요구하지 않는다.
5. **시범**: 모델 매트릭스의 「중급(시범)」 칸은 v05 전환 뒤 시범부터 적용하며, 그 전에는 고급으로 실행한다(1.2절 4항). 시범은 대표님이 CEO 설정으로 그 칸을 중급으로 「저장」해 시작하고 「새로고침(기본값으로)」으로 끝낸다. 시범 결과로 기본값을 중급으로 정하려면 「기록」이나 REQ로 모델 매트릭스를 고친다. 시범의 대상 안건 수와 비교 방법은 대표님이 정한다. Minor에서 격상한 안건은 「중급(시범)」 칸과 CEO 설정의 하향과 관계없이 모든 파트를 고급 이상으로 실행한다(1.2절 6항 ③).
6. **실행 명령과의 관계**: 비서실 세션은 PM 기동과 핫픽스팀 기동 전에 유효 값을 구해 실행 명령에 적는다(`Workflow/05_인수인계_및_실행명령` 「실행 명령」). PM은 시작할 때 자기 파트의 유효 값과 대조한다(1.2절 「PM의 책임」 ①).

<!-- 원천: Workflow/04_모델_운용.md 「effort」 -->
## 2. effort

- 기본값은 `medium`이며 모델 등급과 관계없다.
- `medium` 밖의 값(`low` 포함)은 1.3절대로 REQ 「결정」 열이나 CEO 설정으로 승인받을 때만 쓴다.
- 허용 값은 `low`, `medium`, `high`, `xhigh`, `max`이다.
- **파트별 effort**: PM 세션은 실행 명령의 `--effort`로 실행하고, 서브에이전트는 그 파트의 유효 effort로 실행한다. 유효 effort가 PM 세션 effort와 같으면 `Agent` 호출 인자 `effort`를 주지 않고 세션 effort를 이어받게 하며(실측 근거 `Departments/Development/Implementation/results/DEV-033_v01.md` 6절 ③. 세션 effort `medium`에서 확인), 다르면 호출 인자 `effort`를 준다. 메인 세션 파트(모델 매트릭스 `effort_means` 「실행 단위」: P01·P02·V03)는 파트별 effort가 따로 동작하지 않으므로 실행 명령의 `--effort`만 쓴다. 비서실 세션 파트는 effort를 정하지 않는다.
- 서브에이전트 정의 파일에 `effort`를 적지 않는다. 정의 파일의 `effort`는 호출마다 다른 값을 줄 수 없고 모델 매트릭스와 어긋날 수 있기 때문이다.
- 실행 환경에 `CLAUDE_CODE_EFFORT_LEVEL` 환경 변수가 있으면 그 값이 호출 인자보다 앞서므로 파트별 effort가 모두 무력화된다(같은 결과서 6절 ②). 세션 effort와 다른 값을 호출 인자로 준 서브에이전트가 실제로 그 effort로 실행되는지는 확인하지 못했다(`Workflow/06_통제장치_및_배포` 「알려진 과제」 5행). 실제 사용 effort는 판정서 9절과 각 문서 머리말에 남긴다(4절).

<!-- 원천: Workflow/04_모델_운용.md 「타깃 컨텍스트 규칙」 -->
## 3. 타깃 컨텍스트 규칙

1. **지시문**: 서브에이전트 지시문에는 REQ 경로, EC 경로(EC가 있을 때. `Workflow/03_라이프사이클` 「EC 적용 기준」 첫 문단), 대상 파일 경로, 단계명, effort 표기(`effort: <값>`. 실행 명령의 effort 표기이며, 호출 인자 `effort`를 주면 그 값. `Workflow/05_인수인계_및_실행명령` 「실행 명령」)만 넣고 매뉴얼 본문을 붙이지 않는다. 판정 단계의 지시문에는 그 안건 분류의 유효 값 표(`resolve_model.py` 출력 원문. CEO 설정 `saved_at`과, 격상이나 「결정」 열의 승인이 있으면 그 옵션으로 구한 결과 포함)를 더한다. 판정자가 판정서 9절에 옮겨 적고 최종 판정 기준 10의 대조에 쓰기 때문이다.
2. **매뉴얼 읽기**: 매뉴얼은 필요한 절만 찾아 읽는다. 각 매뉴얼 첫머리의 「이 문서가 정하는 것」으로 읽을 문서를 고른다. 파트 카드로 기동한 서브에이전트는 카드에 실린 지침을 따르고, 카드 끝 「필요할 때 읽는 문서」의 문서와 절은 필요할 때 찾아 읽는다(5절 5항).
3. **재판정 지시문**: 재판정 지시문에는 직전 판정서의 결함 표와 문체 지적 표, 반려 부서 결과서의 수정 목록, 변경분, 대표님 답 뒤 재판정 횟수를 새로 세는 재판정이면 그 사실과 직전 판정서 경로(`Workflow/03_라이프사이클` 「재판정 한도」)만 넣는다. 변경분은 기록 문서 새 버전(REQ·EC 등)은 `git diff --no-index <직전 버전> <새 버전>`, 거버넌스 적용본은 `git diff --no-index <직전 판정 대상 적용본 폴더> <새 적용본 폴더>`, 추적 중인 그 밖의 파일은 `git diff HEAD -- <경로>`로 구한다. 적용본 폴더는 판정 지적을 반영할 때마다 버전을 올리므로(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」 4항) 두 적용본 폴더는 `REQ-xxx_적용본_v01`과 `_v02`처럼 이웃한 버전이다. 새 파일은 `git status --porcelain -uall`로 찾아 전문을 넣는다. 단, 직전 버전이 있는 기록 문서 새 버전과 거버넌스 적용본은 위의 `--no-index` 비교로 변경분을 구하므로 전문을 넣지 않는다. `git diff HEAD`는 마지막 커밋 이후의 누적 차이이므로 직전 판정 이후의 변경은 수정 목록으로 특정한다. 문체 반영 대조(`Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」)의 지시문도 같은 구성(직전 판정서의 문체 지적 표, 변경분)으로 만든다.
4. **작성 과정의 차단**: 작성 과정의 대화 내용은 판정 세션에 넘기지 않는다.
5. **인계 패킷**: 작성 단계는 다음 작성 단계에 인계 패킷(서식 `Workflow/templates/DEV_TEMPLATE.md` 11절. 받는 단계, 읽을 문서 표, 핵심 요약)을 결과서에 적어 넘긴다. 넘기는 단계는 실험(X01) → EC 판단(E01), EC 판단(E01) → EC 작성(E02)이나 명세(E03·E04), 명세(E03·E04) → 구현(V01·V02)이다. EC 작성은 EC가 인계 문서이므로 패킷을 두지 않는다. PM은 받는 단계의 지시문 「대상 파일 경로」에 그 결과서 경로를 넣는다(1항 안에서 넘긴다). 받는 단계는 패킷의 목록부터 읽되, 패킷이 REQ·EC 등 원천 문서를 대신하지 않는다. 판정 단계와 인수 시험 단계에는 패킷을 넘기지 않는다. 작성 과정의 요약이 독립 판정과 독립 시험 작성에 섞이지 않게 하기 위해서다(4항, `AGENTS.md` 「불변 원칙」 4항).

## 5. 계층형 지침

계층형 지침의 계층과 예산, 원천과 생성물의 관계, 계층 구성표의 형식, 안전장치 핵심과 표준 공통 핵심, 세션별 구성은 이 절이 원천이다. 생성 명령과 형상통제 대조의 동작은 `Workflow/06_통제장치_및_배포` 「생성·반영 명령」·「형상통제 대조」, 형상통제팀의 대조·재생성·기준선 절차는 `Workflow/05_인수인계_및_실행명령` 「형상통제 절차」를 따른다.

1. **계층과 예산**: 계층은 「전역 공통 → 표준 공통 → 부 → 팀 → 파트」 다섯 가지이며, 위 계층일수록 얇게 둔다. 부·팀 계층에는 그 아래 모든 파트(대기 파트 포함)에 적용되는 규정만 두고, 한 파트에만 적용되는 규정은 파트 계층에 둔다. 계층마다 본문 글자 수의 상한을 계층 구성표 `budgets`에 둔다(전역 1,000자, 표준 1,000자, 부 500자, 팀 2,000자, 파트 1,500자). 본문 글자 수는 선택자로 옮긴 원천 글자의 Python `len()` 합이며 생성물의 머리 줄·출처 줄·`refs` 목록은 넣지 않는다. 「전역」 상한은 안전장치 핵심에 쓴다. 상한을 넘어도 커밋을 막지 않으며, 형상통제 대조가 「예산 초과」로 출력하고 기준선 기록에 남긴다.
2. **원천과 생성물**: 규정 문장의 원천은 각 매뉴얼 절과 `AGENTS.md` 절이다. 생성물(안전장치 핵심 `.claude/guides/core/safety.md`, 표준 공통 핵심 `.claude/guides/core/standard.md`, 부·팀·파트 지침 `.claude/guides/depts/<부 폴더>.md`·`.claude/guides/teams/<팀 폴더>.md`·`.claude/guides/parts/<코드>.md`, 파트 카드 `.claude/agents/part-<코드 소문자>.md`)은 계층 구성표가 고른 원천 글자를 그대로 옮긴 것이며 규정의 원천이 아니다. 생성물과 원천이 어긋나면 원천을 따른다.
   - 생성물은 손으로 고치지 않고 생성 명령으로만 만든다. 원천(계층 구성표, 구성표가 고른 원천 절, `Workflow/02_부서_구조_및_작업구역` 「조직 표」, 프로세스 맵)을 바꾸는 안건은 같은 안건의 구현 단계에서 생성물 적용본을 함께 만든다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」). 원천이 저장소 밖 전역 지침 원본이면 형상통제팀(C01)이 다시 생성해 반영한다(`Workflow/05_인수인계_및_실행명령` 「형상통제 절차」).
   - 부·팀 지침은 그 계층만 담고, 파트 지침은 그 파트의 부 → 팀 → 파트 계층을 차례로 담는다. 부·팀·파트 지침은 모든 파트(활성·대기)에 만들고, 파트 카드는 서브에이전트 파트에만 만든다.
   - 생성물 폴더 이름에는 Claude Code가 자동으로 읽는 이름(`rules`, `commands`, `skills` 등)을 쓰지 않는다. 계층 밖 지침이 자동으로 실리는 것을 막기 위해서다.
3. **계층 구성표**: `Workflow/data/guide_layers.json`(UTF-8, BOM 없음) 하나에 JSON으로 둔다. 구성표는 규정의 배치를 정하는 설계 판단이므로 그 배치를 바꾸는 안건의 설계 적용본으로 고친다. Markdown이 아니므로 개정 이력 표와 리비전 태그를 두지 않고, 고친 안건은 이 문서 개정 이력 행에 적는다(`Workflow/07_문서_서식_및_번호` 「개정 이력과 리비전 태그」).
   - 최상위 키: `budgets`, `standard`, `depts`, `teams`, `parts`, `excluded_sections` 여섯 가지다. `standard`는 선택자 목록이다. `depts`·`teams`·`parts`는 `{ "<이름 또는 코드>": { "select": [선택자], "refs": [참조] } }`이며, 부·팀 이름은 「조직 표」의 「부」·「팀」 열 글자, 파트는 코드다. `parts`의 항목에는 `"card": true|false`를 두고 서브에이전트 파트만 `true`로 한다. 부·팀·파트의 소속과 카드 설명은 「조직 표」에서 읽고 구성표에 적지 않는다.
   - **선택자**: `{ "doc": "<저장소 루트 기준 경로>", "section": "<제목>" }`이며, 아래 둘 가운데 하나를 더할 수 있다. `section`은 그 문서 H2·H3·H4 제목에서 앞 번호와 리비전 태그를 뗀 글자이며, 같은 제목이 한 문서에 둘 이상이면 오류다.
     - `"items": ["<항목 표제>", …]`: 그 절 자신의 본문 안 맨 앞 단계 번호 항목·목록 항목 가운데 표제가 같은 것(하위 줄 포함)만 고른다. 표제는 항목 첫머리의 굵은 글자(`**…**`) 안의 글자이고, 굵은 글자가 없으면 표시 기호 뒤 첫 30자다. 번호가 아니라 표제로 고르는 이유는 항목이 끼어들거나 번호가 바뀌어도 다른 항목을 조용히 고르지 않게 하기 위해서다.
     - `"rows": ["<첫 칸 글자>", …]`: 그 절 자신의 본문 안 표 가운데 첫 칸 글자가 같은 행만 고른다. 표 머리 줄과 구분 줄을 함께 옮긴다.
   - **덮는 범위**: 선택자 사이, 선택자와 절·전수 대응표 원천 사이의 관계는 이 정의만 쓴다. 「절 S의 줄」은 S의 제목 줄부터 다음 같은 단계 이하 제목 줄 앞까지이고(하위 절 포함), 「절 S 자신의 본문」은 S의 제목 줄 다음부터 S의 첫 하위 제목 줄 앞까지다. 절 선택자(`items`·`rows` 없음)는 절 S의 줄 전체를 덮고, `items`·`rows` 선택자는 절 S 자신의 본문 안의 고른 항목·행만 덮는다. 하위 절의 항목·행은 `items`·`rows`의 대상이 아니며, 절 S 자신의 본문에 그 표제의 항목이나 그 첫 칸의 행이 없으면 오류다. 「A가 B를 포함한다」는 A가 덮는 범위가 B가 덮는 범위(B가 절이면 그 절의 줄 전체)를 모두 담는다는 뜻이고, 「A와 B가 겹친다」는 둘의 덮는 범위에 공통 줄이 하나라도 있다는 뜻이다.
   - **`refs`**: `{doc[, section]}` 목록이다. 파트 지침과 파트 카드 끝 「필요할 때 읽는 문서」에 경로와 절 제목만 적는다. 규정을 싣는 것이 아니므로 전수 대응표 「실리는 곳」 검사에서 실린 것으로 보지 않는다.
   - **`excluded_sections`**: 생성물에 실으면 안 되는 절 `{doc, section}` 목록이다. 개정 이력 절, `Workflow/02_부서_구조_및_작업구역` 「옛 이름과 새 이름의 대응」, 이 문서 「모델 등급과 기본 모델」을 넣는다. 「모델 등급과 기본 모델」은 대표님이 「모델 ID 갱신의 예외」로 직접 고치는 표가 있어, 넣으면 그 수정마다 생성물이 어긋나기 때문이다. 선택자의 덮는 범위가 제외 절의 줄과 한 줄이라도 겹치면 오류다(제외 절을 하위 절로 품는 상위 절 전체를 고르는 것 포함).
   - **배치 규칙**: ① 표준 공통은 4항의 선택자만 둔다. ② 부·팀 계층은 1항의 범위만 둔다. ③ 한 파트의 사슬(표준 공통 → 부 → 팀 → 파트) 안의 어느 두 선택자도 덮는 범위가 겹치면 안 된다(중복). 같은 절을 두 번 고르는 것, 절 전체와 그 절의 항목·행을 함께 고르는 것, 상위 절 전체와 그 하위 절(이나 하위 절의 항목·행)을 함께 고르는 것이 모두 중복이다. ④ 프로세스 맵에서 그 파트가 든 모든 단계의 `reads` 가운데 절 S를 가리키는 것마다, 그 파트의 사슬 안에 ⓐ S를 포함하는 절 선택자 ⓑ S를 `section`으로 둔 `items`·`rows` 선택자 ⓒ S 자신이나 S의 상위 절, 또는 S가 든 문서 전체(`section` 없음)를 가리키는 `refs` 가운데 하나가 있어야 한다(누락). S의 상위 절을 `section`으로 둔 `items`·`rows` 선택자와 S의 하위 절만 고른 선택자는 S를 덮은 것으로 보지 않는다. 절을 가리키지 않는 `reads`(서식 파일 등)는 그 파일을 가리키는 `refs`가 있어야 한다.
4. **안전장치 핵심과 표준 공통 핵심**
   - 안전장치 핵심: 원본 전역 지침에서 「불변 예외:」로 시작하는 목록 항목을 찾고, 그 아래 들여쓴 하위 항목의 「…」 안 글자를 항목 이름으로 읽는다. 이름마다 ① 제목(H2~H4)에 그 이름이 있으면 그 절 전체(다음 같은 단계 이하 제목 앞까지) ② 없으면 `* <이름>:` 또는 `- <이름>:`로 시작하는 목록 항목과 그 하위 줄을 목록 순서대로 옮긴다. 하나도 찾지 못한 이름이 있으면 오류다. 생성물 표시 줄 다음에 원천 표시(갱신 표기, 추출 SHA-256, 생성 근거)와 본문 앞 한 줄 「아래는 사용자 전역 지침이 하위 지침으로 바꿀 수 없다고 정한 항목(불변 예외)의 원문이다.」를 두며, 그 밖의 글자는 원문뿐이다. 불변 예외 밖의 항목은 넣지 않는다.
   - 표준 공통 핵심: 구성표 `standard`는 `AGENTS.md` 「문서 지도」 절 전체와 「불변 원칙」의 항목 「승인 전 착수 금지」, 「범위 통제」, 「거버넌스 구역」, 「생성과 판정의 분리」, 「단순성 우선」, 「추측 금지」, 「단일 원천」, 「추적성」만 고른다. 서브에이전트가 하지 않는 일의 원칙(「커밋·푸시」)과 「규칙 비대화 방지」는 넣지 않는다.
5. **세션별 구성**
   - ① **서브에이전트 파트**(E01, E02, E03, V01, Q01, Q02, Q03, Q05, Q06, Q07, X01): 파트 카드 하나가 다섯 계층을 모두 담는다. 카드 머리말은 `name: part-<코드 소문자>`, `description`(「조직 표」의 「<부> <팀> <코드> <파트>: <주요 업무>」), `model: inherit`, `disallowedTools: Agent`, `omitClaudeMd: true`다. `omitClaudeMd: true`는 전역 지침과 프로젝트 지침(`CLAUDE.md`·`AGENTS.md`)을 싣지 않게 한다(근거 `Departments/Development/Implementation/results/DEV-034_v01.md` 6절 ①). 그래서 「전역 공통」은 안전장치 핵심, 「표준 공통」은 표준 공통 핵심이다. 카드 본문은 안전장치 핵심 → 표준 공통 핵심 → 부 지침 → 팀 지침 → 파트 지침 → 「필요할 때 읽는 문서」(구성표 `refs`) 순서다. X01은 팀이 없고 부가 실행마다 정해지며 실험 파일에는 조직마다의 작성 제한이 적용되지 않으므로 부·팀 계층을 두지 않고, 카드의 그 자리에 「해당 없음」과 사유를 적는다. 판정과 범위 통제의 한계는 표준 공통 핵심과 X01 파트 지침에 실린다.
   - ② **PM(P01·P02)**: 전역 지침을 지금처럼 싣는다. PM 본 세션에서 전역 지침만 빼는 설정은 동작을 확인하지 못했으므로(같은 결과서 6절 ②) 그 설정을 두지 않고 안전장치 핵심도 싣지 않는다. `CLAUDE.md`를 거쳐 `AGENTS.md`(표준 공통)를 싣고, 일을 시작할 때 자기 파트 지침(`.claude/guides/parts/P01.md` 또는 `P02.md`. 부·팀·파트 계층)을 읽는다. 읽기 규정의 위치는 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항(P01)과 「원스톱 파이프라인」 1항(P02)이다.
   - ③ **핫픽스팀(V03)·형상통제팀(C01~C03)**: `AGENTS.md`를 싣는다. Claude Code 세션은 `CLAUDE.md`를 거쳐 싣고, `AGENTS.md`를 자동으로 싣지 않는 서비스는 일을 시작할 때 직접 읽는다. 표준 공통 핵심은 싣지 않는다. 전역 지침 제외 설정이 없으므로 전역 지침은 그 서비스의 방식대로 적용되며 안전장치 핵심을 따로 싣지 않는다. 일을 시작할 때 자기 파트 지침을 읽고, 한 세션이 여러 파트의 일을 하면 시작하는 일의 파트마다 읽는다. 읽기 규정의 위치는 `Workflow/03_라이프사이클` 「핫픽스 트랙」 2항(V03)과 `Workflow/05_인수인계_및_실행명령` 「공통 규칙」(C01~C03)이다.
   - ④ **비서팀(S01~S03)**: 저장소 파일을 읽을 수 있는 비서팀 세션은 일을 시작할 때 `AGENTS.md`와 자기 파트 지침을 읽는다(`Workflow/05_인수인계_및_실행명령` 「공통 규칙」). 저장소 파일을 읽을 수 없는 세션에는 생성물이 실리지 않으며, 지금처럼 필요한 매뉴얼 절을 찾아 읽는다.
   - ⑤ **대기 파트**(E04, V02, Q04, O01, O02, M01~M04): 부·팀·파트 지침은 만들고 파트 카드는 만들지 않는다. 대기 파트의 일은 그 부의 서브에이전트(부서 정의)가 맡으며, 그 파트를 활성으로 바꾸는 안건이 카드를 더한다.
   - ⑥ **전역 지침 제외 설정**: 전역 지침을 빼는 설정을 들이는 안건은 그 설정으로 전역 지침이 빠지는 세션마다 안전장치 핵심을 싣는다. 그 설정이 `AGENTS.md`도 빼면 쓰지 않는다.
6. **적용 시점**: `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」의 `REQ-034` 적용 시점 항목을 따른다.

## 3. 실행 명령

세 명령 모두 형식은 같다. `<모델 ID>`와 `<effort>`는 그 명령으로 기동하는 PM 파트의 유효 값(`Workflow/04_모델_운용` 「단계별 모델」)이다. REQ 작성 명령과 REQ 새 버전 명령은 P01 칸, 원스톱 실행 명령은 P02 칸의 유효 값이며, 분류(`Workflow/04_모델_운용` 「단계별 모델」 5항), CEO 설정, 격상, 「결정」 열의 승인으로 정해진다. 명령을 실행하는 비서실 세션은 실행 전에 `resolve_model.py`(`Workflow/06_통제장치_및_배포` 「준비·판단 명령」)로 그 값을 구해 `--model`·`--effort`와 지시문의 effort 표기에 적는다(8.3절 「PM 기동」 순서 2-2)). REQ 6절의 명령과 유효 값이 다르면 유효 값을 따른다. 셸을 실행할 수 없는 비서실 세션은 이 값을 구하지 못하므로 REQ 6절의 명령을 그대로 안내하고 PM의 확인(`Workflow/04_모델_운용` 「단계별 모델」 「PM의 책임」 ①)에 맡기며, 그 사실을 대표님께 알린다.

```bash
claude --model <모델 ID> --effort <effort> --permission-mode acceptEdits "<지시문>"
```

| 명령 | 지시문 |
| :--- | :--- |
| REQ 작성 명령 | `Departments/Secretariat/Secretary/assets/inbox/ORD-<번호>_v<버전>.md로 REQ 작성 파이프라인을 실행하라. Workflow/03_라이프사이클.md 「REQ 작성 파이프라인」 절을 따른다. effort: <effort>` |
| REQ 새 버전 명령 | `Departments/Secretariat/PM/docs/requests/<REQ 파일>.md의 새 버전을 작성하는 REQ 작성 파이프라인을 실행하라. 근거: <근거 파일>. Workflow/03_라이프사이클.md 「REQ 작성 파이프라인」 절을 따른다. effort: <effort>` |
| 원스톱 실행 명령 | `Departments/Secretariat/PM/docs/requests/<REQ 파일>.md 원스톱 파이프라인을 실행하라. Workflow/03_라이프사이클.md 「원스톱 파이프라인」 절을 따른다. effort: <effort>` |

- REQ 새 버전 명령의 `<REQ 파일>`은 그 안건 REQ의 최신 버전이다. `<근거 파일>`은 대표님 결정의 기록이다. 「문체 반영」 승인의 문체 반영본이면 그 REQ 승인의 승인 기록(대표님 본인이 승인 필드를 기재했으면 그 REQ 파일)이고, 그 밖의 결정(요구 변경, 실험 단계 추가, 격상, 모델·effort 승인, 결정 변경)이면 비서실이 그 결정을 3절 「대화 중 확정된 사항」에 적은 ORDER 새 버전이다. 근거 파일 밖의 지시를 지시문에 더하지 않는다.
- 지시문의 effort 값은 `--effort` 값과 같게 적는다. PM은 이 표기를 서브에이전트에 전달한다(`Workflow/04_모델_운용` 「타깃 컨텍스트 규칙」).
- `--permission-mode acceptEdits`는 파일 편집 확인만 생략한다. `deny`·`ask`의 적용은 `Workflow/06_통제장치_및_배포` 「권한 설정」·「무인 실행 권한」을 따른다.
- `--agent`를 지정하지 않는다. 메인 세션이 오케스트레이터가 되어 부서 서브에이전트를 기동한다.
- 인증 정보를 명령에 넣지 않는다.
- `--dangerously-skip-permissions` 등 권한 통제 전체를 끄는 옵션을 쓰지 않는다.
- 지시문에 REQ에 없는 작업을 넣지 않는다.
- PM은 REQ 작성 명령·REQ 새 버전 명령으로 기동되면 `Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」, 원스톱 실행 명령으로 기동되면 같은 문서 「원스톱 착수 조건」의 판단을 한다. 비서실은 작업 큐의 순서(첫 버전 전에는 ORDER 5절의 착수 조건. 8.7절)와, 두 절이 비서실에 정한 확인(착수 순서, 클라우드 세션, 다시 실행)을 지켜 명령을 안내하거나 실행한다.

### 3.1 핫픽스 실행 명령

핫픽스팀(V03) 세션을 기동하는 명령이다. 형식은 3절과 같고, `<모델 ID>`와 `<effort>`는 V03 칸 「분류 없음」의 유효 값(`Workflow/04_모델_운용` 「단계별 모델」. `resolve_model.py --hotfix`로 구한다)이다. 실행하는 비서실 세션과 순서는 8.3절 「핫픽스」 절차를 따른다. 이 명령은 PM 지시문(2절)이 아니다.

| 명령 | 지시문 |
| :--- | :--- |
| 핫픽스 실행 명령 | `핫픽스 트랙의 수정과 검증을 실행하라. 지시 원문: <지시 원문> / 대상 파일: <사전 승인된 대상 파일 경로를 쉼표로 이은 목록> / 사전 승인: <승인 시각> <승인을 받은 비서실 세션의 세션 식별자>. Workflow/03_라이프사이클.md 「핫픽스 트랙」 절을 따른다. effort: <effort>` |

- 지시문에 지시 원문, 대상 파일, 사전 승인 밖의 지시를 더하지 않는다. 승인 문구 원문은 넣지 않는다.
- 지시 원문에 셸이 큰따옴표 안에서 해석하는 문자(`"`, `$`, `` ` ``, `\`)가 있으면 그 문자 앞에 `\`를 붙여 원문 그대로 전달되게 한다.
- 3절 표 아래의 effort 표기, `--permission-mode acceptEdits`, `--agent`, 인증 정보, 권한 통제를 끄는 옵션에 관한 항목은 이 명령에도 같다.

## 7. PM 실행 기록

PM 실행 기록은 이 절이 원천이다.

1. **성격**: 실행 기록은 PM이 안건마다 남기는 진행 이력이다. 비서실의 대조·보고·브리핑에 쓰는 참고 자료이며 공식 진행 상태의 근거가 아니다(1절).
2. **파일**: 안건마다 하나이며 `Departments/Secretariat/PM/workspace/실행기록_REQ-xxx.md`(파생 안건은 `실행기록_REQ-xxx-n.md`)에 둔다. 버전을 붙이지 않고 행을 더해 쌓는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다. 이름 규칙은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」을 따른다.
3. **작성과 추가**: PM이 REQ를 처음 작성할 때 만들고, 그 세션을 시작한 때(6항 ①)부터 적는다. 행을 더하기만 하고 이미 적은 행은 고치지 않는다.
4. **머리말**: `task_id`, `created`.
5. **본문**: 표 하나이며 열은 `| 시각 | 단계 | 사건 | 판정 결과 | 재판정 횟수 | effort | 중단 사유 | 대표님께 한 질문과 답 |`이다. 해당 없는 칸은 `—`로 적는다.
6. **기록 시점**: ① 실행 명령으로 세션을 시작할 때(effort는 실행 명령 지시문의 값) ② 서브에이전트를 기동할 때 ③ 판정서를 받을 때(판정 결과에 `result`와 판정서 경로를 적고, 재판정 횟수는 `Workflow/03_라이프사이클` 「재판정 한도」의 셈을 따른다) ④ 중단 조건으로 멈출 때 ⑤ 대표님께 질문하고 답을 받을 때(질문과 답을 원문 그대로 적는다) ⑥ 완료 보고할 때.
7. **커밋**: 그 안건의 최종 판정서 승인 뒤 커밋에 함께 넣는다(1.1절 6항 ⑦).

### 4.3 준비·판단 명령

세션이 규정을 읽고 직접 하던 판단 가운데 기계로 할 수 있는 부분을 하는 명령이다. 규칙의 원천은 각 명령이 구현하는 Workflow 절이며 명령은 그 구현이다.

1. **공통**: 모든 명령은 `Departments/Development/Implementation/assets/scripts/` 아래 Python 스크립트다. 기록 파일명, 머리말 읽기, `scope:` 일치, 승인 필드 형식, 종결 기록 판단은 `check_standard.py`의 함수를 불러 쓰고 같은 로직을 다시 구현하지 않는다. 출력은 `[PASS]`·`[INFO]`·`[WARN]`·`[FAIL]`과 원인·조치이며 UTF-8로 고정한다. 명령 안에는 커밋·삭제·이동·파일 쓰기·Git 설정 변경을 하는 명령이 없다. 각 명령의 첫머리 설명에 규칙의 원천 절을 적는다.
2. **최종 승인 커밋 준비**(`prepare_final_commit.py <최종 판정서 경로>`)
   - 읽는 것: 그 최종 판정서(머리말 `result: pass` 확인), 같은 번호 REQ의 최신 버전(`approved:` 형식 확인), 승인 기록 `승인기록_*_<최종 판정서 파일명(확장자 없음)>.md`, 그 안건의 최신 RPT·DEV(「적용본」 표의 적용본 경로·원본 경로·반영 명령과 「삭제 대상」), 최종 판정서 「삭제 대상」, `git status --porcelain -uall`, `git log`.
   - 출력: ① 반영 목록(결과서별 적용본 경로·원본 경로·반영 명령, 표의 순서 그대로) ② 삭제 목록(경로, 추적 여부, 출처) ③ 스테이징 목록(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 6번 ①~⑫의 분류 번호를 경로마다 붙임. ⑫는 파일 이름이 `기준선_<14자리 시각>_<그 안건의 기록 이름>.json`인 `Departments/Secretariat/ConfigControl/results/` 아래 파일) ④ 분류하지 못한 변경 ⑤ 커밋 메시지(`Workflow/07_문서_서식_및_번호` 「커밋 메시지」의 제목 줄과 근거 줄).
   - 실패: 읽을 기록이 없거나 형식이 맞지 않으면 `[FAIL]`·종료 코드 1이다. 사용과 실패 때의 처리는 `Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 4·6·8번을 따른다.
3. **겹침·착수 판단**(`check_overlap.py`)
   - `req-save --number <REQ 번호> --scope <항목> [--scope <항목> …]`: `Workflow/03_라이프사이클` 「다른 안건이 진행 중일 때의 REQ 작성」 4항의 방법으로 진행 중인 안건을 찾고 3항의 겹침을 판단한다. 출력은 진행 중인 안건 목록과 겹친 항목(양쪽 `scope:` 항목과 그 REQ 버전)이다.
   - `onestop <REQ 경로>`: 같은 문서 「원스톱 착수 조건」 1·2항(실행 중인 다른 안건)과 5항(끝난 안건과의 대조)을 판단한다. 5항 「가리키는 절·문구」는 REQ 본문에서 백틱으로 감싼 경로 가운데 `scope:` 밖의 파일과 그 파일을 바꾼 대상 커밋을 「PM 판단 대상」으로 출력하며, 절 제목·인용 문구가 바뀌었는지는 PM이 판단한다.
   - 종료 코드: 0은 겹침·실행 중 안건·대상 커밋 없음, 1은 있음(멈춤 사유), 2는 명령 실패(조회 실패, REQ 파일 형식 오류)다. 사용과 실패 때의 처리는 같은 문서 「다른 안건이 진행 중일 때의 REQ 작성」 10항, 「원스톱 착수 조건」 9항을 따른다.
4. **유효 값 계산**(`resolve_model.py (--class <Critical|Major|Minor> | --hotfix) [--escalated] [--approved-model <모델 ID>] [--approved-effort <값>] [--part <코드>] [--settings <경로>]`): 규칙의 원천은 `Workflow/04_모델_운용` 「단계별 모델」 6항과 「CEO 설정」이다.
   - 옵션: `--class`는 모든 칸의 그 분류 키를, `--hotfix`는 「분류 없음」 키가 있는 칸만 읽는다. `--escalated`는 Minor에서 격상한 안건, `--approved-model`·`--approved-effort`는 REQ 「결정」 열이 승인한 모델 ID·effort다. `--part`는 출력할 파트를 하나로 줄인다. `--settings`는 CEO 설정 파일 경로이며 기본값은 `CEO/settings/model_settings.json`이다. 시험이 저장소의 `CEO/`에 파일을 만들지 않게 하기 위해 둔다.
   - 읽는 것: `Workflow/data/model_matrix.json`, `Workflow/04_모델_운용.md` 1.1절 표(등급 → 모델 ID), `Workflow/03_라이프사이클.md` 「분류별 단계」 표(분류별 기본 모델 등급. 「활성 때 정함」 칸의 등급을 `Workflow/04_모델_운용` 「단계별 모델」 4항대로 읽기 위해 쓴다), CEO 설정 파일(있으면). 파일을 쓰지 않는다.
   - 출력: 첫 줄에 CEO 설정 파일 경로와 `saved_at`(파일이 없으면 「없음(기본값)」), 이어서 칸마다 `[INFO] <파트> <역할> <분류> 모델 <등급> <모델 ID> effort <값> 출처 <기본값|CEO 설정|격상|REQ 결정>`을 출력하고, 하향 확인이 있는 칸은 끝에 `하향 확인 <시각>`을 붙인다. 「제한 없음」·「정하지 않음」은 그 글자를 출력한다.
   - 실패: 종료 코드 1은 CEO 설정이 JSON으로 읽히지 않음, 없는 파트·역할·분류, 허용 밖 값, 「최고급」에 `model_id`가 없음, 판정 역할이나 `Critical` 칸을 중급으로 두면서 `downgrade_confirmed_at`이 없거나 시각 형식이 아님이다. 쓸 수 없는 칸(비서실 세션 파트, 「해당 없음」 칸)의 설정은 `[WARN]`을 출력하고 무시한다. 모델 매트릭스, 1.1절 표, 「분류별 단계」 표 가운데 하나라도 읽지 못하면 종료 코드 2다. 실패 출력에는 원인과 조치(대표님께 보고)를 적는다.
   - 사용: PM이 시작할 때(`Workflow/04_모델_운용` 「단계별 모델」 「PM의 책임」 ①), 비서실 세션이 PM과 핫픽스팀을 기동하기 전(`Workflow/05_인수인계_및_실행명령` 「비서실 실행 절차」의 「PM 기동」·「핫픽스」), 판정 단계의 지시문을 만들 때(`Workflow/04_모델_운용` 「타깃 컨텍스트 규칙」 1항).
5. **판정 전 점검**(`check_prejudge.py <문서 경로> [--req <REQ 경로>] [--applied <적용본 폴더>]`): 규칙의 원천은 `Workflow/03_라이프사이클` 「판정 전 점검」이다.
   - 문서 종류: 파일 이름(`Workflow/07_문서_서식_및_번호` 「문서 체계」)으로 정한다.
   - 결정적 항목: ① 서식 절: 그 종류 서식 파일의 H2 제목이 같은 순서로 모두 있다(제목 끝에 「(…만)」이 붙은 선택 절은 없어도 된다) ② 머리말: `Workflow/07_문서_서식_및_번호` 「머리말」 표의 필수 필드가 있고 형식(날짜·시각·목록)이 맞다 ③ scope 포함: EC `scope:`가 `--req` REQ의 `scope:` 안에 있고, 결과서 「변경 파일」 경로가 REQ `scope:`, 팀 `results/`·`workspace/`, `Workflow/02_부서_구조_및_작업구역` 「작업 구역」의 그 파트 경로 안에 있다. EC는 REQ 3절 표의 D번호마다 「결정 반영 대조」 표에 행이 있고 두 범위 칸이 비어 있지 않다. 결과서의 「결정 반영 대조」 절이 있으면 같은 방식으로 본다 ④ 리비전 태그(`--applied`): 적용본의 Markdown 파일마다 실변경 절(파일 전체 적용본은 원본과 `git diff --no-index`로, 변경 파일은 블록으로 찾는다) 제목에만 현행 태그가 있고, 이전 태그가 남지 않으며, 개정 이력 표에 그 안건의 행이 있다.
   - 출력과 종료 코드: `[PASS]`·`[FAIL]`과 원인·조치. 종료 코드 0(결함 없음), 1(결함 있음), 2(문서를 읽지 못함). 기계로 가릴 수 없는 항목은 검사하지 않고 점검표 「사람이 확인하는 항목」으로 둔다.
   - 겹침·경계: 품질 판정과 커밋 전 검사와는 시점과 목적이 다르다. 이 명령은 작성 단계가 넘기기 전 형식 결함을 줄이는 것이고, 판정은 독립 판정자가 기준 전체로 본다.

## 3. REQ 작성 파이프라인

1. PM(P01)은 시작할 때 `AGENTS.md`(`CLAUDE.md` 경유)와 함께 자기 파트 지침(`.claude/guides/parts/P01.md`)을 읽는다(`Workflow/04_모델_운용` 「계층형 지침」). PM이 ORDER 경로를 받아 메인 세션에서 서식 `Workflow/templates/REQ_TEMPLATE.md`로 REQ를 직접 작성한다(`approved: ""`). REQ 작성용 서브에이전트는 기동하지 않는다. REQ를 처음 작성하면 ORDER 머리말 `related_req`에 그 REQ 이름을 더한다(필드 규칙은 `Workflow/07_문서_서식_및_번호` 「머리말」). PM은 아래 작성 기준을 지킨다. REQ 파일을 저장하기 전에 3.1절대로 다른 안건과의 겹침을 판단한다. REQ 파일을 처음 저장하기 직전에 시각 조회 명령(Bash `date -Iseconds` 또는 PowerShell `Get-Date -Format "yyyy-MM-ddTHH:mm:sszzz"`)으로 조회한 시각을 머리말 `created_at`에 조회 결과 그대로 적는다. 새 버전과 문체 반영본도 그 버전 파일을 처음 저장할 때 같게 적는다. 이 값은 원스톱 착수 때 끝난 안건과 대조하는 기준이다(4.1절 5·8항).
   - **구현 방법(Critical·Major)**: Critical·Major REQ는 구현 방법을 정하지 않는다. 구현 방법은 EC가 있으면 EC에서, 없으면 명세 단계 산출물(설계부 결과서 「구현 계획」 절 포함)에서 정한다(2.1절). 아래 표에서 「대상」인 위치에는 구현 방법을 요구·권고·선택지로 적지 않는다. Minor REQ는 이 기준의 대상이 아니다.
     - 구현 방법: 요청한 결과를 만들기 위해 산출물에 넣거나 산출물을 만들 때 쓰는 수단이다. 바꿀 문서의 문구안, 파일·폴더의 내부 구성, 코드·검사의 로직, 산출물을 만들 때 쓸 명령·도구·설정 규칙이 여기에 해당한다.
     - 구현 방법이 아닌 것: 무엇을 바꾸는지(대상 파일·절, 범위), 무엇을 달성하는지(요구·목적·완료 기준), 대표님이 정할 정책·범위·모델·effort의 선택, 표준 매뉴얼이 이미 정한 절차를 따른다는 기재(예: 「거버넌스 파일은 적용본으로 작성한다」).

     | 서식 절 | 적용 | 근거 |
     | :--- | :--- | :--- |
     | 1. 요청 원문 | 대상 아님 | 대표님 원문을 원형 그대로 인용한다. 원문이 수단을 담아도 그대로 둔다 |
     | 2. 배경 및 목적 | 「목적」만 대상 | 「배경」은 현재 상태와 사례의 사실이다. 현행 파일·함수·명령을 서술해도 구현 방법이 아니다 |
     | 3. 결정 사항 및 선택지 | 대상 | 「정할 일」·「권고안」·「대안」에는 대표님이 정할 정책·범위·완료 기준·모델·effort의 선택만 적는다 |
     | 4. 실행 계획 | 「작업」 열만 대상 | 「작업」 열에는 단계에서 할 일과 산출물의 이름(예: 「적용본 작성」, 「우회 재현 시험」, 「반영 명령을 결과서에 기재」)을 적고, 그 일을 하는 수단은 적지 않는다. 단계·부서·대상 경로 열과 표 아래 안내(적용본 작성 원칙, 중단 조건 참조 등)는 대상이 아니다 |
     | 5. 체크리스트 | 대상 아님 | 확인 방법은 완료를 확인하는 수단이며, 확인에 쓰는 명령·시험을 적어도 구현 방법이 아니다 |
     | 6. 실행 명령 | 대상 아님 | 서식이 정한 파이프라인 실행 명령이다 |

   - **EC 판단과 REQ(모든 분류)**: EC를 붙일지는 승인 뒤 설계부가 판단하므로(2.1절 5항), REQ는 어느 판단이 나와도 진행할 수 있게 쓴다. `workflow:`에는 2절 표의 대괄호 단계를 판단과 관계없이 적고, `scope:`의 EC 경로는 `Workflow/07_문서_서식_및_번호` 「머리말」을 따른다. 실행 계획과 체크리스트는 EC의 유무에 따라 뜻이 달라지게 쓰지 않는다.
   - **분류 근거(모든 분류)**: PM은 ORDER 제안과 같든 다르든 모든 REQ의 서식 2절 「분류 근거」에 2절 정의 기준 가운데 해당하는 것(중요도, 난이도로 올렸으면 그 사유)을 적고, ORDER `classification_proposal`과 다르면 다른 사유를 함께 적는다. 기본값 밖의 모델·effort는 3절 결정 표에 정할 일로 적는다(`Workflow/04_모델_운용` 「기본값 밖 사용」).
   - **결정과 체크리스트(모든 분류)**: 체크리스트(서식 5절)와 실행 계획(서식 4절)은 서식 3절 결정 표에서 어느 선택지를 택하느냐에 따라 뜻이 달라지게 쓰지 않는다(예: 「D1 결정대로」). 선택지에 따라 달라지는 항목은 어느 선택지를 택해도 그대로 확인할 수 있게 쓰거나, 권고안을 전제로 쓰고 그 전제를 REQ에 적는다. 대표님이 REQ 승인 문구에서 권고안이 아닌 선택지나 수정안을 골라도 REQ 새 버전을 작성하지 않는다(`Workflow/07_문서_서식_및_번호` 「승인 기록」 8항). 승인 필드를 기재한 뒤의 결정 변경은 같은 절 6항대로 REQ 새 버전을 작성한다. 대표님이 권고안이 아닌 결정을 고르면 「결정」 열의 결정이 그 결정에 따라 달라지는 체크리스트 항목·실행 계획보다 우선한다. 결정의 이행은 EC가 있으면 EC가 「결정」 열대로 반영하고 EC 판정에서 확인하며(5절 표 「EC 판정」 행 ⑤), EC가 없는 Critical·Major는 명세 단계 산출물이 반영하고 명세 판정에서 확인한다(5절 표 「명세 판정」 행 ⑤). 모든 분류에서 최종 판정이 체크리스트와 함께 「결정」 열과 대조한다(5절 「최종 판정 기준」 1).
   - **REQ 새 버전 명령**: PM이 `Workflow/05_인수인계_및_실행명령` 「실행 명령」의 REQ 새 버전 명령으로 기동되면 근거 파일의 결정대로 대상 REQ의 새 버전을 작성한다. 근거 파일이 ORDER 새 버전이면 2~4항을 따른다. 근거 파일이 「문체 반영」 승인의 기록이면 5.1절 5항 4~7을 따르고, 대조 `pass`와 승인 필드 기재 뒤 `Workflow/05_인수인계_및_실행명령` 「완료 보고」대로 문체 반영본 경로와 대조 판정서 경로를 보고하고 끝낸다. 대표님 재승인은 받지 않으며, 원스톱 파이프라인은 문체 반영본을 대상 파일로 한 원스톱 실행 명령으로 다시 실행한다.
2. 오케스트레이터가 `quality`를 새로 기동한다. 품질보증부 서브에이전트는 아래 기준으로 REQ를 판정하고 `RES-xxx-REQ`를 발행한다.
   - ① 요청 원문의 요구가 빠지거나 바뀌지 않았다 ② 체크리스트가 요청 원문 항목과 1:1로 대응한다 ③ scope가 요구를 모두 덮고 요구 밖 경로가 없다 ④ 분류가 2절의 정의 기준과 맞고(REQ 「분류 근거」), ORDER 제안과 다르면 사유가 있으며, `workflow:`가 2절과 맞다 ⑤ 완료 기준을 실행이나 열람으로 확인할 수 있다 ⑥ 뜻이 둘 이상으로 읽히는 문장이 없다 ⑦ Critical·Major REQ는 1항 「구현 방법」 기준의 「대상」 위치에 구현 방법이 없다 ⑧ 체크리스트와 실행 계획의 뜻이 REQ 3절 결정 표의 선택에 따라 달라지지 않는다. 권고안을 전제로 쓰고 그 전제를 REQ에 적은 항목은 이 기준에 맞는 것으로 본다(1항 「결정과 체크리스트」)
   - 판정서 `auditor.model`의 대조는 `Workflow/04_모델_운용` 「단계별 모델」을 따른다.
3. `fail`이면 PM이 REQ 새 버전을 작성하고 품질보증부 서브에이전트가 변경분을 다시 판정한다. 재판정 한도는 8절을 따른다.
4. `pass`이면 오케스트레이터가 `Workflow/05_인수인계_및_실행명령` 「완료 보고」대로 보고하고 끝낸다. 보고에는 REQ 경로와 판정서 경로를 적는다. 대표님이 REQ를 검토하고 승인한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」).

### 3.1 다른 안건이 진행 중일 때의 REQ 작성

다른 안건이 진행 중일 때 REQ 작성 명령과 REQ 새 버전 명령의 실행 조건은 이 절이 원천이다.

1. **대상**: REQ 작성 명령과 REQ 새 버전 명령(`Workflow/05_인수인계_및_실행명령` 「실행 명령」)으로 작성하는 REQ다. REQ 새 버전 명령의 대상 REQ가 2항의 진행 중인 안건이면(진행 중인 안건 자신의 REQ 새 버전. 대상 REQ의 최신 버전이 승인 전이어도 승인된 버전이 있으면 여기에 든다) 이 절의 대상이 아니며, 6절 「진행 중 변경과 파생 안건」, 8절 「반려와 격상」, 3절 1항 「REQ 새 버전 명령」대로 작성한다.
2. **진행 중인 안건**: 그 번호의 REQ 가운데 `approved:`가 `Workflow/06_통제장치_및_배포` 「커밋 전 검사」의 「승인 요건(구현)」 형식으로 기재된 버전(이하 「승인된 버전」)이 하나라도 생긴 때부터 그 안건이 끝날 때(`Workflow/07_문서_서식_및_번호` 「종결 기록」의 끝난 안건)까지의 안건이다. 판단은 번호 단위이며, 최신 버전의 `approved:`가 비어 있어도 진행 중이다. 원스톱 실행 중, 중단 조건으로 멈춰 대표님 결정을 기다리는 동안(그 결정으로 REQ 새 버전을 작성해 REQ 판정과 대표님 재승인을 기다리는 동안 포함. 5.3절 4항, 4.1절 5항, 6절 「진행 중인 안건의 요구가 바뀜」), 최종 판정 `pass` 뒤 승인·커밋을 기다리는 동안, 「문체 반영」으로 다시 실행하는 동안, 승인 뒤 원스톱 착수 전이 모두 든다. 그 기간 내내 그 안건이 `scope:`의 문서를 바꾸고 있거나 바꿀 예정이기 때문이다.
3. **겹침**: 파일 단위로 보며 절은 따지지 않는다. 두 `scope:` 항목(끝의 `/`와 줄 끝 주석을 뗀 것)이 같거나, 한 항목을 변경 파일로 보고 다른 항목에 `Workflow/06_통제장치_및_배포` 「커밋 전 검사」의 「scope 일치 규칙」을 적용해 포함되면 겹친다. 두 방향 가운데 어느 한쪽으로 포함되어도 겹친 것이다. 한쪽 폴더 항목 안에 다른 쪽 파일·폴더 항목이 있는 경우와, 폴더 항목끼리 같거나 한쪽이 다른 쪽을 포함하는 경우가 여기에 든다. 진행 중인 안건의 대조 대상 `scope:`(4항)에 같은 규칙으로 `Workflow/templates/REQ_TEMPLATE.md`나 `Workflow/03_라이프사이클.md`를 포함하는 항목이 있으면, 새 REQ의 `scope:`와 관계없이 겹친 것으로 본다. 두 문서가 바뀌면 새 REQ의 서식과 작성·판정 기준이 바뀌기 때문이다.
4. **판단**: PM이 REQ의 `scope:`를 정한 뒤, 그 명령에서 그 REQ 파일을 처음 저장하기 전에 판단한다. 진행 중인 안건은 아래 방법으로 찾으며, 작성하는 REQ 자신의 번호는 뺀다.
   - 승인 필드: Grep 도구로 `Departments/Secretariat/PM/docs/requests/`의 `^approved:` 줄을 찾아, 번호마다 값이 2항의 형식으로 기재된 버전이 하나라도 있는지 본다. 최신 버전의 값만 보지 않는다.
   - 끝난 안건: 커밋된 종결 기록으로 본다. `git ls-files -- Departments/Secretariat/Secretary/assets/inbox/`의 결과 가운데 이름이 `종결기록_`으로 시작하는 파일에서, `git status --porcelain -uall -- Departments/Secretariat/Secretary/assets/inbox/`의 결과가 `A`로 시작하는 경로(스테이징만 하고 커밋하지 않은 파일)를 뺀다.
   - 대조: 진행 중인 안건마다 최신 버전과 승인된 모든 버전의 `scope:` 항목을 합쳐 읽어 3항으로 대조한다. 승인된 버전의 범위는 그 안건이 이미 바꿨을 수 있는 문서이고, 최신 버전의 범위는 바꿀 예정인 문서이기 때문이다.
5. **결과**: 겹치지 않으면 그 REQ를 저장하고 3절 1항부터 진행한다. 겹치면 그 REQ 파일을 저장하지 않고, ORDER `related_req`에 더하지 않으며, PM 실행 기록(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」)도 만들지 않고 멈춘다(7절 11항). 보고에는 겹친 안건의 REQ 경로와 겹친 항목(양쪽 `scope:` 항목과 그 항목이 있는 REQ 버전. 3항 끝 문장에 해당하면 그 문서)을 적는다. 한 ORDER에서 REQ를 여러 건 작성하면 REQ마다 판단해, 겹치지 않는 REQ는 저장하고 겹치는 REQ만 저장하지 않으며, 보고에 저장한 REQ와 저장하지 않은 요구 항목을 함께 적는다.
6. **판정 `fail` 뒤 새 버전**: 3절 3항의 새 버전에서 `scope:` 항목을 더하면, 더한 항목을 저장 전에 3항으로 대조한다. 겹치면 그 새 버전을 저장하지 않고 멈춘다(7절 11항). 그 뒤 처리는 대표님이 정한다. 대표님 결정은 ORDER 새 버전에 적고 REQ 새 버전 명령으로 이어 간다(`Workflow/05_인수인계_및_실행명령` 「실행 명령」 표 아래 첫 항목).
7. **재개**: 진행 중이던 안건이 끝난 뒤 비서실이 멈춘 명령과 같은 명령을 다시 실행한다. REQ 새 버전 명령으로 멈췄으면 같은 대상 REQ와 근거 파일로 다시 실행하며, 저장된 새 버전이 없으므로 PM은 그 REQ의 최신 버전 다음 버전을 작성한다. REQ 작성 명령으로 멈췄으면 같은 REQ 작성 명령을 다시 실행하고, PM은 ORDER `related_req`와 REQ 폴더로 이미 저장된 REQ를 확인해 다시 쓰지 않고 건너뛰며, 저장하지 않았던 요구 항목의 REQ만 작성한다. 그 REQ의 번호는 멈출 때 예정했던 번호가 아니라 저장할 때 `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 「번호」 항대로 정하며 `_v01`로 시작한다. 다시 실행한 명령도 이 절의 판단을 처음부터 한다.
8. **작업 큐와의 관계**: 작업 큐의 순서(`Workflow/05_인수인계_및_실행명령` 「작업 큐」)와 이 절·4.1절의 규칙을 함께 지키며, 둘 가운데 늦은 쪽을 따른다. 비서실은 작업 큐의 순서가 충족된 뒤에만 그 명령을 안내하거나 실행하고, PM은 이 절과 4.1절의 판단을 한다. 작업 큐 첫 버전 전에는 작업 큐의 순서 대신 ORDER 5절의 착수 조건을 따른다. 이미 발행된 ORDER의 5절은 고치지 않으며, 작업 큐 첫 버전에 옮겨 적은 뒤에는 작업 큐가 우선한다(같은 절 7항). 순서를 바꾸려면 대표님 결정을 받아 작업 큐만 고친다(같은 절 2항).
9. **적용 시점**: 이 절은 `REQ-029` 커밋 뒤에 REQ 작성 명령이나 REQ 새 버전 명령으로 기동하는 PM 세션부터 적용한다. `REQ-029` 커밋 전에 작성된 REQ 버전은 소급해 판단하지 않는다. 이미 실행 중인 PM 세션은 기동 때의 규정으로 진행한다(5.4절 7항과 같은 방식).
10. **판단 명령**: PM은 4항의 판단 가운데 진행 중인 안건 찾기와 3항의 대조를 `check_overlap.py req-save`(`Workflow/06_통제장치_및_배포` 「준비·판단 명령」)로 하고 결과(명령, 시각, 출력 요지)를 실행 기록에 적는다. 명령을 실행하지 못하거나 종료 코드가 2이면 손으로 대신 판단하지 않고 멈춘다(7절 13항). 규칙의 원천은 1~9항이며 명령은 그 구현이다. 적용 시점은 `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」의 `REQ-032` 적용 시점 항목을 따른다.

- **실행**: 작성 파트는 산출물을 넘기기 전에 `python Departments/Development/Implementation/assets/scripts/check_prejudge.py <문서 경로> [--req <REQ 경로>] [--applied <적용본 폴더>]`를 실행해 `[FAIL]`을 없앤다. 결과서가 있는 단계는 결과서 3절 「검증 결과」에 명령, 시각, 결과 원문을 적는다. 스크립트를 실행하지 못한 서브에이전트는 5.4절대로 처리한다.
- **판정과의 관계**: 이 점검은 판정이 아니며 판정을 대신하지 않는다. 「사람이 확인하는 항목」은 판정 기준의 위치만 가리키며 기준 문장은 그 원천 절에 둔다.
- **적용 시점**: `Workflow/02_부서_구조_및_작업구역` 「부서별 책임과 산출물」의 `REQ-034` 적용 시점 항목을 따른다.

### 5.5 시각 디자인 단계

시각 디자인 문서의 작성 단계(시각 디자인)와 판정 단계(시각 디자인 판정), 설계부·개발부가 그 문서를 입력으로 쓰는 방식은 이 절이 원천이다. 문서의 위치·작성 부서·버전은 `Workflow/07_문서_서식_및_번호` 「문서 체계」를 따른다.

1. **대상**: 시각 디자인 문서를 처음 만들거나 바꾸는 REQ다. 그 밖의 REQ에는 두 단계를 두지 않는다.
2. **REQ 기재**: PM은 `workflow:`에 `Marketing: 시각 디자인`과 `Quality: 시각 디자인 판정`을 이 순서로 함께 적는다. 위치는 명세 단계(`Quality: 명세 판정`이 있으면 그 뒤) 뒤, 인수 시험(Minor는 구현) 앞이다. 흐름이 설계부 → 마케팅부(시각 디자인) → 개발부이기 때문이다. `scope:`에 시각 디자인 문서 경로를 넣는다. 두 단계는 EC 판단과 관계없이 실행한다.
3. **작성**: 마케팅부 서브에이전트가 시각 디자인 문서를 만들거나 고치고, 마케팅부 결과서(RPT)에 바꾼 곳과 근거(REQ 체크리스트 번호, EC가 있으면 EC 절)를 적는다.
4. **판정**: 품질보증부 서브에이전트가 5절 표 「시각 디자인 판정」 행의 기준으로 판정하고 `RES-xxx-DESIGN`을 발행한다. `fail`이면 8절을 따른다.
5. **입력으로 쓰는 방식**
   - 개발부: 이 단계가 있는 안건에서는 그 안건에서 시각 디자인 판정 `pass`를 받은 시각 디자인 문서를 구현의 입력으로 쓴다. 이 단계가 없는 안건에서 화면을 구현하면 HEAD의 시각 디자인 문서(있으면)를 입력으로 쓴다.
   - 설계부: 명세 단계에서 화면의 구조·동작 명세를 쓸 때는 그 전에 시각 디자인 판정을 받아 커밋된 시각 디자인 문서(HEAD의 문서)만 입력으로 쓴다. 그 안건에서 만들거나 바꾸는 시각 디자인 문서는 명세 단계 뒤에 작성되므로 입력으로 쓰지 않는다. HEAD에 시각 디자인 문서가 없으면 그 문서 없이 쓴다.
6. **적용 시점**: 이 절과 이 절을 가리키는 규정은 `REQ-027` 커밋 뒤에 첫 버전을 작성하는 REQ부터 적용한다. 그 전에 작성한 REQ는 작성 때의 규정으로 진행한다.

### 11.2 실험 단계

1. **성격**: 선택 단계다. PM이 REQ를 작성할 때 실험이 필요한 REQ에만 넣는다.
2. **REQ 기재**: `workflow:`에 `<부서>: 실험`(예: `Design: 실험`)을 적는다. 실험 단계를 맡는 부서는 설계부·개발부·운영부·마케팅부 가운데 REQ마다 정한다. 품질보증부는 실험 단계를 맡지 않는다. 실험 결과는 설계 단계 산출물(EC가 있으면 EC, 없으면 설계부 결과서 「EC 판단」 절)에 인용되어 품질보증부가 판정하므로, 품질보증부가 실험하면 자기 결과를 판정하게 되기 때문이다(`AGENTS.md` 「불변 원칙」 4항). 실험 단계는 하나 이상 둘 수 있고 모두 그 REQ의 실험 폴더 하나(11.1절 3항의 파이프라인 안 이름)를 쓴다. `scope:`에 그 실험 폴더를 넣는다. 실행 계획 표에 실험 단계의 목적과 대상 경로를 적는다.
3. **위치**: 분류와 관계없이 설계 단계 앞(EC 판단 전)이다.
4. **승인**: `Workflow/07_문서_서식_및_번호` 「승인 기록」 9항을 따른다.
5. **결과 연결**: 실험한 부서는 자기 결과서(설계부·운영부·마케팅부는 RPT, 개발부는 DEV)에 DEV 서식 6절 「실험 결과」(실험 목적, `Lab/` 경로, 요지, 정규 경로로 복사·이동하지 않았다는 확인)를 적는다. 같은 부서가 뒤 단계에서 결과서를 다시 쓰면 다음 버전으로 저장하고 6절을 그대로 옮긴다. 설계 단계 산출물(EC가 있으면 EC, 없으면 설계부 결과서 「EC 판단」 절)이 그 결과서 경로와 6절을 근거로 인용한다(2.1절 5항). 실험 파일은 정규 경로로 복사하거나 옮기지 않고, 구현 단계에서 정규 경로에 새로 작성한다. 최종 판정은 정규 경로의 산출물로 판정하고 `Lab/` 파일은 범위 대조(5절 기준 2)로만 확인한다.
6. **판정**: 실험 단계는 판정하지 않는다. 그 결과를 인용한 설계 단계 산출물의 판정(EC가 있으면 EC 판정, 없으면 Critical·Major는 명세 판정, Minor는 최종 판정)에서 확인한다.
7. **실험 단계가 없는데 실험이 필요해진 경우**: 7절 1항(scope 밖 변경 필요)으로 멈추고 보고한다. 대표님이 실험을 정하면 PM이 실험 단계를 더한 REQ 새 버전을 작성하고 REQ 판정과 대표님 재승인을 받는다(6절 「진행 중인 안건의 요구가 바뀜」). 7절의 항목은 바꾸지 않는다.
8. **커밋**: 실험 파일은 그 안건의 최종 판정서 승인 뒤 커밋에 함께 들어간다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」 6번 ⑥).
