    - 해시를 기록한 환경과 다시 구하는 환경의 `core.autocrlf`가 다르면 규칙이 없을 때 해시가 달라졌다(E2x: true에서 기록, CRLF 작업 트리를 false로 다시 구함 → 불일치). `* text=auto`와 `* text=auto eol=lf`는 이 경우에도 해시가 같았다. 이 PC의 `core.autocrlf=true`는 저장소 설정이 아니라 Git for Windows 시스템 설정(`C:/Program Files/Git/etc/gitconfig`)에서 온다(E2r).
    - 이 저장소의 추적 파일 1265개는 index가 모두 LF이거나 텍스트가 아니며(`i/crlf`·`i/mixed` 0개), 기본 규칙을 더해도 기존 파일이 변경으로 잡히지 않았다(E2n). 커밋된 인수 시험 `.py` 25개는 지금 index blob 해시와 대조 명령의 해시가 모두 같다(E2r. 미추적 인수 시험 폴더는 세지 않음). 기본 규칙을 더해도 기존 인수 시험 해시 대조는 영향을 받지 않는다.
    - `* text=auto eol=lf`는 작업 트리를 LF로 두어 `core.autocrlf=true` PC에서 LF 파일의 「LF will be replaced by CRLF」 경고(`RES-031_v01` 4절)가 나지 않았고, CRLF로 쓴 파일을 스테이징할 때는 반대 방향 경고가 났다. `* text=auto`는 해시를 같게 하지만 그 경고는 그대로 났다. 어느 값을 쓸지는 구현 방법이며 EC가 정한다.
  - **③ 신뢰 상태와 `allow` 적용 여부의 읽기 점검(확인)**
    - 신뢰 상태는 저장소 밖 사용자 상태 파일 `~/.claude.json`의 `projects["<저장소 경로(슬래시 형태)>"].hasTrustDialogAccepted`로 읽을 수 있었다. 읽기 모드로만 열었고 읽기 전후 파일 해시가 같았다. 이 PC의 `D:/Vibe Coding/Vibe Standard_v05`는 `True`다(E3).
    - 훅 경로는 `git config --get core.hooksPath`로 읽을 수 있었다(값 `.githooks`).
    - `allow` 적용 여부는 세션 밖에서 직접 읽는 수단을 찾지 못했다(확인 불가, N6). 세션 밖에서 읽을 수 있는 것은 신뢰 상태와 설정 파일(저장소 `.claude/settings.local.json` 없음, 사용자 `~/.claude/settings.json`에 `permissions` 키 없음)이다. 세션 안에서는 `allow`에만 기대는 명령(`date -Iseconds`, `python -m pytest --version`)이 확인 요청 없이 실행되는지로 확인된다(A1·A3. 이 세션에서는 실행됨).
    - 신뢰 처리 전 상태에서 값이 `false`이거나 항목이 없는지, 그때 `allow`가 적용되지 않는지는 재현하지 못했다(확인 불가, N5). 키 이름은 공식 문서로 확인하지 못했으며 Claude Code 버전에 따라 바뀔 수 있다(확인 불가, N7).
- **정규 경로로 복사·이동하지 않았다는 확인**: 이번에 만든 실험 파일은 `Lab/REQ-032_검사장치실측/` 아래의 여섯 개(2절 1~6번)이며 정규 경로로 복사·이동하지 않았다. `REQ-032_v04` 때의 실험 파일(`실험기록_v01.md`, `test_probe_eol_trust.py`, `probe/` 아래 다섯 개)도 옮기지 않았다. 커밋 전 검사가 `Lab/REQ-032_검사장치실측/` 아래 13개를 모두 `Lab/` 변경으로 분류했다(3절).
