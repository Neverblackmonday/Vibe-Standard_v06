### 3.4 파일별 변경 내용
명세·구현 단계는 아래 항목을 적용본에 반영한다. 문구는 이 절의 뜻을 바꾸지 않는 범위에서 작성 부서가 정한다.

**F1. `.claude/settings.json`(구현)**
- **`ask`**: `permissions.ask`의 기존 Bash 규칙 여섯 개 뒤에 아래 규칙을 더한다. 형식은 기존 규칙과 같이 명령 앞부분 뒤에 `*`를 붙인다(커밋·푸시는 `PowerShell(git commit*)`, `PowerShell(git push*)`, 그 밖은 `PowerShell(<명령> *)`).
  - 커밋·푸시: `git commit`, `git push`
  - 삭제: `Remove-Item`과 그 기본 별칭. PowerShell 5.1의 예상 별칭은 `rm`, `del`, `erase`, `rd`, `rmdir`, `ri`다.
  - 이동: `Move-Item`과 그 기본 별칭. 예상 별칭은 `mv`, `move`, `mi`다.
  - 별칭 목록은 구현 단계에서 부서 `workspace/`의 스크립트(`Bash(python Departments/*/workspace/*)` 규칙)로 `Get-Alias -Definition Remove-Item, Move-Item` 결과를 조회해 확정하고, 조회 명령과 결과 원문을 결과서에 적는다.
  - 기존 `allow`·`deny`와 Bash `ask` 여섯 개는 바꾸지 않는다(체크리스트 1 ②).
- **훅**: `hooks.PreToolUse`에 항목 하나를 둔다. `matcher`는 서브에이전트 기동 도구 이름(`Agent`. Claude Code가 쓰는 이름은 구현 실측으로 확정한다)이고, `type: command`의 명령 하나가 아래 규칙으로 검사한다. 입력은 표준 입력의 JSON(`tool_input`의 `subagent_type`, `model`, `prompt`와 `transcript_path`)이다.
  - H1 대상: `tool_input.subagent_type`이 `quality`인 호출만 검사하고, 그 밖의 호출은 통과시킨다(D6. 검사가 정상으로 실행되면 다른 부서 서브에이전트의 기동은 바뀌지 않는다. 검사가 실행되지 않거나 오류로 끝나면 H7대로 모든 기동을 막는다).
  - H2 PM 모델: 훅을 실행한 메인 세션(PM)의 실행 모델 ID를 구한다. 후보 출처는 훅 입력의 `transcript_path`가 가리키는 세션 기록 파일에서 메인 세션의 마지막 응답에 적힌 `model` 값이고, 훅 입력에 실행 모델이 직접 있으면 그 값이다. 출처는 구현 실측으로 확정한다. 값을 얻지 못하면 막는다. 이 값은 기동 판단의 입력일 뿐 판정 근거가 아니다(F5 7절 1행).
  - H3 단계 판단: `tool_input.prompt`의 단계명 표기(`단계명:` 뒤의 값. F4 「3절 1항」)를 읽는다. 표기가 없거나 값이 비면 막는다. 값이 「최종 판정」으로 시작하면 최종 판정 기동, 「REQ 판정」으로 시작하면 REQ 판정 기동이다. 값이 그 밖의 품질 단계명(`EC 판정`, `명세 판정`, `시각 디자인 판정`, `인수 시험`, `부적합 기록`) 가운데 하나로 시작하면 그 밖의 품질 기동이다. 어느 것으로도 시작하지 않으면 막는다. 비교할 때 공백은 따지지 않으며, 뒤에 붙은 말(`문체 반영 대조`, `수정`, 괄호 속 설명 등)은 시작 부분 판단에 영향을 주지 않는다. 단계명 목록의 원천은 F4 「3절 1항」이다.
  - H4 판정 모델: 기동 구분마다 아래로 정한다. 근거는 1.2절 표와, F4로 고친 「`workflow:` 밖 세션」 항이다. 계열 이름은 대소문자를 따지지 않는다. 계열로 정하는 구분에서 PM 모델이 아래 계열 밖이거나, 1.1절 표 값이 필요한데 읽지 못하면 막는다.
    - REQ 판정 기동: 표 둘째 행의 고급 기본 모델이다. PM 모델이 고급 계열(`opus`)이면 PM 모델이고, 그 밖의 계열(`fable`·`sonnet`)이면 `Workflow/04_모델_운용.md` 1.1절 표 「고급」 행 「기본 모델 ID」 칸의 값(훅이 실행될 때 읽음)이다. PM 모델이 고급 계열이면 PM 모델로 보는 까닭은, REQ 작성 명령·REQ 새 버전 명령의 PM은 고급 기본 모델로 기동되고 원스톱 PM 모델이 고급 계열이면 그 안건의 모델이 고급 기본 모델이기 때문이다(「PM의 책임」 ①). 이렇게 하면 REQ 작성 파이프라인의 REQ 판정 기동은 1.1절 표를 읽지 않으므로 실행 중 표가 갱신되어도 막히지 않는다(4절 위험 10). 그 밖의 계열인 경우는 원스톱 PM이 REQ 판정 문체 반영 대조를 기동하는 경우다(1절 「변경 배경」 요구 항목 4의 ③).
    - 최종 판정 기동: PM 모델의 계열로 정한다(1.2절 표 넷째 행). 최고급 계열(`fable`)이면 PM 모델(그 안건의 모델이 최고급), 고급 계열(`opus`)이면 PM 모델(그 안건의 모델이 고급 기본 모델), 중급 계열(`sonnet`)이면 `Workflow/04_모델_운용.md` 1.1절 표 「고급」 행 「기본 모델 ID」 칸의 값(훅이 실행될 때 읽음)이다.
    - 그 밖의 품질 기동: PM 모델이다. EC 판정·명세 판정·시각 디자인 판정·인수 시험(그 문체 반영 대조와 인수 시험 수정 포함)은 원스톱에서만 기동되며 표 셋째 행이 PM과 같은 그 안건의 모델로 정한다. 부적합 기록은 F4로 고친 「`workflow:` 밖 세션」 항대로, REQ 작성 명령·REQ 새 버전 명령의 PM이 멈추면 표 둘째 행(PM과 같은 고급 기본 모델), 원스톱 PM이 멈추면 셋째 행(PM과 같은 그 안건의 모델)이다.
  - H5 통과 조건: 호출 인자 `model`이 있으면 그 값이 판정 모델 ID와 같을 때만 통과시킨다. 없으면 PM 모델이 판정 모델 ID와 같을 때만 통과시킨다(정의 파일의 `model: inherit`로 PM 모델을 이어받기 때문이다). 같음은 모델 ID 문자열이 같다는 뜻이며 대소문자는 따지지 않는다. 별칭(`opus` 등)과 같은 계열의 다른 버전 ID는 같은 것으로 보지 않는다. 별칭이 가리키는 버전을 훅이 확인할 수 없기 때문이다. 세션 기록 파일의 `model` 값과 호출 인자의 모델 ID 형식이 다르면(접미사 등) 구현이 맞추는 방법을 정하고 실측하되, 다른 버전 ID를 같은 것으로 보지 않는다.
  - H6 막을 때: 종료 코드 2로 끝내고, 표준 오류에 막은 사유(정한 단계, PM 모델, 판정 모델 ID, 기동될 모델)와 조치(호출 인자 `model`에 판정 모델 ID를 주거나 빼고 다시 기동함, 단계명 표기를 고침, 근거 `Workflow/04_모델_운용` 1.2절 「PM의 책임」 ⑥과 3절 1항)를 출력한다.

**구현 실측(개발)**
아래 실측은 부서 `workspace/`의 일회성 스크립트(2.1절 11번)로 임시 폴더에서 하고, 명령·시각·결과 원문을 결과서에 적는다. 저장소 파일은 적용본과 결과서 밖에서 바꾸지 않는다.
- ① 요구 항목 1: 별칭 목록 조회(F1 「`ask`」).
- ② 요구 항목 2: 적용본 `.gitattributes`를 넣은 임시 저장소에서 `core.autocrlf=true`·`false` 체크아웃의 텍스트 파일 해시와 줄바꿈, `*.bat`·`*.cmd`·`.githooks/*`의 줄바꿈(체크리스트 2 ①②와 같은 내용). 이어서 CRLF로 체크아웃된 작업 트리(`core.autocrlf=true`)에 적용본 `.gitattributes`만 바꿔 넣었을 때 `git status --porcelain -uall`에 `.gitattributes` 밖의 경로가 나오지 않는지(4절 위험 6).
- ③ D4: 임시 복제(수정한 추적 파일과 미추적 파일을 둔 상태)에서 F2 「D4 참고 명령」을 실행한 결과(체크리스트 2 ③).
- ④ 요구 항목 4(훅 명령의 직접 실행): 적용본 훅 명령에 표준 입력 JSON과 시험용 세션 기록 파일(`transcript_path`), 시험용 `Workflow/04_모델_운용.md`를 주어 실행한 종료 코드와 출력. 경우는 최소한 아래와 같다.
  - 품질 밖 기동(통과).
  - REQ 판정 기동(PM 모델 고급 기본 모델 ID): 인자 없음(통과), 인자가 PM 모델 ID(통과), 인자가 중급 모델 ID(막음). 「부적합 기록(중단 조건 8)」(그 밖의 품질 기동, PM 모델 고급 기본 모델 ID): 인자 없음(통과).
  - REQ 판정 기동(PM 모델 중급 ID, 단계명 「REQ 판정 문체 반영 대조」): 인자 없음·중급 모델 ID·`opus`(막음), 1.1절 표의 고급 기본 모델 ID(통과).
  - 그 밖의 품질 기동(PM 모델 중급 ID): 인자 없음(통과), 인자가 PM 모델 ID(통과), 인자가 고급 모델 ID(막음).
  - 최종 판정 기동(PM 모델 중급 ID): 인자 없음, 중급 모델 ID, `sonnet`, `opus`, 같은 계열의 다른 버전 ID(끝 숫자만 바꾼 ID)(모두 막음), 1.1절 표의 고급 기본 모델 ID(통과).
  - 최종 판정 기동(PM 모델 고급 기본 모델 ID): 인자 없음(통과), PM 모델 ID(통과), 최고급 모델 ID·같은 계열의 다른 버전 ID(막음).
  - 최종 판정 기동(PM 모델 최고급 ID): PM 모델 ID(통과), 고급 기본 모델 ID(막음).
  - 단계명 표기: 없음·빈 값·알려지지 않은 단계명(막음), 「최종판정」(최종 판정으로 봄), 「REQ 판정 문체 반영 대조」(REQ 판정 기동으로 봄), 「EC 판정(재판정 1차)」·「인수 시험 수정」·「부적합 기록(중단 조건 8)」(그 밖의 품질 기동으로 봄).
  - 값을 얻지 못함: 세션 기록 파일 없음·`model` 값 없음, PM 모델이 세 계열 밖(최종 판정 기동·REQ 판정 기동일 때), `Workflow/04_모델_운용.md` 없음·표 형식 다름(최종 판정 기동이고 PM 모델이 중급일 때, REQ 판정 기동이고 PM 모델이 고급 계열이 아닐 때), 깨진 JSON(모두 막음).
- ⑤ 요구 항목 4(실제 기동 시도): 적용본 `settings.json`과 정의 파일을 둔 임시 복제에서, PM 모델과 판정 모델이 다른 경우(Minor 안건의 최종 판정: PM 세션 `claude-sonnet-5-5`)를 재현한 Claude Code 세션이 품질 서브에이전트를 판정 모델과 다른 모델로 기동하려는 시도(인자 없이 기동, 인자 `sonnet`·`opus`로 기동)가 막히는지와, 인자 `claude-opus-5-5`로 기동하면 판정 모델로 실행되는지를 확인한다(체크리스트 4 ①). 같은 세션에서 H2의 출처(세션 기록 파일이나 훅 입력)로 PM 모델을 얻는지도 확인한다. 실행 모델의 확인 수단과 그 한계(예: 세션 기록 파일의 `model` 값. `Workflow/06` 7절 1행)를 함께 적는다. 호출이 모델 ID를 받지 않으면 그 결과와 4절 위험 4의 처리를 적는다. 이 시도를 실행할 수 없으면 `Workflow/03_라이프사이클` 「판정 세션 밖의 명령 실행」대로 결과서 「실행하지 못한 명령」 표에 적는다.
- ⑥ 훅이 실행되는 셸에서 F1 H7의 처리(검사가 실행되지 않거나 오류로 끝나면 막음)가 동작하는지.
