# 05. 인수인계 및 실행명령

> 이 문서가 정하는 것: 대표님·비서실·PM 사이의 인수인계 순서, 최종 판정서 승인과 커밋, 비서실 서비스별 명령 전달 방식, 실행 명령 두 가지의 형식, 진행 상태 보고, 완료 보고, 요청받은 푸시, PM 지시문, 브리핑, PM 실행 기록.
> 다른 문서가 정하는 것: 비서실·PM의 책무 → `Workflow/02_부서_구조_및_작업구역` 「비서실과 PM의 책무」, 파이프라인 내부 단계 → `Workflow/03_라이프사이클`, 모델·effort 값 → `Workflow/04_모델_운용`.

## 1. 인수인계 순서 (REQ-014_v01)

```text
① 비서실: 대표님과 대화해 요구를 모으고 Departments/Secretariat/assets/inbox/에 ORDER 작성
② 비서실: 「REQ 작성 명령」 안내 또는 실행
③ PM(Claude Code): REQ 작성 → REQ 판정 → REQ 경로와 판정서 경로 보고
④ 비서실: REQ 승인 브리핑 작성(6절) → 대표님: REQ와 승인 브리핑 확인 → 승인(직접 기재 또는 채팅 승인, Workflow/07_문서_서식_및_번호 「승인 기록」)
⑤ 비서실: 「원스톱 실행 명령」 안내 또는 실행
⑥ PM(Claude Code): workflow: 끝까지 무인 진행 → 최종 판정서 경로 보고
⑦ 비서실: 최종 판정서의 체크리스트 번호별 근거를 대조해 대표님께 보고(승인 기록 경로, 반영 대상 목록, 승인 브리핑 경로 포함)
⑧ 대표님: 최종 판정서와 git diff 확인, 대리 기재된 승인 필드 대조 → 최종 판정서 승인
⑨ 비서실(셸 실행 가능): 1.1절대로 적용본 반영 → 정리 → 스테이징 → 커밋 전 검사 → 커밋 → 완료 보고
```

- **커밋**: 최종 판정서 승인 뒤의 커밋은 1.1절을 따른다. 그 밖의 커밋은 아래와 같다. 대표님이 저장소 루트에서 직접 `git add`와 `git commit -m "<메시지>"`를 실행하거나, 셸을 실행할 수 있는 비서실·PM에 커밋을 명시적으로 요청한다. 메시지 형식은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」을 따른다. 커밋 전 검사가 실패하면 원인을 해결한 뒤 다시 커밋한다.
- **푸시**: 대표님이 따로 명시적으로 요청한 푸시는 셸을 실행할 수 있는 비서실이 한다. 셸을 실행할 수 없는 비서실은 명령문을 대표님께 제시한다. 1.1절의 최종 판정서 승인 뒤 커밋 절차에는 푸시를 넣지 않는다.
- 실행 위치는 저장소 루트다. 루트 밖에서 실행하면 `CLAUDE.md`와 `.claude/` 설정이 적용되지 않는다.
- 파이프라인이 중단 조건으로 멈추면 대표님이 결정한 뒤 같은 명령을 다시 실행한다. 오케스트레이터는 기존 산출물(각 문서의 최신 버전과 머리말 `status:`, `result:`)로 진행 위치를 판단해 이어서 진행한다.
- 공식 진행 상태는 각 단계 산출물로만 판단한다. 비서실의 메모와 대화는 근거로 쓰지 않는다. PM 실행 기록(7절)도 근거로 쓰지 않는다.

### 1.1 최종 판정서 승인과 커밋 (REQ-014_v01)

1. **원칙**: 대표님이 최종 판정서(`RES-xxx_vNN`)를 승인하면 셸을 실행할 수 있는 비서실 서비스가 커밋까지 진행한다. 승인 문구를 커밋의 명시적 요청으로 보고, 결과서 반영 명령 표의 덮어쓰기·삭제 승인으로도 본다. 푸시는 이 절차에 넣지 않고 대표님이 따로 정한다. PM은 이 절차에서 커밋하지 않는다.
2. **문구를 받은 서비스와 승인 기록**: 문구를 대표님에게서 직접 받은 비서실이 승인 기록을 작성한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」). 커밋은 문구를 직접 받은 셸 실행 가능 비서실 서비스가 한다. 셸을 실행할 수 없는 비서실 서비스가 문구를 받았으면 승인 기록만 남기고 커밋하지 않는다. 이때 대표님이 셸을 실행할 수 있는 비서실에 같은 문구를 다시 주거나 1절 「커밋」 항의 다른 경로를 쓴다.
3. **「문체 반영」**: 승인 문구에 「문체 반영」이 있으면 원스톱 실행 명령을 다시 실행해 `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」 5항을 마치고, 대조 `pass`를 확인한 뒤 4번으로 간다. 대표님 재승인은 받지 않는다.
4. **적용본 반영**: 최종 판정을 받은 결과서(RPT·DEV)의 반영 명령대로 반영한다. 3번의 대조를 거쳤으면 대조 `pass`를 받은 최신 버전 결과서의 반영 명령(새 적용본 폴더)대로 반영한다. 반영 전에 원본마다 `git diff --stat <기준 커밋> HEAD -- <원본 경로>`가 비어 있는지 확인한다. 기준 커밋은 결과서에 적힌 값이다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」 2항). 비어 있지 않으면 반영하지 않고 5절의 상세 보고를 한다.
5. **정리**: 결과서에 적힌 삭제 대상을 처리한다.
6. **스테이징**: 그 안건의 변경만 스테이징한다. 「그 안건의 변경」은 작업 트리의 변경 가운데 아래 ①~⑦에 해당하는 것이다. 비서실은 `git status --porcelain -uall`로 작업 트리의 변경을 조회해 ①~⑦로 나눈다. ①~⑦에 들지 않는 변경(다른 안건의 파일, 안건 번호가 없는 파일)은 스테이징하지 않고 보고에 적는다.
   - ① `Workflow/07_문서_서식_및_번호` 「문서 체계」의 파일명에서 안건 번호 자리(`xxx`. 파생 안건은 파생 번호까지 포함)가 그 안건 번호와 같은 REQ, EC, DEV, RPT, RES(REQ 판정, EC 판정, 최종 판정). 승인을 받은 최종 판정서 자신과, 있으면 「문체 반영」으로 생긴 새 버전(REQ, 결과서)과 대조 판정서도 여기에 들어간다
   - ② 그 안건의 승인 기록(REQ 승인 기록과 최종 판정서 승인 기록. 파일명은 `Workflow/07_문서_서식_및_번호` 「승인 기록」 4항)
   - ③ 머리말 `related_req`에 그 안건의 REQ가 있는 ORDER의 모든 버전(같은 `ORD-xxx` 번호의 `_v01`부터 최신 버전까지. 버전마다 `related_req` 기재 여부와 관계없다)
   - ④ 부서 `workspace/`의 그 안건 적용본 폴더(`<REQ 번호>_적용본_vNN/`. 「문체 반영」으로 생긴 다음 버전 포함) 아래 파일
   - ⑤ ①의 결과서(RPT·DEV) 「변경 파일」 절에 적힌 경로와, ①의 판정서 「검증 기록」 명령 열에 들어간 부서 `workspace/` 파일(검증 스크립트 등)
   - ⑥ REQ·EC `scope:` 안의 변경, 4번의 반영 명령으로 바뀐 원본 경로, 5번의 정리로 지운 경로
   - ⑦ 그 안건의 PM 실행 기록(`Departments/Secretariat/workspace/실행기록_REQ-xxx.md`. 7절)
7. **커밋 전 검사**: `python Departments/Development/assets/scripts/check_standard.py --staged`를 실행해 종료 코드 0을 확인한다. 스테이징한 변경만 검사하므로 다른 안건이 진행 중이어도 이 안건의 검사 결과에 영향이 없다.
8. **커밋**: `Workflow/07_문서_서식_및_번호` 「번호와 버전」의 메시지로 커밋한다. 7번 검사나 커밋 때의 pre-commit 훅이 실패하면 `--no-verify`를 쓰지 않고 멈춰 5절의 상세 보고를 한다.
9. **완료 보고**: 5절대로 요약 보고하고, 커밋 해시, 스테이징하지 않은 변경(6번), 「대표님이 할 일: 푸시 여부 결정」을 적는다.

## 2. 비서실 서비스별 명령 전달 방식 (REQ-014_v01)

| 비서실 서비스 | PM 실행 명령 전달 |
| :--- | :--- |
| Antigravity | 대표님의 지시를 받아 저장소 루트에서 CLI(`claude ...` 실행 명령)를 직접 실행한다 |
| 코워크 | bash 명령문 전문을 대표님께 제시하고, 대표님이 저장소 루트의 터미널에서 실행한다 |
| 채팅 서비스(claude.ai 채팅 등) | 코워크와 같다. bash 명령문 전문을 대표님께 제시하고, 대표님이 저장소 루트의 터미널에서 실행한다 |

- **PM 지시문**: 비서실이 PM에 주는 지시는 3절 형식과 3절 표의 지시문에 대상 파일과 effort만 채운 실행 명령 한 줄이며, 서비스와 관계없이 같다. 코워크·채팅 서비스는 그 전문을 대표님께 드리고, Antigravity는 같은 명령을 그대로 실행한다. 정지 조건·보고 방식·그 밖의 지시를 더하지 않는다. 정지 조건은 `Workflow/03_라이프사이클` 「중단 조건」이, 보고 방식은 5절 「완료 보고」가 정하기 때문이다. 작성 틀은 `Workflow/templates/PM_DIRECTIVE_TEMPLATE.md`다. PM 지시문은 파일로 저장하지 않는다.

- 코워크가 대표님 PC에서 셸 명령을 실행할 수 없음은 2026-10-06 확인했다(코워크 세션의 기능 목록에 셸 실행 기능 없음). 화면 조작으로 터미널에 입력하는 방식은 표준 절차로 쓰지 않는다.

## 3. 실행 명령

두 명령 모두 형식은 같다. `<effort>`는 `Workflow/04_모델_운용` 「effort」를 따른다.

```bash
claude --model claude-opus-5-5 --effort <effort> --permission-mode acceptEdits "<지시문>"
```

| 명령 | 지시문 |
| :--- | :--- |
| REQ 작성 명령 | `Departments/Secretariat/assets/inbox/ORD-<번호>_v<버전>.md로 REQ 작성 파이프라인을 실행하라. Workflow/03_라이프사이클.md 「REQ 작성 파이프라인」 절을 따른다. effort: <effort>` |
| 원스톱 실행 명령 | `Departments/Secretariat/docs/requests/<REQ 파일>.md 원스톱 파이프라인을 실행하라. Workflow/03_라이프사이클.md 「원스톱 파이프라인」 절을 따른다. effort: <effort>` |

- 지시문의 effort 값은 `--effort` 값과 같게 적는다. PM은 이 표기를 서브에이전트에 전달한다(`Workflow/04_모델_운용` 「타깃 컨텍스트 규칙」).
- `--permission-mode acceptEdits`는 파일 편집 확인만 생략한다. `deny`·`ask`의 적용은 `Workflow/06_통제장치_및_배포` 「권한 설정」·「무인 실행 권한」을 따른다.
- `--agent`를 지정하지 않는다. 메인 세션이 오케스트레이터가 되어 부서 서브에이전트를 기동한다.
- 인증 정보를 명령에 넣지 않는다.
- `--dangerously-skip-permissions` 등 권한 통제 전체를 끄는 옵션을 쓰지 않는다.
- 지시문에 REQ에 없는 작업을 넣지 않는다.

## 4. 진행 상태 보고

오케스트레이터는 아래 시점에 대화창에 진행 문구를 출력한다. 대기 중인 화면을 교착으로 오인하지 않게 하기 위해서다.

1. 서브에이전트를 기동하기 직전: `[부서명] [단계명] 단계를 시작합니다.`
2. 판정이 `fail`일 때: `[단계명] 판정에서 결함 N건이 지적되어 [부서명]이 수정한 뒤 다시 판정합니다.`
3. 마지막 판정이 `pass`일 때: `최종 판정 결과 pass입니다. 완료 보고를 작성합니다.`

## 5. 완료 보고

1. **적용 대상**: PM과 비서실(코워크, Antigravity)의 작업 완료 보고에 적용한다. 4절의 진행 문구는 이 절과 별개다.
2. **요약 보고(기본)**: 결론(상태: 완료·중단·실패·대기 가운데 하나, 다음 단계), 요약, 대표님이 할 일(없으면 「없음」)만 적는다. 결론은 최상단에만 둔다. 통상 승인(REQ 승인, 최종 판정서 승인)과 REQ 「결정 사항 및 선택지」 표의 결정이 필요하면 「대표님이 할 일」에 적는다.
3. **상세 보고 조건**: 아래 두 경우에만 상세 보고를 하고, 그 밖은 요약 보고를 한다.
   - ① 문제 상황: PM의 파이프라인이 `Workflow/03_라이프사이클` 「중단 조건」으로 멈춘 경우(판정 `rejected`, 재판정 한도 초과 포함), 비서실이 파이프라인 밖에서 하는 작업(핫픽스, 1.1절의 적용본 반영·정리·스테이징·커밋 전 검사·커밋 등)이 실패하거나 끝내지 못하고 멈춘 경우
   - ② 대표님 의결이 필요할 때: 작업은 끝났으나 통상 승인과 REQ 결정 표의 결정 밖에서 대표님이 정해야 할 사항이 판정서나 결과서에 적힌 경우
4. **상세 보고 형식**: 결론을 최상단과 최하단에 두고, 본문은 사용자 전역 지침 「작업 보고 형식」 순서(① 요약 ② 작업 내역 ③ 검증 결과 ④ 잔여 작업 및 위험)를 따른다.
5. **경로로 대신할 것**: 실행 로그와 명령 원문은 보고에 넣지 않고 그 결과가 적힌 파일 경로로 대신한다. 문서 경로(REQ, 판정서, 적용본)는 요약 보고에 남긴다.
6. **비서실의 재작성**: 비서실은 PM의 보고를 그대로 옮겨 붙이지 않고 이 양식으로 다시 작성한다.

## 6. 브리핑 (REQ-014_v01)

브리핑의 요건·종류·작성 시점은 이 절이 원천이다.

1. **정의와 요건**: 브리핑은 비서실이 대표님께 보고하려고 작성하는 시각 자료로, 대표님이 편집기 없이 바로 열어 본다. 맨 위(스크롤 없이 보이는 위치)에 결론과 대표님이 할 일을 둔다.
2. **형식**: HTML 단일 파일이다. 스타일은 파일 안에 두고 외부 파일·네트워크 자원(CDN 글꼴, 스크립트, 원격 이미지 등)을 쓰지 않는다. 문자 인코딩은 UTF-8이다. YAML 머리말은 두지 않고 본문 맨 끝에 작성 날짜, 작성 서비스와 모델, 원천 문서 경로를 적는다.
3. **종류와 작성 시점**

   | 종류 | 작성 시점 | 필수 항목(결론·대표님이 할 일 외) |
   | :--- | :--- | :--- |
   | 조사 브리핑 | 조사 자료를 대표님께 보고할 때 | 조사 질문, 핵심 발견, 조사 자료 경로 |
   | 승인 브리핑 | REQ 승인과 최종 판정서 승인을 요청할 때 | ① 결정 표 비교(REQ 승인: 정할 일마다 권고안과 대안, 각 선택의 영향. 최종 판정서 승인: REQ 「결정」 열의 결정마다 반영 위치) ② 덮어쓰기·삭제 경로 목록(REQ 승인: REQ `scope:` 가운데 기존 파일. 최종 판정서 승인: 결과서 반영 명령 표의 원본 경로와 삭제 대상) ③ 원천 문서 경로(REQ, 판정서, 결과서) |
   | 진행 현황 브리핑 | 대표님이 요청할 때 | 안건마다 현재 단계와 최신 산출물 경로, 멈춘 안건의 사유와 필요한 결정. 현재 단계는 공식 진행 상태(1절)로 판단하고 PM 실행 기록(7절)은 참고만 한다 |
   | 기획 브리핑 | 기획 트랙 ③ 프로젝트화(`Workflow/03_라이프사이클` 「기획 트랙」) | 기획안 항목마다 요약과 Go / Hold / Kill 선택지, 기획안 경로 |

4. **보고와의 관계**: 브리핑은 5절 「완료 보고」와 1절 ⑦의 근거 대조 보고를 대신하지 않고 함께 낸다. 보고는 대화창 텍스트로 하고, 브리핑 경로를 보고에 적는다. 승인 근거의 원천은 판정서·REQ이며 브리핑은 그 요약이다.
5. **판정**: 브리핑은 판정하지 않는다. 판정서·REQ 등 원천 문서의 요약이며 승인 근거가 아니기 때문이다. 이 규정은 사용자 전역 지침 「생성과 판정의 분리」에 대한 이 저장소의 예외다.
6. **위치·이름·서식·버전**: 위치·이름·버전은 `Workflow/07_문서_서식_및_번호` 「문서 체계」·「번호와 버전」을 따르고, 서식은 `Workflow/templates/BRIEFING_TEMPLATE.html`이다.

## 7. PM 실행 기록 (REQ-014_v01)

PM 실행 기록은 이 절이 원천이다.

1. **성격**: 실행 기록은 PM이 안건마다 남기는 진행 이력이다. 비서실의 대조·보고·브리핑에 쓰는 참고 자료이며 공식 진행 상태의 근거가 아니다(1절).
2. **파일**: 안건마다 하나이며 `Departments/Secretariat/workspace/실행기록_REQ-xxx.md`(파생 안건은 `실행기록_REQ-xxx-n.md`)에 둔다. 버전을 붙이지 않고 행을 더해 쌓는다. 이 방식은 사용자 전역 지침 「버전 관리」에 대한 이 저장소의 규정이다. 이름 규칙은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」을 따른다.
3. **작성과 추가**: PM이 REQ를 처음 작성할 때 만들고, 그 세션을 시작한 때(6항 ①)부터 적는다. 행을 더하기만 하고 이미 적은 행은 고치지 않는다.
4. **머리말**: `task_id`, `created`.
5. **본문**: 표 하나이며 열은 `| 시각 | 단계 | 사건 | 판정 결과 | 재판정 횟수 | effort | 중단 사유 | 대표님께 한 질문과 답 |`이다. 해당 없는 칸은 `—`로 적는다.
6. **기록 시점**: ① 실행 명령으로 세션을 시작할 때(effort는 실행 명령 지시문의 값) ② 서브에이전트를 기동할 때 ③ 판정서를 받을 때(판정 결과에 `result`와 판정서 경로를 적고, 재판정 횟수는 `Workflow/03_라이프사이클` 「재판정 한도」의 셈을 따른다) ④ 중단 조건으로 멈출 때 ⑤ 대표님께 질문하고 답을 받을 때(질문과 답을 원문 그대로 적는다) ⑥ 완료 보고할 때.
7. **커밋**: 그 안건의 최종 판정서 승인 뒤 커밋에 함께 넣는다(1.1절 6항 ⑦).
