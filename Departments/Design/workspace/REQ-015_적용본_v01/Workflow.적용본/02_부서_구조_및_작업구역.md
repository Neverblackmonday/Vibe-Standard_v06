# 02. 부서 구조 및 작업구역

> 이 문서가 정하는 것: 저장소 구조, 부서별 책임과 산출물, 비서실·PM의 책무, 작업 구역(누가 언제 어디를 수정할 수 있는가).
> 다른 문서가 정하는 것: 부서별 권한 한계의 원칙 → `AGENTS.md` 「부서와 권한 한계」, 산출물 이름·번호 → `Workflow/07_문서_서식_및_번호`.

## 1. 저장소 구조

```text
[저장소 루트]
├── AGENTS.md            # 최상위 규정
├── CLAUDE.md            # Claude Code 진입 파일 (@AGENTS.md 한 줄)
├── setup.cmd            # 최초 1회: Git 초기화, 훅 경로 설정, 첫 커밋
├── .gitattributes       # 줄바꿈 규칙, 배포본 제외 규칙
├── .gitignore
├── .claude/             # settings.json(권한), agents/(부서 서브에이전트)
├── .githooks/pre-commit # 커밋 전 check_standard.py 실행
├── Workflow/            # 매뉴얼 01~07, templates/(서식)
├── Audits/              # 외부 검토 보고서
├── CEO/References/      # 대표님 전용 자료 (CEO/ 전체가 대표님 구역)
├── Departments/         # 부서 작업 공간 (3절)
├── Package_sample/      # 배포본을 푸는 자리. .gitkeep만 추적 (Workflow/06 「배포본과 업데이트 패키지」)
├── Package_update/      # 업데이트 패키지를 푸는 자리. .gitkeep만 추적 (같은 절)
└── _archive/            # 지난 버전 기록 (읽기 전용)
```

### 2.1 비서실과 PM의 책무 (REQ-015_v02)

| 주체 | 책무 |
| :--- | :--- |
| 비서실 (코워크, Antigravity, 채팅 서비스) | ① 대표님과 대화해 요구를 모으고 `Departments/Secretariat/assets/inbox/`에 ORDER를 작성한다. ORDER 머리말 `classification_proposal`에 분류를 제안한다 ② PM 실행 명령을 서비스별 방식으로 전달한다(`Workflow/05_인수인계_및_실행명령` 「비서실 서비스별 명령 전달 방식」) ③ 최종 판정서의 체크리스트 번호별 근거를 대조해 대표님께 보고한다. 보고에 대조할 승인 기록 경로와 결과서의 반영 대상 목록(반영 명령 표의 원본 경로와 삭제 대상)과 최종 판정서의 「삭제 대상」을 함께 적는다 ④ 핫픽스를 수행한다. 사전 승인 요청, 수정, 검증, HOTFIX 작성의 절차는 `Workflow/03_라이프사이클` 「핫픽스 트랙」을 따른다 ⑤ 대표님에게서 직접 받은 승인 문구로 승인 기록을 남기고 승인 필드와 「결정」 열을 기재한다(`Workflow/07_문서_서식_및_번호` 「승인 기록」) ⑥ 외부 검토 보고서(AUDIT)를 작성한다 ⑦ 셸을 실행할 수 있는 비서실 서비스는 최종 판정서 승인 뒤 적용본 반영·정리·스테이징·커밋 전 검사·커밋을 한다(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」) ⑧ 조사 자료를 `assets/research/`에, 브리핑을 `assets/briefings/`에 작성한다. 조사 자료의 이름과 머리말은 `Workflow/07_문서_서식_및_번호` 「문서 체계」·「머리말」을 따른다. 브리핑의 요건·종류·작성 시점은 `Workflow/05_인수인계_및_실행명령` 「브리핑」을 따른다 ⑨ 대표님이 아이디어 덤프·기획 단계·기획을 요청하면 기획 트랙을 수행한다(`Workflow/03_라이프사이클` 「기획 트랙」) ⑩ 대표님이 따로 명시적으로 요청한 푸시를 한다(`Workflow/05_인수인계_및_실행명령` 1절 「푸시」 항) |
| PM (Claude Code 메인 세션) | ① ORDER로 REQ와 체크리스트를 작성하고 분류를 REQ 머리말 `classification:`에 확정한다. REQ를 처음 작성할 때 ORDER 머리말 `related_req`에 그 REQ 이름을 더한다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」) ② REQ 작성 파이프라인과 원스톱 파이프라인을 지휘한다. 서브에이전트를 순서대로 기동·인계하고 진행 상태를 보고한다 ③ REQ 판정 `fail` 때와 격상 결정 때 REQ 새 버전을 작성한다 ④ 안건마다 실행 기록을 작성한다(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」) |

- 비서실은 ORDER, 승인 기록, 승인 필드와 「결정」 열(4절), 검토 보고서, 핫픽스의 대상 파일과 HOTFIX(4절), 조사 자료, 아이디어 백로그, 기획안, 브리핑(4절), 최종 판정서 승인 뒤 반영 명령 대상(거버넌스 파일 포함)과 정리 대상(4절) 외에는 저장소 파일을 수정하지 않는다. 비서실의 검토 보고서는 `Audits/`에 둔다. PM이 수정할 수 있는 경로는 4절을 따른다.
- 비서실이 저장소나 셸에서 하는 작업의 공통 규칙과 고정 절차, 비서실의 여러 세션을 함께 쓸 때의 담당과 기록은 `Workflow/05_인수인계_및_실행명령` 「비서실 실행 절차」를 따른다.
- 승인 필드(`approved:`, `confirmed:`)와 REQ 「결정」 열의 기재 주체와 방법은 `Workflow/07_문서_서식_및_번호` 「승인 기록」을 따른다.

## 3. 공통 1차 하위폴더

```text
Departments/<부서>/
├── docs/       # 정제된 문서(기획서, 명세, 안건)
├── assets/     # 실제 자산(코드, 테스트, 스크립트, 파라미터, 조사 자료)
├── results/    # 공식 결과서와 판정서
└── workspace/  # 중간 산출물, 메모, 거버넌스 적용본
```

빈 폴더는 `.gitkeep`으로 유지한다. 비서실 `assets/`에는 바로 아래에 파일을 두지 않고 하위 폴더(`inbox/`, `research/`, `planning/`, `briefings/`)에만 둔다. 최종 산출물은 `docs/`, `assets/`, `results/`에만 둔다.

## 4. 작업 구역 (REQ-015_v02)

| 구분 | 수정할 수 있는 경로 | 수정 주체 |
| :--- | :--- | :--- |
| REQ 승인 전 | `Departments/Secretariat/assets/inbox/`(ORDER) | 비서실(ORDER는 그 ORDER의 담당 세션. `Workflow/05_인수인계_및_실행명령` 「비서실 동시 운용」) |
| 조사·기획 자료와 브리핑 | `Departments/Secretariat/assets/research/`(조사 자료), `Departments/Secretariat/assets/planning/`(아이디어 백로그, 기획안), `Departments/Secretariat/assets/briefings/`(브리핑) | 비서실 |
| 승인 기재 | `Departments/Secretariat/assets/inbox/`(승인 기록), 대상 REQ의 승인 필드와 「결정」 열, 대상 HOTFIX의 `confirmed:`(`Workflow/07_문서_서식_및_번호` 「승인 기록」) | 비서실 |
| REQ 승인 전 | `Departments/Secretariat/docs/requests/`, `Departments/Secretariat/workspace/`, ORDER 머리말 `related_req` 필드 | PM |
| 실행 기록 | `Departments/Secretariat/workspace/실행기록_REQ-*.md`(`Workflow/05_인수인계_및_실행명령` 「PM 실행 기록」) | PM(REQ 승인 전과 뒤) |
| REQ 승인 전 | `Departments/Quality/results/`(REQ 판정서), `Departments/Quality/workspace/` | 품질 서브에이전트 |
| REQ 승인 후 | REQ `scope:` 가운데 자기 단계의 경로와 자기 부서 `results/`·`workspace/` | 각 단계 서브에이전트 |
| 핫픽스 | 대표님이 사전 승인한 대상 파일과 `Departments/Secretariat/results/` | 비서실 |
| 최종 승인 뒤 반영 | 최종 판정서를 받은 결과서의 반영 명령 대상과 삭제 대상, 승인받은 최종 판정서의 「삭제 대상」(`Workflow/05_인수인계_및_실행명령` 「최종 판정서 승인과 커밋」) | 셸을 실행할 수 있는 비서실 |
| 외부 검토 | `Audits/` | 비서실 등 저장소 밖 세션 |
| 대표님 전용 | `CEO/`, 거버넌스 파일(「최종 승인 뒤 반영」 행 제외), `_archive/` | 대표님 |

- 커밋 전 검사가 scope 대조에서 빼는 경로는 이 표와 별개의 구현 목록이며, 원천은 `check_standard.py`다(`Workflow/06_통제장치_및_배포` 「커밋 전 검사」).
