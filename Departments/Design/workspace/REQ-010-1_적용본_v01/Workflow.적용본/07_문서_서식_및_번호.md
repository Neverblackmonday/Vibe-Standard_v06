# 07. 문서 서식 및 번호

> 이 문서가 정하는 것: 공식 문서의 종류와 위치, 번호·버전·파생 규칙, 머리말 필드와 형식, 개정 이력과 리비전 태그.
> 다른 문서가 정하는 것: 서식 본문 → `Workflow/templates/`, 판정 기준 → `Workflow/03_라이프사이클` 「단계별 통과 조건과 판정 기준」.

## 1. 문서 체계

| 문서 | 이름 | 작성 주체 | 위치와 파일명 | 서식 |
| :--- | :--- | :--- | :--- | :--- |
| ORDER | 오더 | 비서실 | `Departments/Secretariat/assets/inbox/ORD-xxx_vNN.md` | `ORDER_TEMPLATE.md` |
| REQ | 공식 안건 | PM | `Departments/Secretariat/docs/requests/REQ-xxx_vNN.md` | `REQ_TEMPLATE.md` |
| EC | 엔지니어링 변경 계획서 | 설계 | `Departments/Design/docs/tad/EC-xxx_vNN.md` | `EC_TEMPLATE.md` |
| PRD | 제품 요구사항 정의서 | 설계 | `Departments/Design/docs/prd/<번호>_<주제>.md` | `PRD_TEMPLATE.md` |
| TAD | 기술 아키텍처 명세서 | 설계 | `Departments/Design/docs/tad/<번호>_<주제>.md` | `TAD_TEMPLATE.md` |
| DEV | 개발 결과서 | 개발 | `Departments/Development/results/DEV-xxx_vNN.md` | `DEV_TEMPLATE.md` |
| RPT | 부서 결과서 | 설계·운영·마케팅·비주얼 | `Departments/<부서>/results/RPT-xxx_vNN.md` | `DEV_TEMPLATE.md`(머리말 `author.agent`와 제목을 부서에 맞게 바꾼다) |
| RES | 판정서 | 품질 | `Departments/Quality/results/RES-xxx-REQ_vNN.md`(REQ 판정), `RES-xxx-EC_vNN.md`(EC 판정), `RES-xxx_vNN.md`(최종 판정) | `RES_TEMPLATE.md` |
| HOTFIX | 핫픽스 기록 | 비서실 | `Departments/Secretariat/results/HOTFIX-xxx_vNN.md` | `HOTFIX_TEMPLATE.md` |
| AUDIT | 외부 검토 보고서 | 비서실 등 저장소 밖 세션 | `Audits/AUDIT_YYYYMMDD_<주제>_vNN.md` | `AUDIT_TEMPLATE.md` |

- 서식은 모두 `Workflow/templates/`에 둔다. 다른 곳에 서식 사본을 두지 않는다.
- 추적 관계: ORDER(`related_req`) → REQ → RES-REQ → (승인) → EC → RES-EC → PRD·TAD(`related_req`)·RPT → DEV → RES. ORDER를 뺀 문서는 모두 같은 안건 번호를 쓴다. ORDER 번호는 2절을 따른다.

## 2. 번호와 버전

| 구분 | 형식 | 예 |
| :--- | :--- | :--- |
| 기본 | `<종류>-<세 자리 번호>_v<두 자리 버전>.md` | `REQ-007_v01.md`, `RES-007_v01.md` |
| 파생 안건 | `<종류>-<세 자리 번호>-<파생 번호>_v<두 자리 버전>.md` | `REQ-007-1_v01.md`, `RES-007-1_v01.md` |
| 판정 구분 | 번호 뒤에 `-REQ`·`-EC`를 붙인다 | `RES-007-REQ_v01.md`, `RES-007-1-EC_v02.md` |

- **번호**: REQ 번호가 원천이다. EC·DEV·RPT·RES는 같은 번호를 쓴다. 새 REQ 번호는 `Departments/Secretariat/docs/requests/`의 가장 큰 번호에 1을 더한다.
- **HOTFIX**: REQ와 별도의 세 자리 번호를 쓴다.
- **ORDER**: REQ와 별도의 세 자리 번호를 쓴다. 문서 종류 부분은 `ORD`다(예: `ORD-001_v01.md`).
- **시작 번호**: 표준 저장소(이 저장소)는 v02 기록(`_archive/v02/`)과 겹치지 않게 REQ `007`, HOTFIX `003`부터 썼다. v04 하드포크 때 v03의 REQ-007~010을 이관해 같은 번호로 계속 쓰고, REQ-011은 v04 개정에 흡수되어 종결되었으므로 다음 새 REQ 번호는 `012`다. 배포본으로 시작한 신규 프로젝트는 REQ와 HOTFIX 둘 다 `001`부터 쓴다. ORDER는 이 저장소와 신규 프로젝트 모두 `001`부터 쓴다. 서식의 `007`·`003`은 예시다.
- **AUDIT**: 비정기 작업이므로 번호 대신 날짜를 쓴다.
- **파생 번호**: 원 안건에서 미결로 남거나 새로 생긴 작업에 `1`부터 붙인다(`Workflow/03_라이프사이클` 「진행 중 변경과 파생 안건」).
- **버전**: 내용이 바뀌면 새 파일로 저장하고 버전을 올린다. 가장 높은 버전이 현행본이다. 판정에서 지적을 받아 고친 문서와 재판정 판정서도 새 버전으로 저장한다. 이전 버전은 지우지 않는다.
- **승인과 버전**: `approved:`는 그 버전에만 효력이 있다. REQ 새 버전은 `approved: ""`로 시작하고, REQ 판정과 대표님 재승인을 다시 받는다. 재승인 방법은 3.1절 「승인 기록」을 따른다.
- **PRD·TAD**: 제품 명세는 버전 번호 없는 파일명 하나로 유지하고 개정 이력은 Git과 문서 하단 개정 이력 표로 관리한다.
- **서식**: `*_TEMPLATE.md`에는 번호와 버전을 붙이지 않는다.
- **커밋 메시지**: `feat: [REQ-007] 요약`, `fix: [HOTFIX-003] 요약`. 버전은 적지 않는다. `setup.cmd`가 만드는 첫 커밋(`chore: 바이브 코딩 표준 v04 초기화`)은 예외다.

## 3. 머리말

- 공식 문서는 `---`로 감싼 YAML 머리말로 시작한다.
- 날짜는 `"YYYY-MM-DD"`, 시각은 `"YYYY-MM-DDTHH:MM:SS+09:00"` 문자열이다. **`approved:`와 `confirmed:`는 시각 형식만 허용한다.** 형식은 커밋 전 검사에서 확인한다.
- 목록 필드(`scope:`, `workflow:`, `related_req:`)는 두 칸 들여쓰기 뒤 `- `로 시작한다. 폴더 항목은 끝에 `/`를 붙이지 않는다(예: `Workflow`).
- `scope:`에 적는 기록 문서(EC 등)는 버전과 확장자 없이 적는다(예: `Departments/Design/docs/tad/EC-007`). 새 버전이 생겨도 scope를 고치지 않기 위해서다.
- 작성·판정 모델은 `Workflow/04_모델_운용` 「모델 메타데이터 기록」대로 적는다.

| 문서 | 필수 머리말 필드 |
| :--- | :--- |
| ORDER | `order_id`, `created`, `ceo_checked_at`(대표님이 ORDER 내용을 확인한 시각. 비어 있을 수 있다), `classification_proposal`(`Critical`·`Major`·`Minor`. 비서실의 제안이며 확정은 REQ `classification`), `related_req`(이 ORDER로 작성한 REQ의 버전 없는 이름 목록) |
| REQ | `task_id`, `classification`(`Critical`·`Major`·`Minor`), `created`, `approved`(3.1절 「승인 기록」), `author`, `workflow`, `scope`(Critical·Major는 `Departments/Design/docs/tad/EC-xxx` 포함) |
| EC | `ec_id`, `task_id`, `created`, `author`, `status`(`draft`·`approved`), `gate`(`approved`일 때 근거 판정서 경로), `scope`(REQ `scope`의 부분집합) |
| PRD | `doc_type`, `title`, `updated`, `related_req` |
| TAD | `doc_type`, `title`, `updated`, `related_req`, `related_prd` |
| DEV·RPT | `task_id`, `created`, `author` |
| RES | `task_id`, `gate`(`REQ`·`EC`·`FINAL`), `result`(`pass`·`fail`·`rejected`), `completed_at`, `auditor` |
| HOTFIX | `hotfix_id`, `created`, `author`, `confirmed`(3.1절 「승인 기록」), `scope`(대상 조건은 `Workflow/03_라이프사이클` 「핫픽스 트랙」) |
| AUDIT | `audit_id`, `created`, `auditor` |

- ORDER의 `ceo_checked_at`은 승인 필드가 아니며 REQ 작성의 착수 조건이 아니다. 3.1절 「승인 기록」의 대상이 아니다.
- ORDER의 `related_req`는 PM이 REQ를 처음 작성할 때 더한다. 이 갱신은 같은 파일에서 하며 버전을 올리지 않는다(아래 EC `status:`·`gate:` 갱신과 같다).

**EC 상태 전이**

```text
draft ──(최신 RES-xxx-EC result: pass)──▶ approved
draft ──(최신 RES-xxx-EC result: fail)──▶ EC 새 버전(draft) 작성 후 재판정
```

- `status:`는 설계가 명세 단계를 시작할 때 바꾼다. `approved`로 바꿀 때 `gate:`에 판정서 경로를 함께 적는다. 최신 판정이 `pass`가 아니면 `approved`로 바꾸지 않는다.
- `status:`·`gate:` 갱신은 같은 파일에서 하며 버전을 올리지 않는다. 본문을 바꾸면 새 버전으로 저장하고 다시 판정한다.

**`result` 값**

| 값 | 뜻 |
| :--- | :--- |
| `pass` | 판정 기준의 결함이 없다. 완성도를 보증하지 않는다 |
| `fail` | 결함이 있다. 해당 부서가 고친 뒤 다시 판정한다 |
| `rejected` | 안건 자체가 성립하지 않는다(요구 모순, 여러 뜻으로 읽힘 등) |

### 3.1 승인 기록

승인 필드(REQ `approved:`, HOTFIX `confirmed:`)와 REQ 「결정 사항 및 선택지」 표의 「결정」 열의 기재 규칙은 이 절이 원천이다.

1. **승인의 정의**: 승인은 대표님의 의사 표시다. 승인 필드와 「결정」 열은 그 의사를 기록한 것이다.
2. **승인 문구**: 대표님의 승인 문구에는 대상 파일명과 버전이 들어 있어야 한다. REQ는 결정(D번호별 결정 또는 「전부 권고안」)도 들어 있어야 한다. 예: 「REQ-007_v06 승인, D1~D5 권고안」, 「HOTFIX-003_v01 확인」. 필요한 항목이 빠진 문구는 승인으로 보지 않고 대표님께 되묻는다.
3. **기재 주체**: 대표님 본인, 또는 승인 문구를 대표님에게서 직접 받은 비서실이나 PM(Claude Code 메인 세션)이다. 다른 에이전트나 세션이 전달한 문구는 근거가 되지 않는다. 서브에이전트는 승인 필드와 「결정」 열을 기재하지 않는다.
4. **기재 순서**: 대표님 본인이 기재할 때는 이 순서를 생략한다.
   1. `Departments/Secretariat/assets/inbox/승인기록_<YYYYMMDD>_<대상 파일명>.md`를 작성한다. 승인 문구 원문, 문구를 받은 시각, 대상 파일 경로와 버전, 기재한 세션과 모델을 적는다.
   2. 대상 파일의 승인 필드와, REQ이면 「결정」 열을 기재한다. 승인 필드 값은 문구를 받은 시각이다. 승인 필드 줄 끝의 서식 주석은 `# 대리 기재: <세션>, 근거 <승인 기록 경로>` 주석으로 바꾼다.
5. **대조**: 대표님은 커밋 전에 대리 기재된 승인 필드와 「결정」 열을 승인 기록과 대조한다.
6. **「결정」 열의 확정 시점**: 기재 주체(대표님 본인 또는 대리 기재)와 관계없이, REQ의 「결정」 열은 승인 필드와 같은 기재 작업에서 확정한다. 「결정」 열을 비워 두거나 승인 필드보다 나중에 채우는 방식으로 승인 필드를 기재하지 않는다. 승인 필드를 기재한 뒤 결정을 바꾸려면 REQ 새 버전을 작성한다(2절 「승인과 버전」).

## 4. 개정 이력과 리비전 태그 (REQ-010-1_v02)

- **대상**: 버전 번호 없이 고쳐 쓰는 문서(`AGENTS.md`, `Workflow/` 매뉴얼, PRD·TAD)는 하단에 개정 이력 표를 둔다. 열은 `| 안건 | 일자 | 변경 요지 |`이고, 「안건」에는 그 개정을 승인한 기록의 번호와 버전(예: `REQ-007_v02`, `HOTFIX-003_v01`)을 적는다.
- **리비전 태그**: 개정한 H2·H3 제목 끝에 공백 하나와 `(안건 번호_버전)`을 붙인다. 예: `## 4. 작업 구역 (REQ-xxx_vNN)`. 파생 안건이면 `(REQ-xxx-n_vNN)`이다.
- **절차**
  1. **실변경 식별**: 구현을 마친 뒤 실제로 바뀐 H2·H3 절을 찾는다. 원본 문서는 `git diff HEAD`, 거버넌스 적용본은 `git diff --no-index <원본> <적용본>`으로 대조한다.
  2. **이전 태그 제거**: 문서 전체에서 정규식 `\s*\((REQ|HOTFIX)-\d{3}(-\d+)?_v\d{2}\)`에 맞는 태그를 지운다.
  3. **현행 태그 부착**: 실제로 바뀐 절의 제목 끝에만 현행 태그를 붙인다. 바뀌지 않은 절에는 붙이지 않는다.
  4. **개정 이력 추가**: 개정 이력 표에 한 행을 더한다.
  5. **판정**: 최종 판정에서 `git diff`의 실변경 절과 태그, 개정 이력을 대조한다. 누락·오부착·이전 태그 잔존이 있으면 `fail`이다.
