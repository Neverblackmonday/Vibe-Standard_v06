# EC-009: 비서실·PM 역할 재편과 ORDER 서식 설계

## 1. 개요
- **관련 안건**: `Departments/Secretariat/docs/requests/REQ-009_v06` (결정 D1~D5 모두 권고안. 근거 `Departments/Secretariat/assets/inbox/승인기록_20261008_REQ-009_v06.md`)
- **호칭**: 이 EC는 REQ 1절 끝의 호칭 구분을 따른다. 「비서실 세션」은 현행 Claude Code `secretariat`, 「창구」는 현행 창구, 「세션」을 붙이지 않은 「비서실」과 「PM」은 재편 뒤의 역할이다.
- **변경 배경**
  - 현행 역할은 `Workflow/02_부서_구조_및_작업구역` 2.1절 「비서실 세션과 창구의 책무」가 정한다. 창구 책무는 ①~⑤, 비서실 세션 책무는 ①·②다. 창구의 승인 기재 권한은 `Workflow/07_문서_서식_및_번호` 3.1절 「승인 기록」 3항과 `Workflow/02_부서_구조_및_작업구역` 4절 「작업 구역」 「승인 기재」 행이 정한다.
  - 현행 요구 메모와 REQ는 같은 지시 원문을 두 번 적는다(요청 원문 「요구사항 메모랑 req랑 같은내용을 반복해서 쓰는거 아님?」).
  - 현행 핫픽스는 비서실 세션(Claude Code)이 수정·검증한다(`Workflow/03_라이프사이클` 9절 「핫픽스 트랙」 2항). 재편 뒤 핫픽스를 맡는 비서실은 저장소 밖 서비스(코워크, Antigravity 등)다. `.claude/settings.json`의 `deny`는 Claude Code에만 적용된다(`Workflow/06_통제장치_및_배포` 1절 계층 1 「한계」).
- **변경 목표**
  - 비서실과 PM의 역할 정의, ORDER 서식 초안 전문, ORDER와 REQ의 구분, 후속 안건이 반영할 대상 목록을 `RPT-009`에 확정한다(요청 원문 1~8번, 3.3절).
  - 통제장치 가운데 역할 재편과 ORDER 도입으로 바뀌어야 할 곳을 조사해 `DEV-009`에 기록한다. 코드와 설정은 바꾸지 않는다(3.4절).
  - 거버넌스 파일의 원본과 적용본은 만들지 않는다(요청 원문 9번).

### 3.3 `RPT-009` 설계 (명세 단계)
결과서 서식은 `Workflow/templates/DEV_TEMPLATE.md`(머리말 `author.agent`와 제목을 설계에 맞게 바꾼다)를 따르고, 본문에 아래 다섯 부분을 둔다. 문구는 명세 단계가 정하되 아래 설계 결정과 제약을 지킨다. 「쓰지 않는 말」(`Workflow/01_표준_개요` 「용어」)은 쓰지 않는다. 단, 「창구」는 현행 규정을 인용하거나 변경 전 상태를 가리킬 때만 쓴다.

1. **역할 정의 (체크리스트 1~5·8번)**
   - ① **비서실**: 대상 서비스는 코워크, Antigravity, 채팅 서비스(claude.ai 채팅 등)다. 책무, 수정할 수 있는 경로, 하지 않는 일을 적는다.
   - ② **PM**: PM은 Claude Code 메인 세션이며 오케스트레이터와 같은 주체이고 호칭만 다르다는 문장을 넣는다. 실행 환경은 Claude Code(Claude CLI)이고, 실행 명령으로 기동한다(`Workflow/05_인수인계_및_실행명령` 3절 형식). 책무, 수정할 수 있는 경로, 하지 않는 일을 적는다.
   - ③ **설계 결정 E1(REQ 작성 주체)**: PM이 메인 세션에서 REQ를 직접 작성한다. REQ 작성용 서브에이전트를 두지 않는다. 근거: 요청 원문 6번 「PM이 작성하는 REQ」와 3번 「PM과 오케스트레이터는 같은 주체」를 함께 만족하려면 REQ 작성자가 메인 세션이어야 한다. 비서실 세션의 두 책무가 모두 다른 주체로 넘어가므로(④) `secretariat` 서브에이전트는 맡을 업무가 남지 않는다. 생성과 판정의 분리는 REQ 판정을 품질 서브에이전트가 하므로 유지된다(`AGENTS.md` 「불변 원칙」 4항). 이 결정을 근거와 함께 `RPT-009`에 적는다.
   - ④ **책무 대응표**: 아래 대응을 표로 적는다. 행마다 현행 문구 요지, 재편 뒤 주체, 근거(요청 원문 번호 또는 D번호)를 둔다.

     | 현행 책무 | 재편 뒤 주체 | 근거 |
     | :--- | :--- | :--- |
     | 창구 ① 요구 수집, 요구 메모 작성 | 비서실. 요구 메모 대신 ORDER를 작성한다 | 요청 원문 1·5·6번, D4 |
     | 창구 ② 실행 명령 안내·실행 | 비서실. 서비스별 전달 방식은 ⑦ | 요청 원문 1·4번 |
     | 창구 ③ 최종 판정서 근거 대조·보고 | 비서실 | 요청 원문 1번 |
     | 창구 ④ 핫픽스 대상 목록 제시·사전 승인 | 비서실 | 요청 원문 1·8번 |
     | 창구 ⑤ 승인 기록, 승인 필드·「결정」 열 기재 | 비서실 | 요청 원문 1번 |

   - ⑤ **승인 기재 권한(체크리스트 3번)**: 현행 오케스트레이터의 승인 기재 권한(`Workflow/01_표준_개요` 「용어」 오케스트레이터 행, `Workflow/07_문서_서식_및_번호` 3.1절 3항)은 재편 뒤 PM이 그대로 갖는다. 창구의 권한은 비서실이 갖는다. 서브에이전트는 계속 기재하지 않는다.
   - ⑥ **분류(체크리스트 5번)**: 비서실은 ORDER의 분류 제안 필드에 제안만 적는다. 분류 확정 주체는 PM이고 확정 위치는 REQ 머리말 `classification:`이다.

     | 검증 명령(`check_standard.py`, 관련 테스트) 실행 | 셸을 실행할 수 있는 비서실(Antigravity 등)은 직접 실행한다. 셸을 실행할 수 없는 비서실(코워크, 채팅 서비스)은 bash 명령문을 대표님께 제시하고, 대표님이 실행한 결과 원문을 비서실이 HOTFIX에 적는다(D3) |

     - 비서실 서비스마다 저장소 파일을 수정할 수 있는지 적는다. 확인한 근거가 없으면 「확인 불가」로 적는다. 저장소 파일을 수정할 수 없는 서비스의 핫픽스 처리는 이 안건에서 정하지 않고 5번 미결 사항에 올린다.
   - ⑨ **명칭과 폴더**: D1에 따라 `Departments/Secretariat/` 폴더 이름은 그대로이고, 그 안에 비서실 산출물(ORDER, HOTFIX)과 PM 산출물(REQ)이 함께 있다는 사실을 적는다. REQ 머리말 `author.agent` 값은 `"PM"`, HOTFIX 머리말 `author.agent` 값은 `"Secretariat"`(비서실)으로 정한다.

2. **ORDER 서식 초안 전문 (체크리스트 5~7번)**
   - 초안은 서식 파일 그대로 옮길 수 있는 전문(머리말, 제목, 작성 안내, 본문 절)으로 코드 블록 하나에 적는다.
   - **파일명과 위치**: `Departments/Secretariat/assets/inbox/ORD-<세 자리 번호>_v<두 자리 버전>.md`(D1). 번호는 REQ와 별도로 `001`부터 쓴다. 하나의 ORDER가 여러 REQ로 이어질 수 있으므로 REQ 번호를 쓰지 않는다. 버전은 `Workflow/07_문서_서식_및_번호` 2절 「번호와 버전」을 따른다.
   - **머리말 필드**(메모 4절 구성 1항과 1:1. 다른 필드를 더하지 않는다):

     | 메모 4절 구성 1항 | 필드 | 값 형식 |
     | :--- | :--- | :--- |
     | 오더 번호(`ORD-NNN`) | `order_id` | `"001"`(문서 이름은 `ORD-001`) |
     | 작성일 | `created` | `"YYYY-MM-DD"` |
     | 대표님 확인 일시 | `ceo_checked_at` | `"YYYY-MM-DDTHH:MM:SS+09:00"`. 비어 있을 수 있다 |
     | 분류 제안 | `classification_proposal` | `Critical`·`Major`·`Minor` 가운데 하나 |
     | 연결 REQ 목록 | `related_req` | 목록 필드. 항목은 버전 없는 REQ 이름(예: `REQ-012`) |

     - 승인 필드 이름(`approved`, `confirmed`)을 쓰지 않는다(D2). `ceo_checked_at`은 대표님이 ORDER 내용을 확인한 시각의 기록이며 승인 필드가 아니다. 착수 승인은 REQ `approved:` 하나로 유지한다. 따라서 `ceo_checked_at`은 REQ 작성의 착수 조건이 아니고, `Workflow/07_문서_서식_및_번호` 3.1절 「승인 기록」 절차의 대상도 아니다.
     - `ceo_checked_at`을 기재한 뒤 본문을 바꾸면 ORDER 새 버전을 `ceo_checked_at: ""`로 작성한다.
     - `related_req`는 PM이 REQ를 처음 작성할 때 그 REQ 이름을 더한다. 이 필드 갱신은 버전을 올리지 않는다(EC의 `status:`·`gate:` 갱신과 같은 방식).
   - **본문 절**(메모 4절 구성 2~6항과 1:1, 같은 순서): 1. 지시 원문 2. 요구 항목 3. 대화 중 확정된 사항 4. 대표님 추가 요청사항 5. 우선순위와 기한.
   - **작성 안내**: 아래 두 문장을 그대로 넣는다. 「요구 항목은 번호를 매기고 REQ 체크리스트가 이 번호와 1:1로 대응한다.」, 「대화 중 확정된 사항에는 구현 방법을 넣지 않는다.」 그 밖에 지시 원문은 대표님 말을 원형 그대로 인용한다는 안내를 둔다.
   - **여러 REQ로 나뉘는 경우**: 각 REQ는 자기가 맡는 ORDER 요구 항목을 ORDER의 번호 그대로 인용하고, REQ 체크리스트는 그 항목들과 1:1로 대응한다는 안내를 둔다. ORDER의 어느 요구 항목도 빠지지 않게 하는 확인은 REQ 판정 기준 ①(요구 누락 없음)에 맡기고 새 검사를 더하지 않는다.
   - **추가 항목 기록(체크리스트 7번)**: 메모 4절 구성에 없는 항목이나 필드를 초안에 넣으면 `RPT-009`에 항목별 사유를 적는다. 위 설계는 머리말·본문 항목을 더하지 않으므로, 작성 안내 문구만 있고 추가 항목·필드는 「없음」으로 적는 것이 기대 결과다.

3. **ORDER와 REQ 구분표 (체크리스트 6번)**: 행은 작성 주체, 담는 내용, 보관 위치, 대표님 개입(ORDER: 확인 일시 기록, REQ: `approved:` 승인), 분류(제안·확정), 서식 파일(`ORDER_TEMPLATE.md`(후속 안건이 생성), `REQ_TEMPLATE.md`)으로 둔다. REQ는 ORDER를 1절 「요청 원문」의 출처로 인용하고 지시 원문을 다시 정리하지 않는다는 점과, D4(요구 메모 형식 폐지, 기존 파일은 기록으로 보존)를 함께 적는다.

   - **반드시 들어갈 항목**(체크리스트 8번이 지정한 문장. 아래 네 행은 검색 결과와 관계없이 넣는다):

### 3.4 `DEV-009` 설계 (구현 단계)
결과서 서식은 `Workflow/templates/DEV_TEMPLATE.md`를 따른다. 대상 통제장치는 `check_standard.py`, `.claude/`(`settings.json`, `agents/*.md`), `.githooks/`, `.gitattributes`, `setup.cmd`다.

1. **존재 여부**: 통제장치마다 조사 시점의 존재 여부를 먼저 적는다. 확인은 Glob 도구 또는 `allow` 목록 안의 `git ls-files -- <경로>`로 하고 명령과 결과 원문을 적는다. 없는 것은 없다는 사실과 확인 명령을 적는다.
2. **조사 항목**(통제장치별로 「바꿀 곳 있음/없음」, 근거 행 번호, 바꿀 요지를 적는다. 문구안·코드는 적지 않는다):
   - ① `check_standard.py`: `WHITELIST_PREFIXES`(35·36행 부근)가 ORDER 보관 위치(`Departments/Secretariat/assets/inbox/`)를 scope 대조에서 빼는지, `RECORD_NAME`(58행 부근)과 기록 조회(148·152행 부근)가 ORDER를 승인 기록으로 다루지 않아도 되는지(D2: ORDER에 승인 필드 없음), 주석 문구(36행 「요구 메모」 등)를 바꿀지. 행 번호는 조사 시점 파일에서 다시 확인해 적는다.
   - ② `.gitattributes`: 15~17행이 `Departments/Secretariat/assets/inbox/ORD-*_v*.md`를 배포본에서 빼는지를 패턴으로 판단한다. `git check-attr`는 `allow` 목록에 없으므로 실행하지 않고(`Workflow/03_라이프사이클` 「중단 조건」 5항) 그 사실을 적는다.
   - ③ `.claude/agents/secretariat.md`: 존재 여부와 처리(체크리스트 2번). E1에 따라 이 정의의 두 업무(REQ 작성, 핫픽스)가 모두 다른 주체로 넘어가므로, 이름·설명을 바꾸는지 여부와 함께 「정의 파일 폐지 대상」인지를 근거와 함께 적는다. 다른 정의 파일(`design.md` 등)에 창구·비서실 세션·오케스트레이터 언급이 있는지 검색 결과도 적는다.
   - ④ `.claude/settings.json`: 역할에 따라 달라지는 규칙(`allow`·`deny`·`ask`)이 있는지. 비서실이 저장소 밖 서비스이므로 `deny`가 비서실의 핫픽스 수정에 적용되지 않는다는 사실을 3.3절 5번 ③과 같은 뜻으로 적는다.
   - ⑤ `.githooks/`, `setup.cmd`: 역할·문서 이름에 의존하는 부분이 있는지.
3. **검증**: 조사를 마친 뒤 `python Departments/Development/assets/scripts/check_standard.py`를 실행해 명령, 시각(+09:00), 종료 코드, 출력 원문을 「검증 결과」에 적는다(`Workflow/03_라이프사이클` 5절 「구현」 통과 조건).
4. **금지**: 코드·설정·거버넌스 파일을 수정하지 않고 `workspace/`에 적용본을 만들지 않는다. 조사 중 수정이 필요해 보이는 곳은 결과서에 「후속 안건 반영 대상」으로만 적는다.

### 3.5 체크리스트 9번 확인 방법 (최종 판정 단계)
- ① `git status --porcelain -uall` 출력에 `REQ-009_적용본`이 들어간 경로가 없는지 확인한다.
- ② 1.1절과 같은 명령과 판정 방법으로 거버넌스 파일 변경 줄과 `index` 줄을 다시 구해 1.1절과 비교한다. 1.1절은 「없음」이므로 판정 결과는 다음 두 가지 가운데 하나다.
  - 최종 판정 시점에도 거버넌스 파일 변경 줄이 없으면 1.1절과 같으므로 체크리스트 9번 ②를 충족한다.
  - 거버넌스 파일 변경 줄이 하나라도 있으면 1.1절과 같지 않으므로 체크리스트 9번 ②를 충족하지 않는다. 그 줄과 `index` 줄 원문을 판정서에 적는다. 변경이 어느 안건이나 누구에게서 생겼는지 추정해 충족으로 바꾸지 않는다. REQ 9번 ②가 판정 대상에서 빼는 것은 착수 시점 기준(1.1절)에 이미 있던 변경뿐이고, 1.1절에는 그런 변경이 없다.
- ③ `RPT-009` 반영 대상 목록에서 대상 파일·절·바꿀 요지와 「반영 범위」 열을 확인한다.
