## 3. 세부 설계
### 3.1 구조 변경
```text
[변경 전]                          [변경 후]
[저장소 루트]                      [저장소 루트]
├── ...                            ├── ...
├── Update_Package/                ├── Package_sample/   # 배포본을 푸는 자리. .gitkeep만 추적
│   └── .gitkeep                   │   └── .gitkeep
└── _archive/                      ├── Package_update/   # 업데이트 패키지를 푸는 자리. .gitkeep만 추적
                                   │   └── .gitkeep
                                   └── _archive/
```

데이터 흐름(커밋 뒤, 대표님이 실행):

| 묶음 | 원천 | 만드는 방법 | 푸는 위치 | 가져가는 곳 |
| :--- | :--- | :--- | :--- | :--- |
| 배포본 | `HEAD` 전체에서 `export-ignore` 대상을 뺀 것 | `git archive HEAD` → tar | `Package_sample/`(풀기 전 비우기) | 신규 프로젝트 폴더로 복사 |
| 업데이트 패키지 | `HEAD`의 표준 구역 경로(거버넌스 파일 목록과 `Workflow/templates/`) | `git archive HEAD <표준 구역 경로>` → tar | `Package_update/`(풀기 전 비우기) | 기존 프로젝트 루트에 덮어쓰기. 필요하면 이관 안내 문서를 함께 둔다(D1) |

- 두 폴더 아래 파일은 `.gitignore`로 무시되므로 `git status`, 커밋 전 검사(`git status --porcelain -uall`), `git archive`에 나타나지 않는다. 두 폴더 바로 아래 `.gitkeep`만 추적되어 배포본에도 들어간다.

### 3.3 매뉴얼 적용본 설계 (명세 단계)
적용본은 원본을 복사한 뒤 아래 위치만 고친다. 문구는 명세 단계가 정하되, 아래 내용과 제약을 지킨다.

1. **01 「용어」**
   - 「배포본」 행 「쓰지 않는 말」: 폴더명 `Package_sample`을 예외에 더한다(예: 「sample(파일명 `vibe_sample.tar`, 폴더명 `Package_sample` 제외)」).
   - 「업데이트 패키지」 행 「쓰지 않는 말」: 「Update_Package(폴더명으로만 사용)」를 새 폴더명과 어긋나지 않게 고친다(예: 「Update_Package(옛 폴더명). 폴더명은 `Package_update`」). 이 행과 개정 이력 표 밖에는 `Update_Package`를 남기지 않는다(REQ 체크리스트 1번).
2. **02 「저장소 구조」**: `Update_Package/` 줄을 지우고 `Package_sample/`(배포본을 푸는 자리)과 `Package_update/`(업데이트 패키지를 푸는 자리) 두 줄을 넣는다. 설명 주석은 `Workflow/06` 「배포본과 업데이트 패키지」를 참조하고 「보류」 표기를 넣지 않는다.
3. **06 「배포본과 업데이트 패키지」**
   - ① **6절 표**: 두 행에 폴더(`Package_sample/`, `Package_update/`)와 용도(요청 원문 3·4번: 신규 프로젝트 때 폴더째 복사해 가져감 / 업데이트용)를 적고, 「상태」 열의 「보류」를 해제한다. 업데이트 패키지 행의 「빌더는 `_archive/v02/`에 보관, 다시 도입할 때 별도 REQ」 문구는 빌더 없이 `git archive`로 만든다는 내용으로 바꾼다. 두 폴더의 내용은 커밋하지 않는다(`.gitignore`)는 사실을 적는다.
   - ② **6.1절 배포본 만드는 법**
     - 2항 목록 ①의 `Update_Package/`를 `Package_sample/`·`Package_update/`로 바꾼다(두 폴더 아래는 `.gitkeep`만).
     - 3항: 첫 두 문장 「새로 만든 빈 폴더(`<배포본 폴더>`)에 푼다. 기존 폴더에 풀면 같은 이름의 파일을 덮어쓰므로 쓰지 않는다.」를 삭제하고, 「풀기 전에 `Package_sample/`을 `.gitkeep`만 남기고 비운다」는 단계와 그 명령으로 대체한다. `tar -C`의 대상은 `Package_sample`로 바꾼다.
     - 4항 신설: 풀어 놓은 `Package_sample/`의 내용을 신규 프로젝트 폴더로 복사하는 방법. 루트의 `Package_sample/.gitkeep`(비우기 뒤 남긴 파일)은 복사하지 않거나 복사 뒤 지운다는 점을 적는다(4절 5번 위험).
   - ③ **6.2절 신설: 업데이트 패키지 만드는 법**: 6.1절과 같은 방식(Git Bash, 저장소 루트, `--force-local`)으로 표준 구역 경로만 묶는다. 경로 목록은 `AGENTS.md` 「불변 원칙」 3항을 원천으로 참조하고 06에 다시 나열하지 않는다(`AGENTS.md` 「불변 원칙」 9항). 단, 명령 예시는 3항 목록을 그대로 옮긴 형태로 적어도 되며, 그 경우 「목록이 바뀌면 3항을 따른다」는 문장을 붙인다. 풀기 전에 `Package_update/`를 `.gitkeep`만 남기고 비운 뒤 `Package_update`에 푼다. 대상 프로젝트 루트에 덮어쓰는 방법(`Package_update/.gitkeep`은 덮어쓰지 않음)을 적는다.
   - ④ **비우기 명령**: 권고 명령은 `git clean -fdX -- Package_sample/`(업데이트 패키지는 `Package_update/`)이다. `-X`는 무시 대상 파일만 지우므로 추적 중인 `.gitkeep`은 남는다. 명세는 구현보다 먼저 진행하므로 이 명령으로 적용본을 작성하고, 구현 단계 시험(3.4절 3번 확인 ②)이 동작을 확인한다. 시험 결과가 설계 의도와 다르면 개발은 그 사실을 `DEV-007`에 적고, 처리(반려 부서와 적용본 폴더 `_v02` 작성)는 최종 판정이 정한다(`Workflow/03_라이프사이클` 「반려와 격상」). 이 명령은 「풀기 전 비우기」와 ⑥의 「사용 직후 비우기」에 함께 쓴다.
   - ⑤ **6.3절 신설: 복잡한 업데이트(D1)**
     - 업데이트마다 6.2절대로 표준 구역 파일을 `Package_update/`에 만든다.
     - 이관 안내 문서가 필요한 조건: 덮어쓰기만으로 끝나지 않는 변경, 곧 폴더 이름·구조 변경, 기록 파일명·머리말 형식 변경, 고객 작업 구역 파일 수정이 그 업데이트에 있을 때만이다.
     - 문서: 그 업데이트의 수작업 절차를 적은 문서 하나를 `Package_update/` 바로 아래에 함께 둔다. 파일명은 명세 단계가 하나로 정한다(예: `이관안내.md`). 새 서식은 만들지 않는다.
     - 작성 주체와 근거: 패키지를 만드는 사람(대표님, 또는 대표님 지시를 받은 창구)이 그 업데이트에 포함된 표준 개정 REQ와 결과서(적용본 반영 명령)를 근거로 작성한다. `Package_update/`는 커밋하지 않으므로 이 문서도 커밋되지 않는다는 점을 적는다.
     - 대상 프로젝트의 처리: 대상 프로젝트는 그 안내를 자기 REQ로 처리한다.
   - ⑥ **작업 트리 안 표준 사본의 위험과 대응**(REQ 3절 표 아래 항): `Package_sample/`, `Package_update/` 각각에 대해 따로 적는다.
     - 위험: 두 폴더를 채우면 각 폴더에 `AGENTS.md`, `CLAUDE.md`, `.claude/`, `Workflow/` 사본이 작업 트리 안에 생긴다. Claude Code의 하위 폴더 `CLAUDE.md` 자동 로드와 `deny` 규칙의 하위 폴더 적용은 실측하지 못했다(7절 4·6행). 사본이 현행 규정과 다른 버전이면 에이전트가 사본의 규정을 읽거나, `deny`가 사본에 적용되지 않을 수 있다.
     - 대응: 채운 폴더는 가져가는 작업(복사·덮어쓰기)을 마친 직후 ④의 명령으로 비운다. 두 폴더를 채운 상태로 Claude Code 파이프라인을 실행하지 않는다. 이 대응은 「풀기 전 비우기」와 별개이며 그 단계를 대신하지 않는다고 명시한다.

### 3.4 구현 설계 (구현 단계)
1. **`.gitattributes` 적용본**: 원본 7·8행(`Update_Package/** export-ignore`, `Update_Package/.gitkeep -export-ignore`)만 지운다. 두 새 폴더의 `export-ignore` 규칙은 넣지 않는다(D3: 추적하지 않는 파일은 `git archive`에 들어가지 않는다).
2. **`.gitignore` 적용본**: 원본 끝에 두 폴더 규칙을 더한다. 설계 의도는 「두 폴더 아래 전부 무시, 두 폴더 바로 아래 `.gitkeep` 두 파일만 예외」이며, 권고 규칙은 아래와 같다. 개발은 3번 시험으로 확인하고, 다르게 동작하면 의도를 지키는 규칙으로 고쳐 `DEV-007`에 사유를 적는다.
   ```gitignore
   # 배포본·업데이트 패키지를 푸는 자리: 내용은 커밋하지 않고 폴더 자리(.gitkeep)만 추적한다
   /Package_sample/*
   !/Package_sample/.gitkeep
   /Package_update/*
   !/Package_update/.gitkeep
   ```
   - `/Package_sample/*`는 바로 아래 하위 폴더까지 무시하므로, Git은 무시된 폴더 안을 다시 포함하지 않아 `Package_sample/Audits/.gitkeep` 같은 하위 `.gitkeep`은 무시 대상에 남는다.
3. **시험(임시 Git 저장소)**: `Departments/Development/workspace/`의 Python 스크립트로 실행한다(`Workflow/06_통제장치_및_배포` 「무인 실행 권한」).
   - 준비: 임시 저장소에 2번 적용본을 `.gitignore`로 두고, 두 폴더 바로 아래 `.gitkeep`, 하위 폴더 `.gitkeep`(예: `Package_sample/Audits/.gitkeep`, `Package_update/Workflow/.gitkeep`), 일반 파일(예: `Package_sample/AGENTS.md`, `Package_update/.claude/settings.json`)을 만든다.
   - 확인 ①(REQ 체크리스트 3번): `git status --porcelain -uall` 결과에 `Package_sample/.gitkeep`, `Package_update/.gitkeep` 두 파일만 나타난다.
   - 확인 ②(3.3절 3번 ④): 두 `.gitkeep`을 커밋한 뒤 `git clean -ndX -- Package_sample/ Package_update/`(미리보기)의 삭제 예정 목록에 두 `.gitkeep`이 없고 나머지 파일·폴더가 있다.
   - 명령, 시각(+09:00), 결과 원문을 `DEV-007` 「검증 결과」에 적는다.
4. **규칙과 검사·설정 대조**: 개정 규칙과 `check_standard.py`·`.claude/settings.json`·`setup.cmd`가 어긋나지 않는지 대조해 `DEV-007`에 적는다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」 3항). 최소 대조 항목: `Update_Package` 참조 유무, 두 새 폴더가 scope 대조에 미치는 영향(무시 대상이라 변경 목록에 나타나지 않음), `.gitkeep` 두 파일이 이 REQ `scope:`(`Package_update`, `Package_sample`) 안에 있음.
5. **`Update_Package/` 처리(D4)**: 개발은 삭제·이동 명령을 실행하지 않는다. `DEV-007`에 대표님이 실행할 명령(예: `git rm Update_Package/.gitkeep`)을 적용본 반영 명령과 함께 적는다.
6. **적용본 반영 명령**: `.gitattributes`·`.gitignore` 적용본의 반영 명령을 `DEV-007` 「적용본」 표에 적는다.
