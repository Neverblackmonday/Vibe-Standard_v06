### 3.2 PM
- **정의**: PM은 Claude Code 메인 세션이다. PM과 오케스트레이터는 같은 주체이며 호칭만 다르다(요청 원문 3번).
- **실행 환경**: Claude Code(Claude CLI). 대표님 또는 비서실이 전달한 실행 명령(`Workflow/05_인수인계_및_실행명령` 3절 형식 `claude --model claude-opus-5-5 --effort <effort> --permission-mode acceptEdits "<지시문>"`)으로 기동한다. 실행 명령은 「REQ 작성 명령」(입력: ORDER)과 「원스톱 실행 명령」 두 가지다. 현행 「핫픽스 명령」은 핫픽스를 비서실이 수행하므로 폐지 대상이다(6절 반영 대상 목록).
- **책무**
  1. ORDER로 REQ와 체크리스트를 작성한다. 분류를 REQ 머리말 `classification:`에 확정한다. REQ를 처음 작성할 때 ORDER `related_req`에 그 REQ 이름을 더한다(요청 원문 2·5·6번).
  2. REQ 작성 파이프라인과 원스톱 파이프라인을 지휘한다. 서브에이전트를 순서대로 기동·인계하고 진행 상태를 보고한다(현행 오케스트레이터 책무).
  3. REQ 판정 `fail` 때와 격상 결정 때 REQ 새 버전을 작성한다(현행 비서실 세션 책무).
  4. 대표님에게서 직접 받은 승인 문구로 승인 기록을 남기고 승인 필드와 「결정」 열을 기재한다(3.5절).
- **수정할 수 있는 경로**: `Departments/Secretariat/docs/requests/`(REQ), `Departments/Secretariat/workspace/`, `Departments/Secretariat/assets/research/`·`assets/briefings/`(현행 비서실 세션의 REQ 승인 전 구역 가운데 `inbox/` 밖), ORDER 머리말 `related_req` 필드, 승인 기재 구역(현행 「작업 구역」 「승인 기재」 행).
- **하지 않는 일**: 핫픽스 수정·HOTFIX 작성, 판정, ORDER 본문 수정, 설계·개발 단계 산출물의 직접 작성, 거버넌스 파일 수정(Claude Code `deny`가 적용된다), 대표님의 명시적 요청 없는 커밋·푸시.

# ORD-001: 오더 제목

> 파일명은 `ORD-<세 자리 번호>_v<두 자리 버전>.md`이고 위치는 `Departments/Secretariat/assets/inbox/`다. 번호는 REQ와 별도로 `001`부터 쓴다. 버전은 `Workflow/07_문서_서식_및_번호` 「번호와 버전」을 따른다. `ceo_checked_at`을 기재한 뒤 본문을 바꾸면 새 버전을 `ceo_checked_at: ""`로 작성한다. 착수 승인은 REQ `approved:` 하나뿐이다. 이 안내문은 작성할 때 지운다.

### 4.2 머리말 필드와 메모 4절 구성의 대응
| 메모 4절 구성 1항 | 필드 | 값 형식 |
| :--- | :--- | :--- |
| 오더 번호(`ORD-NNN`) | `order_id` | `"001"`(문서 이름은 `ORD-001`) |
| 작성일 | `created` | `"YYYY-MM-DD"` |
| 대표님 확인 일시 | `ceo_checked_at` | `"YYYY-MM-DDTHH:MM:SS+09:00"`. 비어 있을 수 있다 |
| 분류 제안 | `classification_proposal` | `Critical`·`Major`·`Minor` 가운데 하나 |
| 연결 REQ 목록 | `related_req` | 목록 필드. 항목은 버전 없는 REQ 이름(예: `REQ-012`) |

- 본문 절은 메모 4절 구성 2~6항과 같은 순서로 1:1 대응한다: 1. 지시 원문 2. 요구 항목 3. 대화 중 확정된 사항 4. 대표님 추가 요청사항 5. 우선순위와 기한.
- 승인 필드 이름(`approved`, `confirmed`)을 쓰지 않는다(D2). `ceo_checked_at`은 확인 시각의 기록이며 `Workflow/07_문서_서식_및_번호` 3.1절 「승인 기록」 절차의 대상이 아니다.
- ORDER의 어느 요구 항목도 REQ에서 빠지지 않게 하는 확인은 REQ 판정 기준 ①(요구 누락 없음)에 맡기고 새 검사를 더하지 않는다.

### 4.3 메모 4절 구성에 없는 항목·필드 (체크리스트 7번)
- **추가한 머리말 필드·본문 절**: 없음.
- **작성 안내에만 더한 내용**(항목·필드가 아니며 서식 구성을 바꾸지 않는다):
  - 맨 위 안내문(파일명·위치·번호·버전, `ceo_checked_at` 기재 뒤 새 버전 작성, 착수 승인은 REQ `approved:` 하나): EC 3.3절 2번(파일명과 위치, `ceo_checked_at` 처리)과 D1·D2를 서식에서 바로 보이게 했다.
  - 2절 여러 REQ 안내: EC 3.3절 2번 「여러 REQ로 나뉘는 경우」.
  - 3절의 구현 방법 참조: 「구현 방법」의 뜻이 여러 가지로 읽히지 않게 현행 정의 위치를 가리켰다.
  - 4절·5절 안내: 절에 적을 내용과 내용이 없을 때의 기재(「없음」)를 정했다. 4절의 「작업 요구이면 2절에도 번호를 붙여 넣는다」는 추가 요청이 REQ 체크리스트 1:1 대응(메모 4절 구성 3항)에서 빠지지 않게 하기 위해서다.

## 5. ORDER와 REQ 구분 (체크리스트 6번)
| 구분 | ORDER | REQ |
| :--- | :--- | :--- |
| 작성 주체 | 비서실 | PM |
| 담는 내용 | 대표님 지시 원문, 번호 매긴 요구 항목, 대화 중 확정된 정책 결정, 대표님 추가 요청사항, 우선순위와 기한 | 요청 원문(ORDER 인용), 배경 및 목적, 결정 사항 및 선택지, 실행 계획, 체크리스트, 실행 명령 |
| 보관 위치 | `Departments/Secretariat/assets/inbox/ORD-NNN_vNN.md`(D1) | `Departments/Secretariat/docs/requests/REQ-xxx_vNN.md`(현행) |
| 대표님 개입 | 확인 일시 기록(`ceo_checked_at`). 승인 필드 없음(D2) | `approved:` 승인(`Workflow/07_문서_서식_및_번호` 「승인 기록」) |
| 분류 | 제안(`classification_proposal`) | 확정(`classification:`) |
| 서식 파일 | `Workflow/templates/ORDER_TEMPLATE.md`(후속 안건이 생성) | `Workflow/templates/REQ_TEMPLATE.md` |

- REQ는 ORDER를 1절 「요청 원문」의 출처로 인용하고, 지시 원문을 다시 정리하지 않는다. REQ 체크리스트는 ORDER 요구 항목 번호와 1:1로 대응한다.
- D4: 요구 메모 형식은 폐지하고 ORDER로 대체한다. 기존 요구 메모 파일은 기록으로 남기며 ORDER로 바꾸지 않는다. 진행 중인 안건(`REQ-009`, `REQ-010`)이 인용하는 요구 메모도 그대로 둔다.

## 10. 확인하지 못한 항목
- **채팅 서비스의 저장소 파일 수정·셸 실행 가능 여부**: 확인 불가. 저장소 밖 서비스의 기능은 이 파이프라인에서 조회할 수 없다(EC 2.3절). 코워크·Antigravity도 저장소 안 기록으로만 판단했고 실측하지 않았다(3.8절).
- **`DEV-009` 근거**: 6.2절의 `.gitattributes`·`check_standard.py` 「변경 없음」 사유는 `DEV-009`의 조사 결과를 근거로 참조한다. 이 결과서 작성 시점에 `DEV-009`는 아직 없으며(구현 단계 산출물), 사유는 설계 세션이 해당 행을 읽어 판단한 내용이다. 최종 판정에서 `DEV-009` 조사 ①·②와 대조한다.
- **`.gitattributes` 패턴 판단**: `git check-attr`는 `allow` 목록 밖이라 실행하지 않았다(EC 3.4절 2번 ②).
