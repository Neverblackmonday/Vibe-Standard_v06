# 04. 모델 운용

> 이 문서가 정하는 것: 모델 등급과 등급별 기본 모델, 실행 도구의 모델 제한, 단계별 모델과 effort, 기본값 밖 사용의 명시와 승인, 판정서 모델 대조, 토큰을 줄이는 타깃 컨텍스트 규칙, 모델 메타데이터 기록.
> 다른 문서가 정하는 것: 실행 명령의 형식 → `Workflow/05_인수인계_및_실행명령`, 분류의 정의 기준과 분류별 기본 모델 등급 → `Workflow/03_라이프사이클` 「분류별 단계」, 모델 ID 갱신 절차 → `Workflow/07_문서_서식_및_번호` 「개정 이력과 리비전 태그」.

## 1. 모델

모델 등급, 등급별 기본 모델, 단계별 모델, 기본값 밖 사용은 이 절이 원천이다. 분류별 기본 모델 등급과 이 절의 적용 시점은 `Workflow/03_라이프사이클` 「분류별 단계」를 따른다.

### 1.1 모델 등급과 기본 모델

| 등급 | 해당 모델 | 기본 모델 | 기본 모델 ID |
| :--- | :--- | :--- | :--- |
| 최고급 | Fable급, Astra | 없음(최고급은 기본 등급이 아니다) | — |
| 고급 | Opus, Sol급, Gemini Pro급 | Claude Opus 5.5 | `claude-opus-5-5` |
| 중급 | Sonnet급, GPT Luna급, Gemini Flash급 | Claude Sonnet 5.5 | `claude-sonnet-5-5` |

- 모델은 항상 최신 버전을 쓴다.
- 기본 모델의 모델 ID는 이 표에만 적고, 실행 명령·서식·서브에이전트 정의는 이 표를 따른다.
- 기본 effort는 등급과 관계없이 `medium`이다(2절).
- **실행 도구의 모델 제한**: 현행 실행 도구가 Claude Code이므로, REQ 작성 파이프라인과 원스톱 파이프라인의 모든 세션과 판정에는 Claude Code에서 실행할 수 있는 모델만 쓴다. 위 표 가운데 Claude Code에서 실행할 수 없는 모델(Astra, Sol급, Gemini Pro급, GPT Luna급, Gemini Flash급)은 두 파이프라인과 판정에 쓰지 않는다. 등급표는 그대로 둔다. 다른 실행 도구의 도입은 ORDER·REQ로 정한다.
- **갱신**
  - ① 등급 배정을 그대로 두고 기본 모델을 같은 모델의 더 새 버전으로 바꾸는 갱신은 `Workflow/07_문서_서식_및_번호` 「개정 이력과 리비전 태그」의 「모델 ID 갱신의 예외」를 따른다. 등급 배정이나 모델 계열을 바꾸는 변경은 ORDER·REQ로 한다.
  - ② **적용 시점**: 갱신은 원천 문서를 고친 뒤 기동하는 PM 세션(`Workflow/05_인수인계_및_실행명령` 「실행 명령」의 실행 명령으로 기동하는 파이프라인 실행)부터 적용한다. PM은 시작할 때 이 표를 읽고 그 값을 그 실행이 끝날 때까지 쓴다(실행 명령의 `--model`과 1.2절의 호출 인자). 이미 실행 중인 PM 세션과 그 세션이 띄우는 서브에이전트는, 갱신 뒤에 띄우는 것을 포함해 그 PM 세션을 기동할 때의 값으로 실행한다. 이는 REQ 작성 파이프라인과 원스톱 파이프라인에 같다.
  - ③ **대조 기준**: 1.2절 「판정서 모델 대조」와 `Workflow/03_라이프사이클` 최종 판정 기준 10에서는 이 표의 현행 값과 함께, 이 문서 개정 이력 가운데 일자가 그 안건 REQ 첫 버전(`_v01`) 머리말 `created:`의 날짜와 같거나 뒤인 `CEO` 행의 이전 ID(머리말에 모델 이름을 적었으면 그 ID의 모델 이름)도 맞는 것으로 본다. 두 파이프라인에 같은 기준을 쓴다.

### 1.2 단계별 모델 (REQ-031_v03)

| 대상 | 모델 | effort |
| :--- | :--- | :--- |
| 비서실 세션(비서팀, 형상통제팀) | 제한 없음. 모델과 effort를 정하지 않는다. 실제 실행 모델은 비서실 세션이 쓰는 기록의 머리말이나 작성 정보에 적는다(4절) | 정하지 않는다 |
| 핫픽스팀(V03) 세션(`Workflow/05_인수인계_및_실행명령` 「핫픽스 실행 명령」) | 고급 기본 모델. 핫픽스에는 분류가 없으므로 그 안건의 모델을 쓰지 않는다. 독립 판정 대신 대표님 사후 확인을 받는다(`Workflow/03_라이프사이클` 「핫픽스 트랙」 3항) | `medium` |
| REQ 작성 파이프라인(PM의 REQ 작성과 모든 REQ 새 버전 작성, REQ 판정, REQ 문체 반영본의 대조) | 고급 기본 모델 | `medium` |
| 원스톱 파이프라인의 최종 판정 밖 모든 세션(PM, 설계부, 개발부, 품질보증부의 EC 판정·명세 판정·인수 시험 등) | 그 안건의 모델 | 그 안건의 effort |
| 원스톱 파이프라인의 최종 판정 | 그 안건의 모델이 최고급이면 그 모델, 아니면 고급 기본 모델 | 그 안건의 effort가 `high`·`xhigh`·`max`이면 그 값, 아니면 `medium` |

- **그 안건의 모델과 effort**: 그 안건의 모델은 REQ 분류의 기본 모델 등급(`Workflow/03_라이프사이클` 「분류별 단계」)의 기본 모델이다. REQ 「결정」 열이 1.3절대로 다른 모델을 승인했으면 그 모델이다. 그 안건의 effort는 `medium`이며, REQ 「결정」 열이 다른 값을 승인했으면 그 값이다.
- **`workflow:` 밖 세션**: `Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」 5항의 문체 반영 대조는 대상 판정과 같은 모델·effort로 실행한다. `workflow:` 밖에서 실행하는 그 밖의 세션(최종 판정서 승인의 문체 반영, 인수 시험 수정, 중단 때 부적합 기록)은 표 셋째 행으로 실행한다.
- **REQ 새 버전**: PM이 작성하는 REQ의 모든 새 버전은 작성 사유와 관계없이 표의 REQ 작성 파이프라인 행의 모델·effort로 작성한다. 사유에는 REQ 판정 `fail`(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 3항), 진행 중인 안건의 요구 변경(같은 문서 「진행 중 변경과 파생 안건」), 실험 단계 추가(같은 문서 「실험 단계」 7항), 「문체 반영」 승인의 문체 반영본(같은 문서 「판정 지적의 구분과 문체 지적 처리」 5항), 최종 판정 반려 누적 뒤의 격상과 모델·effort 승인(같은 문서 「반려와 격상」), 승인 필드 기재 뒤의 결정 변경(`Workflow/07_문서_서식_및_번호` 「승인 기록」 6항)이 모두 든다. 그 REQ 판정과 문체 반영본의 대조도 같은 행을 따른다. PM은 REQ 새 버전을 작성하기 전에 자기 실행 모델(세션 시스템 정보)과 effort(실행 명령 지시문의 effort 표기)가 그 행과 같은지 확인한다. 같으면 그 세션에서 작성한다. 다르면 작성하지 않고 `Workflow/03_라이프사이클` 「중단 조건」 9항으로 멈추며, 보고의 「대표님이 할 일」에 REQ 새 버전 명령(`Workflow/05_인수인계_및_실행명령` 「실행 명령」)으로 PM을 다시 기동해야 한다는 사실, 대상 REQ 경로, 근거 파일(그 종류는 `Workflow/05_인수인계_및_실행명령` 「실행 명령」의 REQ 새 버전 명령 항목을 따른다)을 적는다.
- **PM의 책임**: PM은 표의 모델·effort로 세션을 기동한다.
  - ① 실행 명령(`Workflow/05_인수인계_및_실행명령` 「실행 명령」)의 `--model`로 PM 세션의 모델을 정한다. PM은 시작할 때 자기 실행 모델(세션 시스템 정보)이 표의 PM 모델과 같은지 확인하고, 다르면 시작하지 않고 보고한다.
  - ② 서브에이전트의 모델이 PM 모델과 같으면 `Agent` 호출 인자 `model`을 주지 않고 정의 파일의 `model: inherit`로 이어받게 한다.
  - ③ 다르면 `Agent` 호출 인자 `model`에 1.1절 표의 모델 ID(PM이 시작할 때 읽은 값. 1.1절 「갱신」. 최고급은 REQ에 적은 모델 ID)를 준다. 호출이 모델 ID를 받지 않으면 같은 계열의 별칭(예: `opus`)을 주고 PM 실행 기록 「사건」 칸에 적는다.
  - ④ 표의 모델·effort로 세션을 기동할 수 없으면(예: 그 안건 effort가 `low`이면 최종 판정을 `medium`으로 기동할 수 없다) 그 세션을 기동하지 않고 `Workflow/03_라이프사이클` 「중단 조건」 6항으로 멈춘다.
  - ⑤ `--model`과 호출 인자에는 별칭이 아닌 모델 ID를 쓴다(③의 별칭 대신 예외는 제외).
- **핫픽스 실행 명령**: 핫픽스 실행 명령을 실행하는 비서실 세션은 `--model`과 `--effort`를 표의 핫픽스팀(V03) 행으로 적는다. 모델 ID는 1.1절 표의 값이다.
- **서브에이전트 정의**: 서브에이전트 정의 파일(`.claude/agents/*.md`)은 머리말에 `model: inherit`를 적고 모델 이름과 `effort`를 적지 않는다.
- **판정서 모델 대조**: PM은 두 파이프라인에서 판정서를 받으면 머리말 `auditor.model`을 표의 그 단계 모델과 대조하고, 다르면 무효로 보고 판정을 다시 실행한다. 대조는 모델 이름이나 모델 ID로 하며, 1.1절 「갱신」의 대조 기준(이전 ID 허용)을 따른다. 판정서를 작성할 수 있는 주체는 `AGENTS.md` 「불변 원칙」 4항을 따른다.

### 1.3 기본값 밖 사용

1. **대상**: 최고급 모델, 고급으로 올린 Minor, `medium` 밖의 effort(`low` 포함).
2. **명시와 승인**: PM이 REQ 「결정 사항 및 선택지」 표에 정할 일로 적고 대표님 승인을 받을 때만 쓴다. 명시하지 않거나 승인하지 않으면 기본값을 쓴다.
3. **최고급**: 모든 분류에서 쓸 수 있다. 최고급에는 기본 모델이 없으므로 명시할 때 모델 이름과 모델 ID를 늘 적는다. 1.1절 「실행 도구의 모델 제한」 안의 모델만 적을 수 있다.
4. **적용 범위**: 승인한 모델·effort는 그 안건의 원스톱 파이프라인 전체(1.2절 표 셋째 행)에 쓰고, 최종 판정은 1.2절 표 넷째 행을 따른다.
5. **낮추지 않음**: Critical·Major는 중급으로 낮추지 않는다.

## 2. effort

- 기본값은 `medium`이며 모델 등급과 관계없다.
- `medium` 밖의 값(`low` 포함)은 1.3절대로 REQ에 명시해 승인받을 때만 쓴다.
- 허용 값은 `low`, `medium`, `high`, `xhigh`, `max`이다.
- 한 파이프라인 실행의 모든 세션은 실행 명령의 `--effort` 값으로 실행하고, 서브에이전트 정의 파일에 `effort`를 적지 않는다. 정의 파일의 `effort`는 세션 effort보다 앞서 1.2절 표와 어긋나기 때문이다. 서브에이전트가 세션 effort를 이어받는지는 실측하지 않았다(`Workflow/06_통제장치_및_배포` 「알려진 과제」 5행).

## 3. 타깃 컨텍스트 규칙

1. 서브에이전트 지시문에는 REQ 경로, EC 경로(EC가 있을 때. `Workflow/03_라이프사이클` 「EC 적용 기준」 첫 문단), 대상 파일 경로, 단계명, 실행 명령의 effort 표기(`effort: <값>`. `Workflow/05_인수인계_및_실행명령` 「실행 명령」)만 넣고 매뉴얼 본문을 붙이지 않는다.
2. 매뉴얼은 필요한 절만 찾아 읽는다. 각 매뉴얼 첫머리의 「이 문서가 정하는 것」으로 읽을 문서를 고른다.
3. 재판정 지시문에는 직전 판정서의 결함 표와 문체 지적 표, 반려 부서 결과서의 수정 목록, 변경분, 대표님 답 뒤 재판정 횟수를 새로 세는 재판정이면 그 사실과 직전 판정서 경로(`Workflow/03_라이프사이클` 「재판정 한도」)만 넣는다. 변경분은 기록 문서 새 버전(REQ·EC 등)은 `git diff --no-index <직전 버전> <새 버전>`, 거버넌스 적용본은 `git diff --no-index <직전 판정 대상 적용본 폴더> <새 적용본 폴더>`, 추적 중인 그 밖의 파일은 `git diff HEAD -- <경로>`로 구한다. 적용본 폴더는 판정 지적을 반영할 때마다 버전을 올리므로(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」 4항) 두 적용본 폴더는 `REQ-xxx_적용본_v01`과 `_v02`처럼 이웃한 버전이다. 새 파일은 `git status --porcelain -uall`로 찾아 전문을 넣는다. 단, 직전 버전이 있는 기록 문서 새 버전과 거버넌스 적용본은 위의 `--no-index` 비교로 변경분을 구하므로 전문을 넣지 않는다. `git diff HEAD`는 마지막 커밋 이후의 누적 차이이므로 직전 판정 이후의 변경은 수정 목록으로 특정한다. 문체 반영 대조(`Workflow/03_라이프사이클` 「판정 지적의 구분과 문체 지적 처리」)의 지시문도 같은 구성(직전 판정서의 문체 지적 표, 변경분)으로 만든다.
4. 작성 과정의 대화 내용은 판정 세션에 넘기지 않는다.

## 4. 모델 메타데이터 기록 (REQ-031_v03)

공식 문서(REQ, EC, DEV, RES, HOTFIX)의 머리말에 작성하거나 판정한 모델과 effort를 아래 기준으로 적는다.

- **모델**: 확인할 수 없으면 `"확인 불가"`로 적는다. 단, RES의 `auditor.model`에는 `"확인 불가"`를 적지 않는다. 판정서를 작성하는 세션이 자기 실행 모델을 확인할 수 없으면 판정서를 발행하지 않고 오케스트레이터에 보고한다.
- **effort(REQ, EC, DEV, RES, HOTFIX)**: 실행 명령 지시문의 effort 값을 출처와 함께 `"<값> (실행 명령 기준)"`으로 적는다(예: `"medium (실행 명령 기준)"`). PM은 자기 지시문의 표기(`Workflow/05_인수인계_및_실행명령` 「실행 명령」), 서브에이전트는 PM 지시문의 표기(3절 1항), 핫픽스팀(V03)은 핫픽스 실행 명령 지시문의 표기를 출처로 쓴다. 출처에서 값을 얻을 수 없을 때만 `"확인 불가"`로 적는다.
- **`REQ-031` 커밋 전의 HOTFIX**: 비서실이 실행 명령 없이 작성했으므로 실제 적용한 effort를 적었다. 고치지 않는다.

```yaml
author:            # RES는 auditor:
  agent: "Design"
  model: "Claude Opus 5.5"
  effort: "medium (실행 명령 기준)"
```
