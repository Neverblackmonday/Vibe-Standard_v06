## 2. 요구 항목

1. **산출물 종류별 제작 체계**: 표준이 코드 밖의 산출물(릴스 같은 영상, 원고·대본 같은 텍스트 콘텐츠 등)도 같은 파이프라인으로 만들 수 있게 한다. 산출물 종류마다 만드는 부서, 받는 시험실 검사의 종류, 저장 위치를 표준에 둔다. 콘텐츠 산출물의 검사 기준은 7항에서 다룬다. 기획안에서 제작으로 가는 경로도 함께 정한다(원문 B 둘째 줄, 원문 I 둘째 문단).
2. **설계 필수와 EC 적용 기준**: Minor를 포함한 모든 분류의 REQ가 설계 단계를 거친다. 콘텐츠도 설계를 먼저 한다. 핫픽스는 예외다. EC는 기존 설계나 코드를 변경할 때 변경점을 평가하는 항목이며, 설계가 무엇을 어떻게 바꿀지 계획하고 개발이 수정하고 품질이 결과를 평가한다. EC가 필요한지는 설계가 판단한다. 분류(10항)는 EC의 유무를 정하지 않는다(이 항 전체: 3절 1·6·7항, 적용 범위는 1절 경위의 원문 F 뒤 항목).
3. **회차 처리(절차 무게)**: 같은 포맷의 콘텐츠를 여러 회차 만들 때 회차마다 드는 절차를 줄이는 방식을 표준에 둔다. 설계 단계는 빼지 않는다(3절 1항, 원문 C 셋째 줄, 원문 D 넷째 줄).
4. **대표님 작업 단계**: AI가 하지 못하는 일(촬영, 녹음 등)은 대표님이 한다. 파이프라인 안에서 대표님이 그 일을 하는 시점과, 대표님 작업 뒤 파이프라인이 이어지는 방식을 표준에 둔다(3절 2항).
5. **서버실 사용 규칙**: 서버실(`Storage/server/`)의 위치와 Git 제외(ORDER A 3절 8항) 밖의 사용 규칙(서버실에 둘 파일의 범위, 원본의 기록, 백업)을 표준에 둔다(원문 C 넷째 줄, 원문 D 셋째 줄).

## 3. 대화 중 확정된 사항

1. **설계 필수**: 콘텐츠도 기존 프로세스를 따르며 설계 단계를 빼지 않는다. EC가 필요한지는 설계가 판단한다(원문 E 둘째·셋째 줄).
2. **대표님 작업**: AI가 하지 못하는 일은 대표님이 한다. 개입 시점은 정하지 않았다(원문 C 다섯째 줄).
3. **서버실의 Git 제외**: 서버실의 내용은 Git에서 뺀다. 위치는 `Storage/server/`다(원문 D 셋째 줄, ORDER A 3절 8항).
4. **진행 방식**: ORDER B의 확인 항목과 잔여 업무를 한꺼번에 넘긴다. REQ로 나누는 일은 PM이 한다(원문 H). (이 ORDER에 넣은 범위는 비서실 판단이며 1절 경위 원문 H 항목에 적었다)
5. **분류**: 분류는 REQ의 중요도와 난이도로 정하는 값이다. 분류에 따라 후속 업무의 품질 평가 단계나 AI 모델을 강화한다(원문 J 첫째·둘째 줄). 분류가 품질 평가 강도와 AI 강도를 정하고 AI 강도는 effort로 정한다는 비서실 보고(원문 J 뒤)에 대표님이 「분류 부분ㅇㅋ」으로 답했다. 항공 품질의 Critical·Major·Minor 수준 관리를 차용하며, 기능상 중대 결함이 우려되는 항목도 Critical로 관리한다(원문 K 첫째 문단). 원문 M·N·P로 분류별 모델 등급이 정해졌다. effort 기본값은 등급과 관계없이 `medium`이고 `high`는 명시할 때만 쓰므로(12항), 원문 J 뒤 보고의 「AI 강도는 effort로 정한다」는 「분류가 모델 등급을 정하고 effort는 12항을 따른다」로 바뀐다(11·12항).
6. **EC**: EC(Engineering Change)는 기존 설계나 코드를 변경할 때 변경점을 평가하는 항목이다. 무엇이 어떻게 바뀔지 설계가 계획하고, 개발이 수정하고, 품질이 결과를 평가한다(원문 J 둘째 문단).
7. **핫픽스**: 핫픽스는 설계 필수(1항)를 포함한 정규 흐름의 예외다(원문 I 셋째 문단).
8. **추적성**: 모든 워크플로우에서 추적성이 유지되어야 하며, 이것이 가장 중요하다(원문 J 넷째 문단).
9. **통합**: 분류·EC·재작업·추적성 개선을 이 ORDER에 함께 넣는다(원문 K 마지막 줄).
