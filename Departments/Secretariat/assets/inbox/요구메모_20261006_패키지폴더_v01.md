# 요구 메모: 패키지 폴더 재편

- 용도: REQ 작성 파이프라인의 입력(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」)

## 1. 요청 원문

> 요청사항1.
> Update package 폴더를 Package_update로 변경.
> Package_sample폴더 신설.
>
> Package_sample은 신규 프로젝트 때 해당폴더 복사해서 들고가는용도.
> Package_update는 업데이트 용.
>
> 근데 만약 업데이트가 너무 복잡한 경우는 어떻게되지? 그냥 표준업데이트파일 안만들고 그때그때 정리하는게 낫나?

## 2. 창구가 확인한 현황 (2026-10-06, 코워크 작업본 대조)

- `Update_Package/`를 참조하는 곳: `.gitattributes` 7·8행, `Workflow/01_표준_개요.md` 「용어」, `Workflow/02_부서_구조_및_작업구역.md` 「저장소 구조」.
- 「배포본」·「업데이트 패키지」 용어와 절차: `Workflow/06_통제장치_및_배포.md` 「배포본과 업데이트 패키지」(현재 두 묶음 모두 보류).
- `.gitattributes`, `.gitignore`, `Workflow/`는 거버넌스 파일이다(`AGENTS.md` 「불변 원칙」 3항). 따라서 이 안건은 Critical로 분류된다(`Workflow/03_라이프사이클` 「분류별 단계」).

## 3. 창구 권고 (REQ 「결정 사항 및 선택지」로 옮길 것)

| 정할 일 | 권고안 | 대안 | 근거 |
| :--- | :--- | :--- | :--- |
| 패키지 폴더 내용의 Git 관리 | 폴더는 `.gitkeep`만 커밋한다. 내용물은 `.gitignore`로 제외하고 필요할 때 생성한다 | 내용물까지 커밋 | 저장소 안에 `AGENTS.md`·`CLAUDE.md`·`.claude/`·`Workflow/` 사본이 생기면 단일 원천이 깨진다. Claude Code가 하위 폴더 사본을 불러올 위험도 있다 |
| `Package_sample` 생성 방법 | `git archive HEAD`로 만든 배포본을 비운 `Package_sample/`에 푼다 | 수동 복사 | 06 6.1절의 기존 절차를 그대로 사용한다. 개정 기록 제외 규칙(`.gitattributes`)이 자동으로 적용된다 |
| `Package_update` 생성 방법 | `git archive HEAD -- <거버넌스 파일 목록>`의 결과와 `변경요지.md`를 함께 둔다 | v02 빌더 스크립트 복원 | 명령 한 줄로 만들 수 있으므로 별도 빌더가 필요 없다(`AGENTS.md` 「불변 원칙」 6항) |
| 복잡한 업데이트의 처리 | 업데이트를 두 유형으로 나눈다. ① 덮어쓰기형: 패키지를 덮어쓰면 끝난다. ② 이관형: 패키지에 `이관지침.md`를 넣고, 대상 프로젝트가 자기 파이프라인에서 「표준 이관 REQ」(Critical)로 처리한다 | 패키지 없이 그때그때 정리 | 「그때그때 정리」는 무엇을 바꿨는지 기록이 남지 않고 프로젝트마다 결과가 달라진다. 이관형도 패키지와 지침은 만들어야 대상 프로젝트의 REQ 입력이 된다 |
| 이관형 판단 기준 | 다음 가운데 하나라도 해당하면 이관형으로 본다. 폴더 구조 변경, 기록 파일명·머리말 형식 변경, 고객 작업 구역 파일 수정 필요, 대상 프로젝트가 거버넌스 파일을 자체 개정한 이력 있음 | 대표님이 매번 판단 | 덮어쓰기만으로는 기존 기록·구조가 새 규칙과 어긋나는 경우들이다 |
