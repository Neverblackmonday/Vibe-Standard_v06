브리핑: 표준 저장소와 프로젝트 폴더의 관계

결론

  • Vibe Standard_v04는 표준을 만들고 고치는 본사 폴더입니다. 제품 작업은 여기서 하지 않습니다.
  • 신규 프로젝트와 이관 프로젝트는 배포본을 복사한 별도 폴더이며, 자기 Git 저장소, 자기 ORDER·REQ 번호(001부터), 자기 파이프라인을 가집니다. 두 폴더는 서로 파일을 참조하지 않습니다.
  • 둘을 잇는 통로는 두 가지뿐입니다. 시작할 때의 배포본 복사와, 표준을 고친 뒤의 업데이트 패키지 덮어쓰기(표준 구역 파일만)입니다.

대표님이 할 일

  • 아래 「확인이 필요한 점」의 결정 두 가지(CEO/ 배포본 제외, 프로젝트에서 나온 표준 개정 제안의 경로)를 정해 주십시오. 급하지 않으며, 첫 배포본을 만들기 전까지 정하면 됩니다.

1. 조사 질문

신규 프로젝트나 이관 프로젝트에 표준을 적용하면, 기존 Vibe Standard 폴더와 그 프로젝트 폴더는 어떻게 구성되고 어떻게 쓰게 됩니까?

2. 한눈에 보기: PC 폴더 배치

프로젝트 폴더를 어디에 둘지는 표준에 정해져 있지 않습니다(Workflow/06 6.1절 4항 「신규 프로젝트를 둘 위치」). 아래 D:\Vibe Coding\ 아래 배치는 예시입니다.

3. 프로젝트 폴더 안의 구역

프로젝트 폴더도 본사와 같은 뼈대를 가집니다(Workflow/02 1절). 구역마다 누가 바꾸는지가 다릅니다(Workflow/01 3절).

표준 본사가 업데이트로 덮어씀작업 그 프로젝트의 일대표님 AI는 읽기만보관 지난 기록

경로구역프로젝트에서 쓰는 방법
AGENTS.md, CLAUDE.md, setup.cmd, .gitattributes, .gitignore, .claude/, .githooks/, Workflow/, Departments/Development/assets/scripts/표준읽기만 합니다. 업데이트 패키지가 같은 경로에 덮어쓰므로, 프로젝트에서 고친 내용은 다음 업데이트 때 사라집니다(Workflow/06 6.2절 5항). 예외: secret_allowlist.txt는 덮어쓰지 않습니다.
Departments/(위 경로 제외)작업그 프로젝트의 ORDER(Secretariat/assets/inbox/), REQ, EC, 코드(Development/assets/src/), 테스트(assets/tests/), PRD·TAD(Design/docs/), 판정서가 쌓입니다.
Lab/, Audits/, Storage/작업그 프로젝트의 실험, 외부 보고서, 큰 파일(Storage/server/, Git 제외).
CEO/대표님대표님 자료. 에이전트는 수정하지 않습니다.
_archive/보관배포본에서 빠지므로(.gitattributes) 새 프로젝트에는 비어 있습니다.

배포본에서 빠지는 것: 본사의 REQ·EC, 부서 results/·workspace/, 비서실 자료(ORDER·조사·브리핑), 실험, 인수 시험, 부적합 기록, _archive/, Audits/(.gitattributes export-ignore). 그래서 새 프로젝트는 빈 안건 상태로 시작합니다.

4. 세 가지 흐름

① 신규 프로젝트 시작 (현행 규정: Workflow/06 6.1절)

본사 최종 승인·커밋→보안 점검→git archive로 배포본→sample/에 풀기→폴더째 복사·이름 변경→setup.cmd 1회→sample/ 비우기→그 폴더에서 ORDER-001부터

② 표준 업데이트 반영 (현행 규정: Workflow/06 6.2·6.3절)

본사에서 표준 개정 REQ 완료→표준 구역만 묶기→update/에 풀기→프로젝트 루트에 덮어쓰기→update/ 비우기→이관안내.md가 있으면 프로젝트 REQ로 처리

덮어쓰기는 옛 파일을 지우지 못합니다. 폴더 이름·구조가 바뀐 업데이트는 이관안내.md(수작업 절차)가 함께 갑니다.

③ 기존 작업 이관 (ORD-008 요구 항목 29·30. 아직 표준에 없음)

①과 같이 새 폴더 생성→배포본만으로 첫 커밋REQ에서 정함→비밀정보(.env 등) 빼기→이관 REQ로 코드·문서를 표준 위치에→목록·해시·빌드로 기준선 기록→기존 폴더 보관

확정된 것: 새 폴더 방식, 기존 폴더 보관, 대표님 프로젝트 하나로 시범 뒤 표준화, 시범은 새 프로젝트의 파이프라인에서 진행(ORD-008_v02 3절 6·8항, 2026-10-11 대표님 확인). 비서실 권고 단계: Git 이력은 새 저장소로 시작(기존 이력은 원본에 보관), 기존 .claude/·AGENTS.md는 복사하지 않음. 이 권고를 포함해 정해지지 않은 것: 루트 빌드 설정 파일의 자리, 상대 경로를 고치는 커밋 나누기, 첫 커밋 순서(후보 정리 자료 v10 3절 J1).

5. 일할 때 어느 폴더를 여는가

하려는 일여는 폴더기록이 남는 곳
매뉴얼·규정·서식을 고침(표준 개정)Vibe Standard_v04본사의 ORDER·REQ·판정서
제품 기능을 만들거나 고침그 프로젝트 폴더그 프로젝트의 ORDER·REQ·판정서(번호 001부터)
새 프로젝트 시작, 업데이트 패키지 만들기Vibe Standard_v04(만들기) → 프로젝트 폴더(복사·덮어쓰기)본사 쪽 기록 없음(sample/·update/는 커밋하지 않음)
업데이트 반영 뒤 수작업(이관안내.md)그 프로젝트 폴더그 프로젝트의 REQ

비서실(코워크·Antigravity)과 Claude Code도 작업할 프로젝트 폴더를 따로 연결해 엽니다. Claude Code는 연 폴더의 CLAUDE.md → AGENTS.md를 읽으므로, 프로젝트마다 그 폴더에 있는 표준 버전이 적용됩니다.

6. 핵심 발견과 확인이 필요한 점

  • 규정 있음 sample/·update/를 채운 채로 본사에서 파이프라인을 돌리지 않습니다. 표준 사본이 작업 트리에 남아, 에이전트가 다른 버전의 규정을 읽을 수 있습니다(Workflow/06 6.4절).
  • 미정 이관 세부 사항은 ORD-008 요구 항목 29(J1, 시범 이관 뒤 REQ)와 30(J2, 설치 안내)에서 정합니다.
  • 확인 필요 CEO/는 배포본 제외 규칙에 없습니다. .gitattributes의 export-ignore와 .gitignore에 CEO/가 없어, CEO/references/의 파일(디자인 참고 문서 5개, VibeOffice 시안 등)이 커밋되어 있으면 배포본에 그대로 들어갑니다. 커밋되어 있는지는 이 세션에서 Git을 실행할 수 없어 확인하지 못했습니다.
  • 확인 필요 프로젝트에서 나온 표준 개정 제안을 본사로 올리는 경로가 표준에 없습니다. 부적합 기록의 개정 제안은 같은 저장소의 ORDER로 이어지게 되어 있어, 프로젝트에서 나온 제안은 그 프로젝트 안에서 끝납니다. 프로젝트에서 표준 구역을 직접 고치면 다음 업데이트 때 덮어써집니다.

정할 일

정할 일권고안대안근거·영향
CEO/의 배포본 포함Antigravity로 커밋 여부를 먼저 확인하고, 다음 ORDER 후보로 CEO/** export-ignore(빈 자리 .gitkeep만 남김) 추가배포본을 만들 때마다 CEO/를 손으로 확인대표님 개인 자료가 구매자에게 갈 위험. .gitattributes는 거버넌스 파일이라 REQ(또는 핫픽스)가 필요
프로젝트 → 본사 개정 제안 경로후보 정리 자료에 후보로 올림. 「프로젝트의 개정 제안은 대표님이 본사 비서실에 전달해 본사 ORDER로 처리」 같은 한 줄 규정지금은 정하지 않고, 첫 이관 시범 때 생기면 그때 정함프로젝트가 늘수록 같은 문제를 프로젝트마다 따로 고칠 수 있음
