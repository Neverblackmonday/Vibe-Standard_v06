## 1. 결론

1. 문제(세션 사이의 복사·붙여넣기)는 실재하지만, 개선안의 상황판(`BOARD.md`)은 표준에 이미 있는 값을 다시 적는 장치다. 담당 세션은 ORDER 「담당 세션」 줄과 산출물 머리말 `author.session`이, 진행 상태는 각 단계 산출물이 원천이다(`Workflow/05` 1절 「공식 진행 상태」 항, 8.4절 2·3항). 상황판은 두지 않기를 권고한다.
2. 개선안 가운데 「메모 1건 = 파일 1개, 작성 뒤 수정하지 않음, 회신은 새 메모」는 쓸 만하다. 다만 지금 표준에서 비서실이 파일을 둘 수 있는 경로에 `board/`가 없으므로(`Workflow/02` 2.1절 표 아래 첫째 항목, 3절, 4절) 코워크 프로젝트 지침의 임시 규칙만으로는 시범 운영할 수 없다. 대표님 결정 「연락 수단은 비서실 폴더 안에 둔다」를 지금 규정 안에서 지킬 방법은 없다. 그래서 세 가지 경로 가운데 하나를 정해야 한다(6절 D2).
3. 개선안의 사실 전제 가운데 셋이 실물과 다르다. ① 부서별 인박스·아웃박스는 ORD-007·008이 아니라 `조사_20261010_MunderDifflin_v04.md` 5절 순위 1에서 나왔고, 같은 자료 8.1절에서 「반영할 것 없음」으로 처리되었다. ② 잠금 표시는 ORD-008 요구 항목 28(후보 번호 I1)로 이미 접수되어 있다. ③ 표준의 「세션 식별자」는 플랫폼 세션 ID가 아니라 `<서비스>·<세션 이름>`이다(`Workflow/05` 8.4절 2항).

### 3.6 `BOARD.md` 한 파일을 번갈아 고칠 때의 덮어쓰기 위험

- 위험은 남는다. 두 세션이 각각 읽고, 한 줄을 고쳐, 파일 전체를 다시 쓰면 나중에 쓴 쪽이 먼저 쓴 쪽의 줄을 지운다(lost update).
  - 코워크는 대표님 PC 파일을 사본으로 옮겨 고친 뒤 통째로 다시 쓴다. 쓰기 도구에 수정 시각 대조(`expectedMtimeMs`)가 있어 막을 수는 있지만, 세션이 그 값을 넣어야만 작동하고 읽기와 쓰기 사이의 짧은 틈은 남는다.
  - Antigravity·Codex의 편집 도구에 같은 대조가 있는지는 확인 불가다. `Workflow/05` 8.1절 7항 「덮어쓰기 전 대조」는 규정이며 자동 장치가 아니다.
  - Git도 막지 못한다. `BOARD.md`는 커밋 전 작업 트리에서 계속 바뀌는 파일이고, 여러 안건의 줄이 한 파일에 섞인다.
- 커밋 문제도 있다. 개선안의 「상황판을 해당 산출물과 함께 커밋」은 `Workflow/05` 1.1절 6번과 맞지 않는다. 그 항목은 안건 커밋의 스테이징 대상을 ①~⑧로 한정하고 그 밖은 「스테이징하지 않고 보고에 적는다」고 정한다. `BOARD.md`는 ①~⑧ 어디에도 들지 않고, 들게 하더라도 다른 안건의 줄이 같은 커밋에 들어간다.
- 더 단순한 대안: 고쳐 쓰는 공유 파일을 두지 않는다. 연락은 새 파일 만들기만 하고, 파일 이름이 겹치지 않게 정하면(5.2절) 동시 작성에서도 덮어쓰기가 생기지 않는다. 담당과 상태는 기존 원천(ORDER 「담당 세션」 줄, 머리말 `author.session`, 단계 산출물)을 그대로 읽는다.

## 5. 수정 권고안

### 5.1 바꾸는 점

1. **상황판을 두지 않는다.** 「누가 무엇을 맡았나」는 기존 기록을 읽는다. ORDER 「담당 세션」 줄과 산출물 머리말 `author.session`을 한 번에 찾는 명령은 `grep -rn "담당 세션\|session:" Departments/Secretariat/assets/`이다. 진행 상태는 지금처럼 단계 산출물로 판단한다.
2. **잠금을 새로 만들지 않는다.** 비서실 문서는 `Workflow/05` 8.4절 3항 「담당 세션」과 8.1절 7항 「덮어쓰기 전 대조」로 이미 다룬다. PM 쪽 문서(REQ·EC·적용본)의 잠금은 ORD-008 I1 REQ가 다룬다.
3. **연락만 둔다.** 「연락」 1건 = 파일 1개. 새로 만들기만 하고 고치거나 지우지 않는다. 지우는 것은 대표님 승인 뒤 정리 때만이다.
4. **연락에 넣지 않는 것**: 호출 문구, 승인 문구. 이 둘은 지금처럼 대표님이 받는 세션에 직접 준다(`Workflow/05` 8.2절 4항, `Workflow/07` 3.1절 3항). 연락에는 정보(조사 자료 경로, 결정의 배경, 확인 요청, 다른 세션이 담당한 ORDER·브리핑(`Workflow/05` 8.4절 3항 ①)에 대한 수정 요청)만 담는다.
5. **시범 위치는 실험실이다.** 경로는 `Lab/<승인 날짜>_비서실연락/`이다(`Workflow/03` 11.1절 3항). 비서실 자신의 실험실 사용은 대표님 지시가 승인이다(같은 절 1항). 대표님 지시를 직접 받은 세션이 `실험승인.md`를 만들고, 「사용 조직」은 「비서실(모든 세션)」로 적는다(같은 절 2·4항). `Lab/`은 scope 대조에서 빠지고 배포본에도 들어가지 않는다(`.gitattributes` 18행).
   - 이 위치는 대표님 결정 「연락 수단은 비서실 폴더 안에 둔다」와 다르다. 시범 기간에만 쓰는 예외로 제안한다. 정식 위치는 6항대로 비서실 폴더 안에 둔다.
   - 실험실 용도(「버리는 코드와 시안」)와의 관계: 시범의 대상은 연락 절차이며, 연락 파일은 그 시안의 기록이다. 결과가 쓸 만하면 파일을 옮기지 않고 ORDER로 올린다(같은 절 6항). 보관 기간은 정해져 있지 않고 삭제는 대표님 승인을 받아야 하므로(같은 절 9항) 대표님 승인 없이는 지워지지 않는다. 다만 ORDER를 발행하면 그 실험 파일은 같은 항의 정리 대상이 되므로, 지울지 남길지는 그때 대표님이 정한다.
6. **정식 반영 경로**: 「비서실 세션 간 연락」은 ORD-008 I1(잠금)과 목적이 다르므로 별도 REQ로 한다. ORDER는 개선안의 권고 경로와 같이 ORD-008에 넣는 안을 권고하되, 잠금 항목은 I1이 이미 있으므로 다시 넣지 않는다. 정식 위치는 그 REQ에서 `Departments/Secretariat/assets/` 아래 하위 폴더로 정하고 `Workflow/02` 2.1절·3절·4절, `Workflow/07` 1절 표, `Workflow/05` 8.4절에 더한다. ORDER는 6절 D4대로 정한다.

### 5.2 연락 파일 규칙(시범용. 실험 폴더 `README.md`에 둔다)

- 위치: `Lab/<승인 날짜>_비서실연락/`
- 파일명: `연락_<YYYYMMDDTHHMMSS>_<발신 세션 식별자>_<수신>_<작업 번호>.md`
  - 예: `연락_20261011T113005_코워크·20261011T1048_전체_ORD-008.md`
  - 발신은 서비스 이름을 포함한 세션 식별자 전체(`Workflow/05` 8.4절 2항)다. 세션 이름이 같아도 서비스가 다르면 구분된다.
  - 수신은 세션 식별자 또는 「전체」. 작업 번호가 없으면 `없음`
  - 저장 직전에 같은 이름이 있는지 확인하고, 있으면 확장자 앞에 `-2`부터 붙인다(예: `…_ORD-008-2.md`)
- 본문: 첫 줄 `발신: <세션 식별자>`, 둘째 줄 `회신 대상: <원 연락 파일명 또는 없음>`, 그 아래 본문. 머리말(YAML)은 두지 않는다
- 처리 완료의 표시: 회신 파일이 있으면 처리한 것으로 본다. 읽음 표시는 두지 않는다(고쳐 쓰는 파일을 만들지 않기 위해서다)
- 남기는 때: 대표님이 지시할 때만. 다른 세션이 담당한 ORDER·브리핑을 고쳐야 할 때의 처리는 지금처럼 `Workflow/05` 8.4절 3항을 따르며, 연락은 그 요청을 전하는 수단으로 쓸 수 있다
- 읽는 때: 대표님이 「연락 확인」이라고 할 때만. 폴더의 파일 이름 목록을 보고 자기 앞이나 「전체」 앞 파일만 연다
- 금지: 호출 문구·승인 문구, 명령 출력 원문, 설정값
- 커밋: 대표님이 요청할 때 `Lab/` 변경만 담은 커밋(`Workflow/05` 8.3절 「요청 커밋」 예외 (마))

### 5.3 기대 효과와 한계

- 줄어드는 것: 조사 요지·경로·배경 설명을 대표님이 옮겨 붙이는 일. 대표님은 받는 세션에 「연락 확인」 한마디만 하면 된다.
- 남는 것: 호출 문구와 승인 문구의 직접 전달(안전장치라 유지), 세션을 부르는 한마디.
