## 1. 결론

1. **비서실 세션 교대 전체를 다루는 규정은 없고, 일부만 있습니다.** 고정 절차가 도중에 끊긴 경우의 재시작(`Workflow/05` 8.3절 「세션 종료 조건」), 셸 작업 넘기기(8.5절 4항, 8.6절), 작업 큐의 ORDER·REQ별 담당·진행 상태(8.7절 3항), ORDER 담당 세션 변경(8.4절 3항 ②)은 있습니다. 그러나 ORDER에 아직 옮기지 않은 대표님 원문·결정·질문을 어디에 남기고 다음 세션이 무엇부터 읽는지는 없습니다(3섹션).
2. **인계 파일이 필요한 곳은 비서실 하나입니다.** PM팀은 산출물 기준 재개 규정과 PM 실행 기록이 있고, 설계·개발·품질 파트는 단계마다 한 번 실행되어 인계 패킷·EC·결과서로 넘깁니다(4섹션).
3. **관리안: 인계 문서를 업무현황 한 종류로 줄이고, 표준에는 문서 종류와 「시작할 때 업무현황 최신본을 읽는다」는 규칙 한 항만 더합니다.** 참고 문서, 인수인계서, 업무현황 안의 규칙 요약을 없애고, 표준에 반영되면 다음 세션 업무지시도 없앱니다(반영 전에는 짧은 시작 지시 한 장이 남음). 업무현황을 커밋하면 업무현황 자체의 sha256 대조는 필요 없어집니다. 세션마다 커밋하는 입력은 질문 (사)의 답과 커밋 분리 REQ에 달려 있습니다(5섹션).
4. **질문 (자)를 둔 것은 비서실의 잘못입니다.** Claude Code 비서실 세션이 PM 지시문을 셸로 실행한 실적이 저장소 기록에 있습니다(2섹션).

| sha256 대조표, 멈춤 조건 | 업무현황과 커밋된 파일의 대조는 폐지(커밋으로 확인). 커밋되지 않은 파일(ORD-012_v13 등)의 대조는 요청 커밋이나 작업 브랜치 저장 때까지 남김 |

업무현황에 적는 것(상태만):

1. 끝낸 일. 한 줄씩만 적고 세부는 지웁니다(커밋 이력에 남음).
2. 진행 중인 일과 다음 할 일. 순서는 작업 큐를 가리키고 옮겨 적지 않습니다.
3. ORDER에 아직 옮기지 않은 대표님 원문과 수신 시각, 그 원문으로 정해진 것.
4. 답을 받지 않은 질문과 그 배경. 여쭐 시점도 적습니다.
5. 이번 세션이 바꾼 파일, 커밋하지 않은 파일과 그 sha256. 셸 작업 지시는 `셸작업/` 폴더가 원천이므로 적지 않습니다.
6. 멈춘 핫픽스와 그 단계, 멈춘 고정 절차, 진행 중인 실험.
7. ORDER 담당 세션의 변경(8.4절 3항 ②의 대표님 지시).

머리에 적는 것: 작성 세션, 작성 날짜, 판정 상태(「판정 전 작업본」 또는 「판정 반영」), 커밋 여부, 대체하는 버전.

지우는 규칙: ORDER·작업 큐·표준에 옮긴 내용은 다음 버전에서 지웁니다. 이렇게 하면 분량에 상한을 두지 않아도 업무현황이 쌓이지 않습니다.

적는 시점과 쓰는 세션:

- 대표님 원문이나 결정을 받으면 바로 업무현황 작업본에 적습니다. 세션이 예고 없이 끝나도 그때까지의 내용이 대표님 PC의 작업 트리에 남습니다(커밋 전). 다음 세션은 머리의 판정 상태가 「판정 전 작업본」이면 원문을 대표님께 확인받은 뒤 씁니다.
- 세션을 끝낼 때 판정을 받고 커밋합니다.
- 업무현황은 「업무현황 담당 세션」 하나만 씁니다. 업무현황 담당 세션은 대표님이 그 역할을 지정하신 비서실 세션이며, 지정이 없으면 대표님과 대화하는 비서실 세션입니다. 그런 세션이 둘 이상이면 대표님께 여쭙습니다. 셸 작업만 처리하는 세션은 쓰지 않고, 결과는 셸 작업 결과 파일로 남깁니다.

### 5.4 표준 반영과 그 전의 운용

- 반영할 안건: 작성할 ORD-013의 커밋 분리 요구 항목 ①에 「인계 문서를 표준 문서 종류로 정하는 일」이 이미 들어 있습니다(2026-10-24 원문 16번으로 ORD-013은 커밋 분리 REQ와 경량화 REQ 둘). 5.2섹션 B안은 새 고정 절차를 만들지 않으므로 이 ① 안에 넣을 수 있고, REQ를 하나 더 만들지 않습니다. 다만 ①의 내용은 「업무현황·다음 세션 업무지시·인수인계서 세 종류」에서 「업무현황 한 종류와 8.1절 시작 규칙 한 항」으로 바뀝니다(6섹션 결정 4).
- 고칠 곳: `Workflow/07` 1절 문서 체계 표, 2절(이름 규칙, 「비서실 산출물의 버전」 대상), 3절 머리말(작성 날짜·판정 상태 칸), `Workflow/02` 2절 비서실 산출물·2.1절 표 아래 목록(71행)·3절 구조도의 `workspace/` 줄·4절 작업 구역 표, `Workflow/05` 머리 「이 문서가 정하는 것」·1절 「커밋」 항 ②(구역 추가)·8.1절(시작 규칙 한 항)·8.4절(ORDER 담당 변경을 업무현황에도 적음), 생성 지침 재생성(S01·비서실 지침에 실림. 계층 구성표 `guide_layers.json`의 선택자 확인). 조직 골격 REQ 뒤 위치는 그 REQ가 반영합니다.
- 커밋 방법(표준 반영 전): ① 커밋 분리 REQ 반영 뒤 작업 브랜치에 저장(지금 계획. 그때까지 인계 문서는 커밋되지 않은 사본이고 sha256 대조가 남음) ② 대표님이 `Workflow/05` 1절 「커밋」 항 ②에 `workspace/인계/`를 직접 더하심. ②는 권하지 않습니다. 그 목록이 생성 지침 9개에 그대로 실려 있어, 대표님이 고치시면 커밋 전 검사의 생성물 대조(`Workflow/06` 4.6절 2항)가 실패하고 `--no-verify` 지시가 필요해지며, 원천이 매뉴얼이어서 지침 재생성 반영 커밋으로도 맞출 수 없어 그 뒤의 커밋마다 같은 실패가 남습니다.
- 시작 지시(표준 반영 전): 시작 규칙이 표준에 없으므로 업무지시 한 장이 시작 지시로 남습니다. 시범 기간에는 시작 지시를 짧게 줄여(읽을 문서, 능력 확인, 멈춤 조건만) 한 번 판정받습니다. 시작 지시에는 업무현황의 번호를 적지 않고 「`workspace/인계/`의 `업무현황_vNN.md` 가운데 가장 높은 번호」로 적어, 업무현황이 바뀌어도 시작 지시는 다시 쓰지 않게 합니다. 내용이 같은 파일을 다시 쓰지 않는 것은 전역 지침 「버전 관리」(내용이 같으면 다시 생성하지 않음)에 따른 것이지만, 판정 생략으로 읽힐 수 있으므로 대표님께 확인받습니다(6섹션 결정 3).
- 시범 운용은 지금 규정의 비서실 수정 범위(`Workflow/02` 2.1절 71행)에 없는 문서를 쓰는 일입니다. 지금 업무현황·업무지시도 같은 상태이며, 시범 기간을 표준 반영 REQ의 최종 승인까지로 한정합니다.
