2. **모자란 것은 「본사와 포크 사이」입니다.** 현행 업데이트는 표준 구역 파일을 덮어쓰는 방식이 기본이고(`Workflow/06` 6.2절 5항. 예외 목록 파일 하나를 빼고 덮어쓰며, 덮어쓰기만으로 안 되는 변경은 이관 안내 문서로 처리합니다), 고객이 고친 표준 파일은 업데이트 때 사라지고, 일부만 따르는 방법도 없습니다. 포크에는 표준의 주 버전(첫 커밋 메시지)만 남고 어느 본사 커밋·릴리스에서 나왔는지는 남지 않으며, 고객이 본사에 개정을 제안하는 경로도 없습니다.
3. **판매 형태(SaaS·로컬 HTML 엔진)와 관계없이 먼저 필요한 것은 「릴리스 단위」입니다.** 버전 번호, 바뀐 파일 목록과 해시(매니페스트), 바뀐 이유를 적은 릴리스 노트가 있어야 본사가 업데이트를 「쏴 주고」, 고객이 따를지 고를 수 있습니다. 지금의 `git archive` 업데이트 패키지를 이 단위로 정리해 두면, 나중에 SaaS나 로컬 엔진의 배포 기능은 그 단위를 실어 나르기만 하면 됩니다.
4. **「SaaS면 알아서 적용」은 「자체대로갈수도있음」과 부딪칩니다.** 자동 적용은 「자체대로 갈 수도 있음」과 함께 갈 수 없으므로, 고객마다 업데이트 수용 방식(자동, 검토 후 적용, 고정)을 고르게 해야 합니다.
5. **`.env` 관리는 넣기를 권고합니다.** 지금 저장소에는 `.env`가 없지만(2026-10-11 루트 폴더 목록), 판매하면 고객 프로젝트 대부분이 API 키를 씁니다. 현행 표준은 `.env` 한 이름만 Git에서 빼고, 에이전트가 `.env`를 읽는 것은 막지 않습니다(5절).

## 4. 「본사에서 쏴 주는」 업데이트 검토

- **맞는 점**: 판매 뒤에는 본사가 릴리스를 만들고, 고객 쪽 배포 기능이 받아서 적용하는 구조가 됩니다. 지금 대표님이 손으로 하는 `git archive` → 복사 → 덮어쓰기(`Workflow/06` 6.2절)를 기계가 대신하는 것입니다.
- **고칠 점 ①: 자동 적용의 범위.** SaaS라도 고객이 자기 표준을 고쳤거나 본사 개정을 거부한 경우가 있으므로 자동 적용을 기본으로 둘 수 없습니다. 고객별 수용 방식 세 가지를 권고합니다.
  - 자동: 고객 표준을 고치지 않았고 고객이 미리 동의한 포크. 새 릴리스를 바로 덮어씁니다.
  - 검토 후 적용: 고객 표준을 고쳤거나 자동 적용에 동의하지 않은 포크(기본값). 릴리스 노트를 보고 고객 REQ로 반영합니다.
  - 고정: 특정 릴리스에 머뭅니다.
- **고칠 점 ②: 판정과 승인.** 표준 구역은 거버넌스 파일이고, 이 표준은 거버넌스 변경을 판정과 대표님 승인 뒤에만 반영합니다(`AGENTS.md` 「불변 원칙」 3·5항). 고객 저장소에서 「대표님」은 그 고객입니다. 자동 적용도 고객이 미리 동의한 범위에서만 해야 이 원칙과 맞습니다.
- **고칠 점 ③: 고객 데이터.** SaaS에서 고객 코드와 안건 문서를 본사 서버에 두는지, 고객 PC에 두는지에 따라 보안 책임이 크게 달라집니다. 판매 형태(SaaS·로컬 엔진)가 어느 쪽이든 고객 데이터를 본사가 보관하면 보관·유출 책임이 본사에 생기므로, 데이터 위치는 제품 기획에서 가장 먼저 정할 사항입니다(비서실 의견).
- **지금 할 일**: 판매 형태와 관계없이 쓰이는 릴리스 단위(M1)와 수용 방식(M2), 제안 경로(M3)만 표준에 넣고, 배포 기능 자체는 제품 기획으로 미룹니다. 라이선스(재배포, 고객 수정본의 권리)는 판매 전에 정해야 하는 사업 사항이며 이 자료는 법률 검토를 하지 않았습니다.

## 5. 비밀정보 파일(.env) 관리

| 항목 | 현행 | 공백 | 권고 |
| :--- | :--- | :--- | :--- |
| Git 제외 | `.gitignore`에 `.env` 한 줄 | `.env.local`·`.env.production` 같은 변형, 키 파일(`*.pem`, `*.key`)은 빠지지 않습니다 | `.gitignore`에 `.env`, `.env.*`, `!.env.example`(견본은 다시 추적) 세 줄을 둡니다. 키 파일 규칙은 REQ에서 정합니다 |
| 에이전트 읽기 차단 | `settings.json` `deny`에 읽기 규칙이 없습니다 | 에이전트가 `.env`를 읽어 값이 대화·출력·로그에 남을 수 있습니다 | `deny`에 `Read(.env)`, `Read(.env.*)`, `Read(!.env.example)`을 이 순서로 넣습니다. 공식 문서 「Settings」의 예시(`Read(./.env)`)는 현재 폴더의 `.env`에만 맞고, 앞에 경로가 없는 `Read(.env)`는 하위 폴더 어디의 `.env`에도 맞습니다. `!` 규칙은 같은 목록에서 앞의 규칙에서 견본만 빼냅니다. `Read` 거부는 같은 경로의 편집·새 파일 쓰기도 막으므로(Claude Code v2.1.208 이상 편집, v2.1.228 이상 쓰기), 에이전트는 `.env`를 만들거나 고칠 수 없고 값 입력은 사람이 합니다(공식 문서 「Configure permissions」) |
| 차단의 한계 | — | 공식 문서 「Configure permissions」: 읽기 거부는 내장 도구와 `cat`·`head` 같은 명령에 적용되지만, 파일 이름을 적지 않는 명령(`grep -r`)이나 Python 스크립트가 여는 파일에는 적용되지 않습니다. 이 표준은 `Bash(python Departments/*/workspace/*)`를 확인 없이 실행하게 둡니다(`Workflow/06` 2.1절) | 읽기 거부는 사고를 줄이는 장치이지 완전한 차단이 아니라고 표준에 적고, 강한 차단이 필요하면 샌드박스(공식 문서)를 따로 검토합니다 |

## 8. 확인하지 못한 항목

- `CEO/` 아래 파일이 커밋되어 있는지(이 세션은 Git을 실행할 수 없음. 부록의 지시문으로 확인).
- 판매 형태별 구조(SaaS의 고객 데이터 위치, 로컬 HTML 엔진의 업데이트 수신 방식). 제품 기획 전이라 대상이 없습니다.
- 라이선스와 고객 수정본의 권리. 법률 검토 대상이며 이 자료는 다루지 않았습니다.
- 5절 `Read` 규칙 세 개(`!` 규칙 포함)의 Windows 동작. 공식 문서 「Configure permissions」는 Windows 경로를 POSIX 형식으로 바꿔 맞춘다고 적지만, 이 표준 환경에서 실측하지 않았습니다.
- 참고(이 조사 범위 밖): 공식 문서 「Configure permissions」는 파일 권한을 `Edit`·`Read` 규칙으로만 검사하고 `Write(...)` 규칙은 받아들이되 검사하지 않는다고 적습니다(`Edit` 규칙이 모든 편집 도구에 적용됨). 현행 `settings.json`의 `Write(...)` 짝은 효과가 없을 수 있고, `Workflow/06` 2절의 `Write` 도구 기준 실측 서술(근거 DEV-008)과 어긋날 수 있습니다. Claude Code 버전에 따라 다를 수 있어 별도 확인이 필요합니다.
