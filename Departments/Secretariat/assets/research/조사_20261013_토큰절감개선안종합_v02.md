## 2. 결론

1. **v05의 방향(공정 지도 + 계층형 지침 + 파트 편성 + 모델 티어링)은 맞습니다. 다만 마이그레이션 자료의 수치와 일부 수단은 실측과 다르거나 위험해 고쳐야 합니다(3·14절).**
   - 「기동 500~800토큰, 85.7% 절감」은 불가능합니다. 플랫폼 기본 프롬프트만 약 1.07만 토큰입니다. 지침 부분은 78~90% 줄일 수 있지만, 기동 맥락 전체는 약 4만 → 약 1.6만~2.2만 토큰(약 45~60% 감소)이 현실적인 목표입니다(7.2절).
   - 「Sonnet 13개 파트로 원가 80% 절감」은 단가가 틀렸습니다. Sonnet 5.5는 Opus의 절반이므로 해당 파트 비용의 50%가 상한입니다.
   - 격리 실행기(`CLAUDE_CONFIG_DIR`)는 인증 파일을 프로젝트 폴더로 복사하고 전역 지침의 불변 예외(보안, 삭제·덮어쓰기 승인, 커밋·푸시 제한)까지 끊으므로 기각하고, Claude Code용 전역 지침 축소본으로 같은 효과를 냅니다(7.5절).
2. **코워크가 가장 큰 사용처일 가능성이 높습니다. 코워크 운용 개혁(9절)을 v05 구조 개편보다 먼저 별도 ORDER로 시작할 것을 권고합니다.** 두 구간 추정으로 전체의 57~66%(크게 잡힌 쪽의 추정)이고, 고정 기동 맥락(11.5만 토큰)이 Claude Code 본 세션(약 4.9만)의 두 배가 넘습니다.
3. **조직은 6부, 8팀, 24파트(활성 17, 대기 7)로 편성합니다(5절).** 파트 하나는 공정 단계 하나입니다. 마이그레이션 원장의 21개 파트는 24파트 가운데 하나에 대응하거나, 스크립트·대기 파트로 처리하거나, 폐지합니다(실행환경관리). 처리는 5.4절에 파트마다 적었습니다.
4. **모델은 파트에 고정하지 않고 「작성/판정 × 안건 분류」로 정합니다(6절).**
   - 판정 파트(Q1~Q5)는 모든 분류에서 고급(Opus)입니다. Critical은 모든 파트가 고급입니다.
   - 작성 파트 E2·E3·E4·V1·V2·X1과 기록 파트 Q6은 Major에서 중급(Sonnet)을 시범합니다. REQ 작성(P1), EC 판단(E1), 인수 시험(Q7)은 Major에서도 고급을 유지합니다. 반려 누적으로 Minor에서 Major로 격상한 안건은 시범에서 빼고 고급으로 실행합니다.
   - `Workflow/04` 1.2절·1.3절, `Workflow/03` 2절 개정이 필요합니다(6.3절).
5. **새로 찾은 낭비는 재작업입니다(3.3절).** 지난주 v04 서브에이전트 비용의 최대 약 23%($104.1, 상한)가 재판정·수정 실행입니다. REQ 판정 69건 가운데 47건이 새 버전의 재판정입니다. 초도 합격률(첫 판정 `pass` 비율)을 관리 지표로 두고, 판정 전 자체 점검 스크립트로 줄입니다(8.4절).
6. **효과(1주일, Claude Code)는 약 $185~295(Claude Code $931.76의 약 20~32%)입니다(10절).** 계층형 지침 $103~115, 스킬·도구 목록 정리 최대 약 $57, 모델 티어링 0~약 $93, 재작업 감소(목표)를 같은 가정으로 차례로 적용한 값입니다. 코워크는 기록이 없어 금액을 정하지 못했고, 적용 전후 측정으로 정합니다.
7. **대시보드는 공정 지도 원천(`process_map.yaml`)과 검사 결과에서 생성합니다(13절).** 기능 지도 시제품의 구조(노드·연결·검사)를 표준 공정 전체로 넓히고, 조직 트리와 파트 카드 미리보기, 모델 원장, 지침 형상관리, 추적성, 사용량 보기를 둡니다.
8. **이행은 6단계입니다(12절).** 운영 습관과 코워크 개혁을 먼저 하고, 공정 지도 작성 → 매뉴얼 재구성·카드 생성 → 병행 검증 → 전환 순서로 갑니다. 단계마다 진입·종료 기준과 측정 지표를 둡니다. 어디를 어떻게 고치는지는 11절 표에 경로별로 적었습니다.

## 5. 조직 편성

### 5.1 편성 기준

- **파트**: 공정 단계 하나에 하나입니다. 한 단계를 여러 실행으로 쪼개지 않습니다. 같은 산출물의 새 버전(재작업·결함 반영·문체 반영)은 처음 작성한 파트가 맡습니다. 작성과 판정은 다른 파트입니다.
- **예외**: 같은 단계라도 안건 종류에 따라 규정이 크게 다르면 카드를 나눕니다(E3·E4, V1·V2). 비서팀은 대화 업무이므로 책무를 묶은 단위로 둡니다.
- **부**: 조직 표의 행(부서 폴더와 권한 한계)입니다. 지금은 `AGENTS.md` 1절 표이고, 11절대로 상세를 옮기면 `Workflow/02`의 조직 표입니다. 부서 폴더(`Departments/Secretariat`, `Design`, `Development`, `Quality`, `Operations`, `Marketing`)는 그대로 둡니다.
- **팀**: 실행 환경이나 권한이 다르면 다른 팀입니다. 현행 규정이 별도 기능으로 정한 단위(시험실)도 팀으로 둡니다. 팀 지침은 실행 환경·권한이 다르거나 같은 팀 파트 2개 이상이 부 지침 밖의 규정을 함께 쓸 때만 둡니다(비서팀, PM팀, 판정팀).

## 6. 모델 티어링 원장

### 6.1 현행 규정

- 비서실(핫픽스 포함)은 모델 제한이 없습니다(`Workflow/04` 1.2절).
- REQ 작성 파이프라인(REQ 작성, REQ 판정)은 고급입니다.
- 원스톱 파이프라인은 「그 안건의 모델」입니다. Critical·Major는 고급, Minor는 중급이며, Critical·Major는 중급으로 낮추지 못합니다(`Workflow/04` 1.3절 5항, `Workflow/03` 2절). 중단 때 부적합 기록도 「그 안건의 모델」입니다.
- 최종 판정은 고급 이상입니다. 정의 파일은 `model: inherit`이고 PM이 호출 인자로 정합니다.

### 7.2 기동 맥락 목표의 산출

- **실측 구성**(분석 v02 3.4절, 품질 서브에이전트 1개): 첫 호출 캐시 읽기 10,658토큰(기본 프롬프트·내장 도구) + 캐시 쓰기 29,694토큰. 캐시 쓰기 부분의 글자는 전역 `CLAUDE.md` 8,587 + `AGENTS.md` 7,642 + 스킬 목록 19,791 + 도구 이름 목록 약 6,500 + 그 밖 약 6,100 = 48,620자이므로, 실측 환산비는 약 0.61토큰/자입니다.
- **개선 뒤**: 10,658 + (지침 3,000~6,500자 + 그 밖 6,100자) × 환산비
  - 0.61토큰/자: 약 1.6만~1.8만 토큰
  - 0.93토큰/자(한글 위주일 때): 약 1.9만~2.2만 토큰
- 이 값은 스킬 목록과 도구 이름 목록을 모두 없앤다고 가정했으므로 하한 쪽은 낙관적입니다. 따라서 목표는 약 1.6만~2.2만 토큰(약 4만 대비 45~60% 감소)이고, 12절 종료 기준은 「2.2만 토큰 이하」입니다. 스킬·도구 목록 정리(7.5절)를 하지 않으면 약 3.2만~3.4만 토큰에 머뭅니다.

### 13.5 디자인 기준

- **기본 체계**: shadcn/ui 방식의 무채색 토큰(배경·표면·테두리·글자 4단, 주색은 거의 검정). Vibe Office 시안과 같은 계열입니다.
- **상태색**: 성공·경고·위험·정보 4종만 씁니다. 옅은 배경에 진한 글자이고, 색만으로 전달하지 않도록 글자와 함께 씁니다(KRDS, One UI).
- **글꼴과 크기**: Pretendard(설치 글꼴, 없으면 시스템 글꼴), 본문 14px/1.5, 표 13px, ID·경로는 고정폭. 숫자는 `tabular-nums`(토스).
- **간격과 모양**: 4px 단위 간격, 모서리 둥글기 12px 이하(KRDS 상한), 카드는 1px 테두리. 왼쪽 색띠, 이모지와 기호 아이콘은 쓰지 않습니다(KRDS).
- **다크 모드**: 함께 설계하고 시스템 설정과 수동 전환을 모두 지원합니다. 대비 4.5:1을 지킵니다(One UI).
- **모션**: 320ms 이하, `prefers-reduced-motion`을 따름. 무한 반복 애니메이션(기능 지도 시제품의 흐름선)은 정지 수단을 둡니다.
- **참고 자료끼리 충돌하는 곳의 결정**: 주색은 무채색(Vibe Office 시안), 본문 14px, 자간 0, 로딩은 스켈레톤 없이 즉시 렌더(데이터가 파일 안에 있음), 문체는 하십시오체(전역 지침).
