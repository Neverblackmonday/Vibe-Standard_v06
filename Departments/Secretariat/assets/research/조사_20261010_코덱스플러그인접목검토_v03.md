### K3. `/codex:rescue`는 쓰지 않음

- README에서 `/codex:rescue`는 작업을 코덱스에 「위임」하는 명령이며, 리뷰 두 명령과 달리 읽기 전용으로 적혀 있지 않다. E1은 이 명령으로 글 검수를 받고 「고치지 말고 지적만」을 붙이라고 하지만, 이는 모델에 대한 지시일 뿐이다.
- 우리 권한 통제는 이 명령의 쓰기를 막지 못한다. `.claude/settings.json`의 `deny`는 Claude Code 도구 호출에만 적용되는데(`Workflow/06_통제장치_및_배포` 1절 통제 계층 표 1행), 코덱스는 외부 프로세스로 파일을 쓴다. 그러면 범위 통제(`AGENTS.md` 「불변 원칙」 2항)와 거버넌스 구역 보호(같은 3항)가 모델 지시에만 기대게 된다. K1에는 리뷰 두 명령만 쓴다.

### K4. 설치 범위

- README는 설치 범위(사용자·프로젝트)를 적지 않는다. 플러그인이 프로젝트의 `.claude/settings.json`에 쓴다면 거버넌스 파일(`AGENTS.md` 「불변 원칙」 3항) 변경이다. 이 쓰기는 도구 호출이 아닌 내장 명령이라 `deny`의 `.claude/**` 규칙이 막는지 확인 불가다. 막지 못하면 거버넌스 파일이 승인 없이 바뀐다.
- 사용자 범위로 설치하면 그 PC의 모든 Claude Code 세션(파이프라인 PM 세션 포함)에 플러그인이 붙는다. README에 따르면 플러그인은 `SessionStart` 훅과 `codex:codex-rescue` 서브에이전트를 함께 들인다. 결론 2(지금 파이프라인에 들이지 않음)와 실험 범위(`Workflow/03_라이프사이클` 11.1절 2항)에 어긋난다.
- 그래서 실험은 별도 임시 저장소에서 하고(4절. 위치는 4절 「정할 것」), 그 임시 저장소 범위로만 설치할 수 있으면 그렇게 한다. 그럴 수 없으면 실험 기간에는 파이프라인을 실행하지 않고, 실험이 끝나면 플러그인을 제거한다. 어느 경우든 설치 전후 표준 저장소에서 `git status`로 `.claude/` 변경이 없는지 확인한다.

### K5. `Workflow/04_모델_운용` 1.1절 문구

- 현행 문구: 「위 표 가운데 Claude Code에서 실행할 수 없는 모델(Astra, Sol급, Gemini Pro급, GPT Luna급, Gemini Flash급)은 두 파이프라인과 판정에 쓰지 않는다.」
- 플러그인이 있으면 Claude Code 세션 안에서 GPT 계열 모델을 부를 수 있다(README의 `/codex:rescue --model`). 그러면 「Claude Code에서 실행할 수 없는」이라는 분류 근거가 사실과 달라지고, 괄호 안 목록이 계속 맞는지 해석이 엇갈린다.
- 이 항은 두 파이프라인과 판정에만 적용되므로 4절의 파이프라인 밖 실험에는 걸리지 않는다. K1을 파이프라인에 들이는 ORDER를 낼 때 「Claude Code의 `Agent` 호출로 실행할 수 있는 모델」처럼 기준을 바꾸는 개정을 함께 넣기를 권고한다.

### K6. Grok Bot(도입하지 않음)

- **구조가 맞지 않는다**: 모든 Bot이 클라우드 컴퓨터 한 대를 함께 쓰고, 한 Bot에 연결한 도구와 로그인을 다른 Bot도 쓸 수 있다(E2 안전 수칙 3, `x.ai/bot` 공식 페이지). 우리 표준은 조직·구역마다 권한 한계를 따로 두고 있어(`AGENTS.md` 1절 「조직·구역과 권한 한계」), 이 구조로는 그 분리를 재현할 수 없다.
- **저장소에 닿지 않는다**: Bot은 클라우드에서 돌아 localhost 주소를 쓸 수 없다(E2). 로컬 저장소 `D:\Vibe Coding\Vibe Standard_v04`와 Git 훅, `deny` 규칙 위에서 일하는 우리 파이프라인과 따로 논다.
- **이미 있는 것과 겹친다**: E2의 「팀별 첫 메시지(역할과 승인 규칙)」는 우리 `.claude/agents/*.md` 정의 파일과 같은 역할이다. E2의 「발송 전 승인」 규칙은 E2 스스로 완벽한 차단이 아니라고 밝힌다.
- 공식 페이지는 이용 요금제에 SuperGrok을 포함한다. E2와 다른 점은 안드로이드 앱이다. E2는 안드로이드 앱이 있다고 적지만, 공식 페이지의 이용 안내 문장은 macOS·Windows·iOS만 들고 안드로이드는 다운로드 표지로만 나온다. 표준이 아니라 다른 사업(메일 분류, 콘텐츠 조사)의 도구로나 따로 검토할 만하다.

## 4. 권고: 파이프라인 밖 사후 시험

- **실행 주체와 승인**: 코덱스 플러그인은 Claude Code 세션 안에서 돌고, 비서실(저장소 밖 서비스)은 그 명령을 직접 실행할 수 없다. 대표님이 파이프라인 밖에서 띄운 Claude Code 세션이 실행하며, 이는 `Workflow/03_라이프사이클` 11.1절 1항의 「그 밖의 조직」이므로 쓰기 전에 비서실 승인을 받는다. 승인한 비서실이 실험 폴더에 `실험승인.md`를 만든다(같은 절 4항).
- **실험 폴더**: `Lab/<승인 날짜>_코덱스교차검토/`(같은 절 3항).
- **리뷰 대상 제시 방법**: `/codex:review`는 커밋하지 않은 변경분 또는 `--base` 비교만 대상으로 하므로, 리뷰용 임시 Git 저장소가 필요하다.
  - 재판정 대상: 「판정 직전 버전」을 커밋한 뒤 「판정 대상 버전」으로 바꿔 둔 상태에서 리뷰한다. 재판정이 변경분만 판정하는 것(`Workflow/03_라이프사이클` 8절 「재판정 한도」)과 같은 조건이 된다.
  - 최초 판정 대상: 직전 버전이 없으므로 빈 커밋 하나를 만든 뒤 판정 대상 버전 전문을 더한 상태에서 리뷰한다. 최초 판정이 문서 전체를 보는 것과 같은 조건이 된다.
- **정할 것: 임시 저장소의 위치**(대표님 결정). 11.1절 2항은 「승인받은 조직은 그 폴더 안만 수정한다」고 정한다.
  - 안 A(권고): 임시 저장소를 실험 폴더 안에 둔다. 11.1절 2항을 그대로 지킨다. 다만 표준 저장소 안에 다른 Git 저장소가 생기므로, 실험 폴더의 임시 저장소를 표준 저장소 커밋에 넣지 않는 처리가 필요하다. `.gitignore`는 거버넌스 파일이라 고칠 수 없으므로, 실험 폴더 변경을 커밋할 때(11.1절 7항) 임시 저장소 폴더를 빼고 결과 기록만 커밋하는 것으로 처리한다.
  - 안 B: 임시 저장소를 표준 저장소 밖에 둔다. 표준 저장소에 영향이 없다. 다만 승인받은 세션이 승인 폴더 밖을 수정하게 되어 11.1절 2항의 문언에 맞지 않으며, `실험승인.md` 「범위」에 저장소 밖 경로를 적는 방식도 표준에 없다.
- **대상**: 유효한 판정서가 있는 「판정 대상 버전–그 버전의 유효 판정서」 짝으로 정한다. `RES-007-REQ_v01`~`_v06`, `RES-008-REQ_v01`~`_v04`, `RES-010-REQ_v01`~`_v05`는 무효 처리 기록이 있어 제외한다(`조사_20261008_외부에이전트운용자료비교_v03.md` 2절). 우선 후보는 결함이 부적합 기록으로 남은 REQ-018·019·021·022 안건이다(예: `NCR-018_02`, `NCR-019_03`, `NCR-021_02`, `NCR-022_01`. `조사_20261010_ORD-007후보정리_v07.md` A).
- **비교 지표**: ① 같은 버전에 대한 유효 판정의 결함 가운데 코덱스도 찾은 비율 ② 코덱스 지적 가운데 근거 없는 지적(오탐) 수 ③ 코덱스만 찾은 타당한 결함 수 ④ 명령 실행과 결과 읽기에 든 Claude 측 토큰 ⑤ 코덱스 사용량과 소요 시간.
- **승인 범위에 적을 조건**: 리뷰 두 명령만 사용(K3), 설치 직후 리뷰 게이트를 끔(K2), K4의 설치 방식과 `.claude/` 무변경 확인, 실험 파일을 정규 경로로 옮기지 않음(11.1절 6항), 아래 판단 기준값.
- **판단 기준값**: 실험 승인 때 대표님이 정한다. 비서실 제안값은 「① 절반 이상이고, ② 오탐이 ③보다 적을 것」이다.
