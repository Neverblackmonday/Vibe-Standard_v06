## 1. 결론

1. **로컬·클라우드 실행은 파이프라인 실행을 시작할 때마다 고를 수 있다(4절).** 실행 위치를 고르는 전역 설정은 공식 문서에서 찾지 못했다(조직 단위로 클라우드 세션을 허용하는 정책은 있으나 실행 위치 기본값과는 다른 설정이다). 표준에 「실행 위치 기본값」을 두는 방식으로 스위치처럼 쓸 수는 있다. 실행 중 전환은 터미널에서는 클라우드 → 로컬(텔레포트) 한 방향만 된다. 데스크톱 앱에는 로컬 세션을 클라우드로 보내는 경로가 있으나 넘어가는 형태는 확인하지 못했다.
2. **클라우드 세션이 결과를 올릴 수 있는 원격 저장소 호스트는 GitHub뿐이다(3.1절).** `ORD-012_v06` 5절 「v05 저장소 준비」의 비서실 권고(지원 호스트의 비공개 저장소)는 GitHub 비공개 저장소로 구체화할 수 있다. v05에서 GitHub에서 복제하는 경로를 쓰려면 v05 원격 연결, 첫 푸시(대표님 요청), 연결 방법의 준비가 먼저 끝나야 한다(5.8절).
3. **현행 표준과 부딪히거나 새로 정해야 하는 곳은 5.1~5.7절의 일곱 군데다.** 가장 큰 것은 클라우드 세션이 멈출 때마다 작업 브랜치를 자동으로 푸시한다는 점(커밋도 함께 하는 것으로 보임. 5.1절)과, 대표님 PC의 전역 지침(`~/.claude/CLAUDE.md`)이 클라우드 세션에 실리지 않는다는 점(5.2절)이다. 두 가지와 D7 문구의 읽기(5.6절)는, v01 8절의 결정 세 가지에 대해 김비서가 결정 표 네 줄의 권고안을 제시하고 대표님이 2026-10-14에 「권고안」으로 답하셔서 정해졌다(8절). 결정 원문에 없는 사항 셋(「main 브랜치」의 읽기, 표준에 예외를 둘 수 있는지, 「나올 때까지」의 시점)은 v05 복제 뒤 클라우드 도입 ORDER를 쓸 때(9절 머리) 대표님께 확인한다. 그 결정을 지키는 절차(예외 범위, 안전장치 핵심을 싣는 방식, main 브랜치 보호)는 ORDER와 REQ에서 정한다.
4. **클라우드 세션의 역할로는 파이프라인 실행 위치(6절 후보 A)를 권고한다.** 이때 클라우드 세션을 비서실로 정할 필요는 없으나, 표준 실행 명령 밖의 방법으로 시작한 세션을 PM으로 보는지는 새로 정해야 한다(6절). 비서실로 쓰는 경우(후보 B)는 `ORD-012_v06` 요구 항목 12(Claude Code 세션도 비서실이 될 수 있음)와 맞으나, 대표님 PC의 작업 트리를 볼 수 없다. 저장소 하나로 연 클라우드 세션에는 계층 1이 적용된다(5.3절). 계층 3은 `setup.cmd`가 Windows 전용이라 그대로는 실행되지 않는다(5.4절).
5. **REQ-029 D7(로컬·클라우드 합쳐 원스톱 하나씩)은 대표님 결정에 따라 「클라우드 ORDER의 REQ가 나올 때까지」 그대로 둔다(5.6절, 8절 결정 3).** 클라우드에서만 도는 원스톱끼리는 작업 트리가 따로여서 판정의 작업 트리 조회가 섞이지 않는다. 그러나 결과를 기본 브랜치에 넣는 최종 승인 커밋, 로컬과 클라우드가 섞인 경우, `scope:` 겹침과 병합 충돌, 자동 커밋이 판정의 작업 트리 조회에 주는 영향(5.1절)은 D7을 다루는 REQ(이 자료의 제안, 9절에서 확인)에서 새로 정해야 한다. 「클라우드 ORDER의 REQ」가 어느 REQ인지와 「나올 때까지」의 시점(REQ 승인 또는 최종 승인 커밋)은 대표님 확인 사항으로 9절에 두었다.
6. **실행 위치는 세션 종류별로 정할 수 있다(6.1절, 이 자료의 안).** Claude Code PM 세션(부서 서브에이전트 포함)은 실행마다 로컬·클라우드를 고르고, Antigravity 세션(셸 비서실)은 로컬에 두며, 코워크 세션은 지금처럼 둔다. Antigravity의 앱·CLI 세션은 사용자가 운영하는 장비(이 저장소에서는 대표님 PC)에서 실행된다. Google 호스팅 실행은 앱·CLI 세션에는 없고, Antigravity 에이전트를 API로 쓰는 Gemini API Managed Agents와 별도 제품 Jules에서 찾았다(3.6절). 박비서 세션에 해당하는 것은 앱·CLI 쪽이다. Antigravity 에이전트 자체를 Claude Code 클라우드에서 실행하는 기능은 공식 문서에서 찾지 못했다. Antigravity 세션의 셸에서 Claude Code CLI로 클라우드 세션을 시작하는 것은 가능할 것으로 보나 실측하지 않았다. 클라우드 PM 세션의 작업 브랜치를 로컬 셸 비서실이 받아 검사·커밋하는 흐름의 초안을 6.2절에 두었다.

## 3. 확인 결과

### 3.1 원격 저장소 호스트(Q2)

- 클라우드 세션의 저장소 복제와 PR 생성에는 GitHub가 필요하다. 자체 설치 GitHub Enterprise Server는 Team·Enterprise 요금제에서만 된다(D1 「Limitations」).
- GitLab·Bitbucket 등은 로컬 저장소를 묶음으로 올려(`CCR_FORCE_BUNDLE=1`) 클라우드에서 일하게 할 수는 있으나, 결과를 그 원격으로 올릴 수 없다(D1).
- 원격이 없는 저장소도 `claude --cloud`로 로컬 저장소를 묶음으로 올려 일할 수 있다(D1 「Send local repositories without GitHub」).
  - 조건: 커밋 1개 이상. 추적하지 않는 파일은 빠진다.
  - 크기: 100MB를 넘으면 현재 브랜치만 묶고, 그래도 크면 작업 트리 스냅숏 하나로 대신하며, 그것도 크면 실패한다.
  - 결과 올리기: 묶음으로 시작한 세션은 GitHub 연결이 푸시 대상 GitHub 원격의 푸시 권한을 가질 때만 결과를 올릴 수 있다.
- GitHub 연결은 두 방법이다(D1·D2).
  - Claude GitHub App: 공개 저장소 전부와, 앱을 설치한 비공개 저장소.
  - `/web-setup`: 로컬 `gh` 토큰을 넘겨, 그 토큰이 닿는 저장소 전부.
- GitHub 인증 정보는 클라우드 VM 안에 들어가지 않고 프록시가 붙인다(D1 「Security and isolation」).

### 3.2 결과 회수와 푸시(Q4)

- 클라우드 세션은 멈추는 지점에 이를 때마다 자기 브랜치를 GitHub에 푸시한다. 「Accept edits」 모드는 승인을 기다리지 않고 변경하고 브랜치를 푸시한다(D2 「How sessions run」 4, 「Choose a permission mode」). 푸시하려면 커밋이 있어야 하므로 커밋도 함께 하는 것으로 본다(추론). 누가 언제 커밋하는지, 추적하지 않는 파일까지 커밋하는지, 변경이 없을 때의 동작은 문서에 없다(9절).
- 작업마다 세션과 브랜치가 따로 생긴다(D2). 정기 실행 문서(D4)에는 `claude/` 접두사 브랜치로 적혀 있고, 일반 세션의 이름 규칙은 공식 문서에서 확인하지 못했다(9절).
- 프록시는 브랜치 삭제와 브랜치가 아닌 대상(태그 등)의 푸시를 거부하고, 어느 브랜치를 갱신하는지는 막지 않는다. 막으려면 GitHub의 브랜치 보호 규칙을 쓴다(D3 「Push restrictions」).
  - 정기 실행 문서(D4)에는 보호 규칙이 「연결한 GitHub 접근」(App 연결 또는 `/web-setup` 토큰)에 적용되므로 그 접근이 우회할 수 있는 규칙은 실행의 푸시를 막지 못한다고 적혀 있다. 일반 클라우드 세션도 같은 프록시를 쓰므로 같다고 보고, 저장소 소유자 계정의 접근으로 연결하면 우회할 수 없게 설정해야 한다고 본다(추론. 일반 세션 적용은 9절).
- 클라우드 세션이 만든 커밋에는 `Claude-Session: <url>` 트레일러가 붙는다. `attribution.sessionUrl: false`로 끌 수 있다(D3).
- 로컬로 가져오기: `claude --teleport [세션 ID]`, 세션 안의 `/teleport`. 텔레포트는 세션 브랜치를 받아 체크아웃하고 대화 이력을 싣는다. 조건은 작업 트리에 커밋하지 않은 변경이 없을 것, 같은 저장소일 것, 브랜치가 원격에 올라가 있을 것, 같은 claude.ai 계정일 것이다. 가져온 뒤 로컬 작업은 클라우드 세션에 반영되지 않는다(D1 「Continue a cloud session in your terminal」).

### 3.3 로컬과 클라우드 사이 이동(Q1)

- 터미널에서는 한 방향이다. 클라우드 세션을 터미널로 가져올 수 있으나, 실행 중인 터미널 세션을 클라우드로 보낼 수는 없다(D1 Note).
- 데스크톱 앱은 세션을 시작할 때 Local과 Cloud를 고르며, 로컬 세션을 「Open in」 메뉴로 클라우드에 보낼 수 있다(D1). 대화가 어떤 형태로 넘어가는지는 이 세션이 직접 확인하지 못했다(9절).
- `claude --cloud "<작업>"`은 현재 저장소로 새 클라우드 세션을 만든다(D1).
  - 저장소에 Claude GitHub App이 설치되어 있으면 원격의 현재 브랜치를 복제한다. 로컬 작업 트리가 아니므로 로컬 커밋은 먼저 푸시해야 한다.
  - 원격이 없거나 App이 설치되지 않았으면, `/web-setup`으로 연결했더라도 로컬 저장소를 묶음으로 올린다. 묶음에는 모든 브랜치의 이력과 추적 중인 파일의 커밋하지 않은 변경이 들어간다. macOS·Linux·WSL은 인증 정보 이름의 파일과 Git LFS 관리 파일의 커밋하지 않은 변경을 빼고 그 파일의 커밋된 버전으로 시작한다. 대표님 PC 같은 네이티브 Windows는 그 변경을 파일 이름과 관계없이 그대로 올린다.
  - 웹·휴대전화·데스크톱 앱에서 시작한 세션은 묶음을 쓰지 않고 GitHub에서 복제한다. `/web-setup`으로 연결했으면 App 없이도 그 토큰이 닿는 저장소를 복제한다(D2 「Connect from your terminal」).
  - 여러 번 실행하면 세션이 따로 동시에 돈다.
- `claude -p "<메시지>" --cloud <세션 ID>`로 실행 중인 클라우드 세션에 메시지를 넣을 수 있다(D1).
- 클라우드 세션은 노트북을 닫아도 계속 돌고, 휴대전화 앱에서 보고 지시할 수 있다(D1).
- 원격 조종(`--remote-control`)은 대표님 PC에서 돌리는 세션을 터미널·브라우저·휴대전화에서 함께 조종하는 기능이다. 실행 위치가 PC이므로 PC 부하를 줄이지 않는다(D5).
- 조직 장비에서 클라우드 세션을 돌리는 자체 호스팅 환경은 Team·Enterprise 공개 베타다(D6).

### 3.5 실행 환경

- Anthropic 관리 VM, Ubuntu 24.04 x86_64. 설정 스크립트는 root로 Bash에서 실행되며 약 5분 안에 끝나야 환경 캐시가 만들어진다. 캐시는 파일 시스템 스냅숏이며 약 7일 뒤 다시 만든다(D3).
- 미리 설치된 Python은 「Python 3.x」로만 적혀 있다(D3 설치 도구 표).
- 네트워크 단계는 None, Trusted(기본, 허용 목록), Full, Custom이다(D3).
- 환경 변수는 `.env` 형식으로 넣고, 그 환경을 쓰는 사람이 볼 수 있다(D3).
- 활동이 없을 때(D3 「Set environment variables」, D1 「Environment expired」):
  - 몇 분 뒤 VM이 파일을 보존한 채 일시 정지하고, 다음 메시지에 같은 VM이 복원된다.
  - 정지한 VM이 그 뒤 회수되면, 다시 열 때 새 VM을 만든다. 이때 복원되는 것은 대화 이력이고, 실행 중이던 백그라운드 작업(서브에이전트, 셸 명령)은 복원되지 않는다.
- 사용량은 요금제 사용 한도를 로컬 사용과 함께 쓴다. VM 비용은 따로 없다(D1).
- 쓸 수 있는 요금제: Pro, Max, Team, Enterprise(premium 또는 Chat + Claude Code 좌석)(D1).
- 모델·effort: 클라우드 세션 안에서는 `/model <값>`, `/effort <값>`처럼 값을 인자로 주어 바꿀 수 있다(D1 「Manage context」). 시작할 때 지정하는 방법은 확인하지 못했다(9절).

### 3.6 Antigravity의 원격 실행(Q7)

- 실행 위치: Antigravity 앱·CLI 세션의 에이전트는 사용자가 운영하는 장비에서 실행된다. CLI 문서에는 CLI가 사용자의 로컬 셸에서 실행된다고 적혀 있고, 앱은 「로컬 작업 공간 또는 원격 개발 컨테이너」로 적혀 있다(G1). 원격 조종 발표 글에는 세션이 사용자의 여러 장비(노트북, 서버, 데스크톱)에서 실행된다고 적혀 있다(G4b). FAQ에는 에이전트가 실행 중이면 PC가 절전 상태로 들어가지 않게 한다고 적혀 있다(G3). 이 저장소에서 박비서 세션이 실행되는 장비는 대표님 PC다.
- 원격 개발: CLI 문서의 플랫폼 비교표에 CLI의 원격 사용 방식이 「Native SSH, tmux, and terminal multiplexers」로 적혀 있다(G1). 이 경우에도 실행 위치는 사용자가 연결한 장비이며 Google 호스팅이 아니다.
- 원격 조종: 2026-08-20(v2.9.1)에 원격 조종(Remote Control)이 나왔다(G2). 노트북·태블릿·휴대전화의 웹 브라우저에서 호스트 장비의 에이전트를 조종하며, 작업은 호스트에서 계속 실행되고 호스트가 켜져 있고 절전 상태가 아니어야 한다(G4a, G4b). Claude Code의 원격 조종(3.3절, D5)과 같이 PC 부하를 줄이지 않는다.
- Google 호스팅 클라우드 실행은 두 가지로 나뉜다.
  - 앱·CLI 세션: 없다. 2.0 발표 글에는 「클라우드 배포 에이전트」가 앞으로 낼 기능으로만 적혀 있고(G5a), 변경 이력(2026-10-12 v2.23.0까지)에 해당 항목은 없다(G2).
  - Antigravity API: 2.0 발표 글에 2.0과 함께 CLI·SDK·API를 내놓았다고 적혀 있고(G5a), Managed Agents 발표 글에는 새 Antigravity 에이전트로 동작하며 Google이 호스팅하는 원격 Linux 환경에서 실행된다고 적혀 있다(G5b). API로 쓰는 제품이며 박비서의 앱·CLI 세션 기능이 아니다.
  - 별도 제품 Jules의 FAQ에는 작업마다 새 가상 머신에서 실행한다고 적혀 있다(G6b). Antigravity와의 관계를 적은 문서는 찾지 못했다.
- Claude 모델: Antigravity에서 Claude 모델(Opus·Sonnet 계열)을 요금제에 따라 쓸 수 있다(G6a).
- Claude Code 클라우드와의 관계는 두 가지로 나눈다.
  - (가) Antigravity 에이전트 자체를 Claude Code 클라우드 세션에서 실행하는 기능: 조사한 문서에서 찾지 못했다(확인 불가). 김비서 의견 「Antigravity는 Google 제품이라 Claude Code 클라우드 세션으로 돌릴 수 없다」를 이 뜻으로 읽으면, 조사 결과와 어긋나지 않는다.
  - (나) Antigravity 세션의 셸에서 Claude Code CLI 명령(`claude --cloud`)으로 클라우드 PM 세션을 시작하는 것: Claude Code CLI를 실행하는 일이므로 가능할 것으로 본다(추론. 실측하지 않음, 9절).
- 셸 비서실(박비서)에 주는 영향: Antigravity 세션은 대표님 PC에서 실행되므로 대표님 PC의 작업 트리에서 커밋·검사·PM 기동·PC 파일 작업을 할 수 있다. 클라우드 PM 세션의 시작은 (나)가 되면 셸 비서실이 맡을 수 있다.

## 4. 원문 M(on/off)의 가능 여부

- **실행 단위 선택은 된다**: 파이프라인 실행(REQ 작성, 원스톱)을 시작할 때 로컬 명령 대신 클라우드 세션으로 시작하면 그 실행은 클라우드에서 돈다(3.3절). 대표님이 실행마다 「로컬」·「클라우드」를 고르는 방식이다.
- **실행 중 전환은 제한된다**: 실행 중인 로컬 PM 세션을 터미널에서 클라우드로 옮길 수 없다. 데스크톱 앱의 보내기 경로는 넘어가는 형태를 확인하지 못했다(9절). 클라우드에서 로컬로는 텔레포트로 가져올 수 있으나, 그 뒤 두 쪽은 따로 진행된다.
- **PC 부하**: 클라우드 세션은 Claude Code 실행, 서브에이전트, 시험(pytest), Git 작업을 VM에서 한다. 이 세션의 추론으로는 PC에는 결과를 받는 Git 작업과 대표님의 확인 작업만 남는다(실측하지 않음).
- **스위치를 둔다면**: 실행 위치를 고르는 전역 설정은 공식 문서에서 찾지 못했다(조직 단위 허용 정책 `allow_remote_sessions`은 클라우드 세션 사용 자체를 켜고 끄는 설정이다. D1). 따라서 표준에 「실행 위치 기본값」 하나를 두고 비서실이 PM 기동 때 그 값대로 로컬 명령 또는 클라우드 시작 명령을 고르는 형태가 된다. `ORD-012_v06` 요구 항목 15(처리 순서 대장)에는 이미 「실행 위치(로컬·클라우드)」 표시가 있다. ORD-012 담당 세션은 요구 항목 9(컨트롤 화면, 「값만 바뀌고 절차는 같을 것」)의 후보로 실행 위치 전환을 두지 않았다(`ORD-012_v06` 1절 경위). 따라서 스위치는 클라우드 도입 ORDER가 절차까지 정한 뒤에 컨트롤 화면에 올릴 수 있다.

## 5. 현행 표준과의 관계

### 5.1 자동 커밋·푸시

- 클라우드 세션은 멈추는 지점마다 작업 브랜치를 자동으로 푸시하고, 그 전에 커밋도 하는 것으로 보인다(3.2절, 커밋은 추론). 아래 규칙과 부딪힌다.
  - 전역 지침 「Git 커밋 및 푸시는 명시적 요청 시에만 수행」(불변 예외), `Workflow/05` 1절 「커밋」·「푸시」 항: 명시적 요청.
  - `AGENTS.md` 「불변 원칙」 5항: 커밋은 최종 판정 `pass`와 대표님 최종 승인 뒤, 명시적 요청이 있을 때만 한다(커밋 시점).
  - `Workflow/05` 1.1절 1항: PM은 최종 승인 커밋 절차에서 커밋하지 않는다(커밋 주체).
  - 원스톱 파이프라인은 끝까지 커밋하지 않는 것을 전제로 한다(`Workflow/03` 4절 6항). 최종 판정 기준 2는 `git status --porcelain -uall`로 작업 트리의 변경을 본다. 중단 조건으로 멈추거나 대표님 답을 기다리는 지점에서 자동 커밋이 생기면 그 전의 변경이 작업 트리 조회에서 빠진다. 판정 기준의 비교 대상(작업 트리 대 기준 커밋)을 클라우드에서 어떻게 할지 정해야 한다.
- 결과를 원격 브랜치로만 돌려주는 것이 클라우드 세션의 작동 방식이므로, 푸시를 막으면 결과를 받을 수 없다.
- 전역 지침 파일은 `ORD-012_v06` 요구 항목 6과 3절 14항에 따라 바꾸지 않기로 되어 있다. 클라우드 세션은 전역 지침을 싣지도 않는다(5.2절). 따라서 개정 대상은 전역 지침이 아니라 표준(`AGENTS.md` 「불변 원칙」 5항, `Workflow/05`)이다. 다만 `AGENTS.md`는 전역 지침의 불변 예외가 자기보다 앞선다고 정하므로(머리 문단), 표준만 고쳐 불변 예외의 예외를 만들 수 있는지는 대표님이 정해야 한다.
- 선택지(대표님 결정 1(8절)을 이 자료에서는 (가)로 읽었다. (가)의 전제 ①은 결정 원문에 없어 9절에서 확인한다):
  - (가) 대표님이 클라우드 실행을 지시하는 것을 「그 세션의 작업 브랜치의 커밋·푸시 요청」으로 보고, 작업 브랜치 커밋을 최종 판정 전에도 허용하는 예외를 표준에 둔다. 기본 브랜치의 커밋·푸시는 지금처럼 최종 승인 뒤 명시적 요청으로만 하고, GitHub 브랜치 보호(우회할 수 없게 설정)로 막는다. 전제가 둘이다. ① 불변 예외의 예외를 표준만으로 둘 수 있는지(이 절 「전역 지침 파일은」 항목) ② 비공개 저장소에서 브랜치 보호를 쓸 수 있는지(9절). ②가 안 되면 기본 브랜치 보호를 규칙(클라우드 실행 세션은 기본 브랜치에 푸시하지 않음)과 사후 확인으로만 한다.
  - (나) 클라우드에서는 결과를 저장소에 남기지 않는 일(조사·검토)만 한다. 이 경우에도 푸시가 전혀 생기지 않는지는 확인하지 못했다(3.2절, 9절). PC 부하가 큰 파이프라인 실행은 줄지 않는다.
- 결정 2(5.2절)를 (다)로 읽으면 「Git 커밋 및 푸시는 명시적 요청 시에만 수행」이 든 안전장치 핵심이 클라우드 세션에 실린다. (가)의 예외가 그 핵심에도 함께 적혀 있어야 세션 안에서 규칙과 플랫폼 동작이 부딪히지 않는다. 이 문안은 클라우드 도입 ORDER의 REQ에서 정한다.
- 결정 1의 「main 브랜치는 보호」는 이 자료에서 기본 브랜치의 보호로 읽었다(대표님 확인 사항, 9절). v04는 로컬 `master`가 `origin/master`를 추적하며(`.git/config` 사본, 5.8절) 원격의 기본 브랜치는 확인하지 못했다. v05 새 원격의 기본 브랜치 이름은 아직 정해지지 않았다(9절).

### 5.2 전역 지침이 실리지 않음

- 대표님 PC에서 전역 지침은 `~/.claude/CLAUDE.md`로 실린다(`조사_20261013_ClaudeCode지침로드확인_v01.md` 3절). 클라우드 세션은 이 파일을 읽지 않는다(3.4절 표).
- 저장소 지침(`AGENTS.md`)은 실린다. 그러나 `AGENTS.md`는 전역 지침을 직접 가리킨다(머리 문단의 우선순위, 「불변 원칙」 2항 「scope는 사용자 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」의 승인 목록으로 본다」). 전역 지침이 빠지면 그 규정이 가리키는 대상이 세션 안에 없다.
- `ORD-012_v06` 요구 항목 5·6은 전역 지침을 싣지 않는 서브에이전트에 「안전장치 핵심」(전역 지침의 불변 예외 항목)을 정의 파일로 넣게 했다. 클라우드 세션의 PM 본 세션에는 아직 그런 장치가 없다.
- 선택지(대표님 결정 2(8절)를 이 자료에서는 (다)로 읽었다):
  - (가) 클라우드 환경 설정 스크립트가 전역 지침 원본의 사본을 `~/.claude/CLAUDE.md`로 써 넣는다. 사본을 어디에 둘지(환경 설정 화면 또는 저장소 밖 보관)와 원본이 바뀔 때 갱신하는 책임을 정해야 한다. 전역 지침은 다른 프로젝트에도 쓰므로 저장소에 넣지 않는다(같은 조사 1절의 대표님 원문 「현재대로 냅두고」를 이 세션이 그렇게 읽음).
  - (나) 전역 지침 없이 저장소 지침만으로 실행한다. 이 절 둘째 항목의 공백(`AGENTS.md`가 가리키는 대상이 세션 안에 없음)이 남는다.
  - (다) `ORD-012_v06` 요구 항목 5의 「안전장치 핵심」을 클라우드 PM 세션에도 싣는다. 그 요구 항목은 서브에이전트 정의 파일에 넣는 방식이므로, PM 본 세션에는 다른 방식이 필요하다. 저장소 안 파일로 두면 로컬 PM 세션에도 실려 전역 지침과 겹치므로, 클라우드에서만 싣는 방식(예: 환경 설정 스크립트가 저장소의 핵심 파일을 `~/.claude/CLAUDE.md`로 복사)을 정해야 한다. 그 요구 항목의 REQ 결과를 이어받는다.

### 5.3 계층 1(`.claude/settings.json`)

- 저장소 하나로 연 클라우드 세션은 저장소 `.claude/settings.json`의 권한 규칙을 읽는다(3.4절). 따라서 클라우드 세션에도 계층 1이 적용된다.
- `Workflow/06` 1절 계층 1 「한계」의 「저장소 밖 서비스인 비서실의 수정(핫픽스, 최종 판정서 승인 뒤 적용본 반영 포함)에는 적용되지 않는다」는 클라우드 세션을 비서실로 쓸 때 맞지 않는다. `ORD-012_v06` 요구 항목 14(저장소 루트에서 연 Claude Code 비서실 세션에 계층 1 적용)와 같은 전제를 고쳐야 한다.
- D3 설치 도구 표에 PowerShell이 없다. 설치되어 있지 않으면 `settings.json`의 `PowerShell(...)` 규칙은 쓰이지 않고, `Workflow/06` 2.1절 「명령 도구」 항의 「Bash 도구가 거부되면 PowerShell 도구로 대신」도 클라우드에서 쓸 수 없다. 설치 여부는 실측하지 않았다(9절).
- `.claude/settings.local.json`(대표님 PC의 로컬 허용 규칙)은 클라우드에 없다. 로컬에서 허용되던 명령이 클라우드에서 확인 요청이 될 수 있다.
- 권한 모드에 「Manual」이 없으므로, `ask` 규칙(`git commit`, `git push`, `rm` 등)이 클라우드 세션에서 어떻게 처리되는지(확인 요청으로 멈추는지)는 확인하지 못했다(9절).

### 5.4 계층 3(커밋 전 검사)

- 계층 3은 `setup.cmd`가 `core.hooksPath`를 `.githooks`로 설정해야 실행된다(`Workflow/06` 1절 표, 4절). `setup.cmd`는 Windows 명령 파일이라 Ubuntu VM에서 실행되지 않는다.
- 같은 상태를 만드는 후보(추론):
  - 설정 스크립트에서 `git config --global core.hooksPath .githooks`와 `git config --global core.quotepath false`를 넣는다. 설정 스크립트는 캐시가 있으면 다시 실행되지 않으나, 캐시는 설정 스크립트가 디스크에 쓴 것을 보존하는 파일 시스템 스냅숏이므로(D3) 전역 설정은 남는다고 본다(추론, 9절). 저장소는 세션마다 새로 복제하므로(D2) 저장소 설정(`--global` 없음)은 다음 세션에 남지 않을 수 있다.
  - 저장소 `.claude/settings.json`의 SessionStart 훅으로 세션마다 설정한다(D3). 이 훅은 로컬에서도 실행되므로 클라우드에서만 실행되게 조건을 둔다.
  - 어느 쪽이 되는지는 시험이 필요하다(9절).
- 훅은 `python` 명령으로 검사기를 실행한다(`.githooks/pre-commit`). VM에 「Python 3.x」가 있으나 `python` 이름의 명령이 있는지는 확인하지 못했다(9절). `settings.json`의 `Bash(python ...)` 규칙도 같은 이름을 쓴다.
- 계층 3을 켜면 클라우드 세션이 멈추는 지점마다 하는 자동 커밋에도 커밋 전 검사가 실행된다. 최종 판정 전의 작업 브랜치 커밋이 검사에 막히면 결과를 받을 수 없는데, `--no-verify`는 대표님 지시 없이 쓰지 않는다(`AGENTS.md` 「불변 원칙」 5항). 작업 브랜치에서 검사를 어떻게 할지 정해야 한다(5.1절 (가)와 함께).

### 5.5 시각 형식

- 판정서 `completed_at` 등은 `YYYY-MM-DDTHH:MM:SS+09:00` 형식이고 `date -Iseconds` 결과를 그대로 적는다(`Workflow/03` 5.2절 6항).
- VM의 시간대는 공식 문서에서 확인하지 못했다(9절). UTC이면 `date -Iseconds`가 `+00:00`을 내므로, VM에 시간대 자료(tzdata)가 있으면 환경 변수 `TZ=Asia/Seoul`을 넣고, 없으면 설정 스크립트로 설치한다(시간대 자료 유무는 9절).

### 5.6 원스톱 하나씩(REQ-029 D7)과 최종 승인 커밋

- D7 권고안의 이유는 판정 세션의 작업 트리 조회와 최종 승인 커밋의 스테이징 분류가 다른 안건의 변경과 섞이지 않게 하는 것이다(`REQ-029_v04` 3절 D7).
- 클라우드 세션은 세션마다 격리된 VM에서 돈다(D1 「Security and isolation」). 클라우드에서 도는 원스톱끼리는 작업 트리 조회가 섞이지 않는다.
- 남는 문제:
  - 결과가 원격 작업 브랜치로 오고, 최종 승인 커밋(`Workflow/05` 1.1절)은 기본 브랜치의 작업 트리를 전제로 반영·스테이징·커밋 전 검사·커밋을 한다. 클라우드 결과를 이 절차에 넣는 방식(작업 브랜치 병합, 텔레포트 뒤 로컬 비서실이 커밋, 클라우드 세션 안에서 최종 승인 커밋)을 새로 정해야 한다.
  - 로컬 원스톱과 클라우드 원스톱이 함께 있거나, 클라우드 결과를 로컬로 가져와 최종 승인 커밋을 하면 로컬 작업 트리에서 다시 섞일 수 있다.
  - 둘 이상의 안건이 기본 브랜치에 들어갈 때 같은 부분을 고치면 충돌이 나고, 충돌이 없어도 `scope:` 겹침은 확인해야 한다. D7 대안 (가)처럼 착수 때 `scope:` 겹침을 보는 규칙이 필요하다.
  - 최종 판정 `pass` 뒤 대표님 승인을 기다리는 동안 VM이 정지하면 파일이 보존된다. 회수되면 새 VM을 만들며, D1은 대화 이력이 복원되고 백그라운드 작업은 복원되지 않는다고 적었다(3.5절). 일회성 스크립트 같은 삭제 대상은 두 경우로 나뉜다. 자동 커밋에 들어갔으면 작업 브랜치에 남아 기본 브랜치로 섞여 들 수 있고, 들어가지 않았으면 회수 뒤 남지 않는 것으로 보인다(추론, 9절). 어느 쪽이든 「삭제 대상」 처리 절차를 새로 정해야 한다.
- D7 승인 문구는 「ORD-012 조사 결과로 다시 정할 때까지」다(`승인기록_20261013_REQ-029_v04.md`). `ORD-010_v08` 3절 15항은 `REQ-029` 새 버전의 D7 문구를 「클라우드 Claude Code 도입 ORDER의 조사 결과로 다시 정할 때까지」로 고치게 했고, 그 새 버전이 재승인되면 그 문구가 효력을 갖는다. 이 자료가 그 조사 결과이지만 이 자료로는 위 문제를 정할 수 없다. v01에서는 그 문구를 「클라우드 도입 ORDER의 REQ에서 정할 때까지」로 읽고 그때까지 D7을 그대로 두기를 권고했고, 대표님은 김비서가 제시한 권고안대로 「클라우드 ORDER의 REQ가 나올 때까지」로 읽기로 정하셨다(8절 결정 3). 「나올 때까지」의 시점과 클라우드 ORDER의 어느 REQ인지는 대표님 확인 사항이다(9절). 이 자료에서는 「D7을 다루는 REQ가 승인될 때까지」로 읽기를 제안한다.
- 결정 3은 D7 문구를 고치지 않고 읽기만 정했으므로, `ORD-010_v08` 3절 15항이 쓰게 한 `REQ-029` 새 버전 말고 다른 `REQ-029` 새 버전이나 ORD-010 새 버전은 이 결정 때문에 필요하지 않다(15항 원문 「12항·14항과 이 항이 정한 곳 밖의 결정과 내용은 바꾸지 않는다」). `Departments/Secretariat/docs/requests/REQ-029_v05.md`가 2026-10-14 13:16:01에 생성되었다고 연락 `20261014T133750_ORD-012_요청_김비서_셸.md`에 적혀 있으며, 그 D7 문구에 결정 3의 읽기를 적용한다. 이 자료를 쓰면서 `REQ-029_v05`의 내용은 읽지 않았다(확인 불가).

### 5.7 실행 명령과 모델 운용

- `Workflow/05` 3절의 실행 명령은 `claude --model <ID> --effort <값> --permission-mode acceptEdits "<지시문>"` 형식이며, 셸을 실행할 수 있는 비서실이 실행하거나 셸을 실행할 수 없는 비서실이 대표님께 제시해 대표님이 실행한다(`Workflow/05` 2절). 클라우드에서는 `claude --cloud "<지시문>"`으로 시작하거나 웹·휴대전화·데스크톱 앱에서 시작한다. 시작한 뒤에는 세션 안에서 `/model`·`/effort`로 바꿀 수 있다(3.5절).
- `--cloud`와 함께 `--model`·`--effort`를 줄 수 있는지는 확인하지 못했다(9절). `Workflow/04` 1.2절 「PM의 책임」 ①은 실행 명령의 `--model`로 모델을 정하는 것과 PM이 시작할 때 자기 실행 모델을 확인하는 것을 한 쌍으로 둔다. 시작한 뒤 `/model`로 바꾸는 방식이면 시작할 때의 확인은 바꾸기 전 모델을 보게 되므로, 지정과 확인의 순서를 새로 정해야 한다(7절 요구 후보 2).
- `Workflow/01` 용어 표의 PM은 「실행 명령으로 기동한 Claude Code 메인 세션」이다. 위 방법으로 시작한 클라우드 세션이 이 정의에 드는지는 실행 명령의 클라우드 형식을 표준에 넣을지에 달려 있다(7절 요구 후보 2).
- 클라우드 세션 안에서 다시 `claude` 명령으로 PM 세션을 띄우는 방식(셸 비서실의 「PM 기동」)이 되는지는 확인하지 못했다(9절).

- `ORD-012_v06` 3절 19항: v05에는 새 원격 저장소를 두고 복제 직후 연결한다. 5절 「첫 푸시」: 첫 푸시는 대표님 요청으로만 한다.

- ③은 원격 없이도 시작되나, 그 푸시가 「첫 푸시」 규칙(대표님 요청으로만)과 어떤 관계인지는 5.1절 결정 1을 따른다. 비서실 권고는 ③을 쓰지 않고 ①·② 가운데 하나만 쓰는 것이다(커밋하지 않은 변경이 그대로 올라가지 않도록).

### 6.2 클라우드 결과를 로컬 셸 비서실이 받아 커밋하는 흐름(초안)

8절 결정 1(작업 브랜치 커밋·푸시를 요청으로 봄, main 브랜치 보호. 이 자료에서는 기본 브랜치로 읽음, 9절 확인)을 전제로 한 초안이다. 구체 명령과 판정 기준은 클라우드 도입 ORDER의 REQ에서 정한다.

1. **착수**: 대표님이 그 실행의 실행 위치를 「클라우드」로 정한다. 셸 비서실은 다음을 확인한다.
   - 로컬 기본 브랜치의 최신 커밋이 원격에 올라가 있는지. 안 올라가 있으면 대표님께 푸시 요청 여부를 여쭌다.
   - 저장소에 Claude GitHub App이 설치되어 있는지. 설치되어 있으면 `claude --cloud "<지시문>"`로 시작할 수 있다(실측 전, 3.6절 (나)). 설치되어 있지 않으면 `claude --cloud`가 로컬 저장소를 묶어 올리고 네이티브 Windows에서는 커밋하지 않은 변경이 그대로 올라가므로(3.3절, 5.8절 ③) 쓰지 않는다. 이때 `/web-setup`으로 연결되어 있으면 대표님이 웹·휴대전화·데스크톱 앱에서 시작하고, App 설치와 `/web-setup` 연결이 둘 다 없으면 비공개 저장소에서는 시작할 수 없다(D2).
   - 그 원격 커밋을 기준 커밋으로 기록한다.
2. **실행**: 클라우드 PM 세션이 파이프라인을 실행하고, 멈추는 지점마다 작업 브랜치를 푸시한다(커밋은 추론, 3.2절). 판정의 비교 대상(기준 커밋 대 작업 브랜치)은 REQ에서 정한다(5.1절).
3. **최종 판정 뒤, 승인 전**:
   - ① 셸 비서실이 작업 브랜치를 받는다(`git fetch`). 로컬 작업 트리는 바꾸지 않는다.
   - ② `Workflow/05` 1절 ⑦·⑧을 따른다. 비서실이 최종 판정서 근거를 대조해 보고하고, 대표님이 최종 판정서와 변경(받은 작업 브랜치의 `git diff` 또는 웹·앱의 변경 보기)을 확인한 뒤 승인한다. 클라우드용 확인 수단은 REQ에서 정한다.
4. **승인 뒤 커밋(로컬 셸 비서실)**:
   - ① `Workflow/05` 1.1절 2번(승인 기록)과 8.3절 「최종 승인 커밋」의 시작 전 확인을 먼저 한다.
   - ② 작업 브랜치가 바꾼 경로마다, 기준 커밋 뒤 로컬 기본 브랜치에서 그 경로가 바뀌지 않았는지 `git diff --stat <기준 커밋> HEAD -- <경로>`로 확인한다(1.1절 4번과 같은 방식). 바뀌었으면 멈추고 보고한다. 그 사이 다른 경로의 요청 커밋(연락 파일 커밋 등)이 있는 것은 멈출 사유가 아니다.
   - ③ 작업 브랜치의 변경을 커밋하지 않은 상태로 로컬 작업 트리에 옮긴다. 삭제 대상(일회성 스크립트 등)은 옮기지 않는다. 옮기기는 로컬 파일을 덮어쓰며, 이 덮어쓰기는 1.1절 1번이 승인 문구로 갈음하는 범위(반영 명령 표의 덮어쓰기·삭제, 「삭제 대상」)에 들지 않는다. 옮기는 방식과 그 덮어쓰기의 승인 근거는 REQ에서 정한다(9절).
   - ④ 그 뒤는 1.1절의 반영·정리·스테이징·`check_standard.py --staged`·커밋을 그대로 따른다. 푸시는 지금처럼 대표님이 따로 요청할 때만 한다.
   - 「문체 반영」(1.1절 3번)으로 원스톱을 다시 실행할 때 로컬과 클라우드 가운데 어디서 실행하고 결과를 어떻게 가져올지는 REQ에서 정한다.
5. **작업 브랜치 정리**: 원격 작업 브랜치 삭제는 클라우드 세션의 프록시가 막으므로(3.2절) 로컬에서 해야 한다. 원격 브랜치 삭제는 푸시이고 삭제이므로 대표님의 명시적 요청과 승인이 필요하다. 지금 8.3절 「요청 푸시」 순서에는 삭제가 없으므로, 삭제 절차(명령, 승인)는 REQ에서 정한다.

- 이 흐름의 이점: 클라우드 결과를 기본 브랜치에 넣는 커밋은 로컬 셸 비서실이 1.1절로만 하므로 5.1절 (가)의 기본 브랜치 규칙과 맞고, 계층 3이 로컬 PC에서 그대로 실행된다. 클라우드 쪽 계층 3 문제(5.4절)는 작업 브랜치 커밋에만 남는다.
- 남는 문제: 4 ③에서 작업 브랜치의 커밋 이력은 기본 브랜치에 들어가지 않는다. 클라우드 세션의 커밋 트레일러(`Claude-Session`)와 이력을 남길지는 REQ에서 정한다. 셸 비서실이 `claude --cloud`를 실행할 수 있는지는 실측하지 않았다(3.6절 (나), 9절).

## 9. 확인하지 못한 항목

시험 세션으로 확인할 항목(7절 요구 후보 10):

- 일반 클라우드 세션의 작업 브랜치 이름 규칙(정기 실행 문서는 `claude/` 접두사).
- 자동 커밋의 주체·시점·범위(추적하지 않는 파일 포함 여부), 변경이 없을 때도 브랜치를 푸시하는지.
- 데스크톱 앱에서 로컬 세션을 클라우드로 보낼 때 대화가 넘어가는 형태.
- 클라우드 VM의 시간대와 시간대 자료(tzdata) 유무.
- 클라우드 VM에 PowerShell과 `python` 이름의 명령이 있는지.
- `ask` 규칙이 클라우드 세션(「Manual」 모드 없음)에서 어떻게 처리되는지.
- 설정 스크립트의 `git config --global`이 캐시 뒤 세션에 남는지, SessionStart 훅으로 설정하는 방식이 되는지.
- `claude --cloud`와 `--model`·`--effort`를 함께 쓸 수 있는지, 클라우드 세션 안에서 `claude` 명령으로 다른 세션을 띄울 수 있는지.
- VM 회수 뒤 커밋하지 않은 파일이 남지 않는지(3.5절에 따른 추론의 실측).
- 클라우드 세션 커밋의 작성자 표시와 서명 여부, `Co-Authored-By` 줄이 기본으로 붙는지.
- 셸 비서실(Antigravity)의 셸에서 `claude --cloud`로 클라우드 PM 세션을 시작할 수 있는지(3.6절, 6.2절).
- 연결한 GitHub 접근이 우회할 수 있는 보호 규칙이 일반 클라우드 세션의 푸시도 막지 못하는지(3.2절의 추론).

다른 방법으로 확인할 항목:

- 비공개 저장소에서 브랜치 보호 규칙을 쓸 수 있는 GitHub 요금제 조건(GitHub 문서).
- 대표님 계정의 요금제와 조직 설정(클라우드 세션 허용 여부)(대표님 확인).
- v04 원격의 기본 브랜치와 공개 여부(대표님 확인 또는 셸 비서실의 Git 조회).
- 김비서·이비서 말고 다른 코워크 세션의 실행 위치(그 세션이 받은 실행 환경 안내로 확인. 두 세션의 확인 결과는 6.1절).
- 코워크의 「클라우드 샌드박스」가 3.5절의 Claude Code 클라우드 세션 VM과 같은 환경인지(공식 문서로 확인. 6.1절 안의 실행 위치 구분에는 영향이 없어 클라우드 도입 ORDER를 쓰기 전까지 확인하지 않아도 된다).
