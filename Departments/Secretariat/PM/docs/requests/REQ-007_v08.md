# REQ-007: 패키지 폴더 재편(Package_sample 신설, Update_Package를 Package_update로 변경)

## 1. 요청 원문
> 출처: `Departments/Secretariat/assets/inbox/요구메모_20261006_패키지폴더_v02.md` 1절. 원문을 그대로 인용하고 항목마다 번호를 붙였다.

1. > Update package 폴더를 Package_update로 변경.
2. > Package_sample폴더 신설.
3. > Package_sample은 신규 프로젝트 때 해당폴더 복사해서 들고가는용도.
4. > Package_update는 업데이트 용.
5. > 근데 만약 업데이트가 너무 복잡한 경우는 어떻게되지? 그냥 표준업데이트파일 안만들고 그때그때 정리하는게 낫나?

참고(작업 요구가 아님): 같은 메모의 「007-2 폐기사유는 구)창구가 작성했기 때문.」은 `REQ-007_v01`~`v03`을 폐기하는 사유다. 이 REQ는 그 폐기에 따라 비서실 세션이 `REQ-007_v04`부터 새로 작성했으며, `v01`~`v03`은 근거로 쓰지 않는다(메모 2절 3항).

요청 원문 1번의 「Update package 폴더」는 저장소 루트의 `Update_Package/`를 가리킨다(저장소 루트에서 이름이 비슷한 폴더는 그 하나뿐이다. 2026-10-06 비서실 세션이 `Update_Package/**`, `Package_*/**` 경로를 조회해 `Update_Package/.gitkeep` 한 건만 확인).

## 2. 배경 및 목적
- **배경**
  - `Workflow/06_통제장치_및_배포` 「배포본과 업데이트 패키지」는 배포본(신규 프로젝트용)과 업데이트 패키지(기존 프로젝트용)를 구분하지만 두 묶음 모두 「보류」 상태다. 업데이트 패키지 빌더는 `_archive/v02/`에 보관되어 있다.
  - 배포본을 담는 폴더는 없고, 업데이트 패키지 폴더 이름(`Update_Package`)은 대표님이 정한 이름(`Package_update`)과 다르다.
  - 2026-10-06 비서실 세션이 `_archive/` 밖에서 `Update_Package`를 검색한 결과, 거버넌스 파일 가운데 참조하는 곳은 `.gitattributes` 7·8행, `Workflow/01_표준_개요` 「용어」, `Workflow/02_부서_구조_및_작업구역` 「저장소 구조」, `Workflow/06_통제장치_및_배포` 6.1절 2항이다. `check_standard.py`, `.claude/`, `setup.cmd`에는 참조가 없다.
  - `Workflow/01_표준_개요` 「용어」는 배포본을 가리킬 때 「sample」을 쓰지 않는 말로 정하고 있다(`vibe_sample.tar`만 예외). 새 폴더명 `Package_sample`과 어긋나므로 같이 고쳐야 한다.
- **목적**: 신규 프로젝트용 `Package_sample/`과 업데이트용 `Package_update/`를 두고, 두 폴더의 용도·채우는 방법과 복잡한 업데이트의 처리 방법을 매뉴얼에 정한다.

## 3. 결정 사항 및 선택지
| 번호 | 정할 일 | 권고안 | 대안 | 결정 |
| :---: | :--- | :--- | :--- | :--- |
| D1 | 복잡한 업데이트의 처리(요청 원문 5번) | 업데이트마다 `Package_update/`에 표준 구역 파일(덮어쓰기 대상)을 만든다. 덮어쓰기만으로 끝나지 않는 변경(폴더 이름·구조 변경, 기록 파일명·머리말 형식 변경, 고객 작업 구역 파일 수정)이 있을 때만 그 업데이트의 수작업 절차를 적은 이관 안내 문서 하나를 `Package_update/`에 함께 둔다. 대상 프로젝트는 그 안내를 자기 REQ로 처리한다 | 표준 업데이트 파일을 만들지 않고 업데이트마다 그때그때 정리한다(`Package_update/`에는 그때 정리한 자료만 둔다) | 대표님 직접 기재 또는 `Workflow/07_문서_서식_및_번호` 「승인 기록」 |
| D2 | 두 폴더를 채우는 방법 | 빌더 스크립트 없이 `git archive` 명령으로 만든다. `Package_sample/`은 06 6.1절의 배포본 절차를 따르되, 푸는 위치를 `Package_sample/`로 바꾸고 6.1절 3항을 다음과 같이 고친다: 풀기 전에 `Package_sample/`을 `.gitkeep`만 남기고 비운 뒤 푼다. 3항의 「새로 만든 빈 폴더에 푼다. 기존 폴더에 풀면 같은 이름의 파일을 덮어쓰므로 쓰지 않는다」 문장은 이 비우기 단계로 대체해 삭제한다(이전 배포본에만 있던 파일이 남아 신규 프로젝트로 복사되는 것을 막는다). `Package_update/`는 같은 방식으로 표준 구역 경로만 묶고, 풀기 전에 `Package_update/`를 `.gitkeep`만 남기고 비운 뒤 푼다. 06 「보류」 표기는 두 폴더 모두 해제한다 | 폴더 이름만 바꾸고 채우는 방법은 「보류」로 둔 채 별도 REQ로 정한다(이 경우 D1 권고안은 적용할 수 없다) | 대표님 직접 기재 또는 `Workflow/07_문서_서식_및_번호` 「승인 기록」 |
| D3 | 폴더 내용의 Git 추적 | 두 폴더의 내용은 커밋하지 않는다. `.gitignore` 규칙으로 두 폴더 아래 파일을 모두 무시하되, 두 폴더 바로 아래의 `.gitkeep`(`Package_update/.gitkeep`, `Package_sample/.gitkeep`) 두 파일만 무시 대상에서 뺀다. 풀어 놓은 배포본 안의 `.gitkeep`(예: `Package_sample/Audits/.gitkeep`)을 포함한 나머지 파일은 무시 대상에 남긴다. 추적하지 않는 파일은 `git archive`에 들어가지 않으므로 `.gitattributes`의 `Update_Package` 규칙(7·8행)은 지운다 | 내용을 커밋하고 `.gitattributes`에 두 폴더의 `export-ignore` 규칙을 둔다(저장소에 표준 사본이 중복 보관된다) | 대표님 직접 기재 또는 `Workflow/07_문서_서식_및_번호` 「승인 기록」 |
| D4 | `Update_Package/.gitkeep` 삭제 시점 | 삭제·이동 명령은 `ask` 대상이라 파이프라인이 멈추므로(`Workflow/03_라이프사이클` 「중단 조건」 5항), 개발은 새 `.gitkeep` 두 개만 만들고 `Update_Package/` 삭제 명령은 `DEV-007`에 적는다. 대표님이 최종 승인 때 적용본 반영과 함께 실행한다 | 구현 단계에서 개발이 삭제하고, 권한 확인 요청으로 멈추면 대표님이 그 자리에서 허용한다 | 대표님 직접 기재 또는 `Workflow/07_문서_서식_및_번호` 「승인 기록」 |
| D5 | effort | `medium` | `high` | 대표님 직접 기재 또는 `Workflow/07_문서_서식_및_번호` 「승인 기록」 |

- D2 권고안을 택하면 `Package_sample/`에는 배포본을, `Package_update/`에는 표준 구역 파일(거버넌스 파일 목록과 `Workflow/templates/`. 출처 `Workflow/06_통제장치_및_배포` 「배포본과 업데이트 패키지」)을 풀게 되므로, D3 결정과 관계없이 두 폴더 각각에 `AGENTS.md`, `CLAUDE.md`, `.claude/`, `Workflow/` 사본이 작업 트리 안에 생긴다(D3 대안이면 이 사본이 커밋까지 된다).
