# REQ-007: 패키지 폴더 재편(Package_sample·Package_update)

> v02 개정 사유: v01의 결정 D1~D3(패키지 내용물의 Git 관리, 생성 방법)은 구현 방법이다. Critical 안건에서는 EC가 구현 방법을 정하므로 이 결정들을 삭제하고 4절의 EC 위임 사항으로 옮겼다. 그에 따라 scope에서 `.gitignore`를 뺐다. 3절에는 결정 열이 비었을 때의 적용 규칙을 추가했다.

## 1. 요청 원문
> 요구 메모 `Departments/Secretariat/assets/inbox/요구메모_20261006_패키지폴더_v01.md`의 대표님 지시를 원형 그대로 인용한다.

> 요청사항1.
> Update package 폴더를 Package_update로 변경.
> Package_sample폴더 신설.
>
> Package_sample은 신규 프로젝트 때 해당폴더 복사해서 들고가는용도.
> Package_update는 업데이트 용.
>
> 근데 만약 업데이트가 너무 복잡한 경우는 어떻게되지? 그냥 표준업데이트파일 안만들고 그때그때 정리하는게 낫나?

항목 구분:
1. `Update_Package` 폴더를 `Package_update`로 변경한다.
2. `Package_sample` 폴더를 신설한다.
3. `Package_sample`의 용도는 신규 프로젝트 때 폴더째 복사해 가져가는 것이다.
4. `Package_update`의 용도는 기존 프로젝트의 업데이트다.
5. 업데이트가 복잡한 경우의 처리 방법을 정한다.

## 2. 배경 및 목적
- **배경**
  - `Workflow/06_통제장치_및_배포` 「배포본과 업데이트 패키지」는 배포본과 업데이트 패키지의 용도를 구분하지만, 두 묶음 모두 「보류」 상태다.
  - 배포본을 담을 폴더가 없다. 업데이트 패키지 폴더 이름(`Update_Package`)은 대표님이 정한 이름과 다르다.
  - `Update_Package`를 참조하는 곳은 `.gitattributes` 7·8행, `Workflow/01_표준_개요` 「용어」, `Workflow/02_부서_구조_및_작업구역` 「저장소 구조」다(2026-10-06 창구 조회).
- **목적**: 신규 프로젝트용 묶음과 업데이트용 묶음을 이름과 폴더로 구분한다. 각 묶음의 용도와 복잡한 업데이트의 처리 기준을 규정한다.

## 3. 결정 사항 및 선택지
> 「결정」 열은 대표님이 기재한다. 승인 시점에 「결정」 열이 비어 있으면 그 항목은 권고안을 결정으로 본다.

| 번호 | 정할 일 | 권고안 | 대안 | 결정 |
| :---: | :--- | :--- | :--- | :--- |
| D1 | 복잡한 업데이트의 처리 정책 | 업데이트를 두 유형으로 나눈다. 덮어쓰기형은 `Package_update`를 덮어쓰면 끝난다. 이관형은 패키지에 이관 지침을 넣고, 대상 프로젝트가 「표준 이관 REQ」(Critical)로 처리한다. 이관형 판단 기준: 폴더 구조 변경, 기록 파일명·머리말 형식 변경, 고객 작업 구역 파일 수정 필요, 대상 프로젝트의 거버넌스 파일 자체 개정 이력 가운데 하나라도 해당 | 패키지 없이 그때그때 정리 | |
| D2 | 이번 안건에서 패키지 내용물을 실제로 생성할지 | 생성하지 않는다. 폴더와 용도·절차만 정한다 | 이번에 생성 | |
| D3 | effort | `medium` | `high` | |

## 4. 실행 계획
| 단계 | 부서 | 작업 | 대상 경로 |
| :--- | :--- | :--- | :--- |
| EC 작성 | 설계 | 변경 계획 작성 | `Departments/Design/docs/tad/EC-007_v01.md` |
| EC 판정 | 품질 | EC 판정 | `Departments/Quality/results/RES-007-EC_v01.md` |
| 명세 | 설계 | `Workflow/01`·`02`·`06` 적용본 작성 | `Departments/Design/workspace/REQ-007_적용본_v01/` |
| 구현 | 개발 | 폴더 이름 변경과 신설, `.gitattributes` 적용본 작성, 규칙과 검사·설정 대조 | `Update_Package/.gitkeep` → `Package_update/.gitkeep`, `Package_sample/.gitkeep`, `Departments/Development/workspace/REQ-007_적용본_v01/` |
| 최종 판정 | 품질 | 체크리스트 번호별 근거 대조 | `Departments/Quality/results/RES-007_v01.md` |

- **EC 위임 사항**: 패키지 내용물의 Git 관리 방식과 각 패키지의 생성 방법은 설계가 EC에서 정한다. 이때 다음 두 가지를 근거로 대안을 검토한다.
  - 저장소 안에 거버넌스 파일 사본이 생기면 「불변 원칙」 9항(단일 원천)에 어긋날 수 있다.
  - 이미 있는 배포본 절차(06 6.1절)를 다시 사용할 수 있는지 확인한다.
  - 이 과정에서 scope 밖 파일(예: `.gitignore`)이 필요하면 중단하고 보고한다(`Workflow/03_라이프사이클` 「중단 조건」).
- 거버넌스 파일은 적용본으로 작성한다. 대표님이 최종 승인 때 원본에 반영한다(`Workflow/06_통제장치_및_배포` 「거버넌스 파일 개정 절차」).
- `_archive/v02/Update_Package/`는 보관 기록이므로 바꾸지 않는다.

## 5. 검증 및 완료 기준 (체크리스트)
> 작성 기준은 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」을 따른다.

| 번호 | 요청 원문 항목 | 확인 방법 |
| :---: | :--- | :--- |
| 1 | `Update_Package`를 `Package_update`로 변경 | `git status --porcelain -uall`에 `Update_Package/.gitkeep` 삭제와 `Package_update/.gitkeep` 추가가 있다. 적용본(01·02·`.gitattributes`)에서 `grep -rn "Update_Package"`의 결과가 0건이다(`_archive/` 제외) |
| 2 | `Package_sample` 신설 | `Package_sample/.gitkeep`이 있다. 02 적용본 「저장소 구조」에 `Package_sample/`이 있다 |
| 3 | `Package_sample` 용도(신규 프로젝트 복사용) | 01 적용본 「용어」와 06 적용본 「배포본과 업데이트 패키지」에 용도와 생성 절차가 있다 |
| 4 | `Package_update` 용도(업데이트용) | 01 적용본 「용어」와 06 적용본에 용도와 생성 절차가 있다 |
| 5 | 복잡한 업데이트의 처리 | 06 적용본에 3절 D1의 결정 내용이 규정되어 있다 |
