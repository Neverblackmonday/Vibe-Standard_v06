### 3.1 외부 자료 요약 — Instagram Agent Skill
- **정체**: 인스타그램 계정 운영 업무를 맡기는 Claude 스킬 13개 묶음(MIT). README에는 버전 표기가 없고, 저장소 첫 화면의 커밋 메시지에 「v1.0」이 있다. 명령은 `/ig-reel`, `/ig-viral`, `/ig-caption`, `/ig-carousel`, `/ig-story`, `/ig-profile`, `/ig-plan`, `/ig-human`, `/ig-comment`, `/ig-reply`, `/ig-dm`, `/ig-repurpose`, `/ig-audit`다. 홍익인간 가이드는 원본 저장소의 사용법을 비개발자용으로 풀어 쓴 한국어 설명서다.
- **설치**: Claude Code에 저장소 주소를 주고 설치를 요청하거나, `~/.claude/skills/`에 복사하거나, 플러그인 마켓플레이스(`/plugin install instagram-agent`)로 설치한다. 프로젝트 단위 설치(`.claude/skills/`)도 된다.
- **설치 확인**: 가이드의 설치 절은 세 단계다. ① 설치 프롬프트 입력. 이 프롬프트에 「Instagram 관련 Skill 13개가 정상적으로 설치됐는지 확인하고, ig-reel 기능도 정상적으로 사용할 수 있는지 확인해줘.」라는 요청이 들어 있다. ② 설치된 스킬 목록과 역할 질문 ③ `ig-reel`로 후킹 3개 생성. 후킹 후보가 생성되면 기본 설치가 끝난 것으로 본다. README의 설치 문구에도 `/ig-reel`이 동작하는지 확인하라는 요청이 있다.
- **개인화 파일 `voice.md`**: 모든 스킬이 읽는 말투 설명서. 가이드의 권고는 자기 대본 3~5개로 만드는 것이다. 대본 하나만 주면 그 영상에서 우연히 쓴 말투까지 고유 스타일로 판단될 수 있다는 이유다.
- **결정적 검사 도구**: README 절 제목은 "The five tools that actually run"(실행되는 도구 다섯 가지)이지만 스크립트는 여섯 개가 나온다. 모두 외부 의존성과 네트워크 없이 로컬에서 실행된다고 적혀 있다.
  1. `hookscore.py`: 후킹 후보를 다섯 가지 기준 점수 순으로 정렬하고, 가장 약한 기준과 탈락 사유(dealbreaker)를 출력한다.
  2. `beats.py`: 대본의 예상 재생 시간을 계산하고 늘어지는 구간을 표시한다.
  3. `caption.py`: 피드에 보이는 앞 125자를 상자로 출력하고 항목별 `PASS`·`WARN`을 낸다.
  4. `humanize.py`: 보이지 않는 문자, 문장 부호, 상투어 154개(`slop.json`, 사용자가 고쳐 쓰도록 둔 파일)를 자동으로 고친다. 문장 모양을 바꿔야 하는 패턴(「단지 X가 아니라 Y다」, 셋 나열 등)은 고치지 않고 표시만 한다.
  5. `detect.py`: 다섯 가지 휴리스틱 검사로 점수를 내고, 수정 전·후 파일을 함께 넣으면 차이를 출력한다.
  6. `swipe.py`: 릴스를 각 계정 중앙값 대비 배수로 정렬하고 후킹 공식을 붙인다.
- **측정 공개**: README 「What I actually measured」 절에 도구의 한계가 수치로 나와 있다. 일부러 나쁘게 쓴 후킹 10개를 가려내는 성능은 AUC 0.83이지만, 같은 제작자의 잘된 영상과 안된 영상을 구분하는 성능은 AUC 0.56(0.50이 무작위)이다. 측정 과정에서 후킹 공식 분류 정규식의 일치율이 8%에 그친 결함을 찾아 49%로 고쳤다.
- **운영 원칙**: README 「The fine print」 절에 따르면 스킬에는 게시 기능이 없다. 따라서 게시는 사용자만 할 수 있다. 결과가 나쁘면 전체 재생성 대신 범위를 좁혀 일부만 고치라는 팁(예: 본문은 유지하고 후킹만 다시 생성)이 가이드에 있다. 그 밖에 조사 → 대본 → 검사 → 말투 수정 → 캐러셀 → 캡션을 한 번에 잇는 연결 프롬프트, 할 일만 적으면 Claude가 스킬을 고르게 하는 「만능 프롬프트」, 처음에는 조사 → 대본 → 말투 수정 → 캐러셀 → 캡션 흐름만 익히면 된다는 입문 권고가 있다.

### 3.3 장단점

**Instagram Agent Skill**
- 장점
  1. 진입 장벽이 낮다. 복사·붙여넣기 프롬프트만으로 설치부터 첫 결과까지 진행된다.
  2. 기계적으로 판단할 수 있는 품질 항목을 스크립트로 분리했다. 자동 수정 대상(문자·부호·상투어)과 사람 판단 대상(문장 구조)을 나눴고, 규칙 데이터를 코드 밖 파일(`slop.json`, `hooks.json`)에 둬 사용자가 고칠 수 있다.
  3. 설치 직후 실제 기능을 한 번 실행해 확인한다.
  4. 개인화 정보를 파일 하나에 모아 모든 스킬이 읽는다. 매번 프롬프트에 반복하지 않아도 된다.
  5. 재작업 범위를 좁히는 요령(후킹만, 기준에서 벗어난 문장만)이 사용법에 들어 있다.
  6. 검사 도구의 한계를 측정해 공개했다. 명백히 나쁜 후킹은 잘 가려내지만(AUC 0.83) 잘될 영상을 예측하지는 못한다(AUC 0.56)는 결과다.
- 단점
  1. 순서와 범위를 강제하는 장치가 없다. 권한 설정이나 훅이 없다. 게시 승인만은 스킬에 게시 기능이 없어 구조적으로 보장된다.
  2. 산출물을 만든 세션이 도구 점수도 확인한다. 작성과 판정이 분리되지 않는다.
  3. 기록이 남지 않는다. 누가 무엇을 승인했는지 추적할 수 없다.
  4. 도구가 영어 기준이다(분당 165단어, 영어 상투어 목록). 한국어 대본에서의 정확도는 확인 불가다.
  5. 저장소 주소를 주고 설치를 요청하는 방식에서는 외부 코드가 검토 없이 설치·실행된다.

### 3.4 우리가 빠뜨린 것
「불변 원칙」 8항은 「새 규칙은 사고의 근본 원인이 입증되고 플랫폼 기본 기능으로 막을 수 없을 때만 더한다. 사고 이력이 없거나 기본 기능으로 대신할 수 있는 규칙은 없애거나 권고로 낮춘다」고 정한다. 그래서 지적마다 규칙 추가 여부와 근거 사고를 적는다. 근거 사고가 없거나 원인이 확인되지 않은 항목은 권고 수준으로 제안한다.

1. **설치 확인(스모크 테스트)** — 우선순위 높음
   - 현재: `setup.cmd`는 Git 초기화, `core.quotepath`·`core.hooksPath` 설정, 첫 커밋만 수행한다. `.claude/agents/`, `.claude/settings.json`, Git 훅이 실제로 적용되는지 확인하는 단계가 없다. `Workflow/06` 「알려진 과제」 2행(서브에이전트가 `AGENTS.md`를 자동으로 읽는지)과 5행(`model: inherit`가 모델을 이어받는지)은 「확인 불가」 상태다.
   - 외부 자료: 설치 → 설치 확인 요청 → 목록 질문 → 기능 1회 실행.
   - 제안: 배포본으로 새 프로젝트를 시작한 직후와 업데이트 패키지를 적용한 직후에 한 번 실행하는 「설치 확인 명령」을 `Workflow/05`에 둔다. 확인 항목은 ① 필수 파일(`AGENTS.md`, `CLAUDE.md`, `.claude/settings.json`, `.claude/agents/` 정의 파일, `.githooks/pre-commit`) 존재 ② `git config core.hooksPath` 값이 `.githooks`인지 ③ 품질 서브에이전트를 한 번 기동해 `AGENTS.md` 열람 여부와 모델을 보고하게 하는 것이다. ③은 자기 보고값이라 실측이 아니며, 한계는 「알려진 과제」 1·5행과 같다. Claude Code 기본 기능(서브에이전트 목록 조회 등)으로 ①·③을 대신할 수 있는지, 비대화 실행에서 쓸 수 있는지는 확인 불가이므로 먼저 확인한다.
   - 앞선 AUDIT 지적 5와의 관계: 대체가 아니라 병행이다. 앞선 지적 5는 판정 직전마다 확인하고, 이 지적은 설치·업데이트 직후 한 번 확인한다. 설치 시점 확인만으로는 판정 시점에 `.claude/`가 빠진 경우를 잡지 못한다.
   - 규칙 추가 여부: 추가(절차 신설). 근거 사고의 원인과 기본 기능 대체 가능성이 확인 불가이므로 설치 확인 명령은 권고 절차로 둔다. 두 가지를 확인한 뒤 의무화 여부를 정한다.
   - 근거 사고: 앞선 AUDIT 지적 5의 사고(`RES-008-REQ_v01`~`v04`가 `.claude/` 미배치 상태에서 작성됨). 이번 검토에서 `RES-008-REQ_v05`를 직접 읽지 않았고, 이 사고의 원인이 설치 단계였는지는 확인 불가다.

### 3.5 도입하지 않는 편이 나은 것
- **「만능 프롬프트」(Claude가 스킬을 골라 쓰는 방식)**: 우리 표준은 REQ `workflow:`에 기재된 단계만 기재된 순서대로 실행하고(`Workflow/03` 「원스톱 파이프라인」 2항), 요구가 여러 뜻으로 읽히면 임의로 진행하지 않는다(`AGENTS.md` 「불변 원칙」 7항). 자동 선택은 두 원칙과 맞지 않는다.
- **플러그인 마켓플레이스 배포로 전환**: 우리 배포본은 폴더 구조, Git 훅, 권한 설정까지 함께 옮겨야 한다. 플러그인으로 폴더 구조·Git 훅·권한 설정(특히 `settings.json`의 `deny`)을 모두 옮길 수 있는지는 확인 불가다. 현재의 `Package_sample/`·`Package_update/` 방식을 유지한다.
- **저장소 주소를 주고 설치를 요청하는 방식**: 검토하지 않은 외부 코드가 저장소 안에서 실행된다. 외부 스킬이 필요하면 저장소 밖에서 먼저 내용을 확인한 뒤 REQ로 들인다.
- **Instagram Agent Skill 자체**: 소프트웨어 개발 표준에 쓸 자리는 없다. 인스타그램 운영 업무에 쓸지는 이 보고서의 범위 밖이다.

## 5. 결론
Instagram Agent Skill은 산출물을 잘 만드는 도구이고 우리 표준은 함부로 고치지 못하게 하는 체계라, 기반을 바꿀 이유는 없다. 빠뜨린 것은 통제 규칙이 아니라 **확인·자동화 수단**이다. 설치 확인(지적 1, 권고 절차)은 비표준 판정 사고 기록과 연결되고 「알려진 과제」 두 건을 자기 보고 수준에서나마 확인할 수 있어 가장 먼저 권고한다. 다만 그 사고의 원인이 설치 단계였는지는 확인 불가다. 거버넌스 목록 일치 검사(지적 2)는 작고 확실한 작업이다. 표기 검사 스크립트(지적 3)는 최종 판정의 재판정 회차를 줄일 수 있으나 효과가 실측되지 않았으므로 유효한 최종 판정서의 지적 분류부터 한다. 이 스크립트는 REQ 판정 회차와는 관계가 없다. 지적 4·5는 우선순위가 낮다.
