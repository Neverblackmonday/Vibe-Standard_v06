## 3. 검토 내용

### 3.1 문제 정의

대표님이 말씀하신 증상은 두 가지다.

- **증상 A — 엉뚱한 묶음**: 기능이 의도와 다른 메뉴나 모듈 아래에 들어가 있다.
- **증상 B — 끊긴 흐름**: 기능을 구현했지만 사용자가 그 기능까지 가는 경로(앞 단계와 다음 단계)가 없다.

현재 표준에서 기능과 흐름 정보가 놓인 곳은 아래와 같다.

| 위치 | 담는 정보 | 두 증상이 드러나지 않는 이유 |
| :--- | :--- | :--- |
| `PRD_TEMPLATE.md` 3절 사용자 시나리오, 4절 기능 요구사항 | 시나리오(US)와 기능(FR) 목록 | 「이 기능 다음에 어디로 가는가」를 적는 칸이 없다 |
| `TAD_TEMPLATE.md` 1절 아키텍처 개요 | 손으로 그리는 Mermaid 흐름도 | FR 번호·코드 파일과 연결되지 않아, 기능이 늘어 그림 갱신이 빠져도 알 수 없다 |
| `TAD_TEMPLATE.md` 2절 구성 요소, 8절 요구사항 추적표 | 구성 요소별 파일 위치(2절), FR → 구성 요소 → 인터페이스 → 테스트(8절) | 사용자 흐름(다음 단계)을 적는 칸이 없다. 소스 폴더의 모든 파일이 어느 구성 요소에 속하는지 전수 대조하는 검사도 없다 |

결론적으로 두 증상의 원인은 「그림이 없어서」보다 「사용자 흐름 정보가 어디에도 없고, 기능·코드 연결을 기계로 대조하는 장치가 없어서」에 가깝다. 흐름과 연결 정보를 기계가 읽는 형식으로 한 곳에 모으면, 그림은 그 정보에서 자동으로 그릴 수 있고 누락도 스크립트로 찾을 수 있다.

### 3.2 외부 도구 조사

조사한 도구를 성격에 따라 네 가지로 구분했다. 「두 증상 기준 한계」 열은 공개 문서를 근거로 한 판단이며 실측하지 않았다.

| 구분 | 도구 | 하는 일 | 두 증상 기준 한계 |
| :--- | :--- | :--- | :--- |
| 코드에서 자동 추출 | Graphify | tree-sitter로 코드의 호출·import·상속 관계를 추출하고, Markdown 링크·PDF 등은 모델로 해석해 지식 그래프를 만든다. `graph.html`(클릭·검색 가능한 그래프), `graph.json`, Obsidian vault 내보내기를 제공한다. Claude Code 스킬·MCP 서버·Git 훅으로 연동된다 | 코드에 실제로 있는 관계만 보인다. 증상 B(있어야 하는데 없는 연결)는 코드에 흔적이 없으므로 그려지지 않는다. 묶음은 클러스터링(Leiden)으로 자동 생성되므로 대표님이 의도한 메뉴 구조와 다를 수 있다 |
| 코드에서 자동 추출 | GitDiagram | GitHub 저장소를 AI가 해석해 Mermaid 아키텍처 그림을 만들고, 각 상자를 누르면 해당 파일·폴더로 이동한다. MIT 라이선스, 비공개 저장소는 개인 토큰이 필요하다 | AI가 매번 해석하므로 그림이 실행마다 달라질 수 있다. 의도 정보가 없어 두 증상 모두 판단 근거가 없다 |
| 문서 링크 그래프 | Obsidian 그래프 보기, JSON Canvas | 문서 사이의 `[[링크]]`를 점과 선으로 보여 준다. JSON Canvas는 Obsidian이 공개한 노드·연결 JSON 형식이다 | 링크를 사람이 직접 적어야 하고, 연결의 종류(다음 단계, 소속, 구현 파일)를 구분하지 않는다. 누락 검사 기능이 없다 |
| 모델 기반 아키텍처 | LikeC4, Backstage 소프트웨어 카탈로그 | 사람이 구성 요소와 관계를 선언하면 그림을 자동 생성한다. Backstage는 서버 운영이 필요해 1인 사업 규모에서는 오버엔지니어링이다 |

- 유튜브·인스타그램에서 보신 「쭉쭉 이어지는」 화면은 노드 기반 화면(React Flow 계열)으로 추정한다. 해당 영상을 확인하지 못해 추정으로 남긴다.

### 3.3 판단

- 두 증상은 「의도(기획)와 실제(코드)의 차이」이므로, 의도를 선언하는 칸과 그 선언을 실제 소스 폴더와 대조하는 검사가 함께 있어야 드러난다.
- 조사한 도구를 이 기준으로 보면 아래와 같다.
  - Graphify, GitDiagram: 실제(코드)만 다루고 의도를 선언하는 칸이 없다.
  - Obsidian, JSON Canvas: 사람이 링크를 적을 수는 있지만 연결 종류 구분과 누락 검사가 없다.
  - LikeC4, Backstage: 의도를 선언할 수 있지만 시스템 구조 관점이고, 소스 폴더 대조 검사는 공개 문서에서 확인하지 못했다.
  - React Flow, Cytoscape.js: 그리기 기능만 있다.
- 따라서 조사한 도구 가운데 「사용자 흐름 선언 + 소스 폴더 대조」를 함께 하는 도구는 확인하지 못했다. 아래 세 가지를 직접 만들고, 그리는 부분만 필요할 때 외부 라이브러리를 쓰는 방안을 권고한다.
  1. 의도와 구현 연결을 적는 원천 파일
  2. 원천 파일과 소스 폴더를 대조하는 연결 검사
  3. 원천 파일과 검사 결과로 자동 생성하는 화면
- Graphify는 「실제」 쪽 보조 수단으로 나중에 붙일 수 있다. 코드 그래프의 군집과 기능 지도의 그룹을 비교하면 증상 A를 한 번 더 확인할 수 있다.

### 3.4 제안: 기능 지도

#### (1) 원천 파일

부서별 권한 한계(`AGENTS.md` 1절)와 작업 구역(`Workflow/02_부서_구조_및_작업구역` 4절)에 맞추어, 의도는 설계가, 구현 연결은 개발이 각자 자기 부서 파일에 적는다. 두 파일을 합친 것이 기능 지도다.

| 파일 | 작성 부서·단계 | 담는 필드 |
| :--- | :--- | :--- |
| `Departments/Design/docs/prd/feature_map.yaml`(의도 파일) | 설계 · 명세 단계 | `groups`(`id`, `name`, `dir`), `features`(`id`, `name`, `group`, `fr`, `req`, `next`, `entry`, `exit`) |
| `Departments/Development/docs/feature_files.yaml`(구현 파일) | 개발 · 구현 단계 | 기능 ID별 `status`(`built`·`tested`), `files`, `tests`. 구현 파일에 없는 기능은 `planned`(기획)로 본다 |

- **의도 파일 예시**:

```yaml
groups:
  - id: write
    name: 글 작성
    dir: Departments/Development/assets/src/editor   # 이 그룹의 코드 폴더
features:
  - id: F03
    name: 새 글 작성
    group: write
    fr: [FR-03]            # PRD 4절의 FR 번호. FR 내용은 PRD가 원천이다
    req: REQ-002           # 이 기능을 들여온 안건
    next: [F04]            # 사용자가 이 기능 다음에 갈 수 있는 기능
    entry: false           # 시작점(로그인, 첫 화면 등)이면 true
    exit: false            # 흐름의 끝이면 true
```

- **구현 파일 예시**:

```yaml
F03:
  status: tested
  files: [Departments/Development/assets/src/editor/new_post.py]
  tests: [Departments/Development/assets/tests/test_new_post.py]
```

- **기존 문서와의 관계**: FR의 내용은 PRD 4절이 원천이고 기능 지도는 FR 번호만 참조한다. TAD 2절 「파일 위치」 열과 8절 「테스트」 열은 구현 파일의 `files`·`tests`와 겹친다. `AGENTS.md` 「불변 원칙」 9항(단일 원천)을 지키려면 어느 쪽을 원천으로 할지 정해야 한다(5절 결정 사항 ②).
- **기존 규칙과 맞지 않는 점**: PRD 위치(`docs/prd/`)의 파일명은 `<번호>_<주제>.md` 형식이고, 버전 없는 문서는 하단에 개정 이력 표를 둔다(`Workflow/07_문서_서식_및_번호` 1절·2절, `PRD_TEMPLATE.md`). YAML 두 파일은 이 형식에 맞지 않으므로 표준에 넣을 때 파일명 예외와 이력 관리 방식(Git 이력으로 대신하는 안)을 함께 정해야 한다(3.5절). 개발 `docs/`도 `Workflow/02_부서_구조_및_작업구역` 2절 개발 산출물 목록에 없는 위치다.

#### (2) 연결 검사

| 번호 | 검사 | 해당 증상 | 심각도 | 판정 방법 |
| :---: | :--- | :---: | :---: | :--- |

| C7 | 근거 안건 없음 | 기록 누락 | 경고 | `req`가 비었다. 기획 단계면 정상일 수 있다 |
| C8 | 없는 기능 참조 | 기록 누락 | 오류 | `next`나 구현 파일에 의도 파일에 없는 ID가 있다 |
| C9 | 테스트 없음 | 기록 누락 | 경고 | `status: tested`인데 `tests`가 비었다 |

- **실행 방식**: 검사 스크립트(가칭 `check_feature_map.py`)가 두 파일을 합쳐 검사하고, 처음에는 커밋을 막지 않고 결과만 출력하는 방식을 권고한다. 개발 단계 결과서(`DEV-xxx`)에 실행 결과를 붙이고, 품질 서브에이전트가 최종 판정 기준 3항(명세 정합성, 양방향 추적성)의 근거로 쓴다. 커밋 차단(`check_standard.py` 편입)은 시범 운영에서 오탐이 적다는 것을 확인한 뒤 정한다.
- **스크립트 위치**: 시범 단계에서는 해당 제품 저장소의 개발 `workspace/`(예: `Departments/Development/workspace/feature_map/`)에 두고 실행한다. `Departments/Development/assets/scripts/`는 거버넌스 파일(`AGENTS.md` 「불변 원칙」 3항)이므로, 그 위치로 옮기는 일은 표준 개정 REQ(Critical)에서만 한다.

#### (3) 화면

- **생성 방식**: 화면 생성 스크립트가 원천 두 파일과 (2)의 검사 결과를 읽어 단일 HTML 하나에 데이터로 넣는다. 화면은 검사를 다시 계산하지 않고 받은 결과만 표시한다. 검사 규칙의 원천은 검사 스크립트 하나다.
- **1단계(권고)**: 외부 라이브러리 없이 동작하는 단일 HTML. 화면은 아래 세 가지다.
  - **파이프라인 탐색**: 처음에는 시작점과 그다음 열이 펼쳐져 있고, 열의 기능을 누르면 그 기능의 다음 기능이 오른쪽 열에 펼쳐진다(지시 원문의 「대시보드에서 이걸 클릭하면, 그 다음 갈 수 있는 항목」). 시작점에서 도달할 수 없는 기능은 이 화면에 나오지 않는다.
  - **전체 지도**: 모든 기능을 단계별 열로 배치하고, 시작점에서 도달할 수 없는 기능을 아래 줄에 따로 모아 보여 준다.
  - **연결 검사**: (2)의 검사 결과를 오류·경고로 나누어 목록으로 보여 준다. 항목을 누르면 전체 지도에서 해당 기능이 선택되어 표시된다.
- **2단계(필요할 때)**: 기능 수가 늘어 배치가 복잡해지면 그리기 부분만 Cytoscape.js(보기 위주) 또는 React Flow(화면에서 직접 편집까지)로 바꾼다. 원천 파일과 검사는 그대로 쓴다.
- **프로토타입**: 1단계 화면을 예시 데이터로 만든 `feature_map_prototype_v02.html`을 이 보고서와 함께 대화창에 첨부했다. 프로토타입은 아래 점에서 이 제안을 단순화했다.
  - 가상의 블로그 발행 SaaS를 가정한 데이터(기능 13개)이며, 검사 결과를 보여 주려고 연결 누락·그룹 불일치 사례를 일부러 넣었다.
  - 의도 파일과 구현 파일을 한 데이터로 합쳐 두었다. 상세 패널의 「원천 파일의 해당 항목」도 합친 형태로 보여 준다.
  - 검사를 스크립트 대신 브라우저에서 직접 계산한다. C6(소스 폴더를 훑는 검사)은 넣지 않았다.
  - `Audits/`에는 검토 보고서만 두므로 프로토타입은 저장소에 넣지 않았다.

#### (4) 운영 흐름(표준에 넣을 경우)

1. 새 기능 REQ의 `scope:`에 의도 파일과 구현 파일을 넣는다.
2. 설계가 명세 단계에서 의도 파일에 기능 항목과 `next`를 추가한다.
3. 개발이 구현 단계에서 구현 파일에 `status`·`files`·`tests`를 적고, 연결 검사와 화면 생성을 실행해 결과를 `DEV-xxx`에 붙인다.
4. 품질이 최종 판정에서 검사 결과를 최종 판정 기준 3항(명세 정합성)의 근거로 쓴다.
5. 창구가 대표님께 보고할 때 화면 파일을 함께 드린다.

#### (5) 선택: Graphify 교차 대조

- Graphify의 `graph.json`에서 코드 군집을 읽어 기능 지도의 그룹과 비교하면, 지도에는 같은 그룹인데 코드는 서로 다른 군집에 있는 기능을 찾을 수 있다.
- 기능 지도가 자리 잡은 뒤에 검토할 일이며, 1단계에는 넣지 않는다.

### 3.5 표준 반영 시 영향

- **시범 적용**: 시범도 해당 제품 저장소의 정규 REQ로 진행한다. 설계 문서와 개발 쪽 파일을 함께 고치므로 `Workflow/03_라이프사이클` 2절의 「여러 모듈 수정」에 해당해 Major로 본다. `workflow:`는 Major 단계(EC 작성 → EC 판정 → 명세 → 구현 → 최종 판정)를 그대로 따른다. 명세 단계에서 설계가 의도 파일을, 구현 단계에서 개발이 구현 파일과 검사·화면 스크립트(개발 `workspace/`)를 작성한다. REQ `scope:`에는 EC 경로, 의도 파일, 구현 파일을 넣는다. 설계는 코드를 작성하지 않으므로 스크립트는 개발이 맡는다(`AGENTS.md` 1절).
- **표준 개정**: 새 서식(`Workflow/templates/`), 문서 체계 표와 파일명·이력 관리 예외(`Workflow/07_문서_서식_및_번호` 1절·2절), 개발 산출물 목록(`Workflow/02_부서_구조_및_작업구역` 2절), 통과 조건(`Workflow/03_라이프사이클` 5절), 검사 스크립트(`Departments/Development/assets/scripts/`)가 모두 `AGENTS.md` 「불변 원칙」 3항의 거버넌스 파일이다. 따라서 Critical REQ로 진행해야 한다.
- **규칙 비대화 방지**: `AGENTS.md` 「불변 원칙」 8항은 새 규칙을 「사고의 근본 원인이 입증되고 플랫폼 기본 기능으로 막을 수 없을 때만」 더하고, 그렇지 않으면 없애거나 권고로 낮추도록 정한다.
  - 근본 원인 입증: 대표님이 말씀하신 두 증상을 근거로 적을 수 있으나, 실제 사례(제품명과 기능명)는 이번 검토에서 확인하지 못했다. 시범 적용에서 사례를 기록해 입증한다.
  - 기본 기능으로 막을 수 없음: Claude Code 권한 설정과 Git 훅은 흐름 누락을 판단하는 기능이 아니고, 3.3절대로 조사한 외부 도구에서도 같은 기능을 확인하지 못했다. 이 조건은 충족하는 것으로 본다.
  - 근본 원인 입증(첫째 조건)이 시범 적용으로 확인되기 전까지는 검사를 「결과 출력만」(권고 수준)으로 두는 것이 8항과 맞다(5절 결정 사항 ③).
- **적용 대상**: 표준 저장소 자체는 PRD·TAD를 쓰지 않는다(`Workflow/01_표준_개요` 3절). 기능 지도는 배포본으로 시작한 제품 저장소에서만 쓴다.

## 5. 결론

- **권고안**: 기능 지도(의도 파일·구현 파일, 연결 검사, 자동 생성 화면)를 직접 만든다. 외부 도구는 화면이 커졌을 때 그리기 라이브러리만 쓰고, Graphify는 나중에 보조 대조 수단으로 검토한다.
- **진행 순서**: 실제 제품 하나에서 정규 REQ(Major)로 시범 적용 → 두 증상이 실제로 드러나는지 확인하고 사례 기록 → 표준 개정 REQ(Critical).
- **대표님 결정 사항**:

| 번호 | 정할 일 | 권고안 | 대안 | 근거 |
| :---: | :--- | :--- | :--- | :--- |
| ① | 시범 적용할 제품 | 기능 수가 가장 많은 진행 중 제품 하나 | 표준 개정부터 진행 | `AGENTS.md` 「불변 원칙」 8항: 사고 사례가 있어야 규칙을 더한다 |
| ② | TAD 2절 「파일 위치」·8절 「테스트」와의 관계 | 구현 파일을 원천으로 삼고 TAD 2절·8절은 구현 파일을 참조 | TAD를 원천으로 두고 기능 지도는 흐름(`next`)만 담음 | `AGENTS.md` 「불변 원칙」 9항(단일 원천) |
