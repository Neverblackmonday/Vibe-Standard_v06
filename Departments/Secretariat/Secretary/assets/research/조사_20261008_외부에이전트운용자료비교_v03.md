## 3. 검토 내용

### 3.1 외부 자료별 요약

**① OpenRig — 여러 에이전트 세션을 한 팀으로 묶는 런타임**
- 정체: 로컬 데몬 + CLI(`rig`) + 터미널 UI + MCP 서버. 각 에이전트는 tmux 세션에서 돌고, 좌석(seat)은 그 위의 고정 역할·주소다(좌석 안의 대화는 바뀔 수 있다). Claude Code·Codex·Pi를 섞어 쓸 수 있다. Apache 2.0. README 기준 v0.6.6, 별 5.9k(2026-10-08 조회). 해설 글은 v0.5.17 기준이라 내용이 일부 다르다.
- 핵심 장치: 팀 구성을 YAML(RigSpec)로 선언하고 `rig up` 한 번으로 띄운다. 좌석 간 메시지는 `rig send`·`rig broadcast`로 보내고, 작업은 별도의 큐(`rig queue`)에 기록한다. README는 「메시지를 보낸다고 큐 항목이 생기지는 않는다」고 밝힌다. `rig down --snapshot` → `rig up`으로 재부팅 뒤에도 팀을 복원한다. 기본 팀 `starter`는 Claude Code 작성자 + Codex 검토자 구성이다.
- 장점: 세션 지속성, 작업 큐 기록, 진행 상황 가시성(TUI 그래프), 이종 모델 조합을 설정으로 바꿀 수 있음.
- 한계: Windows는 WSL2로만 지원하며 WSL2에서는 자동 시험을 돌리지 않는다. 설치·기동 때 공급자 설정·훅·신뢰 설정 파일을 쓰며 README가 「완전한 보존·롤백을 보장하지 않는다」고 밝힌다. 승인 게이트, 수정 범위 통제 같은 거버넌스 장치는 원문에 없다. 검증은 작성자·검토자 짝 구조에 의존한다.

**② Jev — 판단 전용 소형 모델 스킬**
- 정체: 글을 생성하지 않고 예/아니오(`noul`), 선택(`choice`), 점수(`score`)를 확률과 함께 돌려주는 모델(`typesafe/jev-1.13`, OpenRouter)을 Claude Code·Codex 스킬로 감싼 것. 메일·댓글 분류, 문의 긴급도 정렬 같은 짧은 판단을 0.3~0.6초에 처리한다고 주장한다.
- 장점: 생성형 모델로 하던 단순 분류의 속도·비용 절감, 확률 임계값으로 사람 검토 대상을 고를 수 있음.
- 한계: 글쓰기·계산·날짜 비교에 약하다고 원문이 밝힌다. 확률이 높다고 맞는 것은 아니라는 실측도 원문에 있다(196건 중 자동 알림을 0.6~0.9로 광고 제안으로 분류). OpenRouter API 키가 필요하다.
- 우리 표준과의 관계: 비교 대상이 아니다. 소프트웨어 개발 거버넌스에 쓸 자리가 없다. 다른 사업(댓글·문의 분류 등)의 도구로나 검토할 만하다.

**③ 클로덱스 루프 — 계획 검수를 다른 회사 모델에 맡기는 스킬**
- 정체: 정찰 → 요구사항 → 계획 검수 → 빌드·점검의 네 단계. Claude Code에서 시작하면 검수와 최종 점검을 Codex가, Codex에서 시작하면 Claude가 맡는다. MIT, v2.1.0.
- 핵심 장치
  1. 계획 승인을 계획 파일의 SHA256에 묶는다. 한 줄만 고쳐도 승인이 무효다.
  2. 점검 기록에 빌드 전 커밋과 변경분 지문(스테이징·미추적 파일 포함)을 남긴다. 이후 코드가 바뀌면 재점검이 필요하다.
  3. 라운드 상한(계획 검수 5회, 빌드 수정 2회, 점검 2회)을 다 써도 승인으로 바꾸지 않는다.
  4. 빈 출력·세션 시작 이벤트는 승인으로 치지 않는다.
  5. 요청한 모델과 실제로 관찰된 모델을 따로 기록하고, 조용한 대체(폴백)를 허용하지 않는다.
  6. 최종 점검은 빌드 맥락이 없는 새 세션에서 한다. 조율자가 직접 고친 코드는 재점검 대상이다.
  7. 검수자는 읽기 전용 샌드박스에서 돈다.
- 한계: 원문 스스로 「두 모델이 같은 맹점을 공유할 수 있다. 보장하는 것은 만든 쪽이 자기 것을 채점하지 않는다는 점뿐」이라고 밝힌다. 승인 주체가 사람이 아니라 검수 모델이다. 작업 범위 통제 장치는 원문에 없다.

**④ AI 위임 루프 플레이북 — 일 하나를 폴더 하나(매뉴얼)로 넘기는 방법론**
- 정체: 일마다 `SKILL.md`(절차·결정 규칙·완료 정의), `files/`(도구·서식, `INDEX.md`), `examples/`(승인된 완성본), `notes.md`(수정 기록)를 두는 폴더 구조와, 이를 세우는 붙여넣기 프롬프트 네 가지.
- 핵심 장치: 「괜찮아 보인다」는 증거가 아니며 완료 정의는 원자료·개수·인용 등 외부 증거로 확인한다. 첫 검증에서 두 개보다 많이 실패하면 땜질하지 말고 원인 단계를 보고한다. 같은 실수가 두 번 나오면 명시 규칙을 추가한다. 승인된 좋은 결과물을 `examples/`에 쌓는다.
- 한계: 1인·반복 업무 위임용이다. 사람이 초안을 승인하는 단계는 있으나 승인 기록·범위 통제·독립 판정은 없다. `files/` 안의 도구 파일 이름에 날짜·버전을 넣지 말라고 권하지만 `examples/`는 날짜가 든 파일명을 쓴다.

### 3.4 어느 쪽이 우위인가
네 자료는 우리 표준과 같은 층의 물건이 아니므로 한 줄 서열은 의미가 없다. Jev는 판단 모델이라 이 비교에서 뺀다. 나머지를 층별로 보면 아래와 같다.

- **통제·감사 추적(누가 승인했고, 무엇을 고쳐도 되는가)**: 우리 표준이 우위다. 승인 문구 원문 기록, scope 기계 대조, 거버넌스 파일 쓰기 차단은 다른 자료 어디에도 없다.
- **판정의 무결성(판정이 실제로 그 내용·그 모델에 대한 것인가)**: 클로덱스 루프가 우위다. 해시 결속, 변경분 지문, 관찰 모델 기록은 우리 표준의 빈틈을 일부 메운다. 우리 표준이 「알려진 과제」 1·5로 적어 둔 모델 확인 문제, 「통제 계층」 3행 한계(종결된 안건의 승인으로 같은 경로를 다시 커밋하는 것)가 여기에 해당한다.
- **런타임 지속성·가시성**: OpenRig가 우위다. 다만 우리 표준은 파일 기반 재개로 필요한 만큼은 이미 해결했고, 1인 운영에 데몬·큐까지는 오버엔지니어링이다.
- **업무 지식 축적(좋은 결과물이 다음 작업의 기준이 되는가)**: 위임 루프가 우위다.
- **종합**: 기반은 우리 표준을 유지하고, 클로덱스 루프의 장치 두세 가지를 흡수하는 것이 가장 이득이다. OpenRig 도입은 권하지 않는다(3.6절).

우리 표준의 약점도 분명하다.
- **무겁다**: 안건 다섯 건(REQ-007~011)에 REQ 파일 24개, REQ·EC 판정서 32개가 쌓였다(2026-10-08 폴더 조회). REQ-007은 9번째 버전에서 승인되었다. 다만 판정서 일부는 비표준 판정이어서 정상 운영의 반복 횟수와 같지 않다.
- **같은 모델끼리 판정한다**: 작성·판정이 모두 Opus 5.5라서 같은 맹점을 공유할 수 있다. 참고로 핫픽스 scope로 거버넌스 검사를 우회하는 결함(R5)은 이전 세션에서 이관된 지적이고, Gemini 3.8 Flash의 외부 검토(`AUDIT_20261006`)가 이를 결함으로 확인했다. 최초 발견 모델은 확인 불가이므로 이종 모델 효과의 근거로 쓰지 않는다.
- **판정 모델이 자기 보고값이다**(`Workflow/06` 「알려진 과제」 1·5).

### 3.5 우리가 빠뜨린 것
순서는 권고 우선순위다. 1~5번은 `AGENTS.md` 「불변 원칙」 8항(「새 규칙은 사고의 근본 원인이 입증되고 플랫폼 기본 기능으로 막을 수 없을 때만 더한다」)에 비춘 근거 사고 유무를 함께 적는다.

1. **승인과 내용의 해시 결속 (클로덱스 루프)**
   - 현재: `approved:`는 버전 파일 단위다. `Workflow/06` 「통제 계층」 3행은 REQ·HOTFIX 기록이 대조에서 빠진다고 밝히므로, 같은 버전 파일의 본문을 승인 뒤에 고쳐도 검사가 잡지 못한다. 이 한계는 표준에 명시되어 있지 않고 위 사실에서 따라 나온다. 2절 REQ-007_v09의 수정 시각은 절차상 예상되는 순서이지만, 승인 필드만 바뀌었는지 본문도 바뀌었는지를 지금은 판별할 수단이 없다는 예시가 된다.
   - 제안: 승인 기록(`승인기록_*.md`)에 승인 대상 파일의 해시를 적고, 커밋 전 검사가 현재 파일 해시와 대조한다. 승인 필드·「결정」 열 줄은 해시 계산에서 뺀다.
   - 근거 사고: 없음. 8항에 따르면 권고 대상이다. 커밋 전 검사로 강제할지(8항의 예외)는 대표님이 정한다.
2. **판정 후 변경 감지 (클로덱스 루프)**
   - 현재: 최종 판정 `pass` 뒤에 오케스트레이터나 사람이 코드를 고쳤을 때의 재판정 규칙과 검사 수단이 표준에 없다.
   - 제안: 최종 판정서 머리말에 판정 시점의 변경분 지문(변경 파일 목록과 각 파일 해시)을 적고, 커밋 전 검사가 커밋 대상과 대조한다. 어긋나면 커밋을 막고 재판정을 요구한다. 1번과 함께 쓰면 `Workflow/06` 「통제 계층」 3행 한계(「종결된 안건의 승인으로 같은 경로를 다시 커밋하는 것을 막지 못한다」) 가운데, 같은 경로를 다른 내용으로 다시 커밋하는 경우를 막을 수 있다.
   - 근거 사고: 없음. 1번과 같다.
3. **판정 결과가 비어 있을 때의 처리 (클로덱스 루프)**
   - 현재: `Workflow/03` 「원스톱 파이프라인」 4항은 판정 결과를 `result:`로만 판단하고 각 단계 산출물을 확인한 뒤 넘긴다고 정하지만, 판정서가 없거나 `result:`가 빈 값일 때 재판정할지 멈출지는 정해지지 않았다.
   - 제안: 「`result:`가 `pass`·`fail`·`rejected`가 아니면 판정이 없는 것으로 보고 다시 판정한다」 한 줄.
   - 근거 사고: 없음.
   - 1~3번은 「승인·판정이 지금의 내용에 대한 것임을 보장한다」는 목적 하나로 묶을 수 있으므로, 도입한다면 REQ 하나로 진행할 수 있다(「불변 원칙」 8항의 「REQ 하나에는 목적 하나」).
4. **이종 모델 2차 검토 (클로덱스 루프, OpenRig)**
   - 현재: `AGENTS.md` 「불변 원칙」 4항과 `Workflow/04`가 판정 모델을 Opus 5.5로 고정한다.
   - 제안: 구속력 있는 판정은 그대로 두고, Critical 안건에 한해 다른 회사 모델(이미 창구로 쓰는 Antigravity 등)의 외부 검토(AUDIT)를 권고 단계로 넣는다. 비용과 시간이 늘므로 대표님 결정 사항이다. Codex 사용 가능 여부는 확인 불가.
   - 근거 사고: 없음(3.4절의 R5는 근거로 쓰지 않는다).
5. **판정 실행 환경 확인 기록 (클로덱스 루프)**
   - 현재: RES-008-REQ_v01~v04는 `.claude/` 미배치 상태에서 작성되었다(RES-008-REQ_v05 「판정 차수」). 판정서 머리말의 모델 값은 자기 보고값이므로 이런 환경 차이를 판정서만 보고는 알 수 없다. RES-007·RES-010의 무효 사유는 적혀 있지 않아 확인 불가다.
   - 제안: 오케스트레이터가 판정 서브에이전트를 기동하기 전에 `.claude/agents/quality.md`가 있는지 확인하고 그 결과를 판정서에 적는다. 관찰 모델(`observed_model`) 기록은 대화 기록 파일에 모델 값이 남는지 실측한 뒤 정한다(확인 불가).
   - 근거 사고: 있음(RES-008-REQ_v01~v04). 1~5번 가운데 8항의 요건에 가장 가깝다.
   - 6~8번은 규칙이 아니라 운영 보조 장치이므로 근거 사고 유무를 따지지 않는다.
6. **승인된 모범 예시 (위임 루프)**
   - 현재: `Workflow/templates/`에는 빈 서식만 있다.
   - 제안: 판정을 적게 받고 통과한 REQ·판정서를 예시로 지정한다. 재작업 횟수를 줄인다는 효과는 가설이며, 도입 뒤 REQ 버전 수로 효과를 측정해야 한다.
7. **사고 기록부 (위임 루프)**
   - 현재: 「불변 원칙」 8항은 새 규칙을 사고의 근본 원인이 입증될 때만 더하라고 하지만, 사고를 모아 두는 곳이 없어 판정서·감사 보고서에서 다시 찾아야 한다.
   - 제안: 사고 한 건당 한 줄(일자, 현상, 근본 원인, 조치한 규칙)을 남기는 파일 하나를 둔다. 8항의 입증 근거를 한곳에 모으는 용도다.
8. **판정자 수정 도구 제한 (클로덱스 루프)**
   - 현재: `.claude/agents/quality.md` 머리말은 `disallowedTools: Agent`만 지정한다. 판정 대상을 고치지 말라는 규정은 모델이 따르는 지시일 뿐이다.
   - 제안: `disallowedTools`에 `Edit`를 추가한다. `Write`로 기존 파일을 덮어쓰는 것과 Bash로 쓰는 것은 막지 못하므로 부분적 효과다.

### 3.6 도입하지 않는 편이 나은 것
- **OpenRig 전체 도입**: Windows는 WSL2로만 지원하고 그 환경의 자동 시험이 없다. 기동 때 `.claude/settings.local.json`, `.mcp.json` 같은 공급자 설정과 훅을 쓰는데, 이 쓰기가 우리 `deny`·`ask` 권한 통제를 느슨하게 만드는지는 확인 불가다. 상태가 Git 밖에 생겨 우리 감사 추적과 따로 논다.
- **Jev**: 이 표준에 쓸 자리가 없다.
- **위임 루프의 「도구 파일 이름에 버전 넣지 않기」**: `files/`의 도구 파일에만 적용되는 권고라 우리 표준과 직접 충돌하는 부분은 작다. 다만 공식 기록은 버전 파일로 승인 효력을 구분하는 우리 방식(`Workflow/07` 「번호와 버전」)을 유지하는 편이 감사 추적에 유리하다.

## 5. 결론
우리 표준은 승인·범위 통제와 감사 추적에서 네 자료보다 앞서 있으므로 기반을 바꿀 이유는 없다. 다만 「이 승인과 판정이 지금 이 내용에 대한 것인가」를 기계로 확인하는 장치가 빠져 있다. 클로덱스 루프의 해시 결속·변경분 지문·빈 판정 처리(지적 1·2·3)를 하나의 Critical REQ로 반영하는 것을 먼저 권고하되, 근거 사고가 없어 「불변 원칙」 8항에 따르면 권고 대상이므로, 커밋 전 검사로 강제할지(8항의 예외)는 대표님이 정한다. 판정 실행 환경 기록(지적 5)은 근거 사고가 있어 8항 요건에 가장 가깝다. 이종 모델 검토(지적 4)는 비용이 드는 결정이다. 지적 6·7·8은 우선순위가 낮다. OpenRig와 Jev는 도입하지 않는 편이 낫다.
