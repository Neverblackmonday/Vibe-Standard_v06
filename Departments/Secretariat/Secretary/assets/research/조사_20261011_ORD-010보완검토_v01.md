## 3. 겹치는 발견과 서로 빠진 것

### 3.1 커밋 통제의 두 공백

- 계층 1의 공백(AI 비서 비교 8.1절 「차용 1 후속」, 이번에 `settings.json` 대조로 다시 확인): 커밋·푸시에 대한 `ask` 규칙은 `Bash(git commit*)`, `Bash(git push*)` 형태뿐이고 `PowerShell(...)` 짝이 없습니다. PowerShell 도구로 내리는 커밋은 지금은 `allow`에도 없어 기본 확인을 받습니다. 하지만 나중에 더해지는 `allow` 규칙이나 「다시 묻지 않기」로 저장된 규칙에 맞으면 확인 없이 실행될 수 있습니다.
- 계층 1을 지금도 거치지 않는 경로: `allow`의 `Bash(python Departments/*/workspace/*)`로 실행한 스크립트가 안에서 `git commit`을 부르면 확인을 받지 않습니다. AI 비서 비교에서는 이 경로를 대표님이 승인한 완화로 보고 보완 범위 밖에 두었습니다. `Workflow/06_통제장치_및_배포.md` 2.1절에는 이 완화의 근거로 「`deny`·`ask`와 커밋 전 검사가 위험을 줄인다」가 적혀 있습니다.
- 계층 1의 적용 범위: 계층 1은 Claude Code에만 적용됩니다(`Workflow/06_통제장치_및_배포.md` 1절 계층 1 「한계」). 비서실의 요청 커밋·핫픽스 커밋, 대표님의 직접 커밋에는 처음부터 이 확인이 없습니다. 따라서 위 공백이 문제가 되는 것은 Claude Code 세션(PM·서브에이전트)이 내리는 커밋입니다. PM은 대표님이 명시적으로 요청할 때 커밋합니다(`Workflow/05_인수인계_및_실행명령.md` 1절 「커밋」 항, `AGENTS.md` 2절 5항). 요청 없이 커밋하면 이 규정 위반입니다.
- 계층 3: `.githooks/pre-commit`은 어느 셸에서 커밋하든 `check_standard.py --staged`를 실행합니다(`--no-verify`를 쓰지 않고 `core.hooksPath`가 설정된 PC이면). 그런데 이 검사는 끝난 REQ를 통과 근거로 씁니다(Orca 비교 O11, ORD-010 1절 「문제의 사실」의 REQ-901 재현).
- 계층 1의 커밋 실행 확인은 명령을 실행할지 묻는 장치이고 scope를 대조하지 않습니다. 그래서 확인이 있든 없든, 판정을 거치지 않는 커밋에서 승인 범위를 기계로 확인하는 장치는 커밋 전 검사 하나입니다. 계층 4(최종 판정 범위 대조)는 원스톱 파이프라인 커밋에만 있습니다.
- ORD-010 5절의 임시 조치(커밋 전에 `git diff --cached --name-only`의 파일이 이번 안건 REQ의 `scope:` 안인지 확인)는 커밋하는 대표님·비서실을 대상으로 합니다. PM이 내리는 커밋은 이 확인에서 빠집니다.

### 3.2 진행 상태의 판단

- ORD-010 요구 항목 1~3에서는 REQ·HOTFIX가 끝났는지를 판단하고 기록해야 하고, 요구 항목 5에서는 원스톱 안건이 진행 중인지를 판단해야 합니다.
- AI 비서 비교 차용 2(작업 현황 표)에서도 안건마다 현재·대기·완료를 판단해야 합니다. 그런데 지금 단계 산출물에는 완료를 나타내는 필드가 없습니다. REQ `approved:`, HOTFIX `confirmed:`, 판정서 `result:`만으로는 최종 승인 커밋이 끝났는지 알 수 없습니다. 차용 2에서 완료를 정확히 표시하려면 ORD-010 요구 항목 2의 종결 기록이 먼저 있어야 합니다.
- 두 일은 같은 판단 기준을 써야 합니다. `Workflow/05_인수인계_및_실행명령.md` 1절 끝 항목은 「공식 진행 상태는 각 단계 산출물로만 판단한다」고 정합니다. 종결 기록을 단계 산출물로 두면 커밋 전 검사와 현황 표가 같은 근거를 읽습니다. 같은 값을 여러 곳에 두지 않는다는 대표님 전역 지침 1부 3절 「단일 원천」과도 맞습니다.
- 순서: 차용 2를 `check_standard.py`의 옵션으로 만들면 ORD-010과 같은 파일을 고칩니다. 반영 예정인 ORD-010 요구 항목 5의 기준으로 보아도 바꾸는 문서가 겹치므로, 이 경우 차용 2는 ORD-010 뒤에 해야 다시 쓰지 않습니다. 별도 스크립트로 만들면 파일은 겹치지 않습니다. 실행 주체와 위치는 AI 비서 비교 8.1절대로 REQ 설계에서 정할 사항입니다.

### 3.3 표준에 이미 적힌 한계

- `Workflow/06_통제장치_및_배포.md` 1절 통제 계층 표의 계층 3 「한계」에는 다음 내용이 있습니다. REQ·HOTFIX 기록은 대조에서 빠지므로 ① 승인 기록 없이 승인 필드를 기재하는 것과 ② 종결된 안건의 승인으로 같은 경로를 다시 커밋하는 것을 막지 못한다.
- 개정 이력에서 계층 3 「한계」를 다룬 행은 「v04 하드포크」 행(「1절 통제 계층 3의 한계와 본문의 승인 필드 확인 방법을 … 맞춰 변경」)뿐이고, ②를 더한 REQ 행은 없습니다. 그래서 ②는 하드포크 때 또는 그 전부터 있던 문장으로 보입니다(정확한 시점은 Git 이력을 조회하지 않아 확인 불가).

### 4.2 대표님 결정이 필요한 것

- **D-A. PowerShell `ask` 공백 보완을 ORD-010에 넣을지**
