## 3. 중복·충돌 점검 결과

1. **같은 규정을 코드와 절차가 다르게 구현함**: P1(3.1절)은 승인된 버전이 하나라도 있으면 진행 중으로 보고, 최신 버전과 승인된 모든 버전의 `scope:`를 합치며, 포함을 양방향으로 보고, `Workflow/03`·`REQ_TEMPLATE` 특례를 두고, 스테이징만 한 종결 기록을 뺀다. M3의 코드는 번호별 최신 버전만, 한 방향 포함, HEAD의 종결 기록으로 판단한다. 두 판단은 목적이 달라 그대로 합칠 수 없다. 다만 기록을 읽고 `scope:`를 대조하는 부분 동작이 따로 구현되어 있어, 규정이 바뀔 때 한쪽만 고쳐질 위험이 있다.
2. **같은 검사를 두 번 실행**: M3b는 훅(M3)이 커밋 때 다시 하는 검사를 세션이 커밋 직전에 한 번 더 실행한다. 결과는 같고 실패를 일찍 보는 효과만 있다.
3. **메시지 검사 없음**: 커밋을 막는 검사는 파일만 본다(P4).
4. **설정 문구와 실측의 어긋남**: Claude Code는 `deny`의 `Write(...)` 11개가 「파일 권한 검사에 쓰이지 않는다」고 경고했다(`셸작업/20261015T192218_REQ-031_결과-직접.md`). 그런데 `Workflow/06` 2절은 `deny`를 `Edit`·`Write` 짝으로 등록하게 하고, `Write`의 하위 폴더 적용은 실측됨, `Edit`은 실측하지 않음으로 적고 있다(7절 4행). 어느 규칙이 실제로 막는지는 다시 실측해야 한다.
5. **「v04」 표기**: `check_standard.py`의 첫 설명 줄과 성공 문구, `.githooks/pre-commit` 주석, `setup.cmd`의 안내와 첫 커밋 메시지. 첫 커밋 메시지 `chore: 바이브 코딩 표준 v04 초기화`는 `Workflow/07` 2절의 예외로 적혀 있어 함께 고쳐야 한다.
6. **줄바꿈**: `.gitattributes`에 전체 기본 규칙이 없고, 줄바꿈 규칙의 서술도 Workflow에 없다. 인수 시험 해시 대조 때 「in the working copy … LF will be replaced by CRLF」 경고가 났다(`RES-031_v01` 4절). 작업 트리의 그 파일은 LF이고, Git이 다음에 다룰 때 CRLF로 바꾼다는 뜻이다. 지금까지 실패는 없었다.
7. **사고가 난 단계**: P3은 반영 26건, 삭제 12건, 11종 분류, 메시지 작성을 셸 실행 비서실이 규정대로 따라 한다. 필요한 정보(반영 명령 표, 삭제 대상, 승인 기록 경로)는 결과서·판정서·승인 기록에 이미 있다.
8. **예정된 검사와의 관계**: 승인된 REQ들이 같은 스크립트·훅에 검사를 더할 예정이다. `REQ-032`(작업 구역 대조, 옛 경로 차단. ORDER 요구 항목 18), `REQ-033`(공정 지도 연결 검사. 요구 항목 4), `REQ-034`(형상통제 대조와 커밋 차단, 대응표 검사. 요구 항목 7·16), 판정 전 점검 스크립트(요구 항목 11). 이번 구성안이 이들과 따로 놀면 새 중복이 생긴다.
9. **겹치지 않는 것**: M3의 `CEO/`·`Lab/` 처리, 비밀정보 검출, 종결 기록의 이름·위치 검사는 다른 장치와 하는 일이 겹치지 않는다. 인수 시험(M5)은 커밋 전 검사의 대조 제외 구역이라 커밋 때 다시 돌지 않는다(`Workflow/06` 4절).

## 4. 구성안(요구 수준)

1. **규정 원천은 지금처럼 Workflow 한 곳**: 검사 규칙의 원천은 `Workflow/06` 등의 절이고, 코드는 구현이다(ORDER 요구 항목 5·16, `Workflow/06` 5절 3항). 바꾸는 것은 세션이 규정을 읽고 직접 판단하던 단계를, 그 절의 규칙을 구현한 명령의 실행과 결과 확인으로 바꾸는 것이다.
2. **검사 장치 대장 하나**: 지금 장치(1절)와 예정 장치(3절 8번)를 한 표에서 관리해, 새 검사를 넣을 때 기존 장치와의 중복을 그 표로 확인한다. 위치와 형식은 EC에서 정한다.
3. **확인 화면은 그대로**: 커밋·삭제·덮어쓰기는 지금처럼 `ask`를 거쳐 대표님이 확인 화면에서 승인한다(`Workflow/06` 2.2절 2항). 자동화는 준비(반영 목록, 삭제 목록, 스테이징 목록, 메시지 초안)와 검사만 맡고, 커밋 명령 자체는 확인 화면을 거친다. 확인 없이 실행되는 `allow` 명령 안에서 커밋·삭제를 하지 않는다.
4. **요구 항목(안)**
   - ① 커밋 메시지 검사: 제목 줄의 기록 이름과 근거 줄의 키·경로를 커밋 때 기계로 확인한다. 예외: `setup.cmd`의 첫 커밋, 대표님이 직접 하는 `[CEO]` 커밋(근거 줄 불요), 같은 안건 둘째 커밋의 `Follows` 줄(`Workflow/07` 2절).
   - ② 설치·착수 전 점검: 설치할 때와 PM 기동 전에 훅 경로, Claude Code 폴더 신뢰 상태(읽기만), `allow` 적용 여부를 점검하고, 신뢰 처리 방법을 안내한다. PM 기동 전 점검은 PM 세션 밖에서 한다(신뢰 처리 전에는 PM 세션 안에서 실행해도 권한 거부로 끝나기 때문). 점검을 부르는 곳과 방식은 EC에서 정한다.
   - ③ 최종 승인 커밋 준비 자동화: 결과서·판정서·승인 기록에서 반영 목록, 삭제 목록, 스테이징 목록, 커밋 메시지를 만들어 보인다. 실제 반영·삭제·커밋은 3번대로 확인 화면을 거친다. 세션이 규정을 읽고 직접 하던 분류와 메시지 작성을 없애는 것이 목적이다.
   - ④ 겹침·착수 판단의 기계화: P1·P2의 판단 가운데 기계로 할 수 있는 부분을 명령으로 바꾼다. 규칙은 `Workflow/03` 3.1·4.1절 그대로다.
   - ⑤ 정리: 효력 없는 설정 규칙(실측 뒤), 「v04」 표기, 줄바꿈 기본 규칙(인수 시험 해시 대조 영향 시험 뒤), M3b의 중복 실행 처리.
   - ⑥ 대장: 2번의 검사 장치 대장.
5. **따로 정할 것**: `allow`의 `Bash(python Departments/*/workspace/*)` 완화를 유지할지. 막으면 임시 Git 저장소가 필요한 인수 시험의 실행 방법을 다시 정해야 한다(`Workflow/06` 2.1절).
6. **기계로 바꾸지 않는 것**: P5(셸 작업 조건)는 셸 전달 구조 자체를 줄이는 별도 검토 대상이다. 대표님이 고르신 결정 ①의 「셸 전달 단순화」는 이 조사의 검사 장치 범위 밖이어서 6절의 어느 방법에도 들어 있지 않다(6절 아래 「남은 정할 일」). P6~P9는 판단이 필요한 일이다.

## 5. ORD-012와의 관계

- 4절의 변경 대상(`check_standard.py`, `.githooks/`, `setup.cmd`, `.claude/settings.json`, `.gitattributes`, `Workflow/03·05·06·07`)은 승인된 `REQ-032_v02`·`REQ-033_v02`의 `scope:`(둘 다 `Workflow` 포함)와 겹친다. 그래서 이 일을 새 REQ로 쓰면 두 REQ가 끝나기 전에는 저장되지 않는다(`Workflow/03` 3.1절 2·3·5항. REQ-035 때와 같은 막힘).
- 진행 중인 안건 자신의 새 버전은 이 막힘에서 빠진다(3.1절 1항). `REQ-032`는 메시지 정정과 REQ-031 종결 기록이 커밋된 상태라면 착수 때 REQ-031 커밋과 겹쳐 멈추고, `ORD-012_v09` 3절 38항으로 새 버전을 쓰게 된다.
- 다만 `Workflow/03` 6절의 「요구가 바뀜」은 그 REQ의 요구가 바뀐 경우를 말한다. ORDER에 요구 항목을 더해 REQ-032에 맡기는 것은 REQ-032의 요구가 바뀐 것인지, 「새로 생긴 작업」(파생 안건)인지 분명하지 않다. 파생 안건으로 보면 3.1절 1항의 예외를 받지 못해 같은 막힘이 생긴다. 이 점은 확인 불가이며, REQ 판정이 결정한다.
- `REQ-032_v02` `scope:`에는 `setup.cmd`가 없어, 새 버전에서 scope를 넓혀야 한다.
- `setup.cmd`의 신뢰 처리 안내와 `NCR-031_03`의 제안(복제 뒤 권한 적용 확인)은 대표님이 「오케이 다음 오더에 넣자.」(2026-10-16)로 다음 ORDER에 넣기로 하신 항목이며, 4절 4번 ②와 같은 일이다.
