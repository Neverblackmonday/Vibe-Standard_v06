## 1. 결론

1. **대표님 기준(`assets/`는 프로그램에 남아 있어야 하는 자료)이 맞고, 지금 규정의 정의가 틀렸습니다.** 지금 정의는 `assets/`에 조사 자료까지 넣습니다. 그래서 비서팀 `assets/`에는 ORDER, 작업 큐, 승인 기록, 조사 자료처럼 프로그램과 관계없는 파일이 모여 있습니다. 대표님 기준으로 보면 비서팀 `assets/`의 파일은 모두 다른 폴더로 가야 하고, 시험팀 `assets/acceptance/`의 인수 시험 파일도 마찬가지입니다.
2. **배치가 용도가 아니라 커밋 통제를 따라 정해졌습니다.** 작업 큐를 비서팀 `assets/`에 둔 이유는 그 폴더가 「대표님 직접 지시로 형상통제팀 C02가 판정 전제 없이 커밋할 수 있는 구역」(판정 전제 제외 커밋)이기 때문이었습니다(`REQ-033_v04` D7). 폴더 이름 하나에 용도, 배포본 포함 여부, 커밋 검사 예외, 판정 전제 제외가 함께 묶여 있습니다.
3. **개선안은 용도를 다섯 가지로 정의하고, 파일 종류마다 위치를 표 하나로 정하는 것입니다.** `assets/`(제품 자산), `docs/`(정식 문서), `results/`(결과서·판정서), `records/`(기록, 신설), `workspace/`(작업 자료)입니다. 이렇게 하면 배포본 규칙은 「`Departments/` 아래는 `assets/`만 넣는다」 한 줄이 됩니다. 커밋 검사의 scope 대조 제외는 폴더 종류(`results/`·`records/`·`workspace/`)에 비서팀 `docs/`, PM `docs/requests/`, `Audits/`를 더해 적고, 판정 전제 제외 커밋은 지금처럼 팀 경로를 하나씩 적습니다. 커밋 경로가 문서마다 달라서(ORDER는 요청 커밋, EC는 최종 승인 커밋), 용도만으로 모든 통제가 정해지지는 않습니다.

## 2. 지금 배치의 문제

### 2.1 정의와 실제

지금 정의(`Workflow/02` 3절)는 다음과 같습니다.

- `docs/`: 정제된 문서(기획서, 명세, 안건)
- `assets/`: 실제 자산(코드, 테스트, 스크립트, 파라미터, 조사 자료)
- `results/`: 공식 결과서와 판정서
- `workspace/`: 중간 산출물, 메모, 거버넌스 적용본

실제 배치와 대조한 결과입니다. 형상통제 기록 행만 규정상 위치이며, 그 폴더에는 아직 파일이 없습니다.

| 파일 | 지금 위치 | 어긋나는 점 |
| :--- | :--- | :--- |
| ORDER | 비서팀 `assets/inbox/` | 안건이므로 정의로는 `docs/`. v04의 `Departments/Secretariat/assets/` 구성을 REQ-032가 그대로 옮김 |
| 작업 큐 | 비서팀 `assets/queue/` | 정식 문서인데 판정 전제 제외 구역이라는 이유로 `assets/`에 둠(`REQ-033_v04` D7) |
| 승인·요청·종결 기록 | 비서팀 `assets/inbox/` | 「작성 뒤 고치지 않는 기록」이라는 종류가 정의에 없음 |
| 부적합 기록(NCR) | 부적합관리팀 `docs/` | 같은 이유 |
| 셸 작업 지시·결과, 연락 기록 | 비서팀 `workspace/셸작업/`·`workspace/연락/` | 고치지 않는 기록인데 중간 산출물 폴더에 있음 |
| PM 실행 기록 | PM팀 `workspace/` | 행을 더하기만 하고 고치지 않는 기록인데 중간 산출물 폴더에 있음(`Workflow/05` 7절 3항) |
| 기준선·형상통제 기록(규정상 위치. 아직 파일 없음) | 형상통제팀 `results/` | 결과서가 아니라 기록 |
| 인수 시험 파일 | 시험팀 `assets/acceptance/` | 안건마다 만드는 검증 파일이라 프로그램에 남는 자료가 아님. 그래서 배포본 규칙에 별도 제외 항목이 있음 |
| 조사 자료·브리핑 | 비서팀 `assets/research/`·`assets/briefings/` | 정의 자체가 조사 자료를 `assets/`에 넣음(대표님 지적) |

### 2.2 폴더 이름에 묶인 통제 네 가지

| 통제 | 지금 규칙 | 폴더 종류 규칙 밖에 따로 적은 항목 |
| :--- | :--- | :--- |
| 배포본(신규 프로젝트에 넣는 것) | 팀 `results/`·`workspace/` 제외(`.gitattributes`) | 비서팀 `assets/` 하위 폴더, 시험팀 `assets/acceptance/`, 부적합관리팀 `docs/`, REQ·EC 파일 |
| 커밋 검사의 scope 대조 제외 | 팀 `results/`·`workspace/` 제외(`check_standard.py`) | 비서팀 `assets/`, PM `docs/requests/REQ-`, 시험팀 `assets/acceptance/`, 부적합관리팀 `docs/`, `Audits/` |
| 판정 전제 제외 커밋(REQ 없이 커밋) | 경로를 하나씩 나열(`Workflow/05` 1절 「커밋」 항 ①~⑤) | ② 비서팀 `assets/`·`workspace/연락/`·`workspace/셸작업/`과 `Audits/`, ⑤ 형상통제팀 `results/` |
| 권한(쓰기 금지) | 거버넌스 파일과 검사 스크립트 폴더(`assets/scripts/`) | 옮길 경로가 들어간 규칙 없음(`.claude/settings.json` 확인) |

따로 적은 항목 가운데 비서팀 `assets/`, 인수 시험, 부적합 기록은 2.1절의 어긋난 곳과 겹칩니다. 지금 구조에서는 파일을 용도대로 두면 통제가 달라지기 때문에 예외 목록이 늘었습니다.

### 2.3 부 바로 아래에 남은 폴더

`Departments/Design/workspace/`·`Departments/Secretariat/workspace/`(둘 다 비어 있음), `Departments/Development/workspace/`(`.pyc` 6개), `Departments/Quality/assets/`(`.pyc` 11개)는 저장소 인덱스에 추적 파일이 없습니다. Git은 빈 폴더와 무시 대상(`__pycache__/`)을 추적하지 않으므로, REQ-032 이동 뒤에도 PC에 남았습니다. 규정은 「부 → 팀 → 하위 폴더」이며, 부 바로 아래 `workspace/`·`assets/`는 규정에 없습니다. 팀 폴더 안인 `Departments/Design/Spec/workspace/__pycache__/`에도 `.pyc` 4개가 있습니다.

## 3. 새 용도 정의

### 3.1 다섯 가지 용도

이 정의는 `Departments/`의 팀 폴더에만 적용합니다. `Audits/`, `Lab/`, `CEO/`, `Storage/` 같은 루트 구역은 지금처럼 `Workflow/02` 1.1절을 따릅니다.

| 폴더 | 정의 | 예 |
| :--- | :--- | :--- |
| `assets/` | 제품 자산. 그 저장소가 만드는 제품(이 저장소에서는 표준의 검사·준비 장치, 신규 프로젝트에서는 그 프로젝트의 제품)이 안건이 끝나도 계속 실행·검증에 쓰는 자료 | 코드, 검사·준비 스크립트, 단위 테스트, 설계·런타임 파라미터, 제품 화면용 아이콘·폰트·이미지 |
| `docs/` | 정식 문서. 승인·판정을 받거나 정해진 절차가 현행본을 따르는 문서(버전 파일이나 개정 이력으로 관리) | ORDER, 작업 큐, 아이디어 백로그, 기획안, REQ, EC, PRD, TAD, 시각 디자인 문서 |
| `results/` | 결과서·판정서. 서식·번호·버전이 있는 단계 결과물과 그 증빙 | RPT, DEV, RES, ACC, HOTFIX, 인수 시험 파일 |
| `records/` | 기록. 일어난 일을 남기며 작성 뒤 고치지 않음(새 파일로만 남기고, PM 실행 기록은 행 추가만) | 승인·요청·종결 기록, 부적합 기록, 셸 작업 지시·결과, 연락 기록, PM 실행 기록, 기준선·형상통제 기록, 운영 기록 |
| `workspace/` | 작업 자료. 일을 하며 만드는 참고·중간 자료. 거버넌스 적용본은 판정을 받아도 여기에 둠(반영 뒤 원천은 거버넌스 파일) | 조사 자료, 브리핑, 거버넌스 적용본, 일회성 스크립트, 메모 |

- 파일 종류마다의 위치는 지금처럼 `Workflow/07` 1절 「문서 체계」 표 한 곳이 원천입니다. 4.2절 표는 그 표를 고칠 내용입니다. 정의는 새 파일 종류가 생길 때 위치를 정하는 기준이며, 새 종류는 REQ로 「문서 체계」 표에 더합니다.
- 조사 자료와 브리핑은 대표님 기준대로 `workspace/`입니다. ORDER가 근거 자료로 가리키므로 지우지 않습니다. 파일 삭제는 어느 폴더든 대표님 승인을 받으므로(전역 지침), `workspace/`에 있다는 이유로 정리 대상이 되지는 않습니다.
- 인수 시험 파일은 한 안건의 판정 증빙이며 안건이 끝나면 다시 쓰지 않으므로, `assets/`가 아니라 ACC와 같은 `results/`에 둡니다. 신규 프로젝트에 남는 단위 테스트는 구현팀 `assets/tests/`입니다.
- 이 표준은 배포본에 실려 신규 프로젝트에서도 쓰이므로, 정의는 배포 여부가 아니라 쓰임으로 적었습니다. 배포본 포함은 5절의 별도 규칙입니다.

### 3.2 `records/`를 새로 두는 이유

- 기록은 표준에서 이미 「작성 뒤 고치지 않는다」는 같은 규칙을 받습니다(셸 작업 지시·결과 `Workflow/05` 8.6절 8항, 형상통제 기록 8.8절 5항, 종결 기록 `Workflow/07` 1.1절 4항, 부적합 기록 `Workflow/07` 2절).
- 지금은 이 종류의 폴더가 없어 `assets/inbox/`, `docs/`, `workspace/`, `results/`에 흩어져 있습니다. 그래서 「이 파일을 고쳐도 되는가」를 파일 종류마다 규정에서 찾아야 합니다.
- 기록 수정을 막는 새 검사는 이 개편에 넣지 않습니다. 새 규칙·장치는 근본 원인이 입증되었을 때만 더하기 때문입니다(`AGENTS.md` 「불변 원칙」 8항). 폴더로 나누는 효과는 위치만 보고 성격을 알 수 있게 되는 것입니다.

## 7. 위험

- **이동 범위:** 저장소 인덱스 기준으로 옮길 추적 파일은 471개입니다. 그 밖에 아직 커밋하지 않은 비서실 파일(ORD-012 v13, 작업 큐 v01·v02, 조직 진단 v02 등)도 함께 옮겨집니다. 검사 장치와 판정 전제 제외가 경로에 묶여 있어, 옮기는 동안 보호가 끊기지 않게 해야 합니다(REQ-032 때와 같은 조건).
- **장치가 옛 경로를 읽는 문제:** `prepare_final_commit.py`는 ORDER 「근거 자료」 줄의 경로를 글자 그대로 비교합니다. ORD-012의 근거 자료는 이미 REQ-032 전 경로(`Departments/Secretariat/assets/research/…`)로 적혀 있어, 지금도 분류가 맞지 않을 수 있습니다. 다시 옮기면 ORD-012의 남은 REQ와 ORD-006·007·008에서 같은 문제가 생깁니다. 장치가 대응 표로 읽게 할지는 이동 REQ에서 정해야 합니다.
- **처리 전 셸 작업 지시 파일:** 지시 파일의 「실행할 문구」는 고치지 않고 글자 그대로 실행하며(`Workflow/05` 8.6절 4항), 지시 파일 자체도 고치지 않습니다(같은 절 8항). 이동 전에 써 둔 지시 파일은 옮긴 ORDER를 찾지 못하므로, 이동 REQ를 커밋하기 전에 처리 전 지시 파일이 없는지 확인하거나 남은 지시 파일을 「실행하지 않음」으로 닫고 새로 씁니다.
- **기록의 이동:** 기록은 「고치거나 지우지 않는다」는 규정이 있습니다. REQ-032 때처럼 내용은 바꾸지 않고 위치만 옮기며 대응 표로 읽는다는 해석을 이동 REQ에 적어야 합니다.
- **요구 항목 21과의 순서:** 21도 같은 매뉴얼과 생성 지침을 고칩니다. 폴더 정리를 뒤로 미루면 매뉴얼의 경로 표기와 생성 지침을 두 번 고칩니다.
- **작업 큐와의 겹침(`Workflow/05` 8.7절 4항):** 이 정리를 요구 항목 21 앞에 두면, 작업 큐 순서 8(요구 항목 9·10. 대시보드가 작업 큐 위치를 읽음)과 순서 9~11(ORD-006 ⑨, ORD-007, ORD-008. `Workflow/` 전체 개정)이 바뀐 경로를 기준으로 진행하게 됩니다. 같은 파일(`Workflow/` 매뉴얼, 생성 지침)을 바꾸므로 겹침이 있습니다. 작업 큐 순서 6의 착수 조건(「이 작업 큐(v01·v02)의 대표님 확인」)도 바뀝니다. 그래서 작업 큐 새 버전의 겹침 확인 표에 적고 순서 변경에 대한 대표님 결정을 받아야 합니다.
