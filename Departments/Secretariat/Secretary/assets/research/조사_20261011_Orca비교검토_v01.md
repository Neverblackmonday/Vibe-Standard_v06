## 1. 결론

1. **Orca는 표준과 층위가 다르다.** Orca는 여러 코딩 에이전트를 나란히 띄우는 데스크톱 작업 환경(실행 도구)이다. 표준은 일을 어떤 순서로, 누구 승인으로, 어떻게 판정하고 기록할지를 정한 절차다. 그래서 둘은 맞바꿀 대상이 아니다. Orca에는 필수 승인 절차·독립 판정·범위 통제가 없고(사람 결정을 기다리는 게이트는 선택 기능으로 있다), 표준에는 병렬 실행·완료 알림·실행 중 사용량 표시가 없다.
2. **Orca를 표준의 필수 도구로 넣지 않기를 권고한다.** 표준은 Claude Code·Git·Python만으로 도는데 Orca를 넣으면 빠르게 바뀌는 외부 앱 하나에 기대게 된다(릴리스가 거의 매일 나오고 Windows 권한 오류가 남아 있다는 평가가 있다). 또 Orca는 작업마다 worktree를 만들어 에이전트를 돌리는데, 표준은 저장소 루트에서 PM을 실행하고 커밋 안 된 ORDER·승인 기록을 같은 작업 트리에서 읽는 구조라 그대로는 맞지 않는다(7절).
3. **비교하다 표준의 구멍 하나를 찾았다(O11).** 커밋 전 검사는 승인된 REQ라면 이미 커밋이 끝난 것도 통과 근거로 쓴다. 지금 `REQ-021_v02`·`REQ-022_v02`의 `scope:`가 `Workflow/01`~`07`과 `.claude/agents/` 여러 파일을 덮고 있어, 새 승인 없이 이 파일들을 고쳐도 커밋 전 검사를 통과한다. Orca와는 별개로 가장 먼저 고칠 일이다.
4. **빠뜨린 것 가운데 가져올 만한 것은 둘이다.**
   - ① PM 원스톱 파이프라인 시작 전 점검(Orca 자동 실행의 `--precheck`와 같은 방식): 시작할 때 `git status`로 바뀐 파일을 보고, 자기 REQ `scope:`와 대조 제외 구역 밖의 변경이 있으면 시작하지 않는다. 명령 한 번이라 비용이 작다. ORD-008 I1의 「정할 것」 ④·⑤와 겹치므로 I1 REQ에서 다루기를 권고한다.
   - ② 작업 완료·멈춤 알림: 대표님이 휴대폰으로도 진행을 알 수 있게 한다. 구현 방법과 비용은 확인하지 않았으므로, 먼저 대표님 개인 설정이나 개인 도구로 시험해 보기를 권고한다(표준 개정 아님).
   - 병렬 실행용 worktree 분리는 ORD-008 I1의 선택지로 이미 올라가 있어 거기서 다룬다.

## 5. 장단점

### 5.1 Orca

- 장점
  - 병렬로 여러 과제를 돌려도 worktree가 달라 작업 파일이 섞이지 않는다.
  - 완료 알림과 모바일 앱이 있어 PC 앞에 없어도 진행을 알고 짧은 답을 보낼 수 있다.
  - 사용량·한도·추정 비용을 실행 중에 본다.
  - Claude Code·Codex를 함께 다루고 Antigravity 쿼터도 읽는다.
  - 결정 게이트, 메시지 ID로 지난 재시도를 막는 설계 등 오케스트레이션의 기본 장치를 갖췄다.
- 단점
  - 필수 승인·판정·범위 통제가 없다. 결과를 고르고 합치는 일은 사람 몫이고, 병렬 수만큼 리뷰가 늘어난다.
  - 병합·충돌 처리 문서가 없다.
  - 병렬 수만큼 토큰이 는다.
  - 릴리스가 잦아 동작이 자주 바뀐다. Windows 버그 언급이 있다.
  - 진행 기록이 앱 안에 남고, 커밋 외에는 Git에 남지 않는다.

### 5.2 표준

- 장점
  - 승인·독립 판정·범위 통제·부적합 기록이 절차에 들어 있어 품질과 추적성이 강하다.
  - 외부 앱 없이 Claude Code·Git·Python만으로 돈다.
  - 분류로 모델 등급을 정해 비용을 통제한다.
- 단점(이번 비교로 드러난 것)
  - REQ 파이프라인을 동시에 돌릴 수 없다. 같은 작업 트리에서 둘을 함께 돌리면, 두 변경 전체를 덮는 승인 REQ가 없을 때 작업 트리 검사가 실패한다(재현 시험, `조사_20261011_비서실세션연락검토_v03.md` 3절 8행과 3.1절 C6. 재현 저장소에는 REQ가 둘뿐이었다). 거꾸로 덮는 REQ가 있으면 통과하는데, 그 이유는 아래 O11의 구멍이다.
  - PM이 파이프라인을 시작할 때 다른 안건의 커밋 안 된 변경을 확인하는 단계가 없다(`Workflow/03` 4절). 구현 단계의 통과 조건(`check_standard.py` 종료 코드 0, `Workflow/03` 5절 「구현」 행)에서야 걸린다. 그 앞 단계(EC, 명세, 인수 시험)의 산출물은 남아 같은 명령으로 이어서 진행할 수 있지만, 다른 안건이 커밋될 때까지 그 안건은 멈춰 기다려야 한다.
  - 커밋이 끝난 REQ도 계속 통과 근거로 쓰인다(O11).
  - 작업이 끝나거나 멈춰도 대표님께 알림이 가지 않는다.
  - 사용량·비용을 실행 중에 볼 수 없다.

| O1 | PM 원스톱 파이프라인 시작 전 점검 | 자동 실행의 `--precheck`(실패하면 그 회차 건너뜀) | 가져오기(ORD-008 I1 REQ에서) | 원스톱 파이프라인을 시작할 때 PM이 `git status --porcelain -uall`로 바뀐 파일을 본다. `CEO/`, `Lab/`, 대조 제외 구역(`check_standard.py` `WHITELIST_PREFIXES`와 부서 직속 `results/`·`workspace/`)을 뺀 나머지가 모두 자기 REQ `scope:` 안이면 진행하고, 밖의 파일이 있으면 시작하지 않고 그 파일 목록을 보고한다. 중단 뒤 다시 시작한 경우 자기 안건의 변경은 자기 scope 안이라 막히지 않는다. `check_standard.py`의 통과 문구로 판단하지 않는 이유는, 그 검사가 커밋이 끝난 REQ까지 통과 근거로 쓰고(O11) 테스트도 함께 돌리기 때문이다. REQ 작성 파이프라인은 REQ 파일이 대조 제외 구역에 있어 충돌하지 않으므로 대상에서 뺀다. 명령 한 번이다. 한계: 다른 안건의 변경이 자기 scope 안의 같은 파일에 있으면 누가 고쳤는지 git으로 가릴 수 없어 잡지 못한다. 다른 안건이 대조 제외 구역에만 파일을 만든 단계여도 잡지 못한다. ORD-008 I1 「정할 것」 ④(잠금을 거는 때)·⑤(scope가 겹칠 때 착수를 막을지)와 같은 문제라 따로 ORDER 후보를 만들지 않고 I1에서 다룬다. 같은 파일 동시 수정 사고 기록은 확인하지 못했으므로(9절) `AGENTS.md` 「불변 원칙」 8항에 비추어 대표님 결정으로 넣는 예방 규칙이 된다(비밀정보 검출과 같은 방식. `check_standard.py` 81~82행 주석) |
| O2 | 작업 완료·멈춤 알림 | 완료 알림, 모바일 앱 | 가져오기 검토(표준 밖에서 먼저) | 대표님이 휴대폰 앱으로 지시하는 경우가 있다(이 대화). 후보는 ① Claude Code 사용자 수준 설정(`~/.claude/settings.json`)의 알림 훅 ② Orca 같은 개인 도구의 모바일 알림이다. 둘 다 대표님 개인 설정이라 표준을 고치지 않는다(`AGENTS.md` 「불변 원칙」 8항의 「플랫폼 기본 기능」 우선과 같은 방향). 저장소의 `.claude/settings.json`에 넣으면 거버넌스 개정이 필요하고, 알림 서비스의 토큰·주소가 커밋되면 비밀정보 검출에 걸리며 구매자에게도 배포된다. 구체적인 방법과 비용은 확인하지 않았다. PM 실행 기록을 훅으로 자동 작성하는 안의 기각(ORD-008_v02 3절 4항)과는 목적이 다르다(기록을 대신 쓰지 않고 알리기만 함) |
| O3 | 병렬 실행용 worktree 분리 | 작업마다 worktree | 참고만(ORD-008 I1에서 다룸) | 후보 정리 자료 v10 3절 I1 「정할 것」 ②에 「안건마다 Git worktree를 나누는 방식」이 이미 있다. 도입하면 커밋 때 병합 단계가 생기고 같은 파일을 고친 안건끼리는 충돌을 풀어야 한다. 지금은 ORDER 처리 순서로 하나씩 돌리는 편이 단순하다 |
| O4 | 실행 중 사용량·비용 표시 | 사용량·한도·추정 비용 표시 | 참고만 | 표준에 넣을 일은 아니다. 대표님이 Orca나 Claude 사용량 화면 같은 개인 도구로 보면 된다. 비용 상한 규정은 기각하신 바 있다(후보 정리 자료 v10 5절) |
| O5 | 지난 실행의 결과가 새 실행을 덮지 못하게 하는 식별자 | 메시지에 Task·Dispatch ID | 참고만 | 표준은 산출물 파일의 최신 버전과 머리말(`status:`, `result:`)로 진행 위치를 판단하고(`Workflow/05` 1절), 세션이 끝나면 같은 명령으로 다시 시작한다. 같은 안건을 두 세션이 동시에 돌리는 경우는 이 방식으로도 O1로도 막지 못하지만, PM은 대표님이나 Antigravity가 명령으로 띄우므로 드물다 |
| O6 | 사람이 diff 줄마다 의견을 달아 되돌려 보내기 | Annotate AI Diff | 참고만 | 표준에서는 대표님이 최종 판정서와 `git diff`를 보고 승인한다(`Workflow/05` 1절 ⑧). 고칠 점이 있으면 승인하지 않고 새 지시(ORDER 새 버전과 REQ 새 버전 명령)로 다시 돌린다(`Workflow/05` 3절). 도구 기능이라 표준에 넣을 것은 없다 |

| O8 | 상태 메모 | Worktree checkpoint | 이미 있음 | PM 실행 기록과 그 정식화(RT, ORD-008 F2) |
| O9 | 사람 결정으로 막는 게이트 | Decision gate | 이미 있음 | REQ 「결정 사항 및 선택지」 표, 중단 조건(`Workflow/03` 7절), PM의 대표님 질문과 답의 기록(`Workflow/05` 7절 6항 ⑤, 8.3절 「PM 기동」 예외 (가)) |

| O11 | 끝난 작업의 종결 표시(커밋이 끝난 REQ를 통과 근거에서 빼기) | Task 상태 `completed`, 메시지의 Dispatch ID로 지난 실행이 다른 실행을 완료 처리하지 못하게 함 | 가져오기(우선) | `check_standard.py`는 `docs/requests/`의 번호별 최신 REQ 가운데 `approved:`가 있는 것을 모두 통과 근거로 읽는다(154~167·191~212행). 커밋이 끝났는지는 보지 않는다. 지금 `REQ-021_v02`·`REQ-022_v02`(커밋 완료)의 `scope:`가 `Workflow/01`~`07` 전체와 `.claude/agents/` 여러 파일을 덮으므로, 새 REQ 승인 없이 이 파일들을 고쳐도 작업 트리 검사와 커밋 때의 `--staged` 검사를 통과한다(재현: `조사_20261011_비서실세션연락검토_v03.md` 3.1절 C5는 커밋된 REQ 파일로 통과). 범위 통제(`AGENTS.md` 「불변 원칙」 2항)가 검사 단계에서는 사실상 꺼진 셈이다. 항공 품질의 작업 지시서처럼 끝난 지시를 닫는 표시가 필요하다. 방법 후보: REQ 머리말에 종결 필드를 두고 최종 승인 커밋 때 적는 방식, 또는 검사가 커밋 메시지 `[REQ-xxx]`가 있는 REQ를 빼는 방식. 검사 스크립트와 `Workflow/`를 고치므로 REQ가 필요하다 |

## 7. Orca 도입 여부

| 방식 | 판단 | 이유 |
| :--- | :--- | :--- |
| 표준의 필수 도구로 넣기 | 권고하지 않음 | 표준은 Claude Code·Git·Python만으로 돈다. 릴리스가 잦은 외부 앱에 기대면 표준이 앱 변경에 맞춰 자주 고쳐져야 한다. 승인·판정 절차는 어차피 표준이 맡아야 한다. Orca는 작업마다 worktree에서 에이전트를 돌리는데, 표준은 PM을 저장소 루트에서 실행하고(`Workflow/05` 1절) 커밋 안 된 ORDER·승인 기록을 같은 작업 트리에서 읽는다. worktree에서 PM을 돌리면 이 파일들이 보이지 않고 병합 단계가 생긴다 |
| 대표님 개인 실행 환경으로 시험 사용 | 선택 사항(조건부) | 무료·MIT이고 사용 통계 전송을 끌 수 있다. 완료 알림, 모바일 확인, 사용량 표시를 바로 쓸 수 있다. 확인할 조건: ① 저장소 루트(메인 작업 트리)에서 에이전트를 돌릴 수 있는지(문서에 없음) ② Claude Code용 상태 훅을 어디에 쓰는지, 저장소의 `.claude/`(거버넌스 구역)를 고치지 않는지(문서에 없음) ③ Windows 안정성. 또 모바일에서 PM에 직접 답을 보낼 수 있지만, 그렇게 준 승인 문구는 PM이 기재하지 않으므로 지금처럼 비서실에 다시 주거나 대표님이 직접 기재해야 한다(`Workflow/07` 3.1절 3항 둘째 하위 항목) |
| 쓰지 않기 | 가능 | O1(I1에서)과 O2(개인 설정)로 알림과 시작 전 점검은 Orca 없이도 채울 수 있다. 동시 실행 불가는 Orca 없이 풀리지 않으며 I1(O3)에서 따로 정한다 |
