## 1. 대표님이 정한 원칙(2026-10-08 대화 원문 요지)

1. PM 체계를 도입한 이유: 대표님은 Claude·Antigravity와 일하는데, 대표님 오더가 기능부서에 적절히 전달되지 않았다. 그래서 오더는 오더(ORDER)로 받고, REQ는 오더로부터 작성하는 체계가 되었다.
2. 비서실의 역할: 사람의 말을 기계에게 하달한다.
3. 반대 방향도 비서실이 맡는다: 기계의 업무 결과를 사람에게 보고하는 역할을 구분해 비서실이 한다.
4. 비서실은 PM에게 지시하고, PM이 기능부서의 업무를 리딩한다.

요약: **대표님은 비서실하고만 말한다. PM은 사람 쪽으로는 비서실하고만 말하고, 아래로는 기능부서를 지휘한다.**

## 3. 역할 재정의 제안

### 3.1 흐름도

```text
대표님 ──지시·결정──▶ 비서실 ──ORDER·실행 지시──▶ PM ──REQ·지휘──▶ 기능부서(설계·개발·품질 등)
대표님 ◀──보고·브리핑── 비서실 ◀──실행 기록·질문── PM ◀──결과서·판정서── 기능부서
```

### 3.2 R&R 표

| 주체 | 구분 | 내용 |
| :--- | :--- | :--- |
| 대표님 | 결정 | 지시, 결정(REQ 승인, 결정 표, 최종 승인), 푸시 |
| 비서실 | 하향 | 요구 수집, ORDER 작성, PM 기동과 실행 지시, PM 질문에 대한 대표님 답의 전달 |
| 비서실 | 상향 | PM 실행 기록·판정서 대조, 대화창 요약 보고, 브리핑 자료 작성, PM 질문을 사람 말로 바꿔 대표님께 질의 |
| 비서실 | 접점 | 승인 문구 접수와 기록, 리서치(조사 자료), AUDIT |
| 비서실 | 하지 않음 | REQ·EC·명세·코드·판정 작성, 저장소 기술 작업(적용본 반영, 정리, 검사, 커밋, 핫픽스 수정) |
| PM | 맡는 일 | ORDER로 REQ 작성, 파이프라인 지휘, 비서실 지시에 따른 적용본 반영·정리·커밋 전 검사·커밋, 핫픽스 트랙 지휘와 HOTFIX 작성, 실행 기록 작성 |
| PM | 하지 않음 | 대표님과 직접 소통(보고·질문·승인 접수), 리서치·브리핑 작성 |
| 기능부서 | 맡는 일 | 현행대로(EC, 명세, 구현, 판정) |

- 대표님이 긴급 시 PM에 직접 지시하는 예외는 원칙 밖 사항이다. 둘지 여부는 대표님 결정이 필요하다.

## 4. 검토 의견

- **얻는 것**
  - F1과 F6을 함께 채택하면 대표님이 PM 출력과 권한 확인 화면을 직접 읽을 일이 없어진다. F6 없이 F1만 채택하면 코워크·채팅 경로에서는 대표님이 여전히 PM을 직접 기동하고 출력을 받는다.
  - 실행 기록이 파일로 남아 세션이 끝나도 진행 이력이 보존되고, 브리핑의 원천이 된다.
  - 비서실이 기술 작업을 하지 않게 되어, 서비스마다 셸 실행 가능 여부가 달라 생기던 차이(코워크는 셸 불가, Antigravity는 가능)가 PM 기동 한 가지로 줄어든다.
- **비용과 위험**
  - F3은 대표님이 확정한 ORD-001_v02 3절 8항과 대화로 승인한 REQ-012_v03 D12 권고안을 바꾼다. F4는 REQ-010_v04·REQ-010-1_v02로 표준에 반영된 핫픽스 규정을 바꾼다. 둘 다 대표님 재결정이 필요하다.
  - F2를 채택하면 승인 기재와 대조 보고의 주체가 모두 비서실이 된다. 대표님 확인 시점을 따로 두어야 한다.
  - 비서실을 한 번 더 거치므로 보고 단계가 하나 늘어난다. 실행 기록 파일로 비서실이 빠르게 대조하면 지연은 작다.
  - 비서실이 여러 세션(다른 비서)일 때 누가 PM에 지시했는지 기록이 필요하다. 대표님이 추후 검토로 정한 「비서 여러명」 문제와 함께 다룬다.

## 5. 반영 방법 제안

- REQ-012_v03의 요구 항목 가운데 역할과 무관한 것은 1(문체 지적)뿐이다. 3(완료 보고), 4(승인 뒤 커밋), 5(조사 자료 구역)는 이 제안과 직접 겹친다. 2(effort 기록)는 D14(HOTFIX를 비서실이 작성한다는 전제)가, 6(REQ 없는 커밋의 메시지)은 D11(비서실이 하는 커밋)이 F3·F4에 따라 바뀐다.
- 권고: REQ-012_v03은 승인하지 않고 보류한다. 역할 재정의(F1~F6)를 먼저 ORDER로 작성해 처리하고, 그 결정에 맞춰 ORD-001을 고쳐 REQ-012를 다시 작성한다. 처리 방법은 둘 중 하나다.
  - (가) 역할 재정의와 ORD-001을 한 ORDER로 합쳐 한 안건으로 처리한다. 결정 사항이 20건을 넘어 판정과 승인이 길어진다.
  - (나) 역할 재정의를 새 ORDER(ORD-003, REQ-014)로 먼저 처리하고, 끝난 뒤 ORD-001_v03으로 REQ-012를 다시 작성한다. 안건 순서가 REQ-014 → REQ-012 → REQ-013이 된다.
- 비서실 권고는 (나)다. 역할이 정해지기 전에 보고·커밋 절차를 정하면 다시 고쳐야 하기 때문이다.
