## 2. 요구 항목

1. **끝난 REQ·HOTFIX를 통과 근거에서 빼기**: 커밋 전 검사의 scope 대조는 승인되었고 아직 끝나지 않은 REQ와, 확인되었고 아직 끝나지 않은 HOTFIX만 통과 근거로 쓴다. 「끝난」은 최종 승인 커밋을 마친 것과, 커밋 없이 다른 경로로 끝난 것(다른 안건에 흡수된 것, 중단 조건으로 멈춘 뒤(판정 `rejected` 포함) 대표님이 더 진행하지 않기로 정한 것 등)을 함께 뜻한다. 판정 `fail` 뒤 고쳐서 계속하는 안건은 끝난 것이 아니다(원문 A, Orca 비교 자료 D0. HOTFIX 포함은 1절 경위 마지막 항목의 1, 확인 대기).
2. **종결의 기록**: 어느 REQ·HOTFIX가 언제 어떤 경로(어느 커밋, 또는 요구 항목 1의 커밋 없이 끝난 경로)로 끝났는지 찾을 수 있게 한다. 커밋 경로(최종 승인 커밋, 요청 커밋, 핫픽스 커밋, 대표님 직접 커밋)와 관계없이 기록이 남아야 한다(원문 A, D0에서 비서실이 끌어낸 항목. HOTFIX 부분은 1절 경위 마지막 항목의 1, 확인 대기).
3. **기존 기록의 종결**: 커밋 전 검사가 읽는 두 폴더(`Departments/Secretariat/docs/requests/`, `Departments/Secretariat/results/`)의 REQ·HOTFIX 가운데 이미 끝난 것(파생 안건 `REQ-010-1`과 커밋 없이 끝난 `REQ-011` 포함)을 끝난 상태로 만든다(원문 A, D0에서 비서실이 끌어낸 항목. HOTFIX 부분은 1절 경위 마지막 항목의 1, 확인 대기).
4. **끝난 안건이 통과 근거로 쓰인 기간의 범위 대조**: 커밋 전 검사가 끝난 안건을 통과 근거로 쓴 기간에 승인 범위 밖 변경이 커밋되었는지 커밋 이력과 각 커밋의 근거 REQ·HOTFIX `scope:`를 대조해 확인하고 결과를 기록한다(1절 경위 마지막 항목의 3, 확인 대기).

- REQ에서 정할 사항
  - 공통: REQ 분할 여부(`AGENTS.md` 「불변 원칙」 8항). 구현 방법의 처리는 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항 「구현 방법(Critical·Major)」을 따른다. 끝난 것을 판단하는 수단(예: REQ·HOTFIX 머리말의 필드, 커밋 메시지의 안건 표기 검색, 별도 목록 파일)과 검사 스크립트에 넣는 방법은 구현 방법이다. 커밋 메시지를 쓰는 수단은 1절 경위 「커밋 이력의 사실」(표기 누락, 분리 커밋, amend)을 함께 본다.
  - 요구 항목 1·2: 종결 기록을 그 안건의 커밋에 함께 넣을지 다음 커밋에 넣을지(그 안건의 커밋 전 검사(`Workflow/05` 1.1절 7번)에서는 자기 REQ가 통과 근거로 남아 있어야 한다), 다른 안건에 흡수된 경우를 누가 정하는지(요구 항목 1의 나머지 경우는 대표님이 정한다), 끝낸 것을 다시 열어야 할 때의 경로(`Workflow/03` 「진행 중 변경과 파생 안건」과의 관계), 종결을 기록하는 주체(커밋하는 비서실, 대표님, PM 가운데 누구인지).
  - 요구 항목 3: 이미 끝난 것의 근거 커밋을 누가 확인할지(위 사실처럼 메시지 표기가 빠진 커밋이 있다). 확인 수단은 「공통」 항목대로 구현 방법으로 처리한다.
  - 요구 항목 4: 대조 기간(v04 하드포크 뒤 전체인지), 대조 주체(이 REQ의 단계인지, 운영의 보안 점검(`Workflow/06_통제장치_및_배포` 「보안 점검」)인지), 범위 밖 변경이 나왔을 때의 처리(부적합 기록, 대표님 보고).

## 3. 대화 중 확정된 사항

1. 끝난 REQ를 커밋 전 검사의 통과 근거에서 뺀다(원문 A 「권고안 채택」, Orca 비교 자료 D0).
