## 3. 결정 사항 및 선택지
> 정할 일의 작성 기준은 `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항을 따른다. D1~D5는 ORDER 「REQ에서 정할 사항」의 이 REQ 항목을 정할 일마다 나눈 것이다. D6은 새 규정을 어느 판정부터 적용하는지로, 진행 중인 안건에 적용하는지가 두 뜻으로 읽힐 수 있어 더했다. D7은 서식이 정한 effort 선택이다. 이 REQ는 기본값 밖의 모델·effort를 쓰지 않는다(`Workflow/04_모델_운용` 「기본값 밖 사용」).

REQ 판정의 결함과 문체 지적은 대상이 아니다. 결함과 반려 부서가 처음 정해지는 곳이 판정서이고, 같은 값을 여러 기록에 다시 적지 않기 위해서다(`AGENTS.md` 「불변 원칙」 9항). REQ 판정은 승인 전 판정이어서 아직 승인된 기준이 없고, 문체 지적은 결함이 아니며 처리 절차(`Workflow/03_라이프사이클` 5.1절)가 따로 있다 | (가) 판정서와 함께 부적합 기록에도 같은 태그를 붙인다(부적합 기록만 보고 Repair 건수를 셀 수 있지만, 같은 값을 두 곳에 적어 어긋날 수 있다) (나) REQ 판정의 결함에도 붙인다(모든 판정의 태그가 같아지지만, 승인 전 REQ의 결함은 늘 REQ 새 버전으로 고쳐 구분이 뜻을 갖지 않는다) | |
| D2 | Rework·Repair를 판단하는 주체와 기준 | 판정자(품질 서브에이전트)가 결함을 적을 때 정한다. 기준은 그 결함을 승인된 기준(승인된 REQ의 요구·`scope:`·「결정」 열과, EC가 있으면 판정 `pass`를 받은 EC) 안에서 고쳐 그 기준에 맞출 수 있는지다. 맞출 수 있으면 Rework, 승인된 기준을 바꾸거나 벗어나야 고칠 수 있으면 Repair다. Rework는 승인받은 기준대로 고치므로 승인받은 기능·품질이 바뀌지 않는다(대표님 원문의 「기능이나 품질영향없는」). 항공 품질에서 rework는 도면대로 되돌리는 작업, repair는 도면을 벗어난 상태를 승인받아 쓰는 작업으로 나누는 것과 같다. 판정자가 결함·문체 구분(5.1절 1항)과 반려 부서를 정하므로 같은 자리에서 정한다 | (가) 기준을 대표님 원문 그대로 「기능·품질에 영향이 있는지」로 둔다(원문과 표현이 같지만, 영향의 크기를 재는 기준이 없어 같은 결함을 판정자마다 다르게 나눌 수 있다) (나) 반려 부서가 고칠 때 정한다(고치는 쪽이 대표님 승인 필요 여부를 스스로 정하게 되어 생성과 판정의 분리(`AGENTS.md` 「불변 원칙」 4항)와 맞지 않는다) | |
| D3 | Repair의 대표님 승인 경로 | 현행 경로를 그대로 쓴다. Repair 결함이 있는 판정서가 나오면 파이프라인을 멈추고 대표님께 보고하며, 대표님 결정 뒤 PM이 REQ 새 버전을 작성해 REQ 판정과 재승인을 받는다(`Workflow/03_라이프사이클` 6절 「진행 중인 안건의 요구가 바뀜」). Rework 결함은 현행대로 반려 부서가 고치고 변경분을 다시 판정하며 대표님 승인을 거치지 않는다(같은 문서 8절). 새 승인 문서나 비서실의 별도 전달 경로는 두지 않는다. 중단 보고는 이미 PM → 비서실 → 대표님으로 전달되기 때문이다(`Workflow/05_인수인계_및_실행명령` 1절, 5절 「완료 보고」 3항 ①) | (가) Repair도 멈추지 않고 고친 뒤 최종 판정서 승인 때 대표님이 함께 확인한다(멈춤이 줄지만, 승인된 범위·결정을 벗어난 수정이 승인 전에 진행되어 `AGENTS.md` 「불변 원칙」 2항과 맞지 않는다) (나) Repair를 비서실을 통해 대표님께 바로 전달하는 별도 경로를 둔다(원문 K 둘째 문단의 안. 중단 보고와 같은 일을 하는 경로가 둘이 된다) | |
| D4 | 간단한 문구 변경을 REQ 없이 처리하는 경로를 두는지 | 새로 두지 않는다. 그래서 그 경로에 붙일 Rework 태그도 없다. 지금도 핫픽스, 대표님 직접 수정, 문체 반영, Minor REQ로 문구를 고칠 수 있다(2절 「배경」). AI가 거버넌스 파일을 REQ 없이 고치려면 `AGENTS.md` 「불변 원칙」 1·3·4항의 예외가 필요하고, 사용자 전역 지침이 오탈자도 수정안 승인과 대상 경로 목록 승인을 요구해 줄일 수 있는 절차가 적다. 이 경로가 없어 생긴 사고 기록도 없다(`AGENTS.md` 「불변 원칙」 8항) | (가) 둔다(AI가 문구를 고칠 때 REQ 전체를 거치지 않지만, `AGENTS.md` 개정이 필요하다. 이 대안을 고르면 이 REQ `scope:` 밖인 `AGENTS.md`의 수정이 필요해, 원스톱 파이프라인이 `Workflow/03_라이프사이클` 「중단 조건」 1항으로 멈추고 scope를 넓힌 REQ 새 버전과 재승인이 필요하다) | |
| D5 | 사용자 전역 지침의 덮어쓰기·지침 문서 승인과의 관계 | 재작업 규정에, Rework에 「대표님 승인이 필요 없다」는 것은 REQ 새 버전과 재승인이 필요 없다는 뜻이며 사용자 전역 지침 「파일 삭제·덮어쓰기 전 사용자 승인」·「지침 문서 수정 전 사용자 승인」을 면제하지 않는다고 적는다. Rework의 수정은 승인된 REQ `scope:`(전역 지침의 승인 목록. `AGENTS.md` 「불변 원칙」 2항) 안에서만 하고 거버넌스 파일은 적용본으로 고치므로, 두 승인은 REQ 승인과 최종 판정서 승인으로 이미 거친다. 「승인 불필요」가 모든 승인을 면제하는 것으로 읽히지 않게 하기 위해서다 | (가) 따로 적지 않는다(전역 지침과 `AGENTS.md`가 이미 정해 문장이 하나 줄지만, Rework의 「승인 불필요」가 전역 지침의 승인까지 면제하는 것으로 읽힐 수 있다) | |
| D6 | 새 규정의 적용 시점 | 이 REQ 커밋 뒤에 작성하는 REQ의 판정부터 적용한다. 이미 승인된 REQ의 판정과 기존 판정서는 바꾸지 않는다. 한 안건 안에서 태그가 있는 판정서와 없는 판정서가 섞이지 않고, 진행 중인 안건의 멈춤 조건이 도중에 바뀌지 않기 때문이다(`Workflow/03_라이프사이클` 2.1절 9항, 「분류별 단계」 표 아래 적용 시점 항목과 같은 방식) | (가) 이 REQ 커밋 뒤에 발행하는 모든 판정서부터 적용한다(빨리 적용되지만, 진행 중인 안건의 판정서가 도중부터 태그를 갖고 Repair 멈춤이 도중에 생긴다) | |
| D7 | effort | `medium` | `high` | |

- 「결정」 열의 기재 주체와 시점은 `Workflow/07_문서_서식_및_번호` 「승인 기록」을 따른다.
- 4절 실행 계획과 5절 체크리스트는 D1~D7의 권고안을 전제로 작성했다. 대표님이 권고안이 아닌 결정을 고르면 「결정」 열의 결정이 그 결정에 따라 달라지는 체크리스트 항목·실행 계획보다 우선한다(`Workflow/03_라이프사이클` 「REQ 작성 파이프라인」 1항 「결정과 체크리스트」).
- D6 권고안에 따라 이 REQ 자신의 판정에는 새 규정을 적용하지 않는다.
