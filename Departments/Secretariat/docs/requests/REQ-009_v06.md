# REQ-009: 비서실·PM 역할 재편과 ORDER 서식 설계

## 1. 요청 원문
> 출처: `Departments/Secretariat/assets/inbox/요구메모_20261006_역할재편_v03.md`. 1절의 대표님 지시 원문을 그대로 인용한다.

> 근데 요구사항 메모랑 req랑 같은내용을 반복해서 쓰는거 아님?
> 그리고 창구랑 비서실 구분해야하지않음,
> 창구는 세련된 이름 바꿀수있나?

> 창구,챗 에이전트를 비서실로 칭하고.
> 기존 비서실 역할을 PM으로 변경하는것은?
>
> 비서실이 요구사항 수집, 정리하고, CLASSIFICATION 등을 지정.
> PM이 REQ 쓰고, 전체 작업 지휘.
>
> 이말은 REQ를 분리해서,
> 비서실이 작성하는 오더와
> Pm이 작성하는 req로 분리.
>
> 오더 템플릿 신설.
>
> 어떤데?

> 핫픽스는 신규 비서실에서 수행.
> 오케스트레이터 역할을 PM이 수행. 사실상 호칭 차이임.
> 클로드코드또는 클로드cli. 왜냐면 안티는 cli가능. 코워크나 챗은 배쉬?로 주면됨.
> 분류제안, 템플릿 오케이. 대표님 추가 요청사항 만 추가바람.

이 REQ의 작업 항목은 같은 메모 2절 「대화 중 대표님이 확정한 사항」의 아홉 항목이며, 메모의 번호를 그대로 쓴다.

1. > 창구(코워크·Antigravity 등 채팅 에이전트)를 「비서실」로 부른다.
2. > 기존 비서실 세션(Claude Code `secretariat`)의 역할은 「PM」으로 바꾼다.
3. > PM은 오케스트레이터 역할을 겸한다. PM과 오케스트레이터는 같은 주체이며 호칭만 다르다. PM은 Claude Code(Claude CLI)에서 실행한다.
4. > PM 실행 명령의 전달 방식: Antigravity는 CLI를 직접 실행하고, 코워크와 채팅 서비스는 bash 명령문을 대표님께 제시한다.
5. > 비서실은 요구를 수집·정리하고 분류(classification)를 「제안」한다. 분류는 PM이 REQ에서 확정한다.
6. > 비서실이 작성하는 「오더(ORDER)」와 PM이 작성하는 REQ로 문서를 분리한다. 오더 서식을 신설한다.
7. > 오더 서식은 창구가 제안한 구성(4절)을 따르되, 「대표님 추가 요청사항」 항목을 추가한다.
8. > 핫픽스는 새 비서실이 수행한다.
9. > 이 안건은 역할 정의와 ORDER 서식 설계까지만 다룬다. `Workflow/` 표준 문서 반영과 전체 점검은 후속 안건(`요구메모_20261006_역할재편반영및점검`)에서 한다.

7번이 가리키는 구성은 같은 메모 4절 「창구가 제안하고 대표님이 승인한 오더 구성」이다. 원문을 그대로 인용한다. 이 구성에는 대표님 지시에 따른 「대표님 추가 요청사항」(5항)이 이미 들어 있다.

> 1. 머리말: 오더 번호(`ORD-NNN`), 작성일, 대표님 확인 일시, 분류 제안, 연결 REQ 목록
> 2. 지시 원문: 대표님 말 그대로
> 3. 요구 항목: 번호를 매긴 목록. REQ 체크리스트가 이 번호와 1:1로 대응한다
> 4. 대화 중 확정된 사항: 대표님이 답한 정책 결정. 구현 방법은 넣지 않는다
> 5. 대표님 추가 요청사항
> 6. 우선순위와 기한

참고(작업 요구가 아님): 이 문서의 호칭은 다음과 같이 구분한다. 「비서실 세션」은 현행 Claude Code `secretariat`, 「창구」는 현행 규정에서 대표님과 대화하며 요구를 모으고 결과를 보고하는 AI 세션(코워크, Antigravity 등. `Workflow/01_표준_개요` 「용어」 창구 행)을 가리킨다. 「세션」을 붙이지 않은 「비서실」과 「PM」은 재편 뒤의 역할(요청 원문 1·2번)을 가리킨다. 「메모 4절 구성」은 위에 인용한 여섯 항목을 가리킨다.
