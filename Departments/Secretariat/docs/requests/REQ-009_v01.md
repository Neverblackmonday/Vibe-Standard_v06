# REQ-009: 비서실·PM 역할 재편과 ORDER 서식 설계

## 1. 요청 원문
> 출처: `Departments/Secretariat/assets/inbox/요구메모_20261006_역할재편_v02.md`. 1절의 대표님 지시 원문을 그대로 인용한다.

> 근데 요구사항 메모랑 req랑 같은내용을 반복해서 쓰는거 아님?
> 그리고 창구랑 비서실 구분해야하지않음,
> 창구는 세련된 이름 바꿀수있나?

> 창구,챗 에이전트를 비서실로 칭하고.
> 기존 비서실 역할을 PM으로 변경하는것은?
>
> 비서실이 요구사항 수집, 정리하고, CLASSIFICATION 등을 지정.
> PM이 REQ 쓰고, 전체 작업 지휘.
>
> 이말은 REQ를 분리해서,
> 비서실이 작성하는 오더와
> Pm이 작성하는 req로 분리.
>
> 오더 템플릿 신설.
>
> 어떤데?

> 핫픽스는 신규 비서실에서 수행.
> 오케스트레이터 역할을 PM이 수행. 사실상 호칭 차이임.
> 클로드코드또는 클로드cli. 왜냐면 안티는 cli가능. 코워크나 챗은 배쉬?로 주면됨.
> 분류제안, 템플릿 오케이. 대표님 추가 요청사항 만 추가바람.

이 REQ의 작업 항목은 같은 메모 2절 「대화 중 대표님이 확정한 사항」의 아홉 항목이며, 메모의 번호를 그대로 쓴다.

1. > 창구(코워크·Antigravity 등 채팅 에이전트)를 「비서실」로 부른다.
2. > 기존 비서실 세션(Claude Code `secretariat`)의 역할은 「PM」으로 바꾼다.
3. > PM은 오케스트레이터 역할을 겸한다. PM과 오케스트레이터는 같은 주체이며 호칭만 다르다. PM은 Claude Code(Claude CLI)에서 실행한다.
4. > PM 실행 명령의 전달 방식: Antigravity는 CLI를 직접 실행하고, 코워크와 채팅 서비스는 bash 명령문을 대표님께 제시한다.
5. > 비서실은 요구를 수집·정리하고 분류(classification)를 「제안」한다. 분류는 PM이 REQ에서 확정한다.
6. > 비서실이 작성하는 「오더(ORDER)」와 PM이 작성하는 REQ로 문서를 분리한다. 오더 서식을 신설한다.
7. > 오더 서식은 창구가 제안한 구성을 따르되, 「대표님 추가 요청사항」 항목을 추가한다.
8. > 핫픽스는 새 비서실이 수행한다.
9. > 이 안건은 역할 정의와 ORDER 서식 설계까지만 다룬다. `Workflow/` 표준 문서 반영과 전체 점검은 후속 안건(`요구메모_20261006_역할재편반영및점검`)에서 한다.

참고(작업 요구가 아님): 이 문서의 호칭은 다음과 같이 구분한다. 「비서실 세션」은 현행 Claude Code `secretariat`, 「창구」는 현행 창구를 가리킨다. 「세션」을 붙이지 않은 「비서실」과 「PM」은 재편 뒤의 역할(요청 원문 1·2번)을 가리킨다.

## 2. 배경 및 목적
- **배경**
  - 현행 역할은 `Workflow/02_부서_구조_및_작업구역` 「비서실 세션과 창구의 책무」, `Workflow/03_라이프사이클` 「REQ 작성 파이프라인」·「핫픽스 트랙」, `AGENTS.md` 「부서와 권한 한계」가 정한다. 현행 규정에서 창구는 요구 메모만 남기고 저장소의 다른 파일을 수정하지 않으며, 핫픽스 수정은 비서실 세션이 한다.
  - 2026-10-06 비서실 세션이 `Secretariat|secretariat|창구|오케스트레이터`를 `_archive/`, `Departments/` 밖에서 검색한 결과, `Workflow/` 밖의 거버넌스 파일 가운데 `AGENTS.md`, `.gitattributes`, `.claude/agents/secretariat.md`에 참조가 있다. `Departments/Development/assets/scripts/check_standard.py`는 `Departments/Secretariat/docs/requests/`, `Departments/Secretariat/assets/`, `Departments/Secretariat/results/` 경로를 직접 참조한다(35·36·144·148행).
  - 후속 안건 메모(`요구메모_20261006_역할재편반영및점검_v02.md`)는 반영 범위를 `Workflow/` 표준 문서로 적고 있다. 위의 `Workflow/` 밖 파일을 어느 안건에서 반영할지는 정해져 있지 않다.
  - 요청 원문 7번의 「창구가 제안한 구성」은 요구 메모에 적혀 있지 않다. 2026-10-06 비서실 세션이 저장소 전체에서 `ORDER|오더`를 검색한 결과, 요구 메모 다섯 개 파일(`역할재편_v01`·`v02`, `역할재편반영및점검_v01`·`v02`, `표준보완_v01`)의 언급만 있고 구성 내용은 없다. 따라서 이 REQ는 그 구성을 확인 불가로 두고 3절 D1로 대표님 결정을 받는다.
- **목적**: 요청 원문 1~8번의 역할(비서실, PM)과 ORDER 서식을 설계 문서로 확정하고, 후속 안건이 그 설계를 반영할 대상 파일 목록을 넘긴다. 이 안건은 거버넌스 파일 원본과 적용본을 만들지 않는다(9번). 설계의 구체 내용(역할 표 문구, 서식 항목 배치)은 EC와 명세 단계에서 정한다.
