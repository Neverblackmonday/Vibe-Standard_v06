### 1.1 방법

### 2.3 해석

- `git diff --no-index`가 구한 해시는 작업 트리 바이트 그대로가 아니라, 그 저장소의 `core.autocrlf`와 `.gitattributes`에 따른 정규화(커밋할 때와 같은 변환)를 거친 값이다. `core.autocrlf=true`에서 CRLF로 쓴 파일도 LF 해시(`473ac4b…`)가 나왔다.
- 같은 PC·같은 설정 안에서는 규칙이 없어도, 작성 직후·커밋 뒤·복제한 작업 트리의 해시가 18가지 조합 모두에서 같았다(`match_written_clone` 모두 True). 지금까지 해시 대조 실패가 없었던 것(`RES-031_v01` 4절)과 맞는다.
- 해시를 기록한 PC와 다시 구하는 환경의 `core.autocrlf`가 다르면, 기본 규칙이 없을 때 해시가 달라졌다(E2x 첫 행: true에서 기록, CRLF 작업 트리를 false로 다시 구하면 `72c0048…`). `* text=auto` 또는 `* text=auto eol=lf`를 두면 같은 경우에도 해시가 같았다(E2x 셋째~여섯째 행). 이 저장소의 `core.autocrlf=true`는 저장소 설정이 아니라 Git for Windows 시스템 설정(`C:/Program Files/Git/etc/gitconfig`)에서 온다(E2r). 그래서 다른 Git 설치나 다른 PC에서는 값이 다를 수 있다.
- 이 저장소의 추적 파일은 index가 모두 LF이거나 텍스트가 아니다(`i/crlf`·`i/mixed` 0개). 기본 규칙을 더해도 기존 파일이 변경으로 잡히지 않았다(E2n: `add --renormalize` 뒤에도 `.gitattributes`만 변경). 커밋된 인수 시험 `.py` 25개는 지금 index blob 해시와 no-index 해시가 모두 같다(E2r).
- `* text=auto eol=lf`는 작업 트리를 LF로 두므로 `core.autocrlf=true` PC에서도 「LF will be replaced by CRLF」 경고(`RES-031_v01` 4절의 경고)가 나지 않았다(E2 `text=auto eol=lf | LF` 행의 경고 `no`). 대신 CRLF로 쓴 파일을 스테이징하면 반대 방향 경고가 났다. `* text=auto`는 해시를 같게 하지만 `core.autocrlf=true`에서 LF 파일의 경고는 그대로 났다.
- E2n은 기본 규칙 뒤에 기존 규칙과 같은 형태(`*.cmd text eol=crlf`, 훅 파일 `text eol=lf`)를 함께 두었으며, 이때도 기존 파일이 변경으로 잡히지 않았다. 기존 규칙이 적용된 파일의 작업 트리 줄바꿈은 이 실험에서 보지 않았다(Git 문서상 뒤에 적은 규칙이 앞선다는 점은 이 실험의 실측 범위가 아니다). 값의 선택은 구현 방법이며 EC가 정한다(REQ 3절 머리 설명).

### 3.3 해석

- 신뢰 상태는 저장소 밖 사용자 상태 파일 `~/.claude.json`의 `projects["<저장소 경로>"].hasTrustDialogAccepted`로 읽을 수 있었다. 경로 키는 슬래시(`/`) 형태였다. 읽기만 했고 파일은 바뀌지 않았다(읽기 전후 해시 같음).
- 이 PC의 v05 폴더는 지금 신뢰 처리가 되어 있고(True), 이 세션에서 `allow` 규칙에만 기대는 명령(A1·A3)이 확인 요청 없이 실행되었다. 프로젝트 `allow`가 이 세션에 적용되어 있다.
- 훅 경로는 `git config --get core.hooksPath`로 읽을 수 있었다(A4, E3).
- 이 저장소에 `.claude/settings.local.json`이 없고, 사용자 설정(`~/.claude/settings.json`)에는 `permissions` 키가 없다. 지금 이 PC에서 프로젝트 `allow`·`deny`·`ask`를 바꾸는 다른 설정 계층은 이 두 파일에서는 보이지 않았다(관리 설정은 조회하지 않음).

## 4. 실측하지 못한 항목(D21)

| 번호 | 항목 | 사유 |
| :---: | :--- | :--- |
| N1 | `Write(...)` 규칙 자체의 효력(같은 경로의 `Edit(...)` 규칙 없이 `Write(...)`만 있을 때 Write 도구를 막는지) | `settings.json`은 `deny` 경로이고 거버넌스 파일이어서 이 세션에서 바꿀 수 없다. 규칙을 따로 둔 설정으로 새 Claude Code 세션을 기동해야 하나, `claude` 명령은 `allow`에 없어 확인 요청이 필요하다. 근거로 쓸 수 있는 것은 1.3절의 Claude Code 경고뿐이다 |
| N2 | 실제 거버넌스 경로에 대한 Write 도구 거부 | 막히지 않으면 원본이 바뀌므로 시도하지 않았다. 같은 이름의 하위 폴더 경로(W1~W11)와 실제 경로의 Edit(D1~D11)로 대신 보았다 |
| N3 | `ask` 규칙(Bash·PowerShell의 삭제·이동·커밋·푸시)의 효력 | 시도하면 확인 요청이 생겨 `Workflow/03_라이프사이클` 7절 5항의 멈춤 사유가 된다 |
| N4 | 셸 명령(Bash의 리디렉션, Python 등)으로 `deny` 경로에 쓰는 것을 막는지 | 막히지 않으면 원본이 바뀐다. `Workflow/06_통제장치_및_배포` 1절 표 계층 1의 「한계」가 이미 막지 않는다고 적는다 |
| N5 | 신뢰 처리 전 상태에서 `hasTrustDialogAccepted`가 false이거나 항목이 없는지, 그때 `allow`가 적용되지 않는지(`NCR-031_03` 상황의 재현) | 이 PC의 v05 폴더는 이미 신뢰 처리되어 있고, 신뢰 상태를 되돌리려면 `~/.claude.json`을 고쳐야 한다(요구 항목 20 ②는 읽기만 허용). 신뢰 처리하지 않은 새 폴더에서 Claude Code 세션을 기동해야 하나 `claude` 명령은 확인 요청이 필요하다 |
| N6 | 세션 밖에서 `allow` 적용 여부 자체를 읽는 수단 | 세션 밖에서 읽을 수 있는 것은 신뢰 상태(E3)와 설정 파일의 존재·내용뿐이다. 실제 적용은 세션 안에서 `allow`에만 기대는 명령을 실행해야 확인된다(A1·A3). 세션을 기동하지 않고 적용 여부를 출력하는 Claude Code 명령이 있는지는 확인하지 못했다 |
| N7 | `~/.claude.json`의 키 이름(`projects`, `hasTrustDialogAccepted`)이 Claude Code 버전과 관계없이 유지되는지 | 공식 문서로 확인하지 못했다. 이 기록의 값은 2026-10-16 이 PC의 파일에서 읽은 것이다 |
| N8 | 관리 설정(managed settings) 계층의 권한 규칙 | 조회하지 않았다 |
